# CODEX-05 발표자료 작업 인수인계

## 1. 다른 컴퓨터에서 시작하는 방법

1. 이 저장소의 원격 branch `codex/deck-review-handoff-20260812`를 받는다.
2. 먼저 이 파일을 끝까지 읽는다.
3. 다음 세 파일을 함께 확인한다.

   - `CODEX-05-전략발표_AS-IS.html`: 수정 전 원본. 비교 기준이므로 편집하지 않는다.
   - `CODEX-05-전략발표_TO-BE.html`: 현재 수정 대상.
   - `CODEX-05_AS-IS_TO-BE_비교.html`: 좌우 비교 화면. TO-BE 파일을 자동으로 불러온다.

4. 현재 합의된 수정 범위는 1~11페이지다. 12페이지 이후에는 `재검토 예정` 표시가 있다.
5. 수정 전에는 발표자료 편집 기준과 명료성 사전검토 기준을 적용하고, 수정 후에는 실제 HTML 화면을 확인한다.

## 2. 현재까지 확정된 논리

- 8페이지: 규칙 기반 전체 구조는 유지비가 커서 그대로 운영하지 않는다. 다만 A~D 네 가지 통제는 남긴다.
- 9페이지: `A~D 네 가지 통제`와 `①~⑥ 여섯 업무 단계`를 구분한다.
- 10페이지: A~D마다 `적용 파일 예 → 비교하는 값 → 이점`을 설명한다.
- 11페이지: 관리자는 A~D 결과 네 줄을 보고 최종 통합 코드 전체를 승인한다.
- 최종 승인 기준은 기능별 Git commit SHA가 아니다. 여러 기능이 모두 합쳐진 최종 Git commit SHA 하나다.
- 기능별 구분은 SHA가 아니라 `BANK-OM ID ↔ 필수 테스트` 연결로 유지한다.
- `통합 코드 테스트`는 하나의 거대한 테스트가 아니다. 기능별 API·화면·소스 테스트를 동일한 최종 SHA에서 묶어 실행하는 단계다.
- 최종 코드가 바뀌면 이전 테스트 결과를 현재 코드의 승인 근거로 사용하지 않고 다시 테스트한다.

## 3. 사용자의 수정 스타일

### 문장과 설명

- 설명은 짧고 명료하게 쓴다. 장황한 방어 문장이나 내부 구현자의 독백을 넣지 않는다.
- 새 용어가 나오면 그 자리에서 `무엇인지`, `언제 쓰는지`, `무엇과 무엇을 비교하는지`, `결과가 어떤 판단으로 이어지는지`를 설명한다.
- 추상적인 정의만 쓰지 않는다. 실제 파일과 실제 YAML 필드를 예로 든다.
- `왜 남기나`보다 독자가 바로 이해할 수 있는 `이점` 또는 `효과`를 사용한다.
- 서로 다른 개수나 분류가 등장하면 즉시 구분한다. 예: `4개는 통제 종류, 6개는 업무 단계`.
- `지문`, `계보`, `계약`, `못박기`처럼 이 발표의 업무 문맥에서 낯선 비유는 쓰지 않는다.
- SHA, branch, commit, API, Manifest처럼 정확한 기술 용어는 유지하되 처음 읽는 사람도 이해할 수 있도록 완전한 문장으로 설명한다.
- `채택`, `제한 채택`, `운영 미완료`처럼 판단 기준이 불명확한 상태 라벨을 남발하지 않는다. 현재 상태가 꼭 필요할 때만 구체적인 문장으로 쓴다.

### 논리와 흐름

- 각 페이지는 이전 페이지에서 생긴 질문에 답해야 한다. 설명 없이 새 체계나 목록을 갑자기 제시하지 않는다.
- 동일한 개념은 동일한 이름과 동일한 A~D 순서로 반복한다.
- 같은 내용을 9·10·11페이지에서 반복할 때는 관점을 명확히 다르게 한다.

  - 9페이지: 업무의 전체 흐름
  - 10페이지: 적용 파일·비교 값·이점
  - 11페이지: 관리자가 보는 결과

- 검사기가 LLM의 판단을 대신한다고 표현하지 않는다. LLM은 변경·해석을 수행하고, 검사기는 선언한 값과 실제 값 및 실행 결과를 대조한다.
- LLM 방식이 이미 작동한다는 사실을 부정하지 않는다. 검사기의 가치는 LLM을 대체하는 것이 아니라 반복 확인의 범위를 줄이고, 누락·바꿔치기·미실행을 드러내는 데 둔다.
- 공용 파일의 기능별 코드 조각을 영구 관리해야 한다고 단정하지 않는다. Git diff로 판단이 어려운 항목만 사람 확인 대상으로 남긴다.

### 예시 작성

- YAML 예시는 파일명만 보여주지 말고 비교하는 필드까지 적는다.
- 현재 10페이지에서 사용한 기준 예시는 다음과 같다.

  - A: `upgrade-rehearsal-matrix.yaml`의 `upstream_target.sha` 및 `source_reference.commit_sha`, `customization-registry.yaml`의 `entries[].customization_id`
  - B: Manifest의 `implementation.changed_paths`와 Git이 계산한 실제 `changed_paths`
  - C: `contracts.yaml`의 `customization_ids`·`required_tests`와 `test-run-set.yaml`의 `runs[].test_id`·`outcome`
  - D: `candidate-lock.yaml`, `test-run-set.yaml`, `acgh-result.yaml`의 `commit_sha`·`artifact_digest`

- 예시는 구조를 이해시키기 위한 것이다. 특정 파일명을 영원히 유지해야 한다고 표현하지 않는다. 핵심은 `선언한 값 ↔ 실제 값 ↔ 실행 결과`의 비교 관계다.

### 화면과 변경 표시

- 비교 화면은 AS-IS와 TO-BE가 반드시 좌우로 보여야 한다.
- 변경된 페이지뿐 아니라 실제로 바뀐 문장과 블록에도 형광펜 표시를 한다.
- 형광펜은 비교 검토용이다. 최종 발표본을 확정할 때는 제거 여부를 사용자와 확인한다.
- 제목과 본문이 화면 밖으로 잘리지 않는지, 가로 넘침이 없는지 실제 브라우저에서 확인한다.
- 정보를 추가할 때 글자를 지나치게 줄이지 않는다. 길어지면 문장을 먼저 줄인다.

## 4. 현재 파일의 A~D 기준

| 통제 | 현재 명칭 | 관리 파일 예 | 핵심 비교 |
|---|---|---|---|
| A | 승인 입력 고정 | `upgrade-rehearsal-matrix.yaml`, `customization-registry.yaml` | 공식 대상·시작 코드·반영 기능이 승인 입력과 같은지 |
| B | 실제 변경 대조 | Manifest, `commit-inventory.yaml` | 선언한 경로와 Git 실제 변경 경로가 같은지 |
| C | 필수 테스트 완전성 | `contracts.yaml`, `test-run-set.yaml` | 필수 테스트가 모두 실행됐고 결과가 남았는지 |
| D | 결과와 최종 코드 연결 | `candidate-lock.yaml`, `test-run-set.yaml`, `acgh-result.yaml` | 코드와 모든 테스트 결과가 동일한 최종 SHA·실행 대상인지 |

## 5. 다음 작업자가 지켜야 할 절차

1. 사용자 요청을 먼저 현재 페이지 논리와 대조한다.
2. 발표 문구에 실제 파일·필드를 넣을 때는 `work/review-openmetadata-test`의 현재 파일로 사실을 확인한다.
3. TO-BE만 수정하고 AS-IS는 유지한다.
4. 비교 페이지를 열어 좌우 배치와 형광펜 위치를 확인한다.
5. 1~11페이지 전체를 다시 읽어 용어·숫자·A~D 순서를 확인한다.
6. 화면 잘림과 넘침을 확인한다.
7. 무엇을 바꿨는지와 아직 재검토 예정인 범위를 사용자에게 짧게 보고한다.
