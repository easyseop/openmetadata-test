## 2. 현재까지 확정된 논리

- 표지 제목은 `커스텀 버전업 전략 검증결과 공유`다. 표지에는 전략 전환 설명과 예행연습 버전·날짜 문구를 넣지 않고, 전제 한 줄만 남긴다.
- 최종 발표본에서는 형광펜, `수정` 배지, 상단 검토 배지와 `재검토 예정` 표시를 사용하지 않는다. 표의 `채택`, `B에서 A로 이동`, `자동 검사`, `자동 산출물`, `통합 설계 필요`, `신규 제안` 같은 작업 상태 라벨도 제거한다.
- 1~3페이지: 목표와 초기 규칙 기반 설계를 설명한다. 3페이지에는 관리 파일은 규칙으로 갱신하고 충돌만 LLM으로 해결하려 했으며, 파일 간 관계에 오류가 없어야 배포를 승인하도록 설계했다는 초기 전제를 남긴다.
- 4페이지: 제목은 `규칙이 메인, LLM은 서브`다. AS-IS 여섯 단계를 `수정 전 분석 및 관리 파일 업데이트 → 커스터마이징 반영 → 변경 결과 확인 → 테스트 준비·실행 → 테스트 결과 분석 → 통합 승인` 순서로 보여준다.
- 5페이지: 두 버전업 결과와 1.13.2 구조 변화·충돌 해결을 같은 폭의 세로 항목으로 보여준다. 1.13.1은 자동 병합, 1.13.2는 수동 해석·재적용 후 완료로 설명한다.
- 6페이지: 구조적 한계는 `이동·분리 추적`과 `Git diff의 한계` 두 가지로만 설명한다. 별도 `실행 검증은 별도` 항목은 제거했다.
- 7페이지: 운영상 한계는 정보 분산·반복 갱신·전체 관계 확인·누락 위험으로 설명한다.
- 8페이지: 관리 문서와 자동 검사의 유효한 강점을 설명하고, 다음 장으로 넘어가는 문장은 `관리 기준과 자동 검사의 객관성은 유지하되 구조 해석과 코드 반영은 LLM이 수행`하는 전환으로 끝낸다.
- 9페이지: 작업 방식 통제·결과 형식 통제·스킬 기반 운영 템플릿이라는 방향을 제시한다. `현재 위치` 제작 메모는 넣지 않는다.
- 10페이지: 제목은 `LLM이 메인, 규칙은 서브`다. LLM을 주로 사용하는 것을 전제로 최대한 보수적으로 운영하기 위해 작업·독립 검증·사람 승인 역할을 나누고, TO-BE 여섯 단계를 `사전 분석 → 커스터마이징 반영 → 변경 확인 → 필수 테스트 → 결과 결속 → 통합 승인`으로 통일한다.
- 11~14페이지: A·B·C·D별로 `파일 → 하는 일 → 이점`을 표로 보여준다. 각 페이지 상단에는 6단계 가로 표시줄을 두고 해당 단계만 진하게 표시한다. A=1단계, B=3단계, C=4단계, D=5단계다.
- 15페이지: 실제 완료 수치가 아니라 목표 승인 화면 예시임을 분명히 하고, A~D 결과와 남은 사람 검토를 함께 보여준다.
- 16페이지: 결론은 6단계에 맞춰 역할을 정리한다. 1~2단계는 LLM 분석·반영, 3~5단계는 독립 규칙 검증, 6단계는 사람 승인이다.
- 17페이지: 향후 계획은 `6단계 조합 검증 → 단계별 스킬 생성 → 독립 검증 규칙 모색` 순서로 제시한다.
- 18페이지: 본문에서 제외한 관리 파일·제외 이유·대체 방법을 부록으로 보존한다.
- 19페이지: `LLM이 일하고 검사기가 근거를 붙인다`는 방향 전환의 상세 설명을 부록으로 보존한다.
- 20페이지: A~D 핵심 파일 전체 요약표를 부록으로 보존한다.
- `commit-inventory.yaml`, `test-run-set.yaml`, `acgh-result.yaml`은 사람이 유지할 정책 파일이 아니라 도구가 만드는 자동 산출물로 표시한다.
- 최종 승인 기준은 기능별 Git commit SHA가 아니다. 여러 기능이 모두 합쳐진 최종 Git commit SHA 하나다.
- 기능별 구분은 SHA가 아니라 `BANK-OM ID ↔ 필수 테스트` 연결로 유지한다.
- `통합 코드 테스트`는 하나의 거대한 테스트가 아니다. 기능별 API·화면·소스 테스트를 동일한 최종 SHA에서 묶어 실행하는 단계다.
- 최종 코드가 바뀌면 이전 테스트 결과를 현재 코드의 승인 근거로 사용하지 않고 다시 테스트한다.

## 3. 사용자의 수정 스타일

### 문장과 설명

- 설명은 짧고 명료하게 쓴다. 장황한 방어 문장이나 내부 구현자의 독백을 넣지 않는다.
- 새 용어가 나오면 그 자리에서 `무엇인지`, `언제 쓰는지`, `무엇과 무엇을 비교하는지`, `결과가 어떤 판단으로 이어지는지`를 설명한다.
- 추상적인 정의만 쓰지 않는다. 실제 파일과 실제 YAML 필드를 예로 든다.
- `왜 남기나`보다 독자가 바로 이해할 수 있는 `이점` 또는 `효과`를 사용한다.
- 서로 다른 개수나 분류가 등장하면 즉시 구분한다. 예: `4개는 통제 종류, 6개는 업무 단계`.
- `지문`, `계보`, `계약`, `못박기`처럼 이 발표의 업무 문맥에서 낯선 비유는 쓰지 않는다.
- SHA, branch, commit, API, Manifest처럼 정확한 기술 용어는 유지하되 처음 읽는 사람도 이해할 수 있도록 완전한 문장으로 설명한다.
- `채택`, `제한 채택`, `운영 미완료`처럼 판단 기준이 불명확한 상태 라벨을 남발하지 않는다. 현재 상태가 꼭 필요할 때만 구체적인 문장으로 쓴다.

### 논리와 흐름

- 각 페이지는 이전 페이지에서 생긴 질문에 답해야 한다. 설명 없이 새 체계나 목록을 갑자기 제시하지 않는다.
- 동일한 개념은 동일한 이름과 동일한 A~D 순서로 반복한다.
- 같은 내용을 10~15페이지에서 반복할 때는 관점을 명확히 다르게 한다.

  - 10페이지: 업무의 전체 흐름
  - 11~14페이지: A~D별 본문에 남긴 파일·하는 일·이점
  - 15페이지: 관리자가 보는 결과
  - 18페이지: 본문에서 제외한 파일·제외 이유·대체 방법
  - 20페이지: A~D 핵심 파일 전체 요약

- 검사기가 LLM의 판단을 대신한다고 표현하지 않는다. LLM은 변경·해석을 수행하고, 검사기는 선언한 값과 실제 값 및 실행 결과를 대조한다.
- LLM 방식이 이미 작동한다는 사실을 부정하지 않는다. 검사기의 가치는 LLM을 대체하는 것이 아니라 반복 확인의 범위를 줄이고, 누락·바꿔치기·미실행을 드러내는 데 둔다.
- 공용 파일의 기능별 코드 조각을 영구 관리해야 한다고 단정하지 않는다. Git diff로 판단이 어려운 항목만 사람 확인 대상으로 남긴다.

### 예시 작성

- 원시 필드명부터 제시하지 않는다. 먼저 `파일 | 하는 일 (설명) | 이점` 순서로 이 파일이 어느 단계에서 어떤 실수를 막는지 설명한다.
- SHA는 “해당 코드 상태를 한 가지로 특정하는 Git 번호”, digest는 “파일·이미지 내용이 같은지 확인하는 식별값”처럼 처음 보는 사람도 이해할 말로 먼저 풀어 쓴다.
- 상세 필드명은 구현 명세나 부록에서만 사용한다. 발표 본문에서 유지할 핵심은 다음 네 관계다.

  - A: 이전 공식·현재 커스텀·새 공식 코드의 관계는 Git에서 자동 확인하고, 사람은 유지할 BANK-OM 기능과 필수 동작만 확정한다.
  - B: A의 Manifest 후보와 Git에 실제로 남은 변경 및 commit 이력을 대조한다.
  - C: 기능별 필수 테스트와 실제 실행 결과를 대조한다.
  - D: 최종 코드·테스트 결과·승인이 모두 같은 후보를 가리키는지 확인한다. 배포 이미지가 있으면 이미지 식별값도 함께 확인한다.

- 예시는 구조를 이해시키기 위한 것이다. 특정 파일명을 영원히 유지해야 한다고 표현하지 않는다.

### 화면과 변경 표시

- 비교 화면은 AS-IS와 TO-BE가 반드시 좌우로 보여야 한다.
- 변경된 페이지뿐 아니라 실제로 바뀐 문장과 블록에도 형광펜 표시를 한다.
- 형광펜은 비교 검토용이다. 최종 발표본을 확정할 때는 제거 여부를 사용자와 확인한다.
- 제목과 본문이 화면 밖으로 잘리지 않는지, 가로 넘침이 없는지 실제 브라우저에서 확인한다.
- 정보를 추가할 때 글자를 지나치게 줄이지 않는다. 길어지면 문장을 먼저 줄인다.

## 4. 현재 파일의 A~D 기준

| 통제 | 현재 명칭 | 관리 파일 예 | 핵심 비교 |
|---|---|---|---|
| A | 새 버전 Manifest 후보 작성 | `manifests`, `contracts.yaml`, `policies/sensitive-zones.yaml` | 기존 Manifest와 새 공식 구조를 분석해 목표 경로·추가·삭제·대체·반영 순서를 담은 새 버전 Manifest 후보를 수정 전에 작성 |
| B | 계획과 실제 변경 일치 검사 | Manifest 후보 ↔ Git diff·commit 이력(자동) | Manifest 후보의 계획과 실제 변경을 대조해 누락·계획 밖 변경·기능 ID 없는 commit·후속 commit 누락을 확인 |
| C | 필수 테스트 완전성 | Contract 실행기 → `test-run-set.yaml`, `customization-regression-history.yaml` | A에서 정의한 기능별 필수 테스트와 과거 실패 회귀 테스트가 모두 실행됐고 결과가 남았는지 |
| D | 결과와 최종 코드 연결 | `candidate-lock.yaml`, `test-run-set.yaml`, `acgh-result.yaml` | 테스트한 코드·최종 코드·승인 대상이 동일한 최종 SHA인지. 배포 이미지가 있으면 이미지 식별값도 함께 확인 |

- `customization-registry.yaml`은 기능 목록이 Manifest와 중복되므로 TO-BE의 수기 관리 파일에서 제외한다. 담당자·중요도처럼 필요한 고유 정보는 각 Manifest로 옮기고 전체 목록은 자동 생성하는 방향이다.
- `upgrade-rehearsal-matrix.yaml`은 실제 등록 묶음에 존재하지 않는 제안 파일이며, commit 관계는 Git과 Candidate lock에서 확인하므로 TO-BE에서 제외한다.
- Manifest의 과거 경로와 watch path는 A의 사전 조사 단서다. 새 버전의 최종 경로 정답이나 B의 PASS 조건으로 사용하지 않는다.
- Manifest의 `required_changed_paths`는 대규모 구조 변경에서 옛 경로를 잘못 강제할 수 있으므로, TO-BE에서는 “반드시 같은 경로가 변경돼야 함”이 아니라 “삭제·이동 시 반드시 조사해야 할 과거 핵심 경로”로 의미를 낮춘다. 최종 기능 존속은 contract와 테스트로 판단한다.
- Git 실제 변경 목록은 watch path 이동을 스스로 해석하지 못한다. A가 옛 경로를 유지·변경·삭제·분리·통합·이동으로 분류하고 목표 경로를 정한 뒤, B가 A의 이식 계획과 Git 실제 변경을 함께 대조한다.
- 커스텀 기능은 A가 정한 의존 순서대로 반영한다. 공유 파일을 후행 기능이 다시 수정하면 앞서 반영한 기능의 관련 테스트도 재실행하고, C에서는 전체 기능 테스트를 최종 후보에서 다시 실행한다.
- TO-BE의 Manifest 설명은 “기존 Manifest에서 과거 구현 위치를 읽고, LLM이 새 공식 구조를 조사해 목표 경로·추가·삭제·대체·반영 순서를 담은 새 버전 Manifest 후보를 만든다”로 통일한다.
- Contract 설명은 “커스텀 기능별 확인 동작과 필수 테스트를 기록하고, 실제 동작 확인은 4단계 C에서 수행한다”로 통일한다.
- C에서는 Contract를 다시 별도 행으로 반복하지 않는다. 정확한 표현은 “Contract 실행기가 A에서 정의한 기능별 필수 테스트를 수행하고, `test-run-set.yaml`이 실제 결과를 저장한다”이다. 결과 파일 자체가 테스트를 실행한다고 쓰지 않는다.
- `patch-kill-plan.yaml`과 `runtime-patch-kill-plan.yaml`은 목적은 같지만 현재 입력 구조와 실행 환경이 다르다. TO-BE에서는 하나의 patch-kill 정책 아래 소스·런타임 실행 수준으로 표현하되, 통합 스키마나 자동 변환기가 구현되기 전에는 기존 파일을 바로 삭제하지 않는다.
- 과거 실패 이력은 기존 `previous-run-test-review.yaml`의 “직전 실행 증거 검토” 의미와 다르므로 같은 이름을 재사용하지 않는다. `customization-regression-history.yaml`에 커스텀 기능별 과거 실패 증상·원인·개선 내용·기존 테스트의 누락·보강한 회귀 테스트를 기록하고 C에서 보강된 방식으로 재실행한다.
- 회귀 테스트 실행 결과는 별도 `previous-run-test-review-evidence.yaml`을 추가하지 않고 기존 `test-run-set.yaml`에 함께 기록한다.
- 모델 명칭은 `LM`이 아니라 항상 `LLM`으로 표기한다.
- `source-diff-paths.txt`는 독립된 수기 관리 파일로는 제외하지만, 실제 변경 목록을 Git에서 계산하는 기능은 B에 남긴다.
- `commit-inventory.yaml`도 독립된 관리 파일에서 제외한다. B가 실제 Git commit 이력을 직접 읽어 Manifest 후보와 대조한다.
- `shared-path-owners.yaml`은 Manifest의 경로 정보를 역산해 대체하므로 본문에서 제외한다.
- `policies/sensitive-zones.yaml`은 수정 후 적발보다 수정 전 설계가 중요하므로 B가 아니라 A에 둔다. B는 A에서 정한 위험 구역을 결과 검증에 재사용한다.
- A는 기존 Manifest를 덮어쓰지 않고 새 버전 후보를 만든다. B가 계획과 변경의 일치를 확인하고 C의 필수 테스트가 통과한 뒤에만 후보를 해당 버전의 정식 Manifest로 확정한다.
- A의 Manifest 후보는 자동으로 옳다고 승인되는 정답이 아니다. 코드 수정 전에 이식 계획을 남겨 사후 변경과 비교할 기준을 만드는 것이며, 사람 검토가 필요하다.
- C는 사전에 정의한 필수 테스트의 실행 여부와 결과를 확인한다. 테스트 내용 자체가 충분한지까지 자동 보장하지 않으며, 허위 테스트 방지는 현재 보류 항목이다.
- D는 소스 단계에서는 최종 commit·테스트 결과·승인 대상을 결속한다. 배포 이미지를 실제로 만든 단계에서만 이미지 식별값을 추가로 결속한다.
- `source-candidate-evidence.yaml`은 여러 소스 검사의 상세 항목·판정·대상 코드를 모은 감사자료다. D의 핵심 입력에서는 제외하고 18페이지 부록에서 설명한다.
