# Claude 검토 요청 — A단계와 테스트 조정 경계

## 1. 요청 성격

읽기 전용 설계 검토입니다. 저장소·HTML·코드·문서를 수정하지 말고, 아래 전제와 고민이 실제 버전 업그레이드 운영에 맞는지 적대적으로 검토해 주세요.

검토 대상 발표자료:

- `deliverables/deck-review/CODEX-05-전략발표_TO-BE.html`
- 특히 9페이지의 6단계 흐름과 11~14페이지의 A~D 설명

## 2. 배경

우리는 이미 커스터마이징된 OpenMetadata를 다음 공식 버전으로 옮기는 절차를 만들고 있습니다.

입력 코드는 원칙적으로 세 가지입니다.

1. 이전 공식 코드
2. 이전 공식 코드에 BANK-OM 커스터마이징을 반영한 현재 커스텀 코드
3. 새 공식 코드

기본 전제는 다음과 같습니다.

- 현재 커스텀 코드에 등록된 BANK-OM 기능은 이전 버전에서 정상 작동하고 승인된 기능이다.
- 업그레이드는 이 기능들을 새 공식 버전 구조로 옮기는 작업이다.
- 버전업 후에도 등록된 BANK-OM 기능은 전부 정상 작동해야 한다.
- 새 공식 버전의 기본 기능도 커스터마이징 때문에 훼손되면 안 된다.
- 기존부터 알려진 결함은 정상 기능으로 간주하지 않고 별도로 기록한다.

LLM이 코드 이동·충돌 해결·커스터마이징 재이식을 수행하고, 검사기는 LLM의 자기 보고를 그대로 믿지 않고 독립적인 코드·실행 결과를 대조하도록 설계하고 있습니다.

## 3. 현재 6단계 초안

1. **A — 검사 준비**
   - 세 코드의 Git 관계를 자동 확인
   - 이전에 승인된 BANK-OM 기능 범위와 정상 동작 기준을 승계
2. **LLM 코드 수정**
   - 새 공식 구조에 커스터마이징 이식
   - 충돌 해결 및 코드 이동 대응
3. **B — 변경 확인**
   - LLM 보고와 Git 실제 변경 대조
   - 누락·설명 없는 변경·위험 구역 확인
4. **C — 필수 테스트 실행**
   - BANK-OM별 필수 테스트 완전성 확인
   - 최종 후보에서 테스트 실행
5. **D — 결과 결속**
   - 최종 코드·실행 이미지·테스트 결과·승인이 동일 후보를 가리키는지 확인
6. **통합 승인**
   - A~D 결과와 사람 확인 항목을 보고 최종 후보 승인

## 4. 현재 논의에서 생긴 혼란

처음에는 A에서 유지할 기능뿐 아니라 `필수 테스트`까지 정한다고 설명했습니다. 그러자 다음 문제가 생겼습니다.

- 새 공식 버전에서 파일 경로·함수·API·화면 selector가 바뀌면 기존 테스트가 그대로 실행되지 않을 수 있습니다.
- 그렇다고 3→4단계 사이에서 합격 기준과 테스트를 새로 정하면, 새 후보 코드에 맞춰 쉬운 테스트를 만드는 자기 정답 문제가 생깁니다.
- 기존 커스텀 기능이 정상 작동했다는 전제라면, 기존 기능과 테스트를 A에서 자동 승계하는 것이 더 자연스럽습니다.
- 하지만 기존 테스트가 없거나 약한 기능도 있을 수 있습니다.

현재 잠정 구분은 다음과 같습니다.

### A에서 고정하거나 승계할 것

- 유지해야 할 BANK-OM 기능 목록
- 사용자가 기대하는 정상 동작
- PASS가 의미하는 업무 결과
- 이전 버전에 이미 존재하고 승인된 테스트 목록

### 3→4단계 사이에서 변경할 수 있는 것

- 새 경로에 맞춘 import 경로
- 바뀐 UI 구조에 맞춘 selector
- 바뀐 API·함수 호출 방식
- 테스트 실행 연결 코드

### 바꾸면 안 되는 것

- 기능의 의미
- 사용자 기대 결과
- 테스트 통과 조건을 더 느슨하게 만드는 변경
- 실패하던 후보를 통과시키기 위한 필수 검사의 삭제·skip 처리

## 5. 검토가 필요한 핵심 질문

### Q1. A단계의 정확한 책임

A는 아래 중 어디까지 책임져야 합니까?

1. 기능 목록과 업무 동작 기준만 승계
2. 기능 목록·업무 동작 기준·기존 필수 테스트 목록까지 승계
3. 구체적인 테스트 파일·테스트 ID·실행 명령까지 고정

권고안을 하나 선택하고 이유를 설명해 주세요. 특히 A를 불필요하게 무겁게 만들지 않으면서 LLM의 자기 기준 변경을 막을 수 있어야 합니다.

### Q2. 3→4단계 사이 테스트 조정의 허용 범위

공식 리팩터링으로 경로·selector·API가 바뀐 경우, 어떤 변경은 단순한 호환 조정이고 어떤 변경은 테스트 약화입니까?

기계적으로 차단하거나 사람 승인이 필요한 조건을 구체적으로 제안해 주세요.

### Q3. 신규 테스트가 필요한 경우

기존 커스텀 기능에 적절한 테스트가 없었다면 언제 어떻게 신규 테스트를 추가해야 합니까?

다음 제안이 충분한지 검토해 주세요.

1. 신규 테스트가 이전 정상 커스텀 버전에서 먼저 통과
2. 새 공식 원본에서는 BANK 커스텀이 없으므로 예상대로 실패하거나 해당 기능이 없음을 확인
3. 새 커스텀 후보에서 통과
4. 신규 테스트의 BANK-OM ID·업무 동작 기준·후보 SHA를 증거에 결속

이전 버전과 새 버전의 테스트 실행 환경이 달라 동일 테스트를 그대로 돌릴 수 없는 경우의 대안도 제시해 주세요.

### Q4. 기존 테스트가 약하거나 잘못된 경우

이전 버전에서 통과했다는 이유만으로 테스트를 신뢰하면 안 됩니다. 아래 우회를 어떻게 막아야 합니까?

- assertion 삭제 또는 `assert true`
- 핵심 검증 대신 화면이 열리는지만 확인
- 필수 테스트 목록에서 어려운 테스트 삭제
- skip·조건부 제외 확대
- 테스트 대상 selector를 엉뚱한 항상 존재 요소로 변경

필요한 최소 장치를 우선순위로 제안해 주세요.

### Q5. 단계 구조

테스트 호환 조정을 별도 7단계로 만들지 않고, B와 C 사이의 전환 작업으로 두는 것이 타당합니까?

다른 구성이 더 명확하다면 제안하되, 관리 단계와 파일 수를 불필요하게 늘리지 마세요.

### Q6. 관리 파일 최소화

다음 파일 역할이 중복되는지 검토해 주세요.

- `customization-registry.yaml`: 유지해야 할 BANK-OM 기능 목록
- `contracts.yaml`: 기능별 정상 동작 및 필수 테스트 연결
- `test-run-set.yaml`: 실제 실행한 테스트와 결과
- `previous-run-test-review.yaml`: 이전 버전 대비 테스트 삭제·축소 검토 제안

`previous-run-test-review.yaml`을 별도 수기 파일로 추가하지 않고, `contracts.yaml`과 Git diff에서 자동 산출할 수 있는지도 판단해 주세요.

## 6. 반례 중심 검토 요청

아래 상황에서 현재 설계가 잘못 PASS할 수 있는지 검토해 주세요.

1. 기능 코드는 사라졌지만 테스트 selector만 항상 존재하는 요소로 변경
2. 기존 필수 테스트 하나를 삭제하고 나머지만 실행
3. 신규 테스트를 새 후보에서만 실행해 통과
4. 기존 버전 테스트는 정상이나 새 버전에서 assertion을 약화
5. 테스트 이름은 같지만 본문이 전혀 다른 검사로 교체
6. BANK-OM ID 연결을 다른 기능의 통과 결과로 바꿔치기
7. 새 공식 구조 때문에 테스트 조정이 정당하지만 정책이 과도하게 차단

각 반례마다 다음을 답해 주세요.

- 현재 초안에서 막히는가
- 막히지 않는다면 어느 단계에서 무엇을 추가해야 하는가
- 자동 차단 / 사람 검토 / 정보성 경고 중 무엇이 적절한가

## 7. 요청 출력 형식

1. **전제 사실 정정** — 잘못된 전제가 있으면 먼저 정정
2. **권고 단계 구조** — A, B, 3→4 전환, C의 책임을 한 표로 정리
3. **P0 / P1 / P2 문제** — 잘못 PASS할 위험을 우선
4. **파일별 결정** — 유지 / 자동 산출 / 통합 / 제거
5. **필수 반례 테스트** — 입력 → 기대 결과 → 차단 위치
6. **발표자료에 넣을 비개발자용 문장** — 3문장 이내
7. **최종 판정** — 그대로 채택 / 수정 후 채택 / 재설계

근거 없이 동의하지 말고, 현재 설계가 과도하거나 불필요하다면 명확히 반대해 주세요. 반대로 기존 테스트 승계가 반드시 필요한 이유가 있으면 실제 실패 시나리오로 설명해 주세요.
