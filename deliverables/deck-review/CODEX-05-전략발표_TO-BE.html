S02 / 20 · 시작점 — 검증 목표

버전업 뒤에도 커스텀 기능이 살아 있는지 확인하고 싶었다

목표

우리가 손댄 부분(DB 커넥터·자체 화면·한글 입력 등)이 공식 버전업 뒤에도 안 깨지고 살아 있는지 확인한다.

전제

AI를 쓰는 것 자체는 옳다. 다만 행내에서 운영하는 서비스라 최대한 보수적으로 가야 한다고 봤다.→ 그래서 AI 개입을 최소화하고, 사람·AI 주관을 뺀 채 정해진 규칙(파일 위치·커밋 이력)만 보는 자동 검사로 전부 걸러내는 전략을 먼저 검토했다.

처음 기대한 효과

같은 코드와 같은 입력이면 같은 결과가 나오는 ‘재현 가능한 자동 판정’.

S03 / 20 · 어떻게 만들었나 (초기)

처음에는 파일·커밋 규칙으로 자동 판정했다

파일 위치‘이 기능은 이 파일들에’를 목록에 적고 대조
커밋 이력커밋마다 꼬리표 + 선언 범위 밖 변경 확인
안전장치애매하거나 검사를 못 돌리면 통과시키지 않음
검사 대상 고정검사한 커밋과 소스 전체 내용 식별값을 결과에 기록
예시 — BANK-OM-001 (InstanceCode) 하나가 만드는 관리 문서 2종 + 검사 기준 (실제 값)
① manifests/BANK-OM-001.yaml ← 경로 목록 = ‘경로 기반’의 실체
customization_id: BANK-OM-001   # InstanceCode
allowed_changed_paths:          # 건드려도 되는 경로 ~50개
  - …/resources/instancecode/InstanceCodeResource.java
  - …/json/schema/entity/data/instanceCode.json
  - …/components/InstanceCode/InstanceCodeListPage.tsx
  - …/locale/languages/*.json   (로케일 17개) …
required_changed_paths:         # 반드시 바뀌어야 통과 = 핵심 경로
  - InstanceCodeResource.java
  - instanceCode.json
② contracts.yaml ← 반드시 지켜야 할 동작 기준 + 확인 테스트
- id: CONTRACT-INSTANCE-CODE
  invariant: codeGroup/codeValue가 생성·조회·수정·삭제·검색 반영
             뒤에도 동일하게 조회된다
  required_tests:
    - test_instance_code.py::test_crud_search_roundtrip
  customization_ids: [BANK-OM-001, …]
검사기는 이 둘을 기준으로 검사한다
  1. 경로 기반 — 필수 경로가 공식과 달라졌나? 없거나 공식과 똑같으면(커스텀 소실) 차단.
  2. 커밋 이력 — 커밋에 Customization-ID: BANK-OM-001 꼬리표 + 선언 범위 밖 변경 확인.
  3. 기능별 필수 동작 검사 — 위 동작 기준을 확인하는 test_crud_search_roundtrip을 실제 실행. 일부 기능은 커스텀을 빼면 테스트도 실패하는지 추가 확인했다.
  4. 검사 대상 고정 — 검사한 커밋과 소스 전체 내용 식별값을 결과에 함께 기록 → 코드가 바뀌면 감지.
BANK-OM-006(Sybase)는 공유 파일(DatabaseServiceUtils.tsx 등)까지 목록에 + upgrade_watch로 공식 공용 파일(serviceConnection.json) 변경까지 감시.

초기 계획: 관리 파일의 생성·갱신과 상호 대조는 LLM 없이 규칙 기반 자동화로 처리하고, LLM은 충돌의 의미를 해석하고 해결하는 데만 사용한다. Manifest·Contract·커밋·테스트 결과·검사 대상의 연결에 누락이나 오류가 없어야 배포를 승인하도록 설계했다. 여기 보인 2종을 포함해 관리 파일은 약 25개다. (→ 7페이지 ‘운영상 한계’)

S04 / 20 · AS-IS — 규칙 중심 운영

규칙이 메인, LLM은 서브

1

수정 전 분석 및 관리 파일 업데이트 — 규칙

기존 경로·커밋·기능 정보를 정해진 양식에 맞춰 갱신하고 검사 입력을 준비한다.

2

커스터마이징 반영 — 규칙

정해진 경로와 병합 절차를 따라 커스텀 코드를 새 공식 버전에 반영한다.

3

변경 결과 확인 — 규칙 · 충돌 시 LLM

예상 경로와 실제 변경을 대조하고, 규칙으로 처리할 수 없는 충돌이 발생한 경우에만 LLM을 활용한다.

4

테스트 준비·실행 — 규칙

사전에 등록한 필수 테스트를 정해진 명령과 순서로 실행한다.

5

테스트 결과 분석 — 규칙

PASS·FAIL·미실행 여부와 필수 값의 일치 여부를 자동 판정한다.

6

통합 승인 — 규칙 + 사람 검토

관리 파일의 관계와 검사 결과에 오류가 없을 때 사람이 최종 배포를 승인한다.

AS-IS 요약규칙이 작업과 판정을 주도하고, LLM은 규칙으로 풀 수 없는 충돌이 생겼을 때만 예외적으로 사용한다.

두 버전업 모두 완료했지만, 1.13.2에서는 수동 대응이 크게 늘었다

1.13.0→1.13.1

자동 병합으로 완료 — 변화가 작고 충돌이 없어 기존 규칙 기반 절차가 그대로 작동했다.

1.13.1→1.13.2

수동 해석·재적용 후 완료 — 구조 변경과 다수의 충돌로 자동 절차를 중단하고 사람이 직접 대응했다.

1.13.2에서 확인한 변화

OpenMetadata의 코드 구조가 바뀌면서 기존 파일이 삭제·분리되고 기능이 다른 위치로 이동했다. 그 결과 다수의 충돌이 발생했고, 기존 경로를 전제로 한 자동 절차도 중단됐다.

충돌 해결

커스텀 기능별 관리 문서와 기존 구현 의도를 LLM에 제공했다.LLM은 이를 참고해 충돌을 해소하고 새 구조에 맞게 기능을 재반영했으며, 커스텀 기능별 테스트를 수행해 반영 결과를 확인했다.

이 결과가 드러낸 것최종적으로 버전업은 완료했지만, 그 과정에서 구조 변경을 기존 규칙이 해석하지 못한다는 점과 규칙·관리 파일을 계속 유지하는 비용이 함께 드러났다.
S06 / 20 · 드러난 한계 ① — 구조 변화 해석

구조적 한계

이동·분리 추적

OpenMetadata에서 기존 파일이 사라지고 기능이 여러 파일로 분리·이동되자, 옛 경로를 기준으로 한 검사는 새 구현 위치를 찾지 못했다.

Git diff의 한계

Git diff로 관리 문서에 적힌 파일이 실제로 변경된 것까지는 확인할 수 있었다.하지만 diff는 변경이 존재한다는 사실만 보여주므로, 필수 로직이 빠짐없이 들어갔는지 또는 일부만 반영됐는지는 확신하기 어려웠다.

역할 구분Git·규칙은 변경 사실을 확인하고, LLM은 변경 의미와 반영 방법을 해석한다. 기능이 실제로 동작한다는 최종 증거는 실행 테스트에서 얻는다.
S07 / 20 · 드러난 한계 ② — 지속 가능한 운영

운영상 한계

정보 분산

기능 선언·허용 경로·필수 테스트·커밋 이력·검사 결과·승인이 여러 관리 파일에 흩어졌다.

반복 갱신

버전업마다 경로와 기준을 고치고, 서로 참조하는 값과 새로 생성된 증거를 다시 확인해야 했다.

전체 관계 확인

한 파일만 맞아서는 승인할 수 없었다.Manifest·Contract·커밋·테스트 결과·검사 대상의 연결이 모두 일치해야 하므로 확인 범위가 넓어졌다.

누락 위험

관리 항목이 늘수록 갱신 누락·중복 검사·오래된 결과 재사용·형식적 승인 가능성도 커졌다.

운영상 한계안전성을 높이기 위해 추가한 규칙과 파일이 늘면서, 검사 자체보다 검사 체계를 유지하고 관계를 확인하는 비용이 커졌다.
S08 / 20 · 한계 속에서도 확인한 강점

관리 문서와 자동 검사는 여전히 유효했다

구조 변경의 의미를 자동으로 판정할 수는 없었지만, LLM이 기존 기능을 이해하도록 돕고 실행 사실을 같은 기준으로 재확인하는 기능은 유효했다.

사전 작업 기준 제공

기능별 관리 문서가 기존 구현 위치·의도·확인할 동작을 LLM에 제공했다.LLM이 수정 전에 살펴볼 범위와 유지해야 할 기능을 빠뜨리지 않도록 돕는 참고 기준이 됐다.

미실행 통과 금지

필수 검사가 실패하거나 실행되지 않았다면 전체 통과로 처리하지 않는다.검사를 생략하거나 오류로 끝낸 상태가 완료로 요약되는 것을 막는다.

결과와 코드 연결

검사한 commit과 코드 내용 식별값을 결과에 기록한다.검사 뒤 코드가 바뀌면 이전 결과를 현재 코드의 근거로 재사용하지 못하게 한다.

정확한 값 비교

예상 값과 실제 값, 필수 항목의 존재 여부, 테스트 성공·실패를 항목별로 비교한다.같은 코드·입력·검사 절차에는 같은 판정 규칙을 적용한다.

다음 전환관리 문서가 제공하는 작업 기준과 자동 검사의 객관성은 유지하되, 구조 해석과 코드 반영은 LLM이 수행하는 운영 방식으로 전환한다.
S09 / 20 · 다음 단계 — 커스터마이징 반영 체계화

작업 방법과 결과 형식을 함께 통제하는 운영 템플릿으로 확장한다

① 작업 방식 통제

프롬프트·Markdown 지침으로 LLM이 따라야 할 작업 순서, 확인 범위와 남길 기록을 정한다.기존 규칙이 직접 판단하기 어려웠던 구조 조사와 충돌 해석을 재사용 가능한 작업 절차로 옮긴다.

② 결과 형식 통제

각 과정의 결과를 정해진 형식으로 제출하게 하고, 자동 검사가 누락·실패·값 불일치를 판정한다.LLM의 자유로운 완료 설명이 아니라, 실제 실행 결과와 근거를 기준으로 다음 단계 진입 여부를 결정한다.

③ 최종 목표

작업 지침과 결과 검사를 과정 단위의 재사용 가능한 ‘스킬’로 묶어 OpenMetadata 운영 템플릿으로 만든다.버전업마다 절차를 새로 작성하지 않고, 같은 방식으로 실행·확인할 수 있는 구조를 목표로 한다.

S10 / 20 · TO-BE — 커스터마이징 반영 + 독립 검증

LLM이 메인, 규칙은 서브

LLM을 주로 사용하는 것을 전제로, 최대한 보수적으로 운영할 수 있도록 작업·독립 검증·사람 승인의 역할을 나눈다.

1

사전 분석 — LLM + 사람

A에서 기존 Manifest와 새 구조를 분석해 Manifest(커스터마이징별 변경·추가 파일 관리) 후보를 만들고, 사람이 기능·위험·이식 방향을 확인한다.

2

커스터마이징 반영 — LLM

Manifest 후보의 순서와 목표 구조에 따라 기능을 반영하고 변경 이유를 기록한다.

3

변경 확인 — 규칙 + LLM

B가 Manifest 후보와 Git diff·commit을 비교해 누락·계획 밖 변경을 찾고, 충돌과 예외는 LLM이 해석한다.

4

필수 테스트 — LLM + 규칙

C에서 테스트 연결을 새 구조에 맞게 조정하고, 최종 commit에서 필수 테스트를 모두 실행·기록한다.

5

결과 결속 — 규칙

D가 최종 commit·테스트 결과·승인을 연결하고, 배포 이미지가 있으면 식별값도 함께 묶는다.

6

통합 승인 — 규칙 + 사람

규칙이 A~D 관계를 확인하고, 사람이 위험·예외와 최종 통합 코드를 검토해 승인한다.

TO-BE 요약LLM의 역할은 분석·구현·원인 해석까지 확대하지만, 실행 여부·값 일치·최종 결과는 규칙이 독립적으로 확인한다.
S11 / 20 · A — 6단계 중 1단계

A는 새 공식 구조를 조사해 새 버전 Manifest 후보를 만든다

기존 Manifest는 과거 버전에서 기능이 구현된 위치를 알려준다. LLM은 이를 출발점으로 새 공식 구조를 조사하고, 기능별 목표 경로·추가·삭제·대체·반영 순서를 담은 Manifest 후보를 코드 수정 전에 작성한다.

2커스터마이징 반영
3변경 확인 · B
4필수 테스트 · C
5결과 결속 · D
6통합 승인
파일하는 일 (설명)이점

A · 1단계
manifests		기존 Manifest에서 커스텀 기능의 과거 구현 위치를 읽고, 새 공식 구조를 조사해 목표 경로·추가·삭제·대체·반영 순서를 담은 새 버전 Manifest 후보를 만든다.LLM이 코드를 고치기 전에 기능별 이식 계획을 명시하고, 수정 뒤에는 같은 계획을 검증 기준으로 재사용할 수 있다.
A · 1단계
contracts.yaml		커스텀 기능별로 확인해야 할 동작과 실행할 필수 테스트를 기록한다. 실제 동작 확인은 4단계 C에서 수행한다.LLM이 필수 테스트를 임의로 빼지 못하게 하고, 기능별 검사가 모두 실행됐는지 확인할 수 있다.
A · 1단계
policies/sensitive-zones.yaml		인증·DB 변경·배포 설정처럼 수정 전에 반드시 위험을 인지해야 할 영역을 지정한다.LLM이 수정 계획을 세울 때부터 금지·승인 필요·주의 영역을 구분해 설계할 수 있다.
B · 3단계
자동 변경 감사		별도 수기 파일 없이 Git에서 실제 변경 목록과 commit 이력을 읽어 Manifest 후보의 계획과 최종 코드가 일치하는지 검사한다.계획한 변경 누락, 계획 밖 변경, 기능 ID 없는 commit, 후속 보정 commit 누락을 한 번에 찾는다.
C · 4단계
Contract 실행기
→ test-run-set.yaml		실행기가 A에서 정의한 contract의 커스텀 기능별 필수 테스트를 수행하고, 결과 파일에 PASS·FAIL·skip·미실행을 기록한다.contract를 다시 설명하는 파일을 늘리지 않고, LLM의 “테스트 완료” 문장 대신 실제 실행 기록으로 완전성을 판단한다.
D · 5단계
candidate-locks/		최종 승인 대상으로 선택한 commit·C 테스트 결과 식별값을 고정하고 담당자 승인을 연결한다. 배포 이미지를 만든 경우에는 이미지 식별값도 함께 연결한다.승인 후 코드·테스트 결과·배포 이미지를 바꾸는 일을 막는다.
D · 5단계
acgh-result.yaml		A~D 검사 결과와 중단 사유를 한 개의 최종 판정으로 요약한다.승인자가 여러 로그를 뒤지지 않고 어떤 단계가 막혔는지 한 화면에서 확인한다.
6단계와의 관계A는 1단계 사전 분석·이식 설계, B는 3단계 변경 확인, C는 4단계 테스트, D는 5단계 결과 결속에 쓰인다. 2단계는 LLM이 실제 코드를 고치고, 6단계에서는 사람이 A~D 네 결과를 보고 최종 승인한다.
