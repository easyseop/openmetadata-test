S02 / 16 · 왜 시작했나

배경과 처음의 생각

목표

우리가 손댄 부분(DB 커넥터·자체 화면·한글 입력 등)이 공식 버전업 뒤에도 안 깨지고 살아 있는지 확인한다.

전제

AI를 쓰는 것 자체는 옳다. 다만 행내에서 운영하는 서비스라 최대한 보수적으로 가야 한다고 봤다.→ 그래서 AI 개입을 최소화하고, 사람·AI 주관을 뺀 채 정해진 규칙(파일 위치·커밋 이력)만 보는 자동 검사로 전부 걸러내는 전략을 먼저 검토했다.

처음 기대한 효과

같은 코드와 같은 입력이면 같은 결과가 나오는 ‘재현 가능한 자동 판정’.

S03 / 16 · 어떻게 만들었나 (초기)

처음 만든 것 — 규칙 기반 자동 검사기

파일 위치‘이 기능은 이 파일들에’를 목록에 적고 대조
커밋 이력커밋마다 꼬리표 + 선언 범위 밖 변경 확인
안전장치애매하거나 검사를 못 돌리면 통과시키지 않음
검사 대상 고정검사한 커밋과 소스 전체 내용 식별값을 결과에 기록
예시 — BANK-OM-001 (InstanceCode) 하나가 만드는 관리 문서 2종 + 검사 기준 (실제 값)
① manifests/BANK-OM-001.yaml ← 경로 목록 = ‘경로 기반’의 실체
customization_id: BANK-OM-001   # InstanceCode
allowed_changed_paths:          # 건드려도 되는 경로 ~50개
  - …/resources/instancecode/InstanceCodeResource.java
  - …/json/schema/entity/data/instanceCode.json
  - …/components/InstanceCode/InstanceCodeListPage.tsx
  - …/locale/languages/*.json   (로케일 17개) …
required_changed_paths:         # 반드시 바뀌어야 통과 = 핵심 경로
  - InstanceCodeResource.java
  - instanceCode.json
② contracts.yaml ← 반드시 지켜야 할 동작 기준 + 확인 테스트
- id: CONTRACT-INSTANCE-CODE
  invariant: codeGroup/codeValue가 생성·조회·수정·삭제·검색 반영
             뒤에도 동일하게 조회된다
  required_tests:
    - test_instance_code.py::test_crud_search_roundtrip
  customization_ids: [BANK-OM-001, …]
검사기는 이 둘을 기준으로 검사한다
  1. 경로 기반 — 필수 경로가 공식과 달라졌나? 없거나 공식과 똑같으면(커스텀 소실) 차단.
  2. 커밋 이력 — 커밋에 Customization-ID: BANK-OM-001 꼬리표 + 선언 범위 밖 변경 확인.
  3. 기능별 필수 동작 검사 — 위 동작 기준을 확인하는 test_crud_search_roundtrip을 실제 실행. 일부 기능은 커스텀을 빼면 테스트도 실패하는지 추가 확인했다.
  4. 검사 대상 고정 — 검사한 커밋과 소스 전체 내용 식별값을 결과에 함께 기록 → 코드가 바뀌면 감지.
BANK-OM-006(Sybase)는 공유 파일(DatabaseServiceUtils.tsx 등)까지 목록에 + upgrade_watch로 공식 공용 파일(serviceConnection.json) 변경까지 감시.

↑ 여기 보인 건 2종일 뿐 — 이 외에 등록대장·공유 파일 소유정보·정책·검사 계획·검사 대상 고정 정보·증거 파일이 함께 돈다. 현재 제품 코드에는 최초 업무 커스텀 7개와 후속 기술 보강 4개가 등록돼 있으며, 관리 파일은 약 25개다. (→ 6페이지 ‘운영 부담’의 실체)

① 병합 (먼저)

공식 1.13.2를 커스텀에 병합 → 충돌 다수 + Sybase 코드가 다른 파일로 이동. 커스텀을 새 위치에 수작업 재적용하고 관리 파일 ~25개·커밋 이력도 함께 손봐야 했다. ← ‘충돌’은 여기서 난다.

② 실행·검증 (그 뒤)

병합을 수작업으로 해결한 뒤 이미지 빌드 → 데이터 이관 → 서버 기동 → API 확인. InstanceCode는 실제 서버에서 CRUD·검색까지 동작. 실제 서버 일부 통과 전체 기능·브라우저 검증 완료를 뜻하지 않는다.

▸ 업그레이드 테스트를 하며 겪은 어려움 — 코드 이동은 드러난 계기 중 하나일 뿐이었다.

① 코드 이동

코드가 어디로 옮겨갔는지 규칙으론 못 따라간다. 옛 경로만 보고 “사라졌다”고 오판했다.

② 반쪽 병합

검사기는 우리 코드가 살아있는지를 “그 파일이 공식 버전과 다른가”로만 판정한다 — 다르면 들어간 것으로 본다. 어떻게 다른지는 보지 않는다. 그래서 병합이 어긋나 커스텀이 절반만 들어가도 ‘다르다’는 성립하므로 그대로 통과된다.

③ 등록할 경로가 많다

검사기에게 “우리 커스텀이 여기 있다”고 경로를 전부 등록해야 한다. Sybase 하나에 18개 — 그중 11개가 프로그램이 자동으로 만들어내는 파일이라, 다시 만들어질 때마다 내용이 통째로 바뀐다. 등록해둔 경로가 계속 어긋나고, 기능이 늘수록 곱절로 늘어난다.

④ 관리 부담

그때마다 관리 파일 ~25개와 커밋 이력을 사람이 갱신해야 한다. 고칠수록 따라 붙는 일이 늘어난다.

S05 / 16 · 드러난 한계 ① — 규칙 검사의 사각

규칙 검사만으로는 못 보는 것들

코드 이동

공식이 코드를 다른 파일로 옮기면 못 따라간다 (가장 큰 약점). 실제: Sybase의 case DatabaseServiceType.Sybase 코드가 DatabaseServiceUtils.tsx → *PureUtils.ts로 이사. 검사기는 기능별 관리 카드의 옛 경로만 봐서 “커스텀이 사라졌다”며 차단했다. 실제론 새 파일에 멀쩡히 살아있었음 = 오판.

의미(반쪽 병합)

검사기의 ‘생존’ 판정 기준은 “커스텀 파일이 공식과 다른가”다. 그런데 “다르다” ≠ “기능이 온전하다”. 병합이 어긋나 커스텀 로직이 반쪽만 들어가도 ‘공식과 다름’은 성립 → survived(통과)로 봐버림. (또 DB 마이그레이션이 어긋나 서버가 아예 안 뜬 적도 있음 — 파일은 멀쩡한데 런타임이 깨진 경우. 경로만 보는 검사론 못 잡음.)

입력·권한

검사기가 직접 계산하는 값과 외부에서 받아야 하는 판단이 섞여 있다. 실제 병합으로 계산할 수 있는 충돌 수는 자동 증거로 남길 수 있지만, 승인자가 조직상 권한자인지는 검사기만으로 확인하지 못한다.

결론규칙(파일·글자 기준)을 더 붙여도 이 약점은 반복된다 — 구조적 한계다. 단, 이건 변화가 클 때 얘기다 — 작은 버전업에선 규칙 기반이 잘 통했다.

지속 가능 운영의 한계 — 관리할 파일이 너무 많다

부담

사람이 정해야 하는 선언, 기계가 만드는 증거, 조직이 남기는 승인이 여러 파일에 흩어져 있다.

반복

버전업 때마다 선언과 경로를 갱신하고, 자동 생성된 증거를 다시 검토·보관해야 한다.

본질

‘검사 자체’보다 ‘검사를 유지하는 비용’이 더 크다 — 지속 운영의 벽.

위험

목록이 늘수록 갱신 누락·중복 검사·피로로 인한 형식적 승인 위험이 커진다.

S07 / 16 · 왜 ‘룰베이스 검사기’인가

강점 — LLM 혼자선 보장 못 하는 것들

아래는 LLM도 수행할 수 있다. 다만 보호된 독립 자동화가 같은 입력으로 실행하고 결과를 남겨야 LLM의 자기 보고와 구분되는 검증 근거가 된다.

허위 테스트 방지

기능이 되는지가 아니라, 그 테스트가 진짜인지를 검사한다.

  1. 커스터마이징 기능 테스트 사전 정의
  2. 공식 버전에서 테스트 — 기대결과 FAIL
  3. 커스텀 버전에서 테스트 — 기대결과 통과
  4. 2번이 통과하면 → 속 빈 테스트 (3번의 초록불에 근거 없음)
LLM이 하면“공식 버전에서 돌려봤고 실패했습니다” — 그 말이 사실인지 알 방법이 없다.검사기가 하면어느 커밋에서 무슨 테스트가 어떻게 실패했는지 파일로 남는다.

▸ 테스트는 LLM이 만들어도 된다. 사람이 그걸 다 읽어보고 “제대로 짰나”를 판단할 수는 없으니, 커스텀 없이 한 번 돌려 걸러낸다 — LLM에게 테스트를 맡길수록 이 항목이 더 필요해진다.

▸ 한계 — 아무것도 안 보는 테스트는 걸러내지만, 덜 보는 테스트는 못 걸러낸다. 예: status_code == 200만 확인해도 커스텀이 없으면 404라 실패하므로 “진짜 테스트”로 인정된다 — 정작 값이 맞는지·검색에 반영되는지는 안 보는데도. 향후 개선 — 돌연변이 테스트로 메울 수 있다. 커스텀을 통째로 빼는 대신 한 줄씩만 바꿔(예: 비교 조건을 반대로) 그때도 테스트가 실패하는지 본다 → ‘덜 보는 테스트’까지 드러난다.

실제 결과물
# source-patch-kill-evidence.yaml (커스텀 제외 시 테스트 실패 확인)
gates:
- name: source-patch-kill:BANK-OM-006        # Sybase
  reasons: ['proven: required test failed without the patch']
  verdict: pass                              # ← 커스텀 없으니 실패 = 이 테스트는 진짜
pending_high_critical_ids: [BANK-OM-001, 002, 003]  # ← 아직 못 한 것도 남는다
미실행은 통과 금지

필수 검사 하나라도 못 돌면 전체를 통과시키지 않는다.

  1. 필수 검사 목록 사전 정의
  2. 실행 — 데이터 없음·오류·시간초과는 ‘건너뜀’으로 기록
  3. 집계 — 필수 검사가 미실행이면 전체 통과를 주지 않는다
LLM 자기 보고만 있으면미실행을 통과로 요약할 위험이 있다.검사기가 집계하면필수 검사 미실행을 차단 또는 분석 오류로 남기고 전체 통과를 막는다.
실제 결과물
# 화면 검사할 데이터가 없어 7개를 못 돌린 경우
필수 동작 검사:  2개 통과 · 7개 미실행  →  전체 판정: 차단
                                            ↑ 실패가 0인데도 통과가 아니다
검사 대상 코드 고정

어느 코드를 검사했는지 커밋과 소스 전체 내용 식별값으로 기록해, 이후 바뀌면 드러나게 한다.

  1. 검사 직전 커밋과 소스 전체 내용 식별값 기록
  2. 그 코드로 검사 실행 — 결과에 함께 기록
  3. 나중에 대조 — 식별값이 다르면 다른 코드
LLM이 하면자기가 쓴 기록을 자기가 고칠 수 있다.검사기가 하면보호된 자동화가 쓰고, 기록한 코드와 현재 코드가 다르면 드러난다.
실제 결과물
# source-candidate-evidence.yaml
candidate:
  commit_sha: 849ae756cd23...   # 검사한 바로 그 코드
  tree_sha:   22f92a8e0fd2...
  candidate_lock_digest: sha256:61a3f02d3f22...   # 검사 대상 정보가 바뀌면 값도 달라짐
기계 대조(data-check)

고정된 건 값이 아니라 판정 규칙이다. 값은 매번 달라져도, “무엇을 맞다고 볼 것인가”는 늘 같다.

  1. 값이 정해진 것 → 그 값과 그대로 대조 (예: 스키마 제목이 SybaseConnection인가)
  2. 값이 매번 달라지는 것 → 관계로 대조 — 넣고 → 꺼내고 → 고치고 → 검색까지 넣은 값이 그대로 나오는지
  3. 끝나면 흔적을 지운다 (다음 실행에 영향 없게)
LLM이 하면값이 많아지면 “대체로 맞다”로 흐른다.검사기가 하면넣은 값과 나온 값을 한 건씩 대조 — 하나만 달라도 실패.
실제 테스트 코드
# test_instance_code.py :: test_crud_search_roundtrip
suffix  = uuid.uuid4().hex[:12]                      # 매번 새 값을 만든다
payload = {"codeGroup": "CONTRACT", "codeValue": suffix, "codeName": "before"}

created = client.post("/v1/instanceCodes", payload)  # 넣고
fetched = client.get(f"/v1/instanceCodes/{id}")
assert fetched["codeValue"] == payload["codeValue"]  # 넣은 값 == 나온 값

updated = client.put(..., dict(payload, codeName="after"))
assert updated["codeName"] == "after"                # 고친 값이 반영되나

hit = wait_for(search_hit)                           # 검색 색인에도
assert hit["_source"]["codeValue"] == payload["codeValue"]
finally: client.delete(...)                          # 흔적 지움
결정론(재현성)

LLM의 설명과 분리해, 같은 코드·입력·환경에는 같은 규칙과 같은 판정을 적용한다.

  1. 같은 커밋과 소스 전체 내용이면
  2. 같은 검사 절차로
  3. 항상 같은 판정 — 어제 통과한 게 오늘 막히지 않는다
LLM은같은 입력에도 답이 흔들린다 — 그래서 “배포해도 되나”의 기준으로 삼을 수 없다.검사기는규칙이라 흔들리지 않는다 — 이건 흉내로 메울 수 없는 차이다.

네 가지 통제를 여섯 단계에 적용한다

통제는 A~D 네 가지이고, 업무 순서는 ①~⑥ 여섯 단계다. 9~11페이지는 같은 네 가지 통제를 전체 흐름 / 통제 목적 / 확인 결과 관점으로 나누어 설명한다.

1

검사 준비 — A. 승인 입력 고정

공식 대상 버전·시작할 커스텀 코드·반영할 BANK-OM 기능·필수 동작을 확정한다.

2

LLM 작업 — 실제 수정 단계

LLM이 코드 이동과 충돌을 해결하고 여러 기능을 반영한다. 이 단계 자체는 통제 항목에 포함하지 않는다.

3

변경 결과 확인 — B. 실제 변경 대조

LLM 작업 보고를 Git diff와 비교한다. 공용 파일에서 기능별 구분이 애매하면 사람이 확인한다.

4

통합 코드 테스트 — C. 필수 테스트 완전성

여러 기능이 합쳐진 최종 커밋 SHA 하나에서, 각 기능에 연결된 API·화면·소스 테스트를 모두 실행한다.

5

테스트 결과 묶기 — D. 결과와 최종 코드 연결

모든 기능별 테스트 결과에 동일한 최종 커밋·소스 전체 내용 식별값·실행 이미지 정보를 기록한다.

6

통합 승인 — A~D 결과 확인

사람이 네 가지 결과를 한 화면에서 확인하고 최종 통합 코드 전체를 한 번 승인한다.

숫자를 읽는 법4개는 통제의 종류, 6개는 업무의 순서다. 최종 승인은 기능별 SHA가 아니라, 모든 기능이 합쳐진 최종 SHA 하나를 기준으로 한다.
S10 / 16 · 관점 2 / 3 — 적용 예와 이점

A~D는 어떤 파일과 값을 쓰는가

8페이지에서 남기기로 한 네 가지 통제가 기존 관리 파일 중 무엇을 재사용하는지 예로 본다. 파일을 모두 유지하는 것이 아니라, 비교에 필요한 값만 남기는 방식이다.

A · 승인 입력 고정

적용 파일 예 — upgrade-rehearsal-matrix.yaml · customization-registry.yaml

비교하는 값upstream_target.sha ↔ 공식 태그 SHA
source_reference.commit_sha ↔ 시작 커스텀 코드
entries[].customization_id ↔ 반영할 기능 목록이점LLM이 다른 공식 버전·다른 시작 코드·빠진 기능 범위로 작업하는 일을 시작 전에 드러낸다.
B · 실제 변경 대조

적용 파일 예 — manifests/BANK-OM-001.yaml · commit-inventory.yaml

비교하는 값implementation.changed_paths ↔ Git이 계산한 changed_paths
전체 Manifest 경로의 합 ↔ 공식 코드와 최종 코드의 실제 diff이점LLM 보고에서 빠진 파일과 설명 없는 변경을 먼저 찾는다. 공용 파일의 기능별 의미는 애매한 경우만 사람이 확인한다.
C · 필수 테스트 완전성

적용 파일 예 — contracts.yaml · test-run-set.yaml

비교하는 값customization_ids로 기능과 테스트를 연결
required_tests ↔ runs[].test_id
각 outcome이 통과인지 확인이점여러 기능을 한 커밋에 넣어도 기능별 필수 테스트 누락을 찾는다. 미실행 항목은 전체 통과로 숨길 수 없다.
D · 결과와 최종 코드 연결

적용 파일 예 — candidate-lock.yaml · test-run-set.yaml · acgh-result.yaml

비교하는 값세 파일의 commit_sha가 같은지 확인
artifact_digest도 같은지 확인이점중간 코드나 이전 실행의 통과 결과를 최종 코드 승인에 재사용하지 못하게 한다. 최종 코드가 바뀌면 다시 테스트한다.
실제 용도파일명은 운영 구조에 따라 바뀔 수 있다. 유지해야 하는 것은 선언한 값 ↔ 실제 값 ↔ 실행 결과를 대조하는 관계이며, 이 결과를 최종 승인 화면의 네 줄로 요약한다.
S11 / 16 · 관점 3 / 3 — 확인 결과

관리자는 A~D 네 줄만 확인한다

상세 로그는 실무자가 필요할 때 펼쳐보고, 승인자는 동일한 네 가지 항목의 결과와 다음 조치만 본다.

A · 입력

공식 버전·시작 코드·반영 기능·필수 동작 4/4 일치하나라도 다르면 다른 작업을 검사한 것이므로 즉시 중단한다.

B · 변경

LLM 보고와 Git diff 일치 · 설명 없는 변경 0건 · 사람 확인 2건설명 없는 변경은 보완하고, 공용 파일처럼 의미 구분이 필요한 2건은 사람이 확인한다.

C · 필수 테스트 완전성

대상 SHA ABC123 하나 · 기능별 테스트 9/9 실행 · 통과 9 · 실패 0 · 미실행 0기능별 SHA는 요구하지 않는다. 대신 기능별 테스트 이름과 결과를 남기고, 전부 같은 최종 SHA에서 실행됐는지 확인한다.

D · 코드 일치

최종 커밋 ABC123 · 실행 이미지 ABC123 · 모든 테스트 결과 ABC123세 대상이 같을 때만 승인할 수 있다. 승인 뒤 코드가 바뀌면 이전 승인은 무효로 보고 다시 테스트한다.

승인 예시A~D가 모두 충족되고 사람 확인 2건이 완료되면 최종 커밋 ABC123 전체를 승인한다. 기능별 중간 커밋의 통과 결과는 개발 참고자료일 뿐 최종 승인 근거가 아니다.

그래서 빨라지나 — 시간이 어디서 늘고 줄나

이 질문에 “무조건 빨라진다”고 답하지 않는다. 관리 파일을 전부 유지한 채 LLM까지 얹으면 오히려 두 배로 느려진다 — 이번 1차 검토에서 덜어낸 이유가 바로 이것이다.

버전업에서 시간이 드는 일지금 누가크기바뀌면
병합·충돌 해결 + 리로케이션 재적용사람가장 큼LLM이 대신 → 줄어듦
관리 파일 ~25개 · 커밋 이력 갱신사람큼LLM이 초안 → 줄어듦
검사·테스트 실행기계—늘어도 사람 시간은 아님
확인(화면 열어보기·API 찔러보기)사람중간자동화 가능한 범위만 줄어듦
승인·판단사람작음그대로

▸ LLM은 사람의 병합·정리 시간을 줄일 가능성이 있다. 다만 Docker 빌드·네트워크·브라우저 환경처럼 기계 시간이 전체 일정의 병목이 되는 경우도 있어, 총 소요시간은 별도로 측정해야 한다.

첫 도입

오히려 느리다. 등록·기준선 세팅 비용이 앞에 몰려 있다. “이번에 빨라진다”고 말하면 거짓말이 된다.

반복 운영의 기대

등록·기준선을 재사용하면 사람 작업이 줄어들 가능성이 있다. 아직 두 번째 반복 운영의 실측 시간은 없다.

보류 5종이 이 답을 좌우한다사람 손이 붙는 것을 남기면 느려지고, 자동으로 도는 것만 남기면 빨라진다. 그래서 남은 판단은 “이 검사가 좋은가”가 아니라 “이 검사에 사람 손이 붙는가”다. 예: 화면 기준선은 판정 규칙만 바꾸면 사람 손이 0이 되고, 빼보기는 기능별 계획서를 없애면 실행만 남는다.
8/5 방식과의 관계8/5의 “포팅 시간 크게 단축”은 그쪽의 자체 보고다. 우리는 그 방식을 대체하지 않고, 실제 코드·검사 범위·미실행 항목을 독립 결과와 대조할 수 있는 층을 제안한다. 속도 개선 여부도 이 구조를 도입한 뒤 별도로 측정한다.
S13 / 16 · 독립 검증의 전제

검사기의 정확한 위치 — LLM 위에 얹는 안전장치

검사기는 LLM의 충돌 해석·코드 이동 판단을 대신하지 않는다. 대신 LLM 자기 보고와 분리된 환경에서 증거 존재 여부를 확인하거나 필요한 검사를 독립 재실행한다.

1차 — LLM

무엇을 바꿀지 정하고, 옮겨간 코드를 찾고, 충돌을 풀고, 검사까지 직접 돌린다. 속도는 전부 여기서 나온다. 검사기가 이 자리를 뺏지 않는다.

2차 — 독립 자동화

증거 검증은 실행 기록·후보 지문을 대조하고, 행동 검증은 필수 API·화면·소스 검사를 같은 후보에서 다시 실행한다. 둘을 같은 말로 묶지 않는다.

그래서 독립성

LLM이 실행·기록·증거·승인을 다 하면 ‘한 번 더’가 성립하지 않는다. 별도의 보호된 자동화(CI)가 실제 코드를 받아 검사를 돌려야 한다 — LLM은 요약만, 판정은 못 바꾼다.

한 줄검사기를 ‘LLM보다 똑똑한 판정자’로 쓰면 실패한다 — 그건 이미 해봤다. ‘LLM이 한 일을 한 번 더 확인하는 안전장치’로 쓰면 부담은 작고 얻는 건 크다.

S15 / 16 · 부록 A — 참고한 다른 접근

8/5 공유된 ‘LLM 기반 운영 방식’ (참고)

개념

규칙·지식 문서·자동화로 LLM이 버전 포팅을 빠르게 수행하는 방식. “포팅 시간 크게 단축(빠르고 체계적)”은 그 방식의 자체 보고 수치 — 우리가 실행·검증한 건 아니다.

구조

변경·수정·테스트·결과 기록을 대부분 LLM이 스스로 수행하고, 그 결과도 스스로 문서에 적는다.

우리 생각 — 검증이 아니라 방향 제안이 접근에 검사기로 ‘각 판단의 근거를 자동으로 뒷받침’하는 층을 더하면, 속도(LLM)는 살리고 신뢰(근거)는 끌어올릴 수 있겠다. 경쟁이 아니라 ‘빠른 실행 + 단단한 근거’로 합쳐진다.
S16 / 16 · 부록 B — 방향 전환

LLM이 일하고, 검사기가 근거를 붙인다

LLM

판단·제안무엇을 바꿀지, 코드가 어디로 옮겨졌을지, 충돌 해결, 필요한 테스트.

검사기

뒷받침그 판단을 실제 코드·실행 증거로 확인하고, 위험하면 막는다.

▸ 구체적으로 — LLM의 주장을 검사기가 이렇게 확인한다

“이 파일 바꿨다”

실제 커밋의 변경 내역을 직접 대조한다.

“충돌 0건”

임시로 실제 병합해 충돌 수를 센다. 안 해보고 적어도 티가 안 나는 주장이라, 세어보는 것 말고는 확인할 방법이 없다.

“테스트 통과”

해당 기능에 정의된 필수 검사를 독립 환경에서 다시 실행한다. 현재 1.13.2는 일부 런타임만 실행됐으며, 미실행은 통과로 세지 않는다.

“승인함”

승인을 결과에 묶어 입력이 바뀌면 자동으로 무효가 되게 한다.

향후 자동 대조 규칙LLM이 ‘됐다(✅)’고 적어도, 실제 코드·실행 증거가 없으면 ‘미확인’으로 표시한다. 증거 없다고 곧장 ‘거짓’으로 몰지 않는다 → 확인 반박 미확인 사람검토 4단계.
