## 1. 저장소 목적에 대한 해석

이 저장소의 실질적인 목적은 다음과 같다.

> **OpenMetadata 공식 버전을 업그레이드할 때 행내 커스터마이징이 빠지지 않았는지 자동으로 검증하고, 실제 동작 검증과 릴리스 승격까지 통제하기 위한 거버넌스 체계와 구현 하네스를 개발한다.**

핵심 수단은 다음과 같다.

- 공식 버전과 기준 Commit SHA 고정
- 고유 Customization ID가 붙은 패치 스택
- 기계 판독 가능한 커스터마이징 명세
- 결정적 CI 판정
- 테스트와 후보 SHA의 결속
- 릴리스 산출물 해시·Digest 고정
- LLM은 설명·영향 후보 제시만 담당하고 통과·차단 판정에서는 제외

기술적 핵심 방향은 좋다. 특히 다음 구분은 유지할 가치가 크다.

- **등록·재적용 완전성**: Git·명세·CI가 검증
- **업무 동작의 정확성**: 테스트·업그레이드 검증·운영 승인으로 확인

그러나 현재 저장소는 경영진이나 신규 개발자가 처음 들어와 하나의 기준을 빠르게 이해하는 문서 세트라기보다, 다음이 루트에 함께 놓인 작업 공간에 가깝다.

- 현행 설계 문서
- 과거 설계 문서
- 요구사항 정의서
- 개발 계획
- 진행 상태 문서
- 외부 검토 요청과 응답
- Claude 세션 인수인계
- 구현 코드

따라서 문장 몇 개를 다듬는 것보다 먼저 **문서 역할, 정본, 읽는 순서, 보관 위치**를 정리해야 한다.

또한 저장소 이름 `openmetadata-test`는 실제 목적보다 범위가 좁아 보인다. 이 저장소는 단순 테스트 저장소가 아니라 커스터마이징 거버넌스·업그레이드 검증·릴리스 통제를 다룬다. 이름 변경이 어렵다면 GitHub About 영역에 최소한 다음 수준의 설명을 추가하는 것이 좋다.

> OpenMetadata customization and upgrade governance harness

## 2. 전체 평가

### 2.1 잘된 점

1. 커스터마이징 누락을 사람 기억이 아니라 CI로 검출하려는 문제 정의가 명확하다.
2. 코어 수정 최소화, 고유 ID, 명세, 테스트, 제거 조건을 하나의 통제 체계로 연결한다.
3. LLM이 배포 판정을 대신하지 못하도록 경계를 둔 점이 적절하다.
4. 충돌 없는 의미 변경을 별도 위험으로 인식하고 있다.
5. 소스 재적용 검증과 실제 업무 동작 검증을 분리하려는 방향이 타당하다.
6. 검증기가 발견하지 못하는 한계를 문서화하려는 태도가 좋다.

### 2.2 가장 큰 문제

1. **정본이 하나가 아니다.**  
   README, SRS 부칙, 검토 응답, Build Plan을 모두 읽어야 최신 기준을 해석할 수 있다.

2. **구형 설계와 정정된 설계가 동시에 남아 있다.**  
   예: `affected_paths`, `range-diff` 기계 파싱, 충돌 후 `abort` 흐름 등이 여러 문서에 잔존한다.

3. **경영진 문서와 개발자 문서가 분리되지 않았다.**  
   첫 화면부터 SHA, trailer, glob, drift, clean-room replay 등의 용어가 등장한다.

4. **문서 상태가 구현 상태와 맞지 않는다.**  
   SRS는 Draft인데 로드맵과 세션 문서는 상당 부분 구현 완료라고 기록한다.

5. **개발 계획에 순환 의존과 태스크 번호 불일치가 있다.**  
   이는 표현 문제가 아니라 실제 실행 순서를 잘못 만들 수 있는 계획 결함이다.

6. **검토 대화와 에이전트 세션 파일이 루트에 있다.**  
   신규 독자가 과거 의견을 현행 기준으로 오해할 수 있다.

# 4. 파일별 상세 피드백

## 4.1 `README.md`

### 현재 역할

저장소의 첫 진입 문서이자 문서 지도 역할을 한다. 목적, 보장 범위, 변경 사례, 검증기 목록, 문서 충돌 우선순위, 테스트 정책, 마일스톤과 핵심 원칙을 모두 담고 있다.

### 좋은 점

- “커스터마이징 누락을 사람 기억이 아니라 CI로 막는다”는 문제를 바로 제시한다.
- 자동으로 검증하는 범위와 기능 테스트가 필요한 범위를 구분하려 한다.
- 저장소에 어떤 문서가 있는지 안내한다.

### 개선이 필요한 점

첫 화면부터 다음 용어가 연속해서 등장한다.

- SHA
- cherry-pick
- canary
- patch-kill
- contract
- clean-room replay
- drift
- upgrade_watch
- verifier
- digest
- verdict

개발자라도 처음 접하면 용어 관계를 먼저 해독해야 하며, 경영진에게는 사실상 읽히기 어렵다. 또한 검증기 전체 목록이 문서 앞부분을 차지해 “왜 필요한가”보다 “무엇을 구현하는가”가 먼저 나온다.

다음 표현은 공식 첫 문서에서 다듬는 것이 좋다.

| 현재 표현 | 권장 표현 |
|---|---|
| 기능 의미 | 업무 동작의 정확성 |
| 정책이 빈 총인데 통과만 뜸 | 정책 대상 경로가 사라졌는데도 검사가 정상으로 표시됨 |
| 생존 못 증명하는 껍데기 테스트 | 커스터마이징의 효과를 입증하지 못하는 테스트 |
| 은밀한 변경 섞임 | 승인되지 않은 추가 변경 포함 |
| 고장 우회 | 검사 오류가 정상 또는 승인 대상으로 처리되는 문제 |
| M0 사전 셋팅 | M0 사전 준비 |

README가 SRS를 “일부 정정 대상”으로 표시하고, SRS 부칙·검토 응답·Build Plan을 대조해 최신 기준을 해석하도록 안내한다면 신규 독자는 다음 인상을 받는다.

> 아직 하나의 승인된 기준 문서가 없다.

검토 이력은 유용하지만, 최종 기준 문서가 검토 이력을 읽어야만 해석되는 구조는 피해야 한다.

### 테스트 정책 문구 보완

“모든 픽스처·통합·업그레이드 테스트는 실제 OpenMetadata로 진행한다”는 문장은 범위가 지나치게 넓다. 판정 순서나 결과 집계 같은 순수 알고리즘 단위 테스트까지 실제 OpenMetadata가 필요하지는 않다.

권장 문장:

> OpenMetadata의 파일 구조, 업그레이드 차이, 재적용 동작에 의존하는 통합 및 업그레이드 테스트는 실제 고정 버전의 OpenMetadata를 사용한다. 순수 판정 로직의 단위 테스트는 최소 합성 픽스처를 사용할 수 있다.

### 권장 README 구조

1. 저장소 목적 — 일반인도 이해할 수 있는 3문장
2. 왜 필요한가 — 누락, 이유 소실, 업그레이드 지연
3. 자동으로 확인하는 범위
4. 자동으로 확정하지 않는 범위
5. 현재 구현 상태
6. 대상별 읽는 순서
7. 개발자 빠른 시작
8. 상세 문서 링크
9. 용어집 링크

검증기 전체 표와 세부 마일스톤은 README에서 제거하고 별도 카탈로그와 로드맵으로 이동하는 편이 좋다.

## 4.2 `openmetadata_strategy_briefing.md`

### 현재 역할

패치 스택을 선택한 배경, merge 방식과의 비교, 단점과 보완책, 업그레이드 예시, 자동 게이트, LLM 활용, 로드맵과 기대 효과를 설명하는 전략 브리핑 문서다.

### 좋은 점

- 현재 파일 중 경영진용 설명에 가장 가깝다.
- “원본 책과 포스트잇” 비유는 merge와 패치 스택 차이를 설명하는 데 효과적이다.
- 문제 → 전략 → 단점 → 보완책 흐름이 자연스럽다.
- 코어 수정 최소화 관문을 구체적으로 설명한다.

### 개선이 필요한 점

문서가 경영진 브리핑치고 너무 길다. LLM 위키 페이지 구조, 질의 예시, 3층 영향 분석의 상세 내용은 부록이나 별도 문서로 이동하고 본문은 3~5페이지 수준으로 축약하는 것이 좋다.

문서 내부의 주장 강도도 통일해야 한다.

- 한 곳에서는 “merge도 엄격한 규칙을 추가하면 가능하지만 목록이 덜 선명하다”고 설명한다.
- 다른 곳에서는 merge 방식으로 누락 검출이 “불가능하다”고 단정한다.

앞의 표현이 더 정확하다.

권장 문장:

> 순수 merge 결과만으로는 행내 수정 목록과 누락 여부가 자연스럽게 드러나지 않는다. 별도의 커밋 규칙과 명세 통제를 추가하면 검증할 수 있지만, 패치 스택이 현재 목표에 더 직접적이다.

다음 표현은 구어체이거나 과장으로 읽힐 수 있다.

| 현재 표현 | 권장 표현 |
|---|---|
| 행내 수정을 즉시 재적용 | 행내 수정을 신속하고 반복 가능한 절차로 재적용 |
| merge 방식은 불가능하다 | 순수 merge 방식만으로는 명시적 누락 검증이 어렵다 |
| 업그레이드 부담은 전부 코어에서 발생 | 소스 재적용과 텍스트 충돌 부담은 주로 코어 수정에서 발생 |
| 사람 개입은 0에 수렴 | 패치가 적고 독립적일수록 수동 충돌 해결 범위가 줄어든다 |
| 테스트가 동작을 확정 | 정의된 테스트 범위에서 동작을 확인한다 |
| 명령 1회 실행으로 끝난다 | 자동 재적용 절차를 한 번 실행하며, 충돌과 검토 항목은 별도 처리한다 |

### “4개 자동 게이트” 표현

최신 저장소가 다수의 검증 통제를 갖고 있다면 경영진 문서에서 4개 게이트를 상세 구현 단위처럼 보이게 하기보다 다음 **4개 통제 영역**으로 설명하는 편이 좋다.

1. 수정 등록·재적용 통제
2. 변경 범위·민감 영역 통제
3. 기능 테스트·업그레이드 검증
4. 릴리스 산출물·정책 무결성 통제

### 경영진 문서에 추가할 내용

현재 문서는 기술적으로 무엇을 할지는 잘 설명하지만, 경영진이 무엇을 결정해야 하는지가 명확하지 않다. 다음을 추가하는 것이 좋다.

- 이번 심의에서 승인받을 결정
- 1차 도입 범위와 제외 범위
- 필요한 역할과 담당 조직
- 업그레이드마다 발생하는 운영 부담
- 성공 지표
- 주요 잔여 위험과 수용 책임자
- 예상 중단 조건 또는 재설계 기준

## 4.3 `openmetadata_upstream_customization_design.md`

### 현재 역할

업스트림 미러, 저장소 구성, 커스터마이징 분류, 패치 스택, 명세 YAML, JSON Schema, 테스트 카탈로그, CI, 업그레이드, 반입 패키지, 역할, 지표, LLM 활용, 체크리스트와 템플릿을 모두 포함한 종합 설계서다.

### 가장 큰 문제: 문서 역할이 너무 많음

한 파일에 다음이 모두 섞여 있다.

- 아키텍처 결정
- 저장소 구조
- 데이터 스키마
- 실행 절차
- 코드 예제
- 운영 체크리스트
- 반입·서명 정책
- LLM·Claude 사용 지침
- ADR·보고서 템플릿

이 구조에서는 하나를 수정할 때 동일 개념이 다른 장에 중복되어 있는지 확인하기 어렵다. 경영진은 읽을 수 없고, 개발자도 최신 요구사항을 찾기 어렵다.

### 구형 설계가 남아 있는 문제

다음과 같은 구형 표현이 최신 정정과 함께 존재한다.

1. `affected_paths` 중심 명세
2. `range-diff`를 누락·변형의 기계 판정에 사용하는 설명
3. 충돌 시 `git cherry-pick --abort` 후 사람이 해결하는 흐름
4. 명세의 `verification.command`를 직접 실행하는 구조
5. “최신 릴리스 브랜치”를 동적으로 정본으로 보는 설명

최신 설계에서 다음처럼 정리했다면 상세 설계서에도 반영해야 한다.

- `allowed_changed_paths`
- `required_changed_paths`
- `upgrade_watch`
- 구조화된 patch-lock
- CI 탐지 모드와 담당자 해결 모드 분리
- 선언형 verifier
- 업그레이드 시작 시 source release SHA 고정

## 4.4 `openmetadata_governance_requirements.md`

### 현재 역할

언어 무관 공통 판정 엔진과 재적용·완전성·민감 경로·부채·정본·rerere·오케스트레이션 요구사항을 REQ 단위로 정의하는 SRS다.

### 좋은 점

- 요구사항마다 목적, 입력·출력, 구현 방법, 수용 기준을 제시한다.
- 문제와 요구사항의 추적 관계를 제공한다.
- 판정 범위와 비범위를 구분하려 한다.

### 문서 상태 문제

문서 상단은 여전히 Draft 상태인데 로드맵과 세션 문서에서는 여러 마일스톤이 구현 완료됐다고 기록한다. SRS가 개발 정본이라면 실제 상태를 갱신해야 한다.

예:

```text
v1.0 Approved
v1.1 Draft
```

또는 요구사항별로 다음 상태를 두는 것이 좋다.

```text
planned | implemented | verified | deprecated
```

### 동일 문서 안의 충돌

상단 정정 내용과 뒤의 요구사항·개발 계획이 서로 다를 수 있다.

예:

- 상단에서는 `affected_paths` 폐기를 선언
- 뒤에서는 `affected_paths drift`를 구현 대상으로 유지
- 정정 문서에서는 `range-diff` 파싱을 제거
- 기존 요구사항은 `range-diff` 파싱을 기계 판정으로 정의
- 정정 후 개발 계획과 본문의 T00~T12 체계가 다름

부칙이 본문보다 우선하는 구조를 유지하지 말고, 정정을 본문 전체에 병합한 새 버전을 발행해야 한다.

### 구성과 용어 문제

- `1.1`이 `1.0`보다 먼저 나온다.
- “먼저 읽을 용어”와 “용어” 절이 중복된다.
- 경영진도 읽을 수 있다고 적지만 곧바로 `exit code`, `glob`, `rerere`, `pathspec`이 나온다.
- `사전 환경 셋팅`은 `사전 정책·명세 준비`가 자연스럽다.
- `감사카드`는 공식 감사 산출물로 오해될 수 있다.
- `언어 무관`은 전체 시스템이 아니라 공통 판정 엔진의 특성으로 한정해야 한다.

권장 용어:

| 현재 용어 | 권장 용어 |
|---|---|
| 거버넌스 하네스 | 자동 검증 체계 |
| 스파인 | 공통 판정 엔진 |
| 감사카드 | 검증 결과 요약서 또는 검증 근거 카드 |
| 판정 신호 | 판정 결과 코드 |
| 사전 환경 셋팅 | 사전 정책·명세 준비 |

### 요구사항 작성 방식 권고

1. 부칙과 정정 사항을 본문에 병합한다.
2. 기존 본문과 정정본을 동시에 유지하지 않는다.
3. SRS에서 자체 개발 계획을 제거하고 Build Plan을 참조한다.
4. `MUST`, `SHOULD`, `MAY`를 일관되게 사용한다.
5. 요구사항마다 상태와 구현 태스크를 연결한다.
6. 문서 버전·승인자·변경 이력을 둔다.
7. 분석 오류와 정책 위험을 구분한다.
8. “등록·재적용 완전성”과 “기능 완전성”을 명시적으로 분리한다.

## 4.5 `openmetadata_build_plan.md`

### 현재 역할

마일스톤과 태스크를 구현 가능한 수준으로 정의한 개발 실행 계획이다. 태스크별 목적, 입력, 구현, 수용 기준, 선행 관계를 제시한다.

### 좋은 점

- 개발자가 실제 구현 단위로 분해할 수 있다.
- 요구사항과 구현 태스크를 연결하려는 구조가 있다.
- 완료 기준을 테스트 가능한 형태로 쓰려 한다.

### 즉시 수정해야 할 의존성 모순

다음은 표현 문제가 아니라 실제 개발 순서 결함이다.

1. 마일스톤 개요에서는 `T62 → T32` 순서인데 T62 상세는 T32를 선행으로 요구한다.
2. 개요에서는 `T93 → T42` 순서인데 T93 상세는 T42를 선행으로 요구한다.
3. 개요에는 `T50a/T50b`가 있지만 상세에는 `T50` 하나만 있다.
4. 개요와 상세에서 T50의 마일스톤이 다르다.
5. T93의 마일스톤 위치도 개요와 상세가 다르다.

권장 흐름:

```text
T32 후보 최종 상태 검증 기반
  ↓
T62 테스트 결과와 후보 SHA 결속
  ↓
T90 실제 업그레이드 테스트

T93 감시 경로 유효성 검증
  ↓
T42 유효한 감시 경로를 이용한 영향 분석
```

따라서 T93이 T42의 선행이라면 T93 상세의 선행 조건에서 T42를 제거해야 한다.

### 표현상 개선

다음과 같은 혼합 표현이 한 문장에 너무 많이 등장한다.

- source stack preflight
- path-ownership·glob grammar 정본
- result/CI adapter
- single integrator/CAS
- source tree replay

권장 표기:

> 원본 패치 스택 사전검사(source stack preflight), 경로 소유권 및 패턴 문법 기준, 결과 기록·CI 연계 모듈, 단일 반영자와 기준 버전 일치 확인, 격리 환경 소스 재현 검증

`clean-room replay == candidate tree(bit 재현)`도 표현을 분리해야 한다.

- 소스 트리 해시가 같음 → **소스 상태 재현성**
- 컨테이너·바이너리까지 바이트 단위가 같음 → **재현 가능한 빌드**

두 개념을 같은 것으로 표현하면 안 된다.

### 상태 관리 권고

각 태스크에 다음을 추가하는 것이 좋다.

```text
status
owner
target_release
related_requirement
acceptance_test
last_updated
```

진행 상태는 여러 문서에 수동 복제하지 말고 프로젝트 보드 또는 CI에서 단일 소스로 관리해야 한다.

## 4.13 `om-overview-share.html` 또는 `omoverviewshare.html`

### 현재 역할

경영진·비개발자에게 문제, 해결 방식, Git 구조, 영향 분석, 구현 범위, LLM 역할과 업그레이드 시나리오를 시각적으로 설명하는 개요 문서다.

### 좋은 점

- 색상·카드·단계 구성이 좋아 일반 문서보다 진입 장벽이 낮다.
- “수정이 빠진다 / 왜 고쳤는지 잊힌다 / 위험한 변경이 지나간다”는 문제 구성이 직관적이다.
- 패치 스택을 “새 공식 버전 위에 다시 얹는 구조”로 시각화한 점이 좋다.
- 자동과 사람, LLM의 역할을 구분하려 한다.

### 내용상 반드시 수정할 부분

#### 1. “LLM이 놓쳐도 테스트가 잡으므로 안전 유지”

이 표현은 과도한 보장이다. 기존 테스트가 새로운 `tenantId` 의미를 모르고 있다면 LLM이 놓쳤을 때 테스트도 통과할 수 있다.

권장 문장:

> 기존 테스트에 이미 표현된 회귀는 LLM 없이도 검출할 수 있다. 테스트에 정의되지 않은 새로운 의미 변화는 사람 검토, 릴리스 노트, 추가 테스트 설계가 모두 놓칠 수 있는 잔여 위험으로 관리한다.

#### 2. 시나리오 내부 모순

예시 상황은 BANK-OM-001을 “충돌은 없지만 의미가 달라지는 사례”라고 설명한다. 그러나 후보 재적용 단계에서는 `001·003 충돌`이라고 적는다.

다음처럼 분리하는 것이 좋다.

```text
BANK-OM-001: 충돌 없이 자동 적용되지만 tenant 의미를 놓침
BANK-OM-002: 자동 적용
BANK-OM-003: 물리적 충돌 발생
```

#### 3. `range-diff` 기계 판정 표현

“range-diff로 대조하고 자동 게이트 판정”은 사람 리뷰 보고서와 기계 판정을 섞는다. `range-diff`는 사람 비교용으로 설명하고, 기계 판정은 patch-lock·commit trailer·구조화 JSON을 사용한다고 표현하는 것이 좋다.

#### 4. “완전성(명세 3 = 커밋 3)”

이 표현은 기록상 ID 존재만 확인하며, 커스터마이징의 실제 로직이 살아 있는지 보장하지 않는다.

권장 표현:

> 등록된 수정 3건이 후보 이력에 모두 존재하는지 확인

그리고 실제 동작은 별도 테스트로 확인한다고 이어야 한다.

#### 5. “자동 검출 · 확실”

경로 근접은 해당 커스터마이징이 반드시 영향을 받는다는 뜻이 아니라 검토 후보임을 뜻한다.

권장 표현:

- 직접 겹침: 자동 검출, 높은 관련성
- 경로 근접: 자동 검출, 영향 후보
- 간접 영향: 테스트·리뷰 필요

#### 6. “사람은 위험만”

사람은 위험한 변경만 검토하는 것이 목표지만, 초기 명세 작성, 민감 경로 지정, 충돌 해결, 테스트 설계, 승인, 운영 판단에도 필요하다.

권장 표현:

> 반복 가능한 검사는 자동화하고, 사람은 초기 기준 설정과 위험·예외 판단에 집중한다.

#### 7. “LLM이 틀려도 배포 안전에는 영향이 없다”

LLM이 직접 통과를 만들 수 없다는 의미는 맞지만, false negative와 false positive는 사람의 리뷰 방향과 경보 피로에 간접 영향을 준다.

권장 표현:

> LLM은 직접 통과·차단을 결정하지 않는다. 다만 검토 후보의 누락이나 과다 생성이 사람의 판단 품질에 영향을 줄 수 있으므로 근거 링크와 평가 지표를 함께 관리한다.

### 화면 구성 개선

- “향후 개선 — LLM 위키”가 지나치게 길어 핵심 전략보다 더 중요한 것처럼 보인다.
- 경영진용 버전에서는 LLM 섹션을 1개 카드로 축약하고 상세 내용은 별도 문서로 연결하는 편이 좋다.
- “이번엔 만들지 않는 것”은 좋은 섹션이므로, 그 아래에 “이번 단계의 성공 기준”을 추가하면 의사결정이 쉬워진다.
- 하단에 문서 상태, 대상 독자, 기준 버전, 마지막 갱신일을 표시하는 것이 좋다.

- 테스트가 최종 확정한다

   아키텍처, 명세, CI, 업그레이드 Runbook, 반입, AI 보조를 분리한다.

6. **검토 요청·응답은 날짜와 대상 Commit을 붙여 archive로 이동한다.**

7. **`SESSION_STATE.md`를 `.claude/`로 옮기고 일시적·민감 정보를 제거한다.**

8. **전체 문서에 동일한 용어집과 상태 메타데이터를 적용한다.**

9. **진행 상태와 테스트 수는 자동 생성한다.**  
   여러 문서에 수동 복사하지 않는다.

10. **경영진용 표현의 보장 강도를 조정한다.**  
    “완전 보장”보다 “어떤 범위를 결정적으로 검증하고 어떤 위험이 남는지”를 명시한다.

# 11. 최종 평가

현재 문서의 가장 큰 장점은 기술적 위험을 감추지 않고 자동 검증이 보장하는 범위와 보장하지 못하는 범위를 구분하려는 태도다.

이 장점을 유지하면서 다음 세 가지를 해결하면 전달력과 신뢰도가 크게 높아질 것이다.

1. **현행 정본을 하나로 만든다.**
2. **경영진용 설명과 개발자용 명세를 물리적으로 분리한다.**
3. **구형 설계·검토 이력·세션 상태를 현행 문서에서 분리한다.**

기술 전략 자체를 다시 뒤집을 필요는 크지 않다. 현재 가장 시급한 일은 더 많은 설명을 추가하는 것이 아니라, 이미 있는 설명을 대상 독자와 문서 역할에 맞게 정리하고 서로 모순되지 않게 만드는 것이다.
