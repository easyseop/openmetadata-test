# Claude 검토 01 — Git 기준과 구조 분류

## 1. 범위와 금지사항

Git 계보·diff·merge 증거를 읽기 전용으로 적대적 검토한다. commit, checkout,
reset, merge, 파일 수정, fixture 수정, 제품 build와 Docker 실행은 금지한다.
관련 pytest 실행과 임시 디렉터리의 독립 반례 재현은 허용한다. 실행한 명령,
exit code, 통과·skip 수를 결과에 기록한다.

```text
repository: easyseop/openmetadata-test
branch: codex/structural-upgrade-safety-20260809
diff: 7319481e24063af7d16e9ae1c7bce34d396bbd27..d5153f284d8808e7856896b106f0539e8fcf2c83
```

```text

harness/run_phase_bundle.py
```

## 2. 사실로 가정하면 안 되는 구현 주장

1. 승인 계보용 `upgrade_base`와 Git 비교용 merge-base를 분리했다.
2. `upgrade_base → custom_head → Candidate` 조상 관계를 강제한다.
3. target/custom에 공통 merge-base가 없으면 분석 오류다.
4. 검토 표면은 `base→target ∪ base→custom ∪ base→candidate`다.
5. rename 비활성 A/M/D 목록만 판정 정본이고 `-M -C`는 진단 전용이다.
6. 공식 또는 커스텀 한쪽을 잃은 경로를 loss suspect로 올린다.
7. `DIFFERS_FROM_BOTH`만으로 안전 판정을 내리지 않는다.

## 3. 적대적 질문

각 질문에 코드 위치, 최소 반례, 실제 verdict를 답한다.

1. 조상 조건만으로 승인된 기준선 lock과 정확히 결속되는가? 더 오래된 조상을 넣는
   우회가 가능한가?
2. 기록 merge-base와 Git 재계산 결과를 수집·binder 모두에서 비교하는가?
3. criss-cross merge, unrelated history, shallow/partial clone에서 모호하거나 누락된
   merge-base가 허위 PASS를 만드는가?
4. NUL parser가 tab·newline·Unicode·type change·submodule·symlink 경로를 정확히
   보존하는가?
5. 삭제, Candidate-only, base로 되돌아간 경로가 3집합에서 빠지는가?
6. loss suspect 조건에 삭제 후 동일 blob 재생성 같은 허위 양성·음성이 있는가?
7. binary·rename 진단이 canonical verdict 또는 digest에 우연히 개입하는가?
8. Git 사용자 config, locale, Git version 차이에서 결과와 digest가 어떻게 되는가?
9. non-ancestor upgrade-watch를 일반 range처럼 오해시키는 출력이 있는가?
10. 1,786개 전체 detail이 timeout·메모리·증거 크기 문제를 일으킬 때 fail-closed인가?

## 4. 반례 test 매트릭스

최소 다음 행을 포함해 목차 문서의 반례 완전성 표를 작성한다.

- upgrade base와 merge-base가 다른 정상 계보
- 기준선에서 유지된 release-prep 경로
- unrelated upgrade base와 unrelated target/custom
- A/M/D, rename/copy, type change, binary, symlink, submodule
- target-only, custom-only, both-agree, both-diverge, Candidate-only
- Candidate가 target 또는 custom과 같아지는 양방향 부분 손실
- `DIFFERS_FROM_BOTH`이지만 기능이 부분 손실된 경우
- Git rename config true/false와 서로 다른 Git version
- 삭제 watched path 전체 A/M/D detail
- 증거의 path 1개 누락·1개 추가·순서 변경·status 변조

test 이름만 보지 말고 fixture의 Git 그래프와 assertion을 확인한다. 빠진 반례에는
먼저 실패해야 할 test 이름, fixture 그래프, 예상 verdict를 적는다.

## 5. 결과 형식

```text
1. 사실 정정
2. P0 — 허위 PASS·증거 손상 가능
3. P1 — merge 전 필수 수정
4. P2 — 후속 보완·문서화
5. 반례 완전성 표
6. 실제 실행한 test 명령·exit code·통과·skip 수
7. 빠진 회귀 test와 예상 verdict
8. 불필요하거나 중복된 로직
9. 최종 판정: 착수 불가 / 수정 후 재검토 / 1차 통과
```

P0/P1 반례나 test 공백이 남으면 1차 통과를 선택하지 않는다. 수정은 하지 않는다.
