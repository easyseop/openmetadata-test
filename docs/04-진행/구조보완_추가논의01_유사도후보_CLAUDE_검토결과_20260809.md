### 1.3 실제 1.13.2 후보에서의 실측 — 요청서에 없는 사실

assertion 2개 중 1개(`import sybaseConnection ...`)만 살아남았습니다. 나머지

`exact_definition`이 남을 수 없습니다.** exact가 남았다면 그것은 "리팩터링을 피해
복제된 코드" 쪽이 더 유력하며, 강한 증거가 아니라 오히려 의심 신호입니다.

## 2. 후보 검색 기능의 실제 필요성

**판정: 선택 — 유지 권고. 단 판정 영향 전면 제거를 조건으로 함.**

| 근거 | 수치 |
|---|---|
| 검색이 좁혀주는 범위 | 14,199 파일 → 후보 10건 → 적격 2건, 1순위 정답 |
| 검색을 없앨 때 사람의 탐색 범위 | `utils/` 한 디렉터리만 `PATH_ADDED` 84건 |
| 검색의 오탐 | generated 4건(`sym=2/5`), test 1건 — 모두 context로 격리됨 |

**anchoring은 후보를 숨긴다고 사라지지 않습니다.** 숨기면 기록되지 않는 사람의
이름 유추로 대체될 뿐이며, 감사 추적은 오히려 나빠집니다. 통제해야 할 것은
"후보를 보여주는 행위"가 아니라 **"후보가 판정을 완화하는 경로"**와
**"순위가 선택을 대신하는 구조"**입니다.

## 4. P0 — 허위 PASS·허위 승인 가능성

### P0-1. `eligible_for_migration`이 증거 강도와 무관하다

```python
"eligible_for_migration": context == "source"
...
finding_verdict = verdict.APPROVAL if eligible else verdict.BLOCK
```

증거 강도(`exact_definition` / `partial_assertion` / `symbol_overlap`)는 **정렬에만**
쓰이고 적격 여부에는 전혀 반영되지 않습니다. `sym=2/5`짜리 source 파일 하나가
`BLOCK`을 `APPROVAL`로 뒤집습니다.

같은 모듈의 반환값에 적힌 `rule` 문자열이 이와 정면으로 모순됩니다.

```text
"candidate discovery is diagnostic only; human approval and a versioned
 definition migration are required before PASS"
```

**필요 수정.** relocation finding verdict를 후보 유무와 무관하게 항상 `BLOCK`으로
고정하고, `eligible_for_migration`을 판정 입력에서 제거하여 `migration_selectable`
같은 별도 필드로 격하합니다.

### P0-2. 기능 test 증거가 Candidate SHA에만 결속된다

`_functional_evidence()`가 검사하는 것은 다음이 전부입니다.

```python
required = {
    "evidence_kind": "functional_test",
    "subject_sha": expected_sha,        # Candidate SHA
    "subject_role": expected_role,
    "verdict": "pass",
}
for field in ("test_id", "asserts_behavior", "command"): ...  # 비어 있지 않기만 하면 됨
```

**BANK-OM ID, old definition digest, proposed new path, assertion 중 어느 것과도
결속되지 않습니다.** `asserts_behavior`는 자유 문자열이며 내용 검증이 없습니다.

**반례.** 같은 Candidate에서 통과한 증거 파일 **하나**를 모든 relocation 결정에
재사용할 수 있습니다. BANK-OM-006의 이관을 BANK-OM-002와 무관한 test 증거로 승인해도
거부되지 않습니다. 요청서 §8.2 질문 3의 우려가 그대로 성립합니다.

`absence_only is True`를 거부하는 장치(같은 함수)는 적절하며 유지해야 합니다.

**필요 수정.** 증거에 `customization_id`, `definition_id`, `covers_path`를 필수화하고
proposal의 해당 값과 일치를 강제합니다.

### P0-3. 오탐을 기대값으로 고정한 test

`test_structural_review.py:391-394`

```python

assert finding["candidates"][0]["evidence_strength"] == "symbol_overlap"
```

## 5. P1 — 구현 전 필수 변경

**P1-1. 정렬 1위가 선택을 대신한다.** `strength_order`로 정렬한 뒤 목록의 첫
항목이 사실상 추천이 됩니다. `candidates[0]`을 assert하는 test가 그 구조를 굳힙니다.
순위를 없애고 경로 바이트 순 정렬 + 강도별 그룹핑으로 바꿔야 합니다.

**P1-2. `exact_definition`을 강한 증거로 대우하지 말 것.** 1.3의 실측대로 구조
리팩터링에서 exact는 희귀하며, 나타나면 복제·미사용 코드일 개연성이 높습니다.
"문자열이 그대로 있다"는 "호출된다"를 뜻하지 않습니다.

**P1-3. `asserts_behavior` 무검증.** 비어 있지 않기만 하면 통과합니다. 최소한
`covers_path`·`customization_id`와의 정합을 요구해야 합니다.

## 8. 최종 권고와 상태 전이

**안 B 채택.** 후보 검색은 유지하되 판정 경로에서 완전히 분리합니다.

```text
기존 정의가 Candidate에서 실패
        ↓
relocation finding verdict = BLOCK          (후보 유무와 무관, 항상)
        ↓
후보 목록은 status: UNVERIFIED_CANDIDATE 로만 노출
  · automated_decision: none
  · 순위 없음, 강도별 그룹
  · evidence_strength / matched_assertion_count / matched_symbol_count 원값 표기
        ↓
사람이 새 경로와 새 assertion을 제출
        ↓
기계 검증 4종 (모두 필수)
  · 새 assertion이 Candidate blob에서 실제 통과
  · 기능 test 증거가 customization_id · definition_id · covers_path 와 일치
  · proposal digest에 결속된 사람 승인
  · 옛 정의 보존 + supersedes 기록
        ↓
새 버전 정의로 재실행 → PASS 가능
```

요청서 §7의 LLM 전달 형식은 그대로 채택합니다. 다만 **정책 문장만으로는 부족하고
schema와 gate 코드가 `automated_decision: none`을 기계적으로 강제해야 합니다**
(§8.2 질문 9). 현재 그 강제는 없습니다.

안 D를 채택하지 않는 이유는 3절에 있습니다. 요청서 §6의 잠정 권고와 다른 결론이며,
동의 유도 없이 실측으로 비교한 결과입니다.
