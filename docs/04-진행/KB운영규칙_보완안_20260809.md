# KB 운영 방식 · 검사기 상호 보완안

> 작성일: 2026-08-09 KST
> 대상: `오픈메타데이털~.pptx` 13장이 정의한 KB 운영 방식 ↔ BANK-OM 검사기
> 성격: **어느 한쪽을 대체하지 않는다.** 양쪽이 서로 갖지 못한 것을 교환한다.

## 0. 왜 상호 보완인가

두 방식이 각자 다른 것을 발견했다.

| | KB 운영 방식 | BANK-OM 검사기 |
|---|---|---|
| 강점 | **실전 3회에서 얻은 운영 지식** — 무엇이 실제로 터지는지, 신규 엔티티가 어디를 건드려야 하는지, 샘플 데이터를 어떻게 만드는지 | **기록과 대조 구조** — 기능 ID, 코드 조각 790개, 병합 후 자동 대조 |
| 약점 | 기록이 기능 단위로 묶이지 않아 "무엇이 검증됐나"에 답하기 어려움 | 실행 환경과 운영 노하우가 없어 필수 test 9개가 전부 미실행 |

**KB 방식은 1.12.8 → 1.12.13 → 1.13.1 세 번의 포팅을 성공시켰다.** 포팅 시간
4~5시간 → 30분~1시간, 재작업 5~6회 → 1~2회. 이 방식이 틀렸다는 전제가 아니다.

이 문서는 양방향이다. 1부는 KB 쪽에 추가할 것, 2부는 KB 쪽에서 검사기가 가져올
것이다.

# 1부 · KB 방식에 추가할 여섯 칸

전부 기존 MD 4종에 칸을 추가하는 수준이다. 새 도구·새 절차가 없다.

## ① 기능 ID 도입 — 나머지 다섯 개의 전제

**지금** `KB-CUSTOM-NEW.md` / `KB-CUSTOM-MODIFIED.md`는 버전·파일·용도로 관리된다.
기능 단위 식별자가 없다.

```text
현재   1.12.8-v1 | sybaseConnection.kb-cust.json | Sybase DB 커넥터
보완   BANK-OM-006 | 1.12.8-v1 | sybaseConnection.kb-cust.json | Sybase DB 커넥터
```

**추가할 것:** 두 MD 맨 앞에 `기능 ID` 열 하나.

**새 ID 체계를 만들지 않는다.** 이미 `BANK-OM-001~007`이 있고
`harness/registrations/om-temp-1.13.1/customization-registry.yaml`이 정본이다.
새 번호를 만들면 매핑표가 하나 더 생기고 그 매핑표가 다시 틀어진다.

| ID | 기능 |
|---|---|
| BANK-OM-001 | 기준코드(InstanceCode) |
| BANK-OM-002 | 쿼리 리포트(QueryReport) |
| BANK-OM-003 | 데이터 검증 결과(Data Assertions) |
| BANK-OM-004 | 은행 컬럼 확장 표시 |
| BANK-OM-005 | 한글 입력 조합 보정 |
| BANK-OM-006 | Sybase 연결 유형 |
| BANK-OM-007 | Tibero 연결 유형 |

**이름 대조 주의.** PPT 3~4장의 `ReportProject`는 현재
**`QueryReport`(BANK-OM-002)**로 개명됐다. 커스텀 HEAD `8ac18ad0`의 경로를 확인한
결과 `ReportProject` 경로는 존재하지 않고 `QueryReport`만 있다. MD를 갱신할 때
옛 이름을 그대로 옮기지 않는다.

**ID 부여 원칙**

- 기능 단위로 부여한다. 파일 단위가 아니다.
- 한 기능이 여러 파일에 걸치면 같은 ID를 쓴다.
- 사람이 `customization-registry.yaml`에서 부여한다. LLM이 임의로 정하지 않는다.
- 한 번 부여한 ID는 재사용하지 않는다.

## ④ 예측 검증 칸 추가

`KB-CUSTOM-UPGRADE-CHECK.md`의 1.13.1 기록을 보면 이렇다.

```text
사전 판단   가능. No-Go 조건 없음
실제 결과   TS 타입 에러(리허설 미발견)
            Java SearchIndex 계약 변경(리허설 밖)
            마이그레이션 체크섬 누락(신규 발견) → 서버 기동 실패
            .kb-cust. codegen 비호환(미해결)
최종 결론   일치(가능 → 가능)
```

**네 건을 놓쳤는데 결론이 "일치"다.** 예측한 쪽이 채점했기 때문이다.

표에 두 칸을 추가한다.

| 칸 | 내용 |
|---|---|
| 예측 밖 발견 | 사전 판단에 없었던 문제를 전부 나열. 0건이면 "0건"이라고 명시 |
| 예측 정확도 | `예측한 항목 중 맞은 수 / 실제 발생 수` |

**효과:** 예측 밖 발견이 4건이면 "일치"라고 쓸 수 없다. 이 수치가 쌓이면 리허설을
얼마나 믿을 수 있는지 처음으로 측정된다.

## ⑤ "이관" 유형 추가

`KB-CUSTOM-NEW.md`는 추가, `KB-CUSTOM-MODIFIED.md`는 수정을 기록한다.
**공식이 우리가 손댄 파일을 삭제하거나 쪼갰을 때 적을 곳이 없다.**

1.13.2에서 두 건 발생했다.

```text
BANK-OM-001·002 | 이관 | EntityUtils.tsx (공식 1.13.2에서 삭제)
    → EntityLinkUtils.ts           getEntityLinkFromType
    → EntityBreadcrumbPureUtils.ts getEntityBreadcrumbs
    → EntityNameUtils.ts           EntityTypeName
    사유: 공식이 유틸 파일을 기능별로 분리

BANK-OM-006·007 | 이관 | DatabaseServiceUtils.tsx (커넥터 목록이 빠져나감)
    → DatabaseServicePureUtils.ts  databaseSchemaMap
    사유: 공식이 switch 를 목록표 방식으로 변경하고 파일을 분리
    주의: 옛 switch 를 되살리지 않고 새 방식으로 재이식함
```

**효과:** 다음 업그레이드에서 "그 코드 어디 갔더라"를 다시 찾지 않아도 된다.

## ⑥ 리허설 범위에 빌드 포함

**PPT가 이미 처방을 적어놨다.** 11장 마지막 줄이다.

> *"리허설이 Java빌드/Docker 미포함으로 마이그레이션 이슈 사전 미발견.
> 다음부터 mvn install까지 포함 권장"*

`/kb-upgrade-check`의 리허설 범위에 `mvn install`을 포함한다. 새 제안이 아니라
이미 결론난 항목의 이행이다.

# 2부 · KB 방식에서 검사기가 가져올 여섯 가지

반대 방향이다. 확인해 보니 **KB 쪽이 더 나은 항목이 여섯 개 있다.**

## 1. `kb-seed-sample-data` — 최우선

검사기의 필수 Contract 9개가 **전부 미실행**이다. 원인은 코드가 아니라
**샘플 데이터 부재**다.

```text
BANK_CONTRACT_QUERY_ID       저장된 Query 1건이 미리 있어야 함
BANK_FAILED_ASSERTION_FQN    실패한 test case 1건
BANK_COLUMN_TABLE_FQN/NAME   확장 컬럼이 붙은 테이블
BANK_RUNTIME_UI_HEALTH_URL   화면 1개
OPENMETADATA_BASE_URL
```

PPT 12장의 `kb-seed-sample-data`가 정확히 이것을 만든다 — "서비스 / 테이블 /
대시보드 / InstanceCode / ReportProject 샘플 데이터를 REST API로 생성하는 CLI".

**검사기가 막혀 있던 것을 KB 쪽이 이미 만들어 놓았다.** 이 하나로 1.13.2
Runtime 검증이 열린다.

## 2. `kb-entity-scaffold`의 프론트엔드 12개 접점

검사기 Manifest의 `required_changed_paths`는 **7개 ID를 통틀어 10개**다.
ID당 1~2개뿐이다.

PPT 12장의 스캐폴드는 "DEVELOPER.md 공식 체크리스트 + 이 포크에서만 필요한
프론트엔드 12개 지점(Explore 트리 등록 등)"을 안다.

**KB 쪽 지식이 검사기 등록자료보다 완전하다.** 이 12개 목록을 Manifest의
필수 경로로 반영해야 한다.

## 3. 6단계 중 검사기에 없는 세 가지

PPT 9장의 6단계 점검 중 셋이 검사기 premerge에 대응 항목이 없다.

| PPT 점검 | 검사기 | 실제 발생 이력 |
|---|---|---|
| ② 생성코드 재생성 | 없음 | 1.13.1에서 generated 14개 파일 충돌 |
| ③ Flyway 마이그레이션 | 없음 | 1.13.1에서 체크섬 누락 → **서버 기동 실패** |
| ⑤ 빌드 툴체인 | 없음 | rollup ARM64, Windows longpath |

검사기 premerge는 `upgrade-watch`, `policy-drift`, `structdiff`, `watch-suggest`
넷뿐이다. **셋 다 실제로 터진 적이 있는데 검사기가 안 본다.**

## 4. 14개 항목 중 ⑪ 로그 스캔, ⑬ 재기동

검사기의 Contract는 **기능별**이다. 시스템 레벨 점검이 없다.

- ⑪ `docker logs | grep -iE 'error|exception'` 전체 스캔
- ⑬ `--force-recreate`로 재시작해 동일하게 healthy한지

두 항목 모두 특정 기능에 속하지 않아 Contract로 표현되지 않는다. 별도 시스템
점검으로 추가해야 한다.

## 5. 크리티컬 오류 목록

PPT 5장이 담당자 개입이 필요한 오류를 이미 분류해 놓았다.

```text
환경 문제 (OS, JVM, Python 버전)
외부 모듈 추가 설치 필요
환경/인프라 (포트, 메모리, 디스크, 네트워크)
DB 내용 변경, 토큰, 라이선스
```

검사기에는 "어떤 경로·오류를 LLM이 자동 해결하면 안 되는가"를 정한 정책표가
없다. **이 목록이 그 초안이다.** (다만 분류 주체는 LLM이 아니라 정책표여야 한다 —
1.13.1에서 마이그레이션 체크섬이 "일반 오류"로 처리돼 서버가 안 뜬 사례가 있다.)

## 6. `kb-artifact-freshness`

"고쳤는데 안 보여요" 진단 — 서빙 번들 해시 / Docker 이미지 / 마이그레이션 상태
세 가지가 실제로 최신인지 비교.

검사기도 artifact digest 결속을 갖고 있으나 **gate로만 쓴다.** 막혔을 때 원인을
알려주는 진단 명령이 없다. 운영자 경험 측면에서 KB 쪽이 낫다.

## 이미 양쪽에 있는 것

- **append-only 기록 원칙** → 검사기는 O_EXCL·fsync·원자적 교체로 구현
- **⑭ 배포 신선도** → 검사기는 artifact digest 결속으로 구현

# 3. 합치면 무엇이 되는가

```text
KB 방식        실행하고 기록한다        (사람·LLM)
              ↕  기능 ID 로 연결
검사기         기록을 대조하고 판정한다  (기계)
```

각각 단독으로는 이렇게 답할 수 없다.

| 질문 | KB 단독 | 검사기 단독 | 합쳤을 때 |
|---|---|---|---|
| 이번에 BANK-OM-004를 검증했나 | 답 못 함 | 답 못 함 (실행 안 됨) | **답 가능** |
| 커스텀 코드가 병합 후에도 남아 있나 | 답 못 함 | 답 가능 | 답 가능 |
| 그게 실제로 동작하나 | 답 가능 | 답 못 함 (fixture 없음) | **답 가능** |
| 리허설 예측이 얼마나 맞았나 | 자기채점 | 관여 안 함 | **측정 가능** |

# 4. 이 보완안이 하지 않는 것

정직하게 명시한다.

- **자동 검증을 새로 추가하지 않는다.** 1부는 전부 문서 칸 추가다.
- **기록이 사실인지 기계가 확인하지 않는다.** ✅는 여전히 사람이 쓴 글자다.
- **테스트가 실제로 그 기능을 검증하는지 확인하지 않는다.** 커버리지 표는
  "무엇을 했다고 기록했는가"이지 "무엇이 검증됐는가"가 아니다. 이것은
  patch-kill(커스텀을 지웠을 때 test가 실제로 깨지는지) 영역이며 현재 5개 중 2개다.

# 5. 적용 순서

| 순서 | 항목 | 작업 |
|---|---|---|
| 1 | 2부-1 `kb-seed-sample-data` 이관 | Contract 9개 실행이 여기 걸려 있음 |
| 2 | 1부-① 기능 ID | 두 MD에 열 추가 + `BANK-OM-*` 소급 부여 |
| 3 | 1부-⑤ 이관 유형 | 1.13.2 두 건 기록 |
| 4 | 1부-②③ 테스트 ID·커버리지 표 | ①의 후속 |
| 5 | 1부-④⑥ 예측 칸·리허설 범위 | 독립 |
| 6 | 2부-2~6 | 검사기 쪽 개발 항목 |

1번이 가장 급하다. 나머지 전부가 "실제로 동작하는지"를 답하지 못하는 상태를
유지하기 때문이다. **ID 소급 부여(2번)가 문서 작업 중 가장 손이 많이 간다.**
