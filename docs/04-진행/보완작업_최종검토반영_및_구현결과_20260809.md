# 구조가 크게 바뀌는 업그레이드 검사 보완 결과

작성일: 2026-08-09
상태: 구현·회귀검사 완료, 실제 1.13.2 입력 읽기 전용 적용 완료, 운영 완료 아님

구현 commit: `d5153f284d8808e7856896b106f0539e8fcf2c83`

## 1. 왜 보완했나

기존 검사는 “등록한 파일과 코드 조각이 후보에 남아 있는가”를 엄격하게 확인하는 데
강했다. 반면 OpenMetadata 1.13.1 → 1.13.2처럼 공식 코드가 파일을 삭제·분할하고
기능을 새 PureUtils 구조로 옮긴 경우에는 다음 한계가 있었다.

1. 삭제된 파일을 찾았지만 기능이 어디로 이동했는지는 알려주지 못했다.
2. 업그레이드 기준 commit과 Git의 실제 3-way merge-base를 같은 값처럼 다룰 수
   있었다.
3. 최종 후보가 공식 쪽·커스텀 쪽 중 어느 내용을 잃었는지 경로별로 한눈에 보기
   어려웠다.
4. 옛 공유 코드 정의를 새 경로로 옮기거나 “공식 기능으로 흡수됨”으로 처리하는
   승인 절차가 버전별로 분리되어 있지 않았다.

이번 구현은 검사를 없애거나 느슨하게 만든 것이 아니다. 경로 중심 검사의 빈틈을
구조 비교·이동 후보·기능 증거로 보완한다.

## 2. 가장 중요한 기준 분리

이번 1.13.2 입력에서는 두 기준이 실제로 다르다.

| 구분 | 값 | 용도 |
|---|---|---|
| 업그레이드 기준선 | `afcb2d2cd7e7c28f1d0ce60538c60a96f4eb9dc9` | 승인된 1.13.1 계보와 Candidate lock 연속성 확인 |
| 실제 Git merge-base | `739ee49279afe3b35f1e9b7da1df01ff9612425c` | target·custom이 갈라진 지점에서 변경·충돌 범위 계산 |

업그레이드 기준선은 “승인된 이전 제품에서 출발했는가”를 확인한다. merge-base는
“Git이 실제로 양쪽 변경을 어디서부터 비교해야 하는가”를 결정한다. 둘은 목적이
다르므로 같다고 강제하지 않는다. 대신 다음을 각각 검사한다.

- `upgrade_base`가 `custom_head`의 조상이어야 한다.
- `custom_head`가 최종 Candidate에 포함되어야 한다.
- target과 custom에 공통 merge-base가 없으면 `ANALYSIS_ERROR`로 중단한다.
- 증거에 적힌 merge-base는 Git 재계산 결과와 완전히 같아야 한다.

## 3. 새로 자동화된 검사

### 3.1 전체 구조 검토 표면

검사기는 다음 세 변경 집합의 합집합을 모두 본다.

```text
merge-base → 공식 target
merge-base → 이전 커스텀 head
merge-base → 최종 Candidate
```

충돌률 계산에 쓰는 `merge_changed_paths`와 사람이 검토할
`review_surface_paths`를 분리했다. 충돌률이 낮더라도 Candidate에서 새로 생기거나
사라진 경로는 검토 표면에서 빠지지 않는다.

각 경로는 다음 두 축으로 분류된다.

- 변경 출처: 공식만 변경, 커스텀만 변경, 양쪽 변경·일치, 양쪽 변경·불일치
- 최종 관계: 공식과 같음, 커스텀과 같음, 양쪽과 같음, 양쪽 모두와 다름

`CUSTOM_LOSS_SUSPECT`와 `OFFICIAL_LOSS_SUSPECT`는 우선 검토 대상으로 올린다.
`DIFFERS_FROM_BOTH`만으로 안전하다고 판정하지 않는다. 공유 코드 정의와 BANK 전용
기능 테스트가 별도로 뒷받침해야 한다.

### 3.2 rename·리팩터링 후보

판정용 변경 목록은 Git 사용자 설정과 관계없이 rename 탐지를 끈 정본으로 만든다.
rename 탐지는 사람에게 후보를 추천하는 보조 진단으로만 실행한다.

- `.ts`와 `.tsx`는 같은 TypeScript 이동 후보군으로 비교한다.
- 예전 코드 조각 전체 일치, 일부 assertion 일치, 의미 있는 symbol 겹침을 구분한다.
- 테스트 파일과 생성 파일은 후보로 보여줄 수 있지만 자동 이관 대상에서는 제외한다.
- 부분 일치 후보는 예전 assertion을 재사용하지 못한다. 담당자가 새 경로에 맞는
  `proposed_assertions`를 제시해야 하며 도구가 Candidate에서 다시 검증한다.

후보를 찾았다는 이유만으로 PASS가 되지는 않는다. 후보가 없으면 `BLOCK`, 후보가
있으면 사람 검토가 필요한 `APPROVAL`이다.

### 3.3 버전별 공유 코드 정의 이관

다음 공개 명령을 추가했다.

- `definition-migration-propose`: Candidate·공식 target·기능 증거에 결속한 이관안 생성
- `definition-migration-approval-template`: 이관안 digest에 결속한 사람 승인 양식 생성
- `definition-migration-apply`: 승인된 이관안으로 새 버전 등록 묶음 초안 생성

처리는 정의마다 둘 중 하나다.

1. `relocated`: 새 Candidate 경로와 새 assertion, Candidate 기능 테스트를 결속한다.
2. `absorbed_by_upstream`: 공식 target에서 기능이 실제 제공된다는 양성 기능 테스트를
   결속한다. “예전 파일이 없다”는 부재 증거만으로는 처리할 수 없다.

옛 버전 정의는 수정하지 않는다. 새 버전의 `shared-code-definitions.yaml`과
`shared-path-owners.yaml`을 함께 바꾸고 coverage를 다시 검사한다. 새 폴더는
`definition-migration-draft` 상태로 만들어지며, 새 registry·Manifest·Candidate
lock을 재생성하기 전에는 정식 등록으로 취급하지 않는다.

## 6. 다음 실행 순서

이 branch를 현재 진행 중인 예행연습 증거에 바로 섞지 않는다. 검사기 코드가 바뀌면
`harness_version`도 바뀌므로, 적용할 때는 Candidate 선택부터 새 검사기 버전으로
Phase를 다시 시작한다.

Candidate lock 준비·승인·활성화 공개 CLI는 별도 branch
`codex/candidate-activation-cli-20260809`에 있다. 현재 branch와 그 branch를 검토
후 통합하기 전에는 활성 lock이 이미 준비되어 있어야 아래 수집 명령을 실행할 수
있다. 두 branch를 통합하면 검사기 digest가 바뀌므로 기존 Phase 결과를 이어 쓰지
않고 Candidate 선택부터 다시 실행한다.

작업 시작 전 준비물은 다음과 같다.

| 준비물 | 누가·언제 준비하나 | 사용처 |
|---|---|---|
| 최종 제품 Candidate SHA | 개발 담당자가 소스·bundle·Runtime 검증 후 확정 | 새 Candidate lock과 모든 구조 증거 결속 |
| 이전 기준선 lock digest | 1.13.1 승인 lock에서 도구가 계산 | custom head가 승인 기준선인지 확인 |
| 활성 1.13.2 Candidate lock | 담당자가 lock 내용을 검토·승인한 뒤 활성화 | 충돌 증거 수집기가 base·target·Candidate를 읽음 |
| 기능 테스트 증거 | BANK 기능 테스트 실행자가 Candidate 또는 공식 target별로 생성 | 이동·공식 흡수 판단 |
| 이관 결정 파일 | 담당자가 후보 코드와 기능 테스트를 검토한 뒤 작성 | 이관 proposal 생성 |
| 이관 승인 파일 | 조직 승인자가 proposal digest를 확인한 뒤 직접 작성 | 새 등록 묶음 초안 생성 |

최종 Candidate SHA·승인자·기능 테스트 결과를 아직 모르면 값을 추측하지 말고 이
단계에서 멈춘다.

1. 최종 제품 Candidate SHA를 확정한다.
2. 새 Candidate lock을 준비·사람 승인·활성화한다.
3. `collect-conflict-evidence`를 실행한다.
4. 출력의 손실 의심 경로와 relocation 후보를 검토한다.
5. 필요한 경우 정의 이관안과 기능 증거를 작성한다.
6. 담당자가 proposal digest를 확인하고 승인 파일을 직접 완성한다.
7. 새 1.13.2 등록 묶음 초안을 만들고 registry·Manifest를 다시 생성한다.
8. 등록 검사와 BANK 전용 테스트를 다시 통과한다.
9. 새 Candidate lock을 다시 승인한 뒤 postmerge를 실행한다.

2번의 첫 lock은 기존 1.13.1 등록 묶음이 최종 제품 SHA를 선택하도록 만들기 위한
전환용 lock이다. 9번의 두 번째 lock은 새 1.13.2 등록 묶음과 갱신된 정의까지
결속한 정식 lock이다. 제품 SHA가 같더라도 등록 기준과 digest가 달라지므로 첫
lock을 그대로 복사하지 않는다.

충돌 증거 수집 예시는 다음과 같다.

```bash
cd "$HOME/om-work/openmetadata-test"

./.venv/bin/python harness/om_workflow.py collect-conflict-evidence \
  --repo "$HOME/om-work/om-1.13.2-rehearsal" \
  --version 1.13.1 \
  --baseline-lock-digest "$BASELINE_LOCK_DIGEST" \
  --custom-head 8ac18ad053d9274774e274ba17b35911ac0b9dcb \
  --output "$HOME/om-work/evidence/1.13.2-conflict-evidence.yaml"
```

이 명령은 승인된 1.13.2 Candidate lock이 이미 활성화된 뒤에만 실행한다. 병합 전
기준선 lock이 활성 상태면 명확한 오류와 함께 중단한다.

이관 결정 파일은 도구가 자동으로 채우지 않는다. 다음은 BANK-OM-006을 새 경로로
이관하는 형식 예시다. `REPLACE_...` 값은 예시일 뿐이며 그대로 실행하면 검증에서
차단되어야 한다.

```yaml
BANK-OM-006:openmetadata-ui/src/main/resources/ui/src/utils/DatabaseServiceUtils.tsx:
  disposition: relocated
  proposed_new_path: openmetadata-ui/src/main/resources/ui/src/utils/DatabaseServicePureUtils.ts
  proposed_assertions:
    - id: REPLACE_WITH_APPROVED_SYBASE_ASSERTION
      matcher: code_fragment
      fragment: REPLACE_WITH_EXACT_REFACTORED_CODE_FRAGMENT
  functional_evidence: /absolute/path/BANK-OM-006-candidate-test.yaml
```

기능 테스트 증거는 단순히 “옛 파일이 사라졌다”고 쓰는 문서가 아니다. 어떤 SHA의
어떤 동작을 어떤 명령으로 확인했는지 기록한다.

```yaml
schema_version: 1
evidence_kind: functional_test
subject_sha: REPLACE_WITH_FULL_40_CHARACTER_CANDIDATE_SHA
subject_role: candidate
verdict: pass
test_id: BANK-OM-006-SYBASE-CONNECTION
asserts_behavior: Sybase 서비스 선택과 연결 테스트 제외 조건이 유지된다
command:
  - yarn
  - test
  - DatabaseServicePureUtils.test.ts
absence_only: false
```

`absorbed_by_upstream`을 선택할 때는 `subject_role: official_target`과 공식 1.13.2
SHA가 필요하다. 공식 target에서 기능 테스트가 통과해야 하며, Candidate에서만
통과한 결과를 공식 흡수 증거로 재사용할 수 없다.

정의 이관 명령은 다음 순서다.

```bash
./.venv/bin/python harness/om_workflow.py definition-migration-propose \
  --repo "$HOME/om-work/om-1.13.2-rehearsal" \
  --version 1.13.1 \
  --target-version 1.13.2 \
  --candidate "$FINAL_CANDIDATE_SHA" \
  --upstream-target 2763bf97ce265662793a1a38d353147cc6d6c2e3 \
  --structural-evidence "$HOME/om-work/evidence/1.13.2-conflict-evidence.yaml" \
  --decisions "$HOME/om-work/evidence/1.13.2-definition-decisions.yaml" \
  --output "$HOME/om-work/evidence/1.13.2-definition-proposal.yaml"

./.venv/bin/python harness/om_workflow.py definition-migration-approval-template \
  --proposal "$HOME/om-work/evidence/1.13.2-definition-proposal.yaml" \
  --output "$HOME/om-work/evidence/1.13.2-definition-approval.yaml"

# 담당자가 승인 파일을 직접 검토·작성한 뒤 실행한다.
./.venv/bin/python harness/om_workflow.py definition-migration-apply \
  --repo "$HOME/om-work/om-1.13.2-rehearsal" \
  --version 1.13.1 \
  --target-version 1.13.2 \
  --proposal "$HOME/om-work/evidence/1.13.2-definition-proposal.yaml" \
  --approval "$HOME/om-work/evidence/1.13.2-definition-approval.yaml"
```

정상 실행 후 보존할 파일은 충돌 증거, 이관 결정, proposal, 승인, 기능 테스트 증거,
새 `harness/registrations/om-temp-1.13.2/` 초안이다. 파일을 덮어쓰지 않으므로 같은
경로가 이미 있으면 기존 파일을 먼저 읽고 재사용 가능 여부를 확인한다. 내용을
확인하지 않고 삭제하거나 `--force`로 우회하지 않는다.

| `PASS` | 해당 기계 검사가 요구사항을 충족 | 다음 검사로 진행하되 사람 승인 필요 여부는 별도 확인 |
| `APPROVAL` | 후보 또는 손실 의심을 찾았으며 사람이 판단해야 함 | 코드·기능 테스트·proposal digest를 검토하고 승인 또는 수정 |
| `BLOCK` | 필수 정의·기능 증거·계보가 불충분 | 원인을 수정하고 Candidate 선택 또는 증거 수집부터 재실행 |
| `ANALYSIS_ERROR` | 입력 누락·변조·unrelated history 등으로 신뢰할 판정 불가 | 값을 추측하지 말고 lock·SHA·증거 파일을 바로잡아 재실행 |

Candidate SHA나 새 assertion이 바뀌면 기존 proposal과 승인을 재사용하지 않는다.
새 Candidate를 다시 승인·활성화하고 충돌 증거부터 재생성한다. 이관 후 등록 검사나
BANK 기능 테스트가 실패하면 새 등록 묶음을 정식 상태로 승격하지 않고 담당자에게
실패 경로와 증거 파일을 전달한다.

## 7. 자동화되지 않은 사람 책임

다음은 도구가 대신 결정하지 않는다.

- 이동 후보 중 실제 기능 위치 선택
- 리팩터링된 코드에 맞는 새 assertion 작성
- BANK-OM-006·007 기능 테스트가 실제 요구사항을 검증하는지 판단
- 공식 기능 흡수 여부 승인
- 승인자의 조직 권한 확인
- 최종 production bundle·Docker Runtime·화면 클릭 검증
- 운영 배포·release 승인

`watch-suggest`는 삭제·이동 가능성을 빠르게 알리는 사전 경보다. 이번 구조 검토는
실제 병합 후보의 전체 경로 관계와 정의 이관을 다룬다. BANK 전용 Contract test는
기능 보존을 확인한다. 세 기능은 서로 대체하지 않고 함께 써야 한다.

PPT에서 제안한 cherry-pick 리허설·기능별 테스트·KB 누적 방식도 여전히 참고할 수
있다. 특히 기능별 테스트와 변경 지식 축적은 이번 이관 승인 근거를 강화한다. 다만
이번 구현은 자동으로 PR 의미를 이해하거나 충돌을 해결하는 LLM이 아니다.

LLM 운영 기준 G-1~G-16 검토는 별도 주제다. 이 branch는 LLM이 수기 승인·기능
증거·artifact digest를 만들어도 된다는 권한을 추가하지 않는다. 자동화 에이전트는
명령 실행과 결과 정리만 할 수 있고, 사람 입력을 추측해서는 안 된다.

## 8. 최종 경계

이 구현으로 큰 구조 변경에서도 검사기를 쓸 이유가 분명해졌다. “파일이 그대로
남았는지”만 보는 대신, 전체 구조 변화·손실 의심·이동 후보·버전별 정의 이관을
한 흐름으로 관리한다.

그러나 현재 1.13.2 WIP Candidate가 운영 가능하다는 뜻은 아니다. 최종 bundle,
Docker Runtime, 화면 검증, 최종 Candidate lock, 담당자 승인, postmerge, 운영
release는 아직 남아 있다. 이 문서와 테스트 결과를 최종 PASS 또는 배포 승인으로
해석하면 안 된다.
