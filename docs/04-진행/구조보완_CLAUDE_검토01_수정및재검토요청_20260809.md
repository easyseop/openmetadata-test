# 구조보완 Claude 검토 01 — 수정 결과와 재검토 요청

작성일: 2026-08-09

## 1. 재검토 범위

1차 결과의 P0 2건과 P1 3건을 수정했다. 원래 구현 전체를 다시 칭찬하지 말고,
수정 diff가 결함을 실제로 닫았는지와 새 우회가 생겼는지를 읽기 전용으로
적대적으로 검토한다.

```text
repository: easyseop/openmetadata-test
branch: codex/structural-upgrade-safety-20260809
original implementation: d5153f284d8808e7856896b106f0539e8fcf2c83
repair implementation: df1eee22f2e8c0c0b7db999a2428f8637696124f
review diff: d5153f284d8808e7856896b106f0539e8fcf2c83..df1eee22f2e8c0c0b7db999a2428f8637696124f
```

코드·문서·Git 상태를 수정하지 않는다. 제품 build, Docker, 실제 예행연습 증거
재생성도 하지 않는다. 임시 저장소의 반례 재현과 pytest 실행만 허용한다.

## 2. 수정한 내용

### 2.1 P0-1 — 진단 rename과 정본 판정 분리

- structural review schema를 2로 올렸다.
- `review_digest`는 `_canonical_projection()`만 계산한다.
- rename·binary 단서는 `diagnostic_flags`로 분리해 `risk_flags`와 gate 판정에서
  제외했다.
- 진단은 별도 `diagnostics_digest`로 저장된 내용 자체만 결속한다. binder는 이를
  다시 실행하지 않는다.
- `verify_review()`는 정본만 재계산하며 rename·binary 진단을 실행하지 않는다.
- 진단 threshold, Git version, 사용자 `diff.renameLimit` 변화가 정본 digest를
  바꾸지 않게 했다.
- 진단 명령은 `diff.renameLimit=0`을 명시하고, 성공 stderr 경고와 timeout을
  `degraded`·`warnings`에 보존한다. 진단 실패는 판정 정본을 바꾸지 않는다.

### 2.2 P0-2 — 양쪽 변경을 merge-base로 되돌린 후보 탐지

한 경로에서 target과 custom이 모두 merge-base와 다른데 Candidate가 merge-base와
같으면 다음 플래그를 함께 기록한다.

```text
CUSTOM_LOSS_SUSPECT
OFFICIAL_LOSS_SUSPECT
REVERTED_TO_MERGE_BASE
```

gate는 `approval`이 되어 사람 검토 없이 PASS하지 않는다. 삭제 후 merge-base와
동일한 blob을 다시 만든 경우도 같은 규칙으로 고정했다.

### 2.3 P1·P2 보완

- 공개 `diagnostic_threshold`가 달라도 binder 정본 재검증이 실패하지 않는다.
- 성공 stderr의 rename 열화 경고를 버리지 않는다.
- binder의 rename 3회·binary 3회 재실행을 제거했다.
- manifest 감시는 `MANIFEST_WATCHED`, sensitive-zone 감시는 `WATCHED`로 분리했다.
- criss-cross history에서 best merge-base가 여러 개면 임의 SHA를 고르지 않고
  `GitPrimitiveError`로 fail-closed한다.
- rename 진단에 30초 timeout을 두었다.

전체 review 크기·시간 상한과 중복 canonical diff 최적화는 P2로 남겼다. 현재
규모에서 확인된 성능을 이유로 완료 처리하지 않는다.

## 3. 추가한 반례와 기대 판정

| 반례 | 기대 결과 |
|---|---|
| threshold 50↔90, Git version 변경, 사용자 renameLimit 변경 | 정본 digest 동일, 진단만 다를 수 있음 |
| binder 실행 중 진단 함수를 강제 실패 | 정본 검증 통과, 진단 재실행 없음 |
| 정본 risk flag 변조 | canonical digest mismatch |
| diagnostic flag 변조 | diagnostics digest mismatch |
| Candidate가 merge-base로 회귀 | 양쪽 loss suspect, gate APPROVAL |
| target 삭제·custom 수정 뒤 base blob 재생성 | 양쪽 loss suspect |
| symlink·gitlink·mode 변경 | T/T/M 상태와 mode·type 보존 |
| criss-cross best merge-base 2개 | analysis error로 이어질 GitPrimitiveError |
| 성공 stderr에 rename 경고 | degraded=true와 warning 보존 |
| rename 진단 timeout | 빈 진단·degraded=true, 정본 판정 유지 |
| manifest watched와 zone watched 동시 일치 | 서로 다른 두 플래그 |

## 5. 반드시 다시 공격할 질문

1. `review_digest`에서 진단 정보가 정말 완전히 빠졌는가? `diagnostic_flags`,
   `rename_diagnostics`, `diagnostics_digest`, Git version, threshold 각각을 변조·변주해
   정본 digest와 gate가 바뀌는지 실측한다.
2. 별도 `diagnostics_digest`가 진단 변조는 잡되, 다른 기기에서 진단을 재계산하지
   않아도 binder가 통과하는가?
3. `include_diagnostics=False` 경로가 binary 또는 rename 단서를 우연히 정본
   `risk_flags`에 남기거나 제거하지 않는가?
4. Candidate가 merge-base와 동일한 mode·type·blob일 때만 회귀로 잡히는가?
   양쪽 부모가 같은 변경을 했거나 한쪽만 변경한 정상 경우에 허위 APPROVAL을
   만들지 않는가?
5. `DIFFERS_FROM_BOTH`의 다른 제3 상태가 여전히 PASS할 수 있다. 이것이 현재
   설계의 사람 검토 공백인지, 별도 기능 증거로만 다뤄야 하는지 반례로 판정한다.
6. 여러 best merge-base를 거부한 것이 수집기와 binder 양쪽에서 같은
   `analysis_error`로 노출되는가? 예외가 traceback 또는 허위 BLOCK으로 새지 않는가?
7. 진단 timeout·Git stderr·진단 명령 실패가 정보성으로 남으면서 정본 PASS를
   미화하지 않는가? 사용자 화면에서 `degraded`가 숨지 않는가?
8. schema 1 구조 증거를 schema 2 binder에 넣었을 때 예측 가능한 재실행 안내와
   함께 차단되는가? 자동 호환으로 오래된 digest를 잘못 승인하지 않는가?
9. `diff.renameLimit=0`이 실제 대규모 변경에서도 사용자 config와 무관한지,
   진단 시간·메모리를 무제한으로 키우는 새 위험은 없는지 확인한다.
10. test 이름이 아니라 fixture가 실제 criss-cross, base 회귀, gitlink, timeout,
    stderr 경고를 만들고 있는지 대조한다.

## 6. 재검토 결과 형식

```text
1. 이전 P0·P1별 해소/미해소/부분 해소 표
2. 새 P0
3. 새 P1
4. 남은 P2와 운영 제약
5. 반례 완전성 표
6. 실제 실행한 명령·exit code·통과·skip 수
7. test fixture 사실 대조
8. 1차 최종 판정: 재수정 / 1차 통과
```

P0·P1 또는 필수 반례 공백이 하나라도 남으면 `1차 통과`로 판정하지 않는다.
1차 통과 전에는 2차 공유 정의 이관 검토를 시작하지 않는다.
