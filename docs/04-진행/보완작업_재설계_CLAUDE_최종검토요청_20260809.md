## 1. 왜 이 검토가 필요한가

1.13.1 BANK 커스터마이징을 공식 OpenMetadata 1.13.2 구조에 병합하는 과정에서
Git 충돌 48개를 해결했습니다. 소스 병합 결과는 commit으로 보존했고 BANK 전용
Jest test 88개도 통과했습니다. 그러나 이 결과만으로 **커스터마이징의 의미가
모두 유지됐다고 자동 판정할 수는 없습니다.**

현재 검사기는 주로 다음 정보를 봅니다.

- Git에서 변경된 파일 경로
- Manifest의 `upgrade_watch.paths`
- `shared-code-definitions.yaml`에 등록한 경로와 코드 조각
- Candidate SHA·tree·digest와 Phase 결과의 결속

이 구조는 변경을 누락하거나 결과를 임의로 바꾸기 어렵게 만드는 데는 강합니다.
반면 공식 버전이 파일을 분리·이동·삭제하거나 API 구조를 크게 바꾸면 다음 문제가
발생할 수 있습니다.

1. 중요한 삭제가 많은 변경 경로 속에 묻힙니다.
2. 코드는 새 파일로 정상 이동했는데 기존 경로가 사라졌다는 이유로 `BLOCK`이
   발생합니다.
3. 최종 파일이 공식 target과 같아져 커스텀 코드가 사라진 경우가 기존 축소식
   리뷰 목록에서 빠질 수 있습니다.
4. 검사 통과를 위해 기준 정의의 경로만 새 위치로 고치면, 실제 기능 보존을
   확인하지 않고 검사 기준을 결과에 맞추는 **정의 세탁**이 될 수 있습니다.
5. 같은 문자열이 주석·test·다른 기능에 남아 있는 것만으로 이동 성공이라고
   오판할 수 있습니다.

이번 1.13.2 tree에서 실제로 드러난 예는 다음과 같습니다.

- `upgrade_watch` 결과는 6개 BANK-OM ID와 95개 변경 경로를 검토 대상으로
  표시했지만, `EntityUtils.tsx` 삭제는 ID별 경로 수와 다른 예시 뒤에 묻혔습니다.
- 공유 코드 검사는 4건을 `BLOCK`했지만, 네 건 모두 기능 유실이 아니라
  `DatabaseServiceUtils.tsx`에서 `DatabaseServicePureUtils.ts`로 이동한 사례였습니다.
- 기존의 축소식 검토 표면 `전체 1,707 → 양쪽 부모와 모두 다른 파일 44 → 삭제
  포함 19`는 우선순위에는 유용하지만, Candidate가 target과 같아져 커스텀이
  사라진 파일을 44개 목록에서 제외할 수 있습니다.

따라서 이번 요청의 목적은 충돌을 다시 해결하는 것이 아닙니다. 앞으로 구조 변경이
큰 버전에서도 검사기가 **검토 대상을 빠뜨리지 않고**, 이동과 유실을 구분할 때
근거 이상으로 확신하지 않으며, 기준 정의를 승인 없이 바꾸지 못하게 하는 최소
보완 설계를 검증하는 것입니다.

검사 결과의 의미도 구분합니다.

- `PASS`: 기계가 선언된 조건을 모두 확인했습니다.
- `APPROVAL`: 기계 근거는 모였지만 사람의 의미 판단과 승인이 필요합니다.
- `BLOCK`: 필수 보존 근거가 확인되지 않아 다음 단계로 진행할 수 없습니다.

## 4. 반드시 막아야 하는 네 가지 반례

### 반례 R1 — 커스텀 코드가 사라졌는데 축소 목록에서 제외

base에서 target과 custom head가 모두 같은 파일을 변경했습니다. 병합 후 Candidate의
파일 내용이 target과 완전히 같다면 custom 변경이 사라졌을 수 있습니다. 기존의
“양쪽 부모와 모두 다른 파일만 검토” 조건은 이 파일을 제외하므로 거짓 안전 판정을
만들 수 있습니다.

필수 결과: `change_origin=BOTH_CHANGED_PARENTS_DIVERGE`,
`result_relation=EQUALS_TARGET`로 분류하고 우선 검토합니다.

### 반례 R2 — 공식 변경을 버리고 커스텀 옛 파일만 유지

같은 상황에서 Candidate 파일 내용이 custom head와 완전히 같다면 공식 1.13.2
변경을 잃었을 수 있습니다.

필수 결과: `change_origin=BOTH_CHANGED_PARENTS_DIVERGE`,
`result_relation=EQUALS_CUSTOM`으로 분류하고 자동 PASS하지 않습니다.

### 반례 R3 — 코드 조각이 엉뚱한 곳에 남아 이동 성공으로 오판

기존 등록 경로는 사라졌지만 같은 문자열이 test, 주석, 생성물 또는 무관한 기능에
남아 있습니다. 전역 문자열 검색만으로 새 위치를 선택하면 실제 기능 유실을 이동
성공으로 오판할 수 있습니다.

필수 결과: 전역 검색은 `POSSIBLE_RELOCATION` 후보만 만들며, 사람 승인과 새 정의
결속 전에는 PASS하지 않습니다.

### 반례 R4 — 검사 통과를 위해 기준 정의를 결과에 맞춤

Candidate가 만들어진 뒤 `shared-code-definitions.yaml`의 기존 경로를 새 파일로 바로
덮어쓰면, 옛 기준으로 실패했어야 할 결과가 사라집니다. 누가 어떤 근거로 정의를
바꿨는지도 추적할 수 없습니다.

필수 결과: 1.13.1 정의와 digest는 보존하고, Candidate SHA·옛 정의 digest·제안된
새 경로·근거·사람 승인이 결속된 버전별 이관 절차를 사용합니다.

## 5. 이번 구현 범위의 재설계안

### A1. 변경 종류를 숨기지 않는 출력

구현 목표:

1. 판정 입력은 rename 탐지를 끈 canonical A/M/D 목록으로 고정합니다.
2. 삭제 `D`, 경로 소멸, 양쪽 변경 파일을 사람용 출력의 최상단에 분리합니다.
3. 각 finding에 경로, 관련 BANK-OM ID, 네 Git ref를 기록합니다. A/M/D 상태는
   `base→target`, `base→custom head`, `base→Candidate` 중 어느 비교의 값인지
   필드 이름으로 구분합니다.
4. ID별 “경로 수 + 예시 한 건”만 보여주지 말고, 상세 결과 파일 경로와 삭제 목록을
   즉시 표시합니다.
5. 진단용 rename 결과는 A16의 별도 참고 자료로 연결합니다.

필수 반례 test:

- `upgrade_watch.paths`의 파일이 삭제되면 다른 변경이 많아도 삭제 finding이 보입니다.
- 사용자 `diff.renames` 설정을 바꿔도 canonical 결과와 digest가 같습니다.
- 출력 순서가 달라져도 canonical 결과 digest는 바뀌지 않습니다.

### A3. 리뷰 표면을 제외식이 아닌 다축 분류로 생성

기존 `전체 → 양쪽 부모와 모두 다름 → 삭제 포함` 숫자는 우선순위 참고용으로만
사용합니다. 어떤 파일도 중간 단계에서 안전하다고 제외하지 않습니다.

검토 대상 경로의 정본은 다음 세 집합의 합집합입니다.

```text
changed(base, target)
∪ changed(base, custom head)
∪ changed(base, Candidate)
```

세 번째 집합을 포함해야 양쪽 부모에는 없었지만 병합 후 수동 수정에서 새로 생긴
변경도 검토할 수 있습니다.

파일 하나를 단일 이름에 억지로 넣지 않고 다음 세 축을 모두 기록합니다.

| 축 | 허용 값 | 의미 |
|---|---|---|
| `change_origin` | `NEITHER_PARENT_CHANGED`, `TARGET_ONLY`, `CUSTOM_ONLY`, `BOTH_CHANGED_PARENTS_AGREE`, `BOTH_CHANGED_PARENTS_DIVERGE` | base 대비 어느 부모가 바뀌었고 두 부모의 최종 상태가 같은지 구분. 첫 값은 Candidate에서만 새 변경이 생긴 경우 |
| `result_relation` | `EQUALS_BOTH_PARENTS`, `EQUALS_TARGET`, `EQUALS_CUSTOM`, `DIFFERS_FROM_BOTH` | Candidate의 blob 또는 경로 부재 상태가 어느 부모와 같은지 구분 |
| `risk_flags` | `PATH_ADDED`, `PATH_DELETED`, `POSSIBLE_RENAME`, `WATCHED`, `PROTECTED`, `BINARY` 등 | 삭제·이동·정책 위험을 중복 가능한 표식으로 기록 |

`result_relation`은 다음 순서로 계산해 한 값만 선택합니다.

1. Candidate, target, custom head 상태가 모두 같으면 `EQUALS_BOTH_PARENTS`
2. Candidate가 target과만 같으면 `EQUALS_TARGET`
3. Candidate가 custom head와만 같으면 `EQUALS_CUSTOM`
4. 어느 쪽과도 같지 않으면 `DIFFERS_FROM_BOTH`

경로가 존재하지 않는 상태도 비교 가능한 명시적 값으로 취급합니다. 따라서 양쪽
부모가 같은 파일을 삭제했고 Candidate에도 파일이 없는 경우처럼, 두 부모 상태가
같은 사례도 중복 분류 없이 처리해야 합니다.

필수 규칙:

- 파일 단위 blob 비교는 base·target·custom head·Candidate SHA에 결속합니다.
- `change_origin`과 `result_relation`은 각 축 안에서 상호 배타적이고 누락 없이
  계산해야 합니다. `risk_flags`만 여러 값을 함께 가질 수 있습니다.
- `EQUALS_TARGET`과 `EQUALS_CUSTOM`을 자동 안전으로 해석하지 않습니다.
- protected 경로와 관련 BANK-OM ID를 함께 표시합니다.

R1은 `BOTH_CHANGED_PARENTS_DIVERGE + EQUALS_TARGET`, R2는
`BOTH_CHANGED_PARENTS_DIVERGE + EQUALS_CUSTOM`으로 나와야 합니다.

필수 반례 test: R1, R2, 양쪽과 다른 정상 수동 병합, 양쪽 부모가 같은 내용을 만든
경우, 한쪽·양쪽 파일 삭제, binary 파일, rename 진단 유무가 canonical 분류를
바꾸지 않는 경우입니다.

### A4. 이동 후보 발견과 기능 보존 판정을 분리

기존 경로에서 코드 조각을 찾지 못했을 때만 후보 탐색을 실행합니다.

허용되는 자동화:

- 후보 tree 안에서 token·심볼·진단용 rename 정보를 사용해 새 경로 후보를 수집
- 후보별 경로, match 수, old/new blob digest, 관련 BANK-OM ID 출력
- 후보 0개·1개·복수 개를 구분

금지되는 자동화:

- 전역 문자열 한 건만으로 이동 성공 또는 PASS 판정
- test·주석·생성물·무관한 동일 이름을 근거 없이 정식 새 경로로 선택
- 복수 후보 중 “가장 그럴듯한” 파일을 자동 확정

판정:

- 후보 0개: 기능 보존 미확인으로 `BLOCK`
- 후보 1개 이상: `POSSIBLE_RELOCATION`과 근거를 출력하고 `APPROVAL`
- 사람 승인과 A5 이관이 완료된 후 새 정의로 원래 검사를 다시 실행해야 PASS 가능

필수 반례 test: R3, 동일 조각 복수 위치, test에만 존재, 주석에만 존재, 포맷 변경,
부분 조각만 존재, 실제 새 파일에서 유일하게 보존된 경우입니다.

### A5. 기준 정의를 보존하는 버전별 이관

순서를 다음과 같이 고정합니다.

1. 제품 Candidate commit과 tree를 먼저 확정합니다.
2. 변경 전 1.13.1 공유 코드 정의와 digest로 Candidate를 검사합니다.
3. 누락이 발생한 정의만 A4 후보와 blob 근거를 포함한 이관 제안으로 생성합니다.
4. 담당자가 기능 의미·관련 test·새 경로를 검토하고 승인합니다.
5. 도구가 1.13.2용 새 정의를 생성하고 옛 정의는 변경하지 않습니다.
6. 새 정의 digest, 승인 정보, Candidate SHA·tree를 결속합니다.
7. 새 정의로 공유 코드 검사와 관련 direct test를 다시 실행합니다.

이관 제안의 필수 필드:

- registration/version, BANK-OM ID, definition ID
- old definition digest, old path, old fragment/token digest
- Candidate commit SHA와 tree
- proposed new path와 blob digest
- 발견 근거와 match 수
- 관련 test 또는 사람이 확인해야 할 invariant
- approver, approved_at, rationale, approval source

금지 규칙:

- 기존 정의 파일 제자리 덮어쓰기
- Candidate SHA가 바뀐 뒤 이전 제안·승인 재사용
- 승인 없이 가장 최신 proposal 자동 선택
- 이관 후 관련 test 없이 경로·조각 존재만으로 완료 처리

필수 반례 test: R4, Candidate SHA 변경, proposal 변조, 복수 후보, 옛 정의 digest
불일치, 승인 누락, 승인 후 새 정의 검사 실패입니다.

### A16. 결정적 판정과 이동 진단의 rename 정책 분리

- canonical 판정: `diff.renames=false`, `merge.renames=false`, `--no-renames`
- 진단 보고: 명시적 `-M -C`와 실제 사용한 threshold·Git version 기록
- 진단 결과는 경로 후보를 제안할 뿐 canonical A/M/D와 gate verdict를 바꾸지 않음
- 사용자 전역 Git config가 두 결과에 개입하지 못하도록 명령 옵션으로 고정

필수 반례 test: 같은 저장소에서 사용자 rename 설정을 true/false로 바꿔도
canonical 결과가 같고, 진단 후보만 별도 필드로 재현되는지 확인합니다.
