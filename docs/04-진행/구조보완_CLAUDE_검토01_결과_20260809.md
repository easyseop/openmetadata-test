## 2. P0 — 허위 PASS·증거 손상 가능

### P0-1. 진단 rename이 canonical digest와 risk_flags에 개입한다

**코드 위치.** `build_review`가 `rename_diagnostics`를 payload에 넣은 뒤 payload
**전체**로 digest를 계산합니다(`structural_review.py:218-236`). 그 블록에는
`git_version`과 `-M -C` 결과가 들어 있습니다. 또한 `POSSIBLE_RENAME` 플래그가
진단 결과에서 파생됩니다(`:150-155, :178-179`).

**최소 반례 A — 진단 threshold만 변경, canonical 분류는 동일.**

```text
canonical 분류 동일 : True
review_digest 동일  : False
  threshold 50% : sha256:f107dd76ef69925863058b32e7a...
  threshold 90% : sha256:cb20f2891003bd7c262ac01a2b7...
payload 내 git_version : 'git version 2.39.3 (Apple Git-145)'
```

**최소 반례 B — 사용자 Git config만 변경 (실제 1.13.2 규모).**

```text
기본값(미설정)            R/C 발견 = 30
diff.renameLimit=20000    R/C 발견 =  0
```

`diff.renameLimit`은 `_STABLE_CONFIG`(`gitprim.py:22-29`)에 포함돼 있지 않습니다.
게다가 Git이 stderr로 다음 경고를 내는데 `gitprim.git()`은 성공 시 stderr를
버립니다(`gitprim.py:74-88`).

```text
warning: only found copies from modified paths due to too many files.
warning: you may want to set your diff.renameLimit variable to at least 13988 and retry the command.
```

실제 후보에 `POSSIBLE_RENAME`이 82건 붙어 있으므로 이 경로는 이론이 아니라 활성
상태입니다.

**실제 verdict.** `verify_review`가 binder에서 payload 전체 동일성을
요구하므로(`structural_review.py:250-260`, `run_phase_bundle.py:93-97`), Git 버전이나
`diff.renameLimit`이 다른 기계에서 검증하면 **허위 BLOCK / ANALYSIS_ERROR**가
발생합니다. 감사 digest가 canonical 입력만의 함수가 아닙니다.

### P0-2. Candidate를 merge base로 되돌린 해결이 무플래그 PASS

**코드 위치.** 두 loss suspect 조건은 Candidate가 **한쪽 부모와 정확히 같을 때만**
발화합니다(`structural_review.py:186-189`). 양쪽 변경을 모두 버리고 base로 되돌린
결과는 어느 조건에도 걸리지 않습니다.

**최소 반례.** `only.txt` — base=`base`, target=`target`, custom=`custom`,
candidate=`base`

```text
BOTH_CHANGED_PARENTS_DIVERGE  DIFFERS_FROM_BOTH  flags=[]
gate verdict = pass   reasons = ()
```

공식 변경과 커스텀 변경이 **둘 다** 사라졌는데 게이트가 `PASS`입니다. 부분 손실
같은 미세 사례가 아니라 blob 전체가 base로 회귀한 경우입니다.
`PHASE_안전성_출력디자인` 문서에서 "base 내용으로 해결한 충돌"을 필수 반례로 이미
지정한 바 있는데, 새 축이 그 사례를 되돌려 놓았습니다.

**실제 1.13.2 후보에서 해당 경로는 0건입니다.** 활성 결함이 아니라 설계 구멍이며
다음 업그레이드에서 실현될 수 있습니다.

## 3. P1 — merge 전 필수 수정

### P1-1. `verify_review`가 비기본 threshold 증거를 영구 검증 불가

`build_review`는 `diagnostic_threshold`를 받는데(`:105`) `verify_review`는 payload의
`policy` 문자열을 파싱하지 않고 기본값 50으로만 재계산합니다(`:252-258`).

```text
threshold 90 으로 만든 증거 → verify_review
  실패: structural review evidence differs from deterministic recomputation
```

파라미터를 노출하면서 검증 불가능한 증거를 만들 수 있는 구조입니다.

### P1-2. `gitprim.git()`이 성공 시 stderr를 폐기

Git의 rename-limit 열화 경고가 사라집니다. 진단이 불완전해도 증거에 흔적이
남지 않습니다.

### P1-3. `verify_review` 재계산 비용

binder가 진단 3회(`-M -C --find-copies-harder`)와 binary diff 3회를 다시 돌립니다.
digest에 들어가면 안 되는 블록을 비교하기 위해 지불하는 비용이며, P0-1을 고치면
함께 사라집니다.

## 9. 최종 판정

**수정 후 재검토**

P0 2건이 남아 있어 1차 통과를 선택하지 않습니다.

1. 진단 rename의 canonical digest 개입 — 구현 주장 5 반증, 사용자 config 의존 실증
2. Candidate가 merge base로 회귀한 해결의 무플래그 PASS — 구현 주장 7 반증

주장 1~4와 6은 코드·실행으로 확인했습니다. 특히 `upgrade_base`/merge-base 분리는
binder와 수집기 양쪽에서 정확히 결속되며, 검토자가 독립 계산한 검토 표면 1,786경로와
`CUSTOM_LOSS_SUSPECT` 28건이 구현 결과와 정확히 일치했습니다.

### 수정 방향 (2줄)

1. `rename_diagnostics`와 `git_version`을 digest 입력에서 제외하고, `POSSIBLE_RENAME`을
   canonical finding 밖으로 옮긴다.
2. `candidate == merge_base`이면서 어느 부모든 변경한 경우를 세 번째 loss 조건으로
   추가한다.

두 수정과 7절의 회귀 test가 들어오면 같은 단계를 재검토합니다. 2·3차 요청서는 1차
P0가 해소된 뒤에 전달받는 것이 목차 문서의 순서와 맞습니다.
