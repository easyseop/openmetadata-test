## 4. 그래서 T61은 몇 개인가

**5/5이 아니다.** 근거는 다음 세 가지다.

### 4-1. 전임 커밋이 계획서와 다르다 (002·003)

`harness/registrations/kb-openmetadata/runtime-patch-kill-plan.yaml`은 ID마다 다른
전임을 요구한다.

| ID | 계획서 `without_patch_sha` | 오늘 사용한 스택 |
|---|---|---|
| BANK-OM-001 | `afcb2d2c…` (공식 upstream) | **일치** |
| BANK-OM-002 | `a2566fac…` (InstanceCode는 있고 QueryReport만 없음) | 불일치 — 둘 다 없는 순정 |
| BANK-OM-003 | `4108411c…` (001·002는 있고 003만 없음) | 불일치 |

`predecessor-runtime-negative-control`의 목적이 **실패를 그 ID에 귀속**시키는 것이므로,
패치를 전부 뺀 스택 하나로는 002·003의 귀속이 성립하지 않는다. 다만 002는 테스트의
첫 동작이 `POST /v1/queryReports`이고 그게 404이므로 인과는 명확하다.

### 4-2. 계획서의 candidate가 배포 이미지와 다르다

계획서 `candidate.commit_sha`는 `849ae756…`, 오늘 배포 이미지는 `8ac18ad0…`이다.
또 이 계획 파일은 `registrations/kb-openmetadata/`에만 있고, 오늘 후보의 등록 폴더
`registrations/om-temp-1.13.1/`에는 patch-kill 계획이 **없다.**

### 4-3. 006·007은 서버 교체로 판정할 수 없다

`test_sybase`·`test_tibero`는 `OPENMETADATA_PRODUCT_REPO`의 **소스 파일**을 읽는
계약이다. 서버 이미지를 바꿔도 소스는 여전히 `8ac18ad0`이므로 구조적으로 죽지 않는다.
순정에서 통과했다고 해서 껍데기가 아니며, 이 둘은 이미 source patch-kill
(`6e5b654f`, `41b224ad`)로 입증된 2/5다.

**따라서 오늘의 증분은 BANK-OM-001 1건이다. T61은 2/5 → 3/5.**

## 5. 새로 드러난 문제

### 5-1. [Serious] BANK-OM-005 필수 테스트가 커스터마이징을 입증하지 못한다

`test_korean_ime::test_hangul_composition_roundtrip`이 **순정 서버에서도 통과**했다.
BANK-OM-005의 필수 런타임 테스트는 이것 하나뿐이므로, 이 기능은 현재 런타임 생존
입증 수단이 없다. 인수인계 3-5가 찾으려던 "껍데기"가 실제로 나온 사례다.

같은 파일의 `test_hangul_composition_source_guard`는 소스 조각을 검사하지만
`contracts.yaml`의 `required_tests`에 등재돼 있지 않다.

- 반례: `var/rehearsal/evidence/om-1.13.1-t61-vanilla-attempt1-20260810-013333/test-run-set.yaml`
  — 순정 digest `sha256:eaa31858…`에서 `outcome: pass`

### 5-2. [Serious] 003·004의 API 계층 테스트가 판별력이 없다

`test_failed_assertion_projection`과 `test_extended_column_projection`이 순정에서
통과한다. 두 Contract 모두 `rendered_row` 쪽이 죽어서 계약 전체로는 판별되지만,
API 계층 절반은 커스터마이징에 민감하지 않다.

### 5-3. [Blocking] 순정 롤백이 데이터 계층에서 불가능하다

BANK 데이터가 있는 DB에 순정 1.13.1을 올리면 **마이그레이션이 exit 1로 실패하고
서버가 기동하지 않는다.**

```
Caused by: java.lang.IllegalArgumentException: Sybase
  at CreateDatabaseService$DatabaseServiceType.fromValue(CreateDatabaseService.java:552)
  at SecretsManagerUpdateService.retrieveServices(SecretsManagerUpdateService.java:188)
```

`bank_mock_sybase`·`bank_mock_tibero` 서비스의 `serviceType`을 순정 enum이 모른다.
같은 순정 이미지가 **빈 DB에서는 exit 0으로 정상 기동**하므로 순정의 결함이 아니라
데이터 비가역성이다.

인수인계 14-1의 "롤백 — 계획 없음"은 계획 부재가 아니라 **현재 구조에서 데이터
계층 롤백이 막혀 있다**로 갱신해야 한다. 운영 도입 전에 반드시 다뤄야 할 항목이다.

### 5-4. [Minor] 이 기계에서 rehearsal 재현이 문서대로 되지 않는다

`docker/rehearsal/docker-compose.override.yml`의 contract-runner가
`platform: linux/amd64`로 고정돼 있어 Apple Silicon에서 x86 에뮬레이션으로 돈다.
Rosetta로 변환된 Chromium이 OpenMetadata SPA를 렌더링하지 못해
(`Locator.fill` 30초 초과, `load` 이벤트 120초 초과, CPU 1코어 100% 점유)
`prepare_runtime_contract_environment.py:243`의 `browser_state()`에서 매번 죽었다.
`browser_state()`에 우회 수단이 없어 **API 전용 계약 6개도 함께 막힌다.**

arm64 네이티브로 러너를 빌드하니 같은 화면이 **1.7초**에 렌더링됐다.

- 조치: override의 플랫폼을 `${OM_CONTRACT_RUNNER_PLATFORM:-linux/amd64}`로
  변경(기본값 유지, CI 무영향).
- 남은 문제: `docker/rehearsal/test.sh`가 러너 이미지를 항상 `pull`하므로 로컬
  빌드 이미지를 쓸 수 없다. 이번 실행은 pull만 건너뛴 동등 스크립트로 우회했다.

## 8. 환경 변경 사항 (되돌리는 법)

이번 실행을 위해 다음을 바꿨다. 전부 되돌릴 수 있다.

| 변경 | 현재 | 되돌리기 |
|---|---|---|
| colima `rosetta` | `true` | `~/.colima/default/colima.yaml`에서 `false` 후 `colima stop && colima start` |
| colima `memory` | `5` (원래 4) | 같은 파일에서 `4`. **단 5GB는 검증된 구성이고 4GB는 미검증** |
| override 플랫폼 | `${OM_CONTRACT_RUNNER_PLATFORM:-linux/amd64}` | 기본값이 원래와 같아 되돌릴 필요 없음 |
| 로컬 러너 이미지 | `local/openmetadata-contract-runner:1.13.1-runtime-arm64` | `docker rmi` |
| 순정 T61 DB | `var/rehearsal/docker-volume/db-data.vanilla-t61-20260810` | 불필요 시 삭제(약 500MB) |
| 순정 T61 ES 볼륨 | `om-bank-t61-vanilla_es-data` | `docker volume rm om-bank-t61-vanilla_es-data` |

커스텀 DB(`db-data`)는 그대로 보존돼 있다. 삭제한 데이터는 없다.

메모리 5GB는 **원인 오진에 따른 변경**이었다. 실제 원인은 CPU(에뮬레이션)였고
5GB 증설은 문제를 고치지 못했다. 다만 4GB에서는 스택만으로 여유가 659MB라
Elasticsearch OOM(exit 137)이 관측됐으므로, 되돌릴 때 이 점을 감안한다.
