### 문제 2 — 정책과 제품 코드 동시 약화

**저장소 분리가 이미 1차 방어입니다.** 정책·관리파일은 검사기 저장소
(`easyseop/openmetadata-test`)에, Candidate는 제품 저장소
(`easyseop/OpenMetadata`)에 있습니다. 제품 Candidate는 정책 파일을 물리적으로
바꿀 수 없습니다.

실측으로 확인했습니다. 제품 Candidate `390c439e77` 기준:

| 정책 glob | 제품 저장소 존재 |
|---|---|
| `harness/acgh/**` · `harness/registrations/**` · `harness/tests/**` | 없음 |
| `policies/**` · `.bank/**` · `docs/02-설계/**` · `STATUS.md` | 없음 |
| `CLAUDE.md` · `.github/workflows/**` | **존재** (OpenMetadata 자체 파일) |

**따라서 실제 위험은 검사기 저장소의 자기수정입니다.** 오늘 하루 Codex가
`codex/structural-upgrade-safety-20260809`에서 정책·test·검사기 코드를 함께
수정해 온 경로가 바로 그것입니다.

현재 방어는 digest 두 개뿐입니다.

```python
_harness_version()      # run_phase_bundle.py, om_workflow.py,
                        # run_source_candidate_gates.py, harness/acgh/*.py
_registration_digests() # customization-registry / contracts /
                        # shared-code-definitions / shared-path-owners /
                        # commit-inventory + manifests/BANK-OM-*.yaml
```

**이 둘은 기록만 하고 이전 정책과 비교하지 않습니다.** digest가 바뀌면 옛 증거
재사용은 막히지만, 새 digest로 새로 실행하면 완화된 정책이 그대로 판정 기준이
됩니다. 그 비교가 정확히 T70의 역할인데 미연결입니다.

### 문제 3 — 필수 test 의미 약화


## 5. 최소 안전 수정안과 영향받는 공개 실행 경로

### 수정 1 — T70의 대상을 제품이 아니라 검사기로 재정의

현재 설계는 정책과 코드가 한 저장소에 있는 모델을 전제합니다. 이 배치는 두
저장소로 분리돼 있으므로 대상을 바꿔야 합니다.

```text
before:  check_self_approval(candidate_changed_paths, ...)   ← 영구 PASS
after :  check_self_approval(harness_changed_paths, ...)
         base_ref      = 직전 승인된 검사기 commit
         candidate_ref = 현재 검사기 HEAD
```

`DEFAULT_POLICY_GLOBS`에서 제품 저장소에만 존재하는 항목(`policies/**`,
`.bank/**`, `.github/workflows/**`)과 검사기 저장소 항목을 분리하고, 후자만
사용합니다. `CLAUDE.md`는 양쪽에 있으므로 저장소를 명시해야 합니다.

영향 경로: `om_workflow.py`의 모든 phase 명령, `run_phase_bundle.py` premerge·
postmerge 진입점. gate 이름은 `policy-self-protection`으로 두 phase 모두에 등록.

### 수정 2 — 결속 범위 확장

```python
_registration_digests():  + sensitive-zones.yaml
                          + repository-layout.yaml
                          + source-snapshot-path-owners.yaml

_harness_version():       + tests/bank/contracts/**/*.py
```

`candidate-locks/`는 실행마다 바뀌므로 제외가 맞습니다. `current-diff-paths.txt`
등 생성물도 제외 유지.

### 수정 3 — test 본문을 Contract catalog에 결속

`contracts.yaml`의 `required_tests` 각 항목에 구현 파일의 blob digest를 함께
기록하고, `check_required_test_implementations()`가 selector 해석에 더해 digest
일치를 확인합니다. 불일치는 `APPROVAL`(정당한 test 수정도 있으므로 BLOCK이 아님)로
두고, 사람 승인으로 새 digest를 등록합니다.

의미 검증 자체는 T61이 담당하며 5/5 완성이 최종 조건입니다.

## 9. 1차 최종 판정

**설계 수정 후 구현**

P0 3건이 있습니다. 다만 세 건 모두 **설계 방향이 이미 존재하고 구현 범위가
작습니다** — T70은 이미 구현돼 있고 연결 대상만 바꾸면 되며, 나머지 둘은 digest
목록에 항목을 추가하는 일입니다.

가장 중요한 발견은 **P0-1의 성격**입니다. `policy_guard`를 그냥 연결하는 것은
해결이 아닙니다. 정책 glob이 검사기 저장소를 기술하는데 판정 대상은 제품
저장소이므로, 순진한 연결은 영구 PASS를 만드는 **안전 연극**이 됩니다. 저장소
분리 구조에 맞게 대상 자체를 재정의해야 합니다.

부수적으로, 이 배치의 저장소 분리가 이미 상당한 방어라는 점은 기록해 둘 가치가
있습니다. 제품 Candidate를 다루는 작업자는 정책 파일에 물리적으로 접근할 수
없습니다. 남은 위험은 검사기 저장소에서 작업하는 주체이며, 그것이 지금까지
논의되지 않았습니다.

§7.1~7.6의 30개 질문은 폐기하지 않았습니다. 위 6건 수정과 1.13.2 Runtime 증거가
확보된 뒤 §9.2 형식으로 2차 종합 검토를 수행하는 것이 맞습니다.
