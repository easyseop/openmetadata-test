# 구조 변경 대응 검사기 — Claude 단계별 검토 목차

작성일: 2026-08-09

## 1. 목적과 대상

구조 변경 대응 검사기를 한 번에 승인받지 않는다. 서로 다른 신뢰 경계를 네 번으로
나눠 검토한다. 1~3차는 독립 검토이고 4차에서 세 결과를 함께 재판정한다.

```text
repository: easyseop/openmetadata-test
branch: codex/structural-upgrade-safety-20260809
base: 7319481e24063af7d16e9ae1c7bce34d396bbd27
implementation: d5153f284d8808e7856896b106f0539e8fcf2c83
handoff: 00a0c581b97832b584abc5aac403c94e1bffa3c0
review 01 repair: df1eee22f2e8c0c0b7db999a2428f8637696124f
```

## 2. 검토 순서

| 순서 | 요청서 | 판정 대상 |
|---|---|---|
| 1차 | `구조보완_CLAUDE_검토01_GIT기준과구조분류_20260809.md` | upgrade base, merge-base, 3집합 구조 분류 |
| 2차 | `구조보완_CLAUDE_검토02_공유정의이관과승인_20260809.md` | 이동 후보, 기능 증거, 정의 이관·승인 |
| 3차 | `구조보완_CLAUDE_검토03_PHASE결속과호환성_20260809.md` | Phase gate, digest, CLI, 기존 증거 호환성 |
| 4차 | `구조보완_CLAUDE_검토04_실제적용과통합판정_20260809.md` | 실제 1.13.2 결과와 최종 통합 판정 |

1~3차 결과를 모두 받은 뒤에만 4차를 전달한다. 1~3차 중 P0가 나오면 먼저 수정하고
같은 단계를 재검토한다.

1차 최초 검토는 P0 2건·P1 3건으로 `수정 후 재검토` 판정을 받았다. 결과 원문과
수정 재검토 요청은 다음 두 파일에 보관한다. **1차 통과 판정을 다시 받기 전에는
2차를 전달하지 않는다.**

```text
구조보완_CLAUDE_검토01_결과_20260809.md
구조보완_CLAUDE_검토01_수정및재검토요청_20260809.md
```

## 3. 반례 완전성 규칙

“현재 test가 통과한다”는 이유만으로 승인하지 않는다. 각 검토자는 다음 표를 반드시
작성한다.

```text
구현 주장 | 정상 test | 경계 test | 변조 test | 동시성/중단 test |
이전 버전 test | 빠진 반례 | 실제 판정
```

다음 규칙을 적용한다.

1. 구현 주장 하나마다 최소 정상 1건과 실패 반례 1건을 확인한다.
2. SHA·digest·경로·승인·증거 입력은 누락, 위조, stale, 불일치 반례를 각각 확인한다.
3. Git 입력은 삭제, 추가, 수정, rename, binary, unrelated history를 확인한다.
4. 파일 생성은 기존 파일, 동시 실행, 중간 실패, symlink·경로 이탈을 확인한다.
5. 과거 schema와 새 schema를 각각 확인한다.
6. test 이름이 아니라 fixture가 실제 반례를 만드는지 확인한다.
7. 발견한 결함은 “수정안”만 내지 말고 먼저 실패해야 하는 회귀 test를 제시한다.
8. P0/P1 반례 또는 test 공백이 남으면 해당 단계는 통과로 판정하지 않는다.

검토자는 기존 관련 pytest를 실제 실행하고 명령·exit code·통과·skip 수를 기록한다.
새 반례가 필요하면 repository를 수정하지 말고 임시 clone/임시 fixture에서 재현하거나
실패해야 하는 test 코드를 답변에 제시한다. test 실행이 환경 문제로 불가능하면
통과로 간주하지 않고 `환경 미검증`으로 표시한다.

모든 가능한 미래 반례가 없다고 단정하지 않는다. 대신 확인한 범주와 확인하지 못한
범위를 명시해 검증 공백을 숨기지 않는다.

## 4. Claude에 전달할 공통 문장

```text
지정한 요청서를 끝까지 읽고 그 형식대로 읽기 전용 적대적 검토를 수행해줘.
코드·문서·Git 상태를 수정하지 말고 구현자의 설명을 사실로 가정하지 마.
실제 코드와 test fixture를 대조하고, 반례 완전성 표를 작성해줘.
관련 pytest를 실제 실행하고 명령·exit code·통과·skip 수를 기록해줘.
기존 test 통과만으로 승인하지 말고 허위 PASS·허위 BLOCK·증거 누락을 먼저 찾아줘.
발견한 문제마다 먼저 실패해야 하는 회귀 test와 예상 verdict를 적어줘.
P0/P1 반례나 test 공백이 남으면 통과 판정을 내리지 마.
출력은 요청서가 지정한 결과 형식만 사용해줘.
```

## 5. 결과 보관과 금지사항

```text
구조보완_CLAUDE_검토01_결과_20260809.md
구조보완_CLAUDE_검토02_결과_20260809.md
구조보완_CLAUDE_검토03_결과_20260809.md
구조보완_CLAUDE_검토04_통합결과_20260809.md
```

검토자는 코드·제품 WIP Candidate·Candidate lock·예행연습 증거를 수정하지 않는다.
제품 build와 Docker도 재실행하지 않는다. 이번 검토는 소스 검사기 설계 검증이며
최종 bundle, Runtime, 조직 승인, 운영 배포를 대신하지 않는다.
