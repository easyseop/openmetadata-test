# 클로드 하네스 경량화·스킬 자동화 제안 비판 검토

## 1. 결론

클로드의 핵심 방향은 타당합니다. 검사 강도를 줄이지 않고, 파생자료의 손편집과 반복 명령만 줄여야 합니다. 또한 Codex skill은 판정 로직을 가지지 않고, 결정론적 CLI를 호출하는 사용자 인터페이스로만 사용하는 편이 맞습니다.

다만 현재 문서의 수치와 몇 가지 단정은 현재 코드와 다릅니다. 따라서 제안된 실행 태스크를 바로 수행하지 말고, **1.13.1 runtime Contract test 기준선을 먼저 완성한 뒤** 단계적으로 리팩터링해야 합니다.

| 판단 | 결론 |
|---|---|
| 검사 삭제·통합 | 현재 보류. 실패 모드별 목록이 없이 “중복 0개”를 확정할 수 없음 |
| 공유 픽스처·parametrize | 수용 가능. assertion과 실패 메시지를 그대로 유지해야 함 |
| 파생자료 자동 생성 | 수용. Git이 판단할 수 있는 경로·SHA·교집합에 한함 |
| 러너를 제품 등록 폴더에서 분리 | 방향은 타당. 현 runtime 기준선 완성 후 수행 |
| `source-candidate-evidence.yaml` 바로 3분할 | 보류. 현재 test·문서·matrix가 이 파일을 직접 참조함 |
| skill로 반복 작업 자동화 | 조건부 수용. 실체는 결정론적 CLI, skill은 호출·결과 요약만 담당 |

## 2. 실제 코드와 다른 부분

### 2-1. “검사기 54개 전수”는 단위가 명확하지 않음

현재 `harness/tests/`에는 test 파일 58개와 test 함수 413개가 있습니다. “검사기 54개”가 gate, test 파일, test 함수 중 무엇을 의미하는지 정의되지 않아 “중복 없음”의 근거로 쓸 수 없습니다.

정리 전에 gate ID, 입력, 판정, 실패 모드, 최종 소비자를 한 행씩 적은 목록이 먼저 필요합니다. 두 test가 같은 함수를 호출해도 서로 다른 실패를 잡는다면 중복으로 분류하면 안 됩니다.

### 2-2. 루트 러너 수와 범위가 부정확함

제품 등록 폴더의 구현을 `runpy` 호출로 전달하는 루트 런처는 문서에 적힌 4개보다 많습니다.

- `run_source_candidate_gates.py`
- `run_source_patch_kills.py`
- `run_runtime_contracts.py`
- `compare_ui_typecheck.py`
- `run_upgrade_risk_gates.py`

`run_upgrade_watch.py`는 루트에 실제 구현이 있으므로 단순 위임 런처와 구분해야 합니다. 러너 분리 제안은 타당하지만, 대상 파일과 CI 호출 경로를 다시 목록화해야 합니다.

### 2-3. `harness/tools/`는 비어 있지 않음

현재 다음 도구 3개가 있습니다.

| 도구 | 역할 | 현재 판단 |
|---|---|---|
| `capture_conflict_replay.py` | 실제 cherry-pick 충돌과 해결 증거 수집 | 파생 증거 도구. 러너와 중복 아님 |
| `resolve_nonoverlapping_json_conflicts.py` | 겹치지 않는 JSON leaf 충돌만 해결 | 상태 변경 도구. 수동 검토를 유지해야 함 |
| `enable_guide_navigation.py` | HTML 가이드 이동 UI 추가 | 문서 도구. 하네스 판정과 무관 |

### 2-4. 현재 수치는 113개가 아님

2026-08-06에 승인한 1.13.1 기준은 다음과 같습니다.

| 항목 | 현재 값 |
|---|---:|
| 등록한 변경 경로 | 111개 |
| 제외 경로 | 2개 |
| 여러 BANK-OM ID가 공유하는 경로 | 37개 |
| 공용 경로–ID 조합 | 114개 |
| 공용 코드 assertion | 790개 |

따라서 `113개`, `100/100`같은 고정 표현을 일반 자동화 규칙에 넣으면 안 됩니다. 실행 시점의 pinned Git diff와 승인한 등록자료에서 기대값을 계산해야 합니다.

### 2-5. 증거 파일 3분할은 즉시 수행할 일이 아님

`source-candidate-evidence.yaml`은 현재 단순 메모가 아닙니다. test, `upgrade-rehearsal-matrix.yaml`, README, 로드맵과 인수인계서가 직접 참조합니다. 새 구조를 도입하려면 다음이 먼저 필요합니다.

1. 현재 모든 소비자 목록화
2. 새 파일별 schema와 소유자 정의
3. 기존 파일을 새 구조로 생성하는 migration 도구
4. 기존·신규 구조의 판정 결과가 같은지 확인하는 회귀 test

## 3. 타당한 제안

### 3-1. 정본과 파생자료를 구분해야 함

Git이 자동으로 알 수 있는 값과 사람이 판단해야 하는 값을 분리하는 방향은 맞습니다.

| 자동 생성 가능 | 사람 판단 필요 |
|---|---|
| official–custom Git diff, commit SHA, commit별 변경 경로, 경로 교집합 | 담당 부서, 중요도, BANK-OM ID 의존 관계, 정상 업무 동작, 필수 test |

자동 생성기는 제안을 만들 수는 있지만, 사람 판단 값을 임의로 확정해서는 안 됩니다.

### 3-2. 검사 assertion이 아닌 중복 구현만 줄이는 것은 타당함

반복되는 fixture를 공유하거나 동일한 형태의 test를 parametrize하는 것은 가능합니다. 단, test ID·실패 메시지·입력·판정이 변하지 않음을 비교하는 회귀 test가 필요합니다.

### 3-3. 반복 명령을 하나의 CLI로 묶는 방향은 타당함

`om_workflow.py`가 이미 plan, apply, validate, source, runtime 등을 묶고 있으므로 새 자동화도 이 CLI를 확장하는 편이 일관됩니다. 다만 사람이 코드 내용을 확인하고 BANK-OM ID를 승인하는 단계는 자동 PASS하면 안 됩니다.

## 4. skill 자동화 제안 평가

### 4-1. 독립 정답 기준은 하나가 아님

클로드는 Manifest union이나 `source-diff-paths.txt`를 독립 정답 기준으로 제안했습니다. 그러나 두 파일이 같은 잘못된 생성기에서 나오면 함께 누락될 수 있습니다. 적어도 다음 세 가지를 교차 비교해야 합니다.

1. pinned official commit과 pinned custom commit의 실제 Git diff
2. 승인한 Manifest의 경로 합집합
3. 승인한 제외 경로

세 입력이 같은 범위를 가리킬 때만 요약 PASS를 표시해야 합니다.

### 4-2. `100/100` 한 줄은 운영 판정으로 부족함

요약은 필요하지만 숫자 하나로 압축하면 무엇이 실패했는지 보이지 않습니다. 최소 단위는 gate별 판정입니다.

```text
기준 commit: d952a838...
등록 경로: 111/111 PASS
제외 경로: 2/2 PASS
공용 경로–ID: 114/114 PASS
공용 코드 assertion: 790/790 PASS
runtime Contract test: 0/9 NOT_RUN
최종 판정: BLOCK
```

### 4-3. skill은 증거 생성자가 아님

skill이 출력한 요약은 편의 UI입니다. 운영 증거는 실제 CLI·검사기가 생성한 JSON/YAML과 그 내용을 고정하는 digest입니다. skill은 결과 파일을 임의로 바꾸거나 독자적 verdict를 만들면 안 됩니다.

### 4-4. `skip = FAIL` 표현은 현재 verdict와 맞춰야 함

필수 Contract test가 skip되면 최종 PASS가 아닌 것은 맞습니다. 다만 현재 하네스는 `PASS/BLOCK/APPROVAL/ANALYSIS_ERROR`를 사용하므로, skill이 새로운 `FAIL`을 만들면 안 됩니다. 환경변수 누락은 실행 전 `ANALYSIS_ERROR`, 필수 test 미수행은 검사기가 반환하는 `BLOCK`으로 전달해야 합니다.

## 5. 현재 예행연습에 대한 영향

2026-08-07 현재 Docker 상태는 다음과 같습니다.

| 항목 | 확인 결과 | 판단 |
|---|---|---|
| OpenMetadata server | `healthy`, 1.13.1 API 응답 | 연결 가능 |
| MySQL | `healthy` | 연결 가능 |
| Elasticsearch | `healthy` | 연결 가능 |
| 실행 중인 서비스 commit | `59dae915...` | 현재 소스 기준 |
| 등록·검사한 1.13.1 commit | `d952a838...` | runtime test 대상 |
| Query fixture | 0개 | `BANK-OM-002` 실행 불가 |
| 실패 assertion fixture | 0개 | `BANK-OM-003` 실행 불가 |
| 행내 확장 컬럼 table fixture | 0개 | `BANK-OM-004` 실행 불가 |

서비스가 실행 중인 것은 필요조건이지만 완료조건은 아닙니다. 먼저 `d952a838...`를 실행하는 Docker image를 만들고, Query·실패 assertion·확장 컬럼 fixture와 브라우저 로그인 상태를 준비해야 9개 필수 Contract test를 정식 실행할 수 있습니다.

## 6. 권장 실행 순서

1. **P0 — runtime 기준선 완성:** 검사한 commit을 Docker에 배포하고 9개 Contract test를 실행합니다.
2. **P1 — 조회 요약 CLI:** 기존 결과 JSON/YAML을 gate별로 요약하는 read-only 명령을 만듭니다.
3. **P2 — 반복 명령 오케스트레이션:** `om_workflow.py`에 결정론적 작업만 추가합니다.
4. **P3 — 러너 공통화:** CI와 로컬이 같은 코드 경로를 사용하도록 제품 등록 폴더에서 공통 모듈로 이동합니다.
5. **P4 — 증거 구조 개편:** 모든 소비자와 migration 경로가 확정된 뒤 수행합니다.

## 7. 최종 의견

클로드 답변은 **“검사 강도는 유지하고 손작업만 줄이자”는 원칙 제안으로는 좋습니다.** 그러나 전수 조사를 근거로 한 수치와 “중복 0개” 단정은 그대로 받으면 안 됩니다. 또한 현재 가장 큰 빈칸은 문서 명령 수가 아니라 **실제 1.13.1 runtime 증거가 아직 없다는 점**입니다. 이 기준선을 먼저 만든 후에 경량화 전·후의 판정이 같은지 비교해야 안전합니다.
