# Claude 검토 02 — 공유 정의 이관과 승인 안전성

## 1. 범위와 금지사항

코드 이동 탐지·기능 증거·사람 승인 경계를 독립적으로 적대적 검토한다. 읽기
전용이며 코드·Git·승인 자료를 수정하지 않는다.
관련 pytest 실행과 임시 디렉터리의 독립 반례 재현은 허용한다. 실행한 명령,
exit code, 통과·skip 수를 결과에 기록한다.

```text
repository: easyseop/openmetadata-test
branch: codex/structural-upgrade-safety-20260809
implementation: d5153f284d8808e7856896b106f0539e8fcf2c83
```

## 2. 사실로 가정하면 안 되는 구현 주장

1. `.ts`·`.tsx` 후보를 함께 찾되 자동 확정하지 않는다.
2. exact, partial assertion, symbol overlap을 구분한다.
3. test·generated 파일은 이관 대상에서 제외한다.
4. partial·symbol 후보에는 새 `proposed_assertions`가 필수다.
5. `relocated`는 Candidate 기능 test, `absorbed_by_upstream`은 공식 target의 양성
   기능 test에 결속된다.
6. 이전 catalog·owners는 불변이고 새 버전에서 함께 갱신된다.
7. proposal·승인·Candidate tree·기능 증거·harness가 digest로 결속된다.
8. 자동화만으로 승인 완료 파일을 만들 수 없다.
9. 새 등록 묶음은 `definition-migration-draft`다.

## 3. 적대적 질문

1. symbol 기준이 무관한 후보를 과다 추천하거나 실제 refactor를 누락하는가?
2. source처럼 보이는 generated/test/vendor 파일로 분류를 우회할 수 있는가?
3. comment·string·dead code·unused export가 assertion으로 통과하는가?
4. 새 assertion을 BANK 요구보다 약하게 바꿔도 Candidate source check가 통과하는가?
5. 기능 증거 YAML은 실제 명령 실행을 증명하는가, 사람이 `pass`를 쓴 사실만
   증명하는가? 문서가 이 한계를 과장하는가?
6. 공식 target SHA의 기능 test가 BANK 요구와 의미적으로 다른데도
   `absorbed_by_upstream`이 통과할 수 있는가?
7. proposal 이후 Candidate commit/tree, target, catalog, owners, 기능 증거, verifier
   code 중 stale 변경 검사가 빠진 항목이 있는가?
8. public wrapper와 migration orchestrator가 `harness_version`에 포함되는가?
9. 비대화형 자동화가 승인 파일을 편집하면 CLI가 사람 승인을 구분할 수 있는가?
10. 기능 증거 절대경로가 다른 노트북 재현성과 proposal portability를 깨는가?
11. copy된 과거 registry·Manifest가 draft를 정식 등록처럼 보이게 만드는가?
12. 동시 apply·중간 종료·기존 target·stale temp·symlink에서 반쪽 등록이 남는가?
13. 같은 새 경로를 여러 BANK-OM ID가 소유할 때 catalog/owners가 정확한가?
14. `supersedes`가 새 정의의 의미적 계보와 승인 근거를 충분히 보존하는가?

## 4. 실제 후보 대조

```text
old: openmetadata-ui/src/main/resources/ui/src/utils/DatabaseServiceUtils.tsx
primary: openmetadata-ui/src/main/resources/ui/src/utils/DatabaseServicePureUtils.ts
weak BANK-OM-006 candidate: ServicePureUtils.ts
```

BANK-OM-006·007이 어떤 assertion 때문에 partial인지 확인한다. 후보 발견과 기능 보존
승인을 혼동하지 않는다. weak 후보가 오탐이면 그 이유와 개선 기준을 적는다.

## 5. 반례 test 매트릭스

- exact 이동, `.tsx→.ts` partial 이동, 무관 symbol 오탐, 실제 이동 누락
- comment-only, string-only, dead code, test/generated/source 위장
- 새 assertion 누락·약화·다른 customization assertion 재사용
- 기능 증거 누락·변조·stale SHA·wrong role·absence-only·실패 command
- proposal digest·approval digest·Candidate tree·harness 변경
- unconfirmed 승인·timezone 누락·자동 생성 승인·조직 권한 없음
- 기존 target folder·동시 apply·중간 실패·symlink·경로 이탈
- owners만 변경, catalog만 변경, 여러 owner 공유 경로
- relocated와 absorbed가 같은 customization에 함께 존재
- 다른 노트북에서 evidence path가 달라지는 경우

각 행에 정상 test와 먼저 실패해야 하는 반례 test를 대응한다. P0/P1 범주의 행이
test 없이 남으면 통과로 판정하지 않는다.
