# 1부 · 왜 이 일을 하고 있나

## 1-1. 시작점

팀원이 **"오픈소스 버전이 올라가면 LLM으로 커스터마이징을 업데이트하면 되고,
잘 된다"**고 했다. PPT 근거로는 실제로 잘 됐다.

```
1.12.8 → 1.12.13 → 1.13.1   세 번 성공
포팅 시간   4~5시간 → 30분~1시간
재작업 횟수 5~6회   → 1~2회
```

사용자의 목표는 그 방식을 부정하는 게 아니라 **한계를 보완해서 개발 리더들에게
"운영 가능하다"는 확신을 주는 것**이다. 이 작업 전체가 그 질문을 다룬다.

## 1-2. 검사기가 답하려는 한 줄

> **"LLM이 잘한다" → "LLM이 틀려도 걸린다"**

리더는 "LLM이 잘한다"를 검증할 수 없다. 믿는 수밖에 없어서 승인이 안 난다.
"틀려도 걸린다"는 메커니즘은 보여줄 수 있고, 그래서 검증 가능하다.

프레이밍도 정해 뒀다.

```
❌ "방향을 LLM 상호작용으로 바꿨습니다"   → 이전이 틀렸다는 뜻이 되고 낭비 소리가 나온다
✅ "각자 하다 보니 서로 필요한 걸 갖고 있더라"
```

두 번째가 사실이기도 하다. 두 갈래가 각자 진행됐고 이제 합치는 것이다.

## 1-3. 왜 하필 "테스트"를 먼저 했나

단계 로드맵을 놓고 보면 이유가 분명하다.

| 단계 | 무엇 | 답할 수 있게 되는 것 | 2026-08-10 이전 |
|---|---|---|---|
| 0 | 현재 | "했습니다" — 믿는 수밖에 | |
| 1 | 기록 — ID·커버리지 표·예측 칸 | "BANK-OM-004를 이렇게 검증했습니다" | 제안 단계 |
| **2** | **실행 — Docker + Contract 9개** | **"실제로 동작합니다"** | **미실행** |
| **3** | **유효성 — T61** | **"그 확인이 진짜입니다"** | **2/5** |
| 4 | 자동 대조 | "기록이 사실입니다" | 따로 돎 |
| 5 | 커버리지 | "안 본 곳이 어디인지 압니다" | 없음 |
| 6 | 자기승인 차단 | "작업자가 기준을 못 바꿉니다" | 미연결 |

**논의 대부분이 4·6단계에 가 있었는데 1~3이 비어 있었다.** 4단계(자동 대조)는
"기록이 사실이다"를 보장하지만, 그 기록이 가리키는 테스트가 **애초에 아무것도
안 보고 있으면** 아무 의미가 없다. 순서가 뒤집혀 있었던 것이다.

그리고 2·3단계는 세트다. Docker를 띄운 김에 순정 이미지로 한 번 더 돌리는
것이라, 나중에 따로 하면 Docker를 또 띄워야 한다. 8GB 기기에서 이건 큰 비용이다.

**그래서 재부팅까지 하고 2·3단계를 먼저 실행했다.**

## 1-4. 결정적 발견 — 빌드가 필요 없었다

`docker/rehearsal/common.sh` 확인 결과 커스텀 이미지가 이미 배포돼 있었다.

```
OM_SERVER_IMAGE          ghcr.io/easyseop/openmetadata-bank:1.13.1-bank-8ac18ad0
OM_CONTRACT_RUNNER_IMAGE ghcr.io/easyseop/openmetadata-contract-runner:1.13.1-runtime
```

`8ac18ad0`은 1.13.1 커스텀 HEAD다. 목 데이터 생성기
(`create_mock_database_metadata.py`)도 스택에 포함돼 자동 실행된다.
**소스 빌드 없이 다운로드만으로 기동된다.** 이것 때문에 8GB 기기에서도
오늘 실행이 가능했다.

# 2부 · 무엇을 테스트한 것인가

## 2-1. 순정과 커스텀

OpenMetadata는 오픈소스다. 우리는 거기에 은행 기능 7개를 얹었다.

```
순정   = 오픈소스 그대로.        docker.getcollate.io/openmetadata/server:1.13.1
커스텀 = 순정 + BANK-OM 7개.     ghcr.io/easyseop/openmetadata-bank:1.13.1-bank-8ac18ad0
```

| ID | 기능 |
|---|---|
| BANK-OM-001 | 기준코드(InstanceCode) |
| BANK-OM-002 | 쿼리 리포트(QueryReport) |
| BANK-OM-003 | 데이터 검증 결과(Data Assertions) |
| BANK-OM-004 | 은행 컬럼 확장 표시 |
| BANK-OM-005 | 한글 입력 조합 보정 |
| BANK-OM-006 | Sybase 연결 유형 |
| BANK-OM-007 | Tibero 연결 유형 |

정본은 `harness/registrations/om-temp-1.13.1/customization-registry.yaml`이며
Contract·Manifest·조각 790개가 이미 이 ID에 묶여 있다.

## 2-2. T61이 답하려는 것

테스트가 커스텀에서 통과했다는 것만으로는 **그 테스트가 은행 기능을 실제로
보고 있는지** 알 수 없다. 아무것도 안 보고 통과 도장만 찍어도 결과는 똑같이
`pass`다.

그래서 기능이 **없는** 빌드에 같은 테스트를 돌린다. 거기서 실패해야 그 테스트가
눈을 뜨고 있다는 증거가 된다. 이게 patch-kill(T61)이다.

`docs/04-진행/openmetadata_build_plan.md` T61 정의:

> critical/high 패치를 제외한 임시 스택 생성 → 그 ID required 테스트 실행 →
> **적어도 하나는 assertion failure여야** 함. 전부 통과하면 그 테스트는 생존
> 미입증으로 block. skip·test error·timeout은 analysis_error이며 patch-kill
> 성공으로 인정하지 않는다.

## 2-3. Contract 7개와 필수 테스트 9개

| Contract | 필수 테스트 | ID | 판정 계층 |
|---|---|---|---|

| QUERY-REPORT | `test_query_report::test_query_usage_roundtrip` | 002 | 서버 API |
| DATA-ASSERTIONS | `test_data_assertions::test_failed_assertion_projection` | 003 | 서버 API |
| | `test_data_assertions::test_failed_assertion_rendered_row` | 003 | 브라우저 |
| BANK-COLUMN-VIEW | `test_bank_columns::test_extended_column_projection` | 004 | 서버 API |
| | `test_bank_columns::test_extended_column_rendered_row` | 004 | 브라우저 |
| KOREAN-IME | `test_korean_ime::test_hangul_composition_roundtrip` | 005 | 브라우저 |

**실행 전에 확인한 중요한 사실**: 006·007은 `OPENMETADATA_PRODUCT_REPO`의 소스
파일을 읽는 계약이다. 서버 이미지를 바꿔도 소스는 여전히 커스텀(`8ac18ad0`)이라
**구조적으로 죽지 않는다.** 인수인계서 3-5의 판정 규칙 "하나라도 통과 → 껍데기다"를
그대로 적용했다면 **이미 source patch-kill로 입증된 006·007을 오판**했을 것이다.

## 3-2. 세 번 막힌 이유와 오진 기록

실행을 세 번 실패했다. 원인 진단을 **두 번 틀렸다.** 기록을 남긴다.

**1차 실패.** `prepare_runtime_contract_environment.py:243`의 `browser_state()`가
Playwright Chromium을 띄우다가 `new_context()`에서 `TargetClosedError`로 죽었다.
`--shm-size=1g`, `--disable-dev-shm-usage --no-sandbox` 둘 다 효과 없었다.

**오진 1 — "qemu 에뮬레이션 때문"이라고 단정했다.** colima `rosetta: false`라
`platform: linux/amd64` 러너가 qemu-x86_64로 돈다는 것까지는 맞았고, rosetta를
켜니 Chromium 단독 기동은 됐다. 그런데 그 비교는 **메모리 조건이 달랐다**
(실패 시 스택 가동 중, 성공 시 스택 정지). 단정할 근거가 부족했다.

**2차 실패.** 브라우저는 뜨는데 `/signin`에서 `input[type="text"]`을 30초 안에
못 찾는다.

**오진 2 — "메모리 부족"이라고 판단했다.** 이때 Elasticsearch가 OOM(exit 137)으로
죽어 있었는데, 원인은 제품이 아니라 **내가 띄운 진단 컨테이너 2개**였다(하나는
타임아웃 후에도 살아남아 있었다). 그걸 정리하니 여유가 2136MB로 회복됐다.
사용자 판단으로 colima 메모리를 4GB→5GB로 올려 재시도했다.

**3차 실패.** 5GB에서도 같은 지점에서 실패. 여기서 `docker stats`가 답을 줬다.

```
signin-diag3   CPU 102.23%   MEM 382.3MiB / 4.79GiB
```

**메모리는 382MB만 쓰면서 CPU 한 코어를 100% 점유하고 있었다.** Rosetta로 변환된
x86 Chromium이 OpenMetadata SPA의 자바스크립트를 감당하지 못해 `load` 이벤트가
끝나지 않았다. 메모리가 아니라 CPU였다.

**해결.** contract-runner를 arm64 네이티브로 빌드했다
(`mcr.microsoft.com/playwright/python:v1.52.0-noble`에 arm64가 있다).
4분 넘게 안 되던 화면이 **1.7초**에 렌더링됐다. 이후 9/9 통과.

## 3-3. T61 순정 — 첫 시도가 기동조차 못 했다

기존 DB(커스텀이 만든 데이터 포함)에 순정을 올리니 마이그레이션이 exit 1.

```
Caused by: java.lang.IllegalArgumentException: Sybase
  at CreateDatabaseService$DatabaseServiceType.fromValue(CreateDatabaseService.java:552)
  at SecretsManagerUpdateService.retrieveServices(SecretsManagerUpdateService.java:188)
```

목 데이터에 `bank_mock_sybase`·`bank_mock_tibero`가 있는데 순정의
`DatabaseServiceType` enum에 `Sybase`가 없다. 순정이 기동하며 기존 서비스를
읽다가 모르는 값을 만나 그냥 죽는다.

**커스텀 데이터를 지우지 않고** `db-data`를 옆으로 옮겨 순정용 빈 DB를 만들었고,
거기서는 마이그레이션이 **exit 0으로 정상 기동**했다. 순정의 결함이 아니라
데이터 비가역성이라는 뜻이다.

## 3-5. T61은 3/5이지 5/5가 아니다

세 가지 이유다.

1. **전임 불일치 (002·003).** 계획서는 per-ID 전임을 요구하는데 우리는 패치를
   전부 뺀 스택 하나를 썼다. 002는 테스트의 첫 동작이 `POST /v1/queryReports`이고
   그게 404이므로 인과는 명확하지만, 계획서 요건은 아니다.
2. **candidate 불일치.** 계획서 `candidate.commit_sha`는 `849ae756…`, 배포
   이미지는 `8ac18ad0…`. 게다가 이 계획 파일은
   `registrations/kb-openmetadata/`에만 있고 오늘 후보의 등록 폴더
   `registrations/om-temp-1.13.1/`에는 patch-kill 계획이 **없다.**
3. **006·007은 이 방법으로 판정 불가.** 이미 source patch-kill
   (`6e5b654f`·`41b224ad`)로 입증된 2/5다.

**증분은 BANK-OM-001 1건. T61 = source 2/5 + runtime 1/5 = 3/5.**

# 4부 · 새로 나온 문제

## 4-1. [Serious] BANK-OM-005 필수 테스트가 커스터마이징을 입증하지 못한다

`test_korean_ime::test_hangul_composition_roundtrip`이 순정
digest `sha256:eaa31858…`에서 `outcome: pass`다. BANK-OM-005의 필수 런타임
테스트는 이것 하나뿐이므로 **이 기능은 사라져도 검사기가 모른다.**

같은 파일에 `test_hangul_composition_source_guard`가 구현돼 있지만
`contracts.yaml`의 `required_tests`에 등재돼 있지 않다.

반례: `evidence/om-1.13.1-runtime-t61-20260810/t61-vanilla-negative-control/test-run-set.yaml`

인수인계서 3-5가 찾으려던 "껍데기"가 실제로 나온 사례다.

## 4-2. [Serious] 003·004의 API 계층 테스트가 판별력이 없다

`test_failed_assertion_projection`과 `test_extended_column_projection`이
순정에서 통과한다. 두 Contract 모두 `rendered_row` 쪽이 죽어서 계약 전체로는
판별되지만, API 계층 절반은 커스터마이징에 민감하지 않다.

## 4-3. [Blocking] 순정 롤백이 데이터 계층에서 불가능하다

3-3에서 본 그대로다. **은행 버전을 운영에 올려 데이터가 쌓이면 오픈소스
원본으로 되돌아갈 수 없다.** 데이터를 통째로 버리지 않는 한 앞으로만 갈 수 있다.

이건 검사기 문제도 1.13.2 문제도 아니고 **설계 문제**다. 그리고 소스만 봐서는
절대 안 나온다 — 코드에는 "Sybase를 지원한다"고만 적혀 있지 그 데이터가 나중에
발목을 잡는다는 건 안 적혀 있다. PPT 방식(LLM 포팅 + 리허설)으로도 안 나온다.
**실제로 두 벌을 같은 데이터에 물려봐야 나온다.**

로드맵 14-1의 "롤백 — 계획 없음"은 계획 부재가 아니라 **구조적 차단**으로
승격해야 한다.

## 4-4. [Minor] 이 기계에서 문서대로는 재현되지 않았다

`docker-compose.override.yml`의 contract-runner가 `linux/amd64` 고정이라
Apple Silicon에서 에뮬레이션된 Chromium이 SPA를 렌더링하지 못한다.
`browser_state()`에 우회 수단이 없어 **API 전용 계약 6개도 함께 막힌다.**

인수인계서의 "1.13.1 기준선에서 이미 9/9 통과 이력"은 이 기계의 그 설정에서는
재현되지 않았다.

1.13.1 코드에서 자동 추출해 사람이 승인했다. PPT의 KB-CUSTOM-* MD와 다른 점은

좋았다.** 다음번에 테스트 파일까지 쪼개지면 아무도 모르게 검증이 없어진다.

등록돼 있지 않다.

## 8-7. 남은 P0 4건

| | 내용 |

| D | 기능 test 증거가 Candidate SHA에만 결속 |

**A+B가 동시에 열려 있으면 필수 테스트를 `assert True`로 바꿔도 증거에 안 남는다.**

막혀 있는 것(확인됨): 조건부 `pytest.skip` 공격은 차단된다.
`pytest_runs.py:64-66`이 *"Any skip means this required selector was not fully
proven"*으로 처리한다.
