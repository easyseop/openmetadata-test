# Phase 통합 7단계 가이드 구성 외부 검토 요청

> 상태: 사용자 피드백용 구성 초안
> 원본 예행연습: 1.13.1→1.13.2 기존 11단계 가이드, 변경하지 않음
> 비교 초안: 새 Phase 검사기를 도입한다고 가정해 11단계를 7단계로 묶은 화면
> 실제 적용 상태: 검사기 구현·합성 회귀 완료, 실제 OM_TEMP 예행연습에는 미적용
> 구현 기준 commit: `6079aaff4d1b227df699d3f67262d60a96cd6b07`

## 검토 배경

기존 예행연습은 준비부터 release 고정까지 11개의 상세 페이지로 구성돼 있다.
별도로 개발한 새 Phase 검사기는 Candidate 선택, 공식 버전 고정, 실행 전 점검,
병합 전 검사, 병합 후 검사와 결과 재검증을 공통 흐름으로 제공한다. 기존 상세
가이드를 삭제하지 않고, 반복 준비·확인 작업을 통합한 7단계 시작 페이지를 추가할
수 있는지 검토받으려 한다.

## 제안하는 7단계

### 1. 작업환경과 1.13.1 기준 branch 확인 — 원본 1~2 통합

- 넣을 내용: 저장소 역할·경로, Git 접근 권한, 도구·환경변수,
  official/custom branch와 commit SHA, dirty worktree 확인, 정상·실패 예시.
- 강조: 코드를 수정하지 않는 준비 단계이며 저장소·branch·SHA가 다르면 중단.
- 완료: 사용할 저장소 경로와 1.13.1 기준 SHA 기록.
- 중단: 접근 불가, branch 누락, dirty worktree, 예상 SHA 불일치.

### 2. BANK-OM 코드와 등록자료 준비 — 원본 3~5 통합

- 넣을 내용: 111개 등록·2개 제외 경로(근거:
  `docs/04-진행/STRICT_SCOPE_IMPROVEMENT_PROGRESS.md`), BANK-OM-001~007 연결, 공용 경로,
  ID별 commit, Manifest·Registry·Contract·공용 코드 정의,
  changed/required/watch 차이.
- 강조: Git은 경로·commit 후보만 계산하며 업무 기능·필수 경로·담당자·Contract는
  사람이 결정. 빈 assertion을 임의 값으로 채우지 않음.
- 완료: ID별 commit 후보와 검토 가능한 등록자료 초안.
- 중단: 미등록 경로, 중복 ID 연결, 제외 경로 잔존, 업무 입력 누락.

### 3. 1.13.1 기준선 승인과 자동 검증 — 원본 6~7 통합

- 넣을 내용: 네 판정값, plan→승인→apply, 승인 digest, 등록·소스 기준 검사,
  Candidate lock, active pointer, candidate-select 정상·실패 출력.
- 강조: 승인 판단은 자동화하지 않음. 검사기는 승인 형식·digest만
  검증하며 승인자의 조직 권한은 검증하지 못함. 기준선 PASS는 1.13.2
  또는 배포 완료가 아님.
- 완료: 승인된 1.13.1 Candidate lock과 검사 증거의 SHA 결속.
- 중단: 승인 누락, stale proposal, active pointer 불일치, 필수 검사 미완료.

### 4. 공식 1.13.2 준비와 병합 전 검사 — 원본 8 유지

- 넣을 내용: 공식 tag·commit·branch 관계, prep-official 증거, preflight 누락
  목록, premerge 영향·민감 경로, 담당자의 병합 진행 판단.
- 강조: 아직 vendor merge를 실행하지 않으며 T42 영향은 충돌 확정이 아님.
- 완료: 공식 기준 증거와 premerge 결과를 같은 target SHA에 결속.
- 중단: tag·commit·branch 불일치, target 누락, BLOCK, ANALYSIS_ERROR.

### 5. vendor merge와 충돌 해결 — 원본 9 유지

- 넣을 내용: 병합 방향, custom_head_sha, merge-base, 병합 명령, 충돌 유형,
  해결 diff·근거, 해결 commit, Candidate SHA·lock, 충돌 경로 증거.
- 필수 순서: merge·해결 commit → 새 1.13.2 Candidate lock 작성·승인·활성화
  → candidate-select → conflict evidence 수집 → phase-preflight → postmerge-check.
- 자동 수집 명령: `python harness/om_workflow.py collect-conflict-evidence
  --repo <제품저장소> --version 1.13.1 --baseline-lock-digest <digest>
  --custom-head <SHA> --output <증거.yaml>`.
- 강조: 수집기가 rename 탐지를 비활성화한 정책으로 diff 합집합과
  merge-tree 충돌 결과를 생성·자기 검증함. 목록을 손으로 수정하지 않음.
  허용되지 않은 merge driver 설정은 ANALYSIS_ERROR로 차단. 검사기는 병합·충돌 해결을
  대신하지 않으며 Git 충돌 해결과 기능 정상은 다름.
- 정책 의미: conflict-rate는 rename 탐지를 끈 결정적 재현 기준 지표이며
  실제 대화형 merge의 충돌 표시와 다를 수 있음. custom merge driver 허용
  override는 없음. `replay_config_digest`는 사용자의 무효화된 설정까지 담을 수
  있는 감사용 정보 필드임.
- 제약: custom head는 승인된 기준선 Candidate commit과 정확히 같아야 함.
  fix commit이 있으면 먼저 새 기준선으로 등록·승인.
- 완료: 병합 부모와 해결 commit이 있는 하나의 1.13.2 Candidate SHA.
- 중단: 해결 기준 불명확, 미해결 충돌, test 실패, 승인되지 않은 코드 선택.
- 복구: fix commit으로 Candidate SHA가 바뀌면 기존 lock·결과·승인을 폐기하고,
  새 lock 승인 후 candidate-select부터 재실행.

### 6. 1.13.2 종합 검사와 승인 판단 — 원본 10 유지

- 넣을 내용: postmerge Candidate 선택·preflight, custom head·merge-base·ancestry,
  merge-tree 완전 일치, 등록·소스·공용 코드·build·Contract·Runtime,
  source-only/artifact-verified, 3단 보고서와 phase-status.
- 강조: source-only PASS는 artifact·Runtime 완료가 아니며 APPROVAL은 자동 진행
  허가가 아님. 검사기는 승인 형식·digest만 검증하며 조직 권한은 검증하지 못함.
- 완료: 같은 Candidate SHA·artifact digest·결과를 가리키는 종합 증거.
- 중단: 충돌 증거 불일치, 필수 gate 미실행, build·Runtime 실패, 보고서 변조,
  조직 승인 누락.

### 7. 검증 tag와 release branch 고정 — 원본 11 유지

- 넣을 내용: Candidate SHA·image·Helm·결과 digest, release lock, T91,
  tag·release branch 명령과 권한, 증거 보관·인수인계·rollback.
- 강조: phase-status 통과가 자동 tag·release·운영 배포를 뜻하지 않으며 승인 후
  대상이 바뀌면 재검사. 승인자의 조직 권한은 별도로 확인.
- 완료: 검증한 동일 commit을 tag·release branch·release lock으로 고정.
- 중단: digest 불일치, 승인 권한 미확인, release lock 누락, 배포 대상 변경.

## 반영한 1차 검토 결과

- 단계 표기는 `새 4단계(원본 8) · 검사기 화면 [3/6]` 형식으로 통일.
- candidate-select와 preflight가 premerge·postmerge 맥락에서 재실행된다는 안내 추가.
- APPROVAL 예시의 1차 다음 행동을 `실무자 검토 후 담당자 승인`으로 정정.
- 잔존 lock·구버전 증거, Candidate SHA 변경, custom head 완전 일치 제약과
  복구 절차 추가.
- 2차 검토의 P1을 따라 rename 설정을 고정하고 임의 merge driver를 차단했으며,
  경로 목록 자동 수집기를 구현함. 수집기는 NUL 파싱, byte 정렬,
  생성 즉시 동일 검증 함수 self-check, 기존 파일·동시 실행 거부를 수행함.

## 검토 요청

1. 원본 1~2, 3~5, 6~7의 통합이 초보 운영자에게 너무 넓거나 모호하지 않은가?
2. vendor merge와 release를 독립 단계로 남긴 것이 적절한가?
3. 각 가이드의 자동 확인과 사람 판단 경계가 분명한가?
4. 각 단계의 완료 결과와 중단 조건이 다음 단계 진입 여부를 판단하기에 충분한가?
5. source-only와 artifact-verified, 검사 완료와 운영 배포의 차이가 충분히 강조됐는가?
6. 빠진 정상 예시·실패 예시·복구 절차·보관 증거가 있는가?
7. 최종 권고를 `채택 / 수정 후 채택 / 기각` 중 하나로 제시하고 P0·P1·P2로
   문제를 분류해 달라.
