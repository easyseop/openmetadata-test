# 구조보완 추가 논의 01 — 유사도 후보 판정 Claude 검토 요청

작성일: 2026-08-09

## 1. 이 검토가 필요한 이유

구조가 크게 바뀐 업그레이드에서는 기존 `shared-code-definitions.yaml` 경로가
사라질 수 있다. 현재 검사기는 기존 정의와 비슷한 코드가 있는 새 경로를 찾아
이관 후보로 제시한다. 이 기능은 담당자의 검색 시간을 줄일 수 있지만, 부분 코드나
흔한 symbol이 우연히 일치하면 잘못된 후보가 만들어질 수 있다.

잘못된 후보를 사람이나 LLM이 “기능이 이동한 위치”로 오해하면, 실제 BANK 기능이
없는 경로를 새 감시 경로로 승인할 위험이 있다. 따라서 후보 검색이 필요한지,
후보가 gate 판정에 영향을 줘도 되는지, LLM에 어떤 형태로 노출해야 하는지를
구현 전에 다시 검토한다.

## 2. 검토 대상

```text
repository: easyseop/openmetadata-test
branch: codex/structural-upgrade-safety-20260809
implementation under discussion: d5153f284d8808e7856896b106f0539e8fcf2c83
latest repair: df1eee22f2e8c0c0b7db999a2428f8637696124f
```

주요 코드:

```text
harness/acgh/structural_review.py
harness/acgh/shared_code_migration.py
harness/tests/test_structural_review.py
harness/tests/test_shared_code_migration.py
```

이번 요청은 읽기 전용 설계 검토다. 코드·문서·Git 상태, 제품 WIP, Candidate lock,
예행연습 증거를 수정하지 않는다. 제품 build와 Docker도 실행하지 않는다.

## 3. 먼저 구분해야 하는 세 가지

### 3.1 Git 충돌

Git 충돌은 공식 코드와 BANK 코드가 같은 파일·같은 부분을 자동으로 합치지 못한
상태다. 충돌 해소가 끝났다는 사실은 BANK 기능이나 공식 기능이 유지됐다는 증명이
아니다. 사람이 한쪽 코드를 선택하면 Git 충돌은 없어져도 다른 쪽 변경이 빠질 수
있다.

### 3.2 구조 손실 의심

구조 검사는 merge-base, 공식 target, BANK custom head, 최종 Candidate의 파일
상태를 비교한다. 검사기가 확정할 수 있는 것은 “공식 또는 BANK의 코드 변경이
최종 Candidate의 같은 경로에 보이지 않는다”는 사실이다. 실제 기능 손실은 공식
test, BANK 전용 test, Runtime 검증 전에는 확정할 수 없다.

### 3.3 새 경로 후보 검색

후보 검색은 사라진 기존 정의의 코드 조각·설정값·주요 symbol을 새 Candidate의
변경 경로에서 찾는다. 이것은 기능 유지 판정이 아니라 담당자가 먼저 확인할 파일을
줄여주는 검색 결과다.

## 4. 현재 구현의 실제 동작

현재 `find_relocations()`는 다음 순서로 후보를 만든다.

1. 기존 경로가 없거나 기존 assertion이 실패하면 검색을 시작한다.
2. 구조 검토 표면에 포함되고 Candidate tree에 존재하는 경로만 검색한다.
3. TypeScript는 `.ts`와 `.tsx`, YAML은 `.yaml`과 `.yml`을 같은 그룹으로 본다.
4. assertion 전체 일치는 `exact_definition`으로 분류한다.
5. assertion 일부 일치는 `partial_assertion`으로 분류한다.
6. code fragment에서 추출한 의미 있는 symbol이 최소 2개이면서 기존 symbol의
   30% 이상 겹치면 `symbol_overlap`으로 분류한다.
7. source context의 후보는 `eligible_for_migration: true`가 된다.

현재 판정은 다음과 같다.

```text
source 후보가 1개 이상 있음 → finding verdict = APPROVAL
source 후보가 없음          → finding verdict = BLOCK
```

`to_gate_result()`는 이 relocation verdict를 `structural-review` gate 판정에
반영한다. 따라서 현재 후보 검색은 설명과 달리 완전한 참고 정보만은 아니며,
BLOCK과 APPROVAL을 가르는 판정 영향이 있다.

정의 이관 proposal은 추가로 다음을 요구한다.

- 선택 경로가 `eligible_for_migration` 후보에 포함될 것
- Candidate SHA에 결속된 기능 test 증거가 있을 것
- partial 또는 symbol 후보는 새 assertion을 사람이 제시할 것
- 새 assertion이 Candidate 파일에서 실제 통과할 것
- proposal digest에 결속된 사람 승인이 있을 것

이 안전장치가 있어 후보만으로 PASS가 되지는 않는다. 그러나 잘못된 후보가
APPROVAL과 사람·LLM의 판단 방향에 영향을 주는지 검토가 필요하다.

## 5. 실제로 우려하는 실패 사례

### 정상 사례

```text
기존: DatabaseServiceUtils.tsx
신규: DatabaseServicePureUtils.ts
결과: BANK assertion이 새 경로에서도 일치하고 BANK 전용 test가 통과
```

이 경우 제품 병합 또는 BANK 기능 재이식이 성공했을 가능성이 높다. 사람은 코드를
확인한 후 검사기가 감시할 정의 경로를 새 버전 등록자료에 승인할 수 있다.

### 오탐 사례

```text
기존 assertion: buildBankValue(BANK_MODE)
새 후보 코드: buildBankValue(OFFICIAL_MODE)
공통 symbol: buildBankValue, createBankValue
```

현재 test는 이 파일을 `symbol_overlap`, `eligible_for_migration: true`,
finding `APPROVAL` 후보로 고정한다. 그러나 실제 BANK 동작은 없을 수 있다.

### 후보 없음

새 Candidate 어디에서도 기존 정의 단서를 찾지 못하면 현재는 BLOCK이다. 이 BLOCK의
정확한 의미는 “기능이 사라졌음”이 아니라 “기존 감시 정의를 새 버전에서 검증할
방법이 아직 없음”이어야 한다.

## 6. 비교할 설계안

### 안 A — 현행 유지

```text
후보 있음 → APPROVAL
후보 없음 → BLOCK
```

장점은 사람이 조사할 경로와 이관 가능 경로를 빠르게 얻는 것이다. 단점은 부분·
symbol 후보가 gate 판정과 LLM 판단을 유도한다는 점이다.

### 안 B — 모든 후보를 순수 진단으로 격하

```text
기존 정의 실패 → 후보 유무와 관계없이 BLOCK
후보 목록       → 상세보기의 UNVERIFIED_CANDIDATE
사람 확인 + 기능 test + 새 정의 승인 → 다음 실행에서 BLOCK 해제
```

장점은 유사도가 어떤 판정도 완화하지 않는다는 것이다. 단점은 exact match가 있어도
승인 전까지 동일하게 BLOCK되어 운영 흐름이 더 엄격해진다는 점이다.

### 안 C — exact와 fuzzy를 분리

```text
exact_definition → 사람 검토용 APPROVAL 후보
partial_assertion / symbol_overlap → 판정 영향 없는 UNVERIFIED_CANDIDATE
후보 없음 → BLOCK
```

장점은 완전 일치와 추정 후보를 구분하는 것이다. 단점은 exact code가 복사된
미사용 코드이거나 기능상 깨진 경우에도 강한 후보처럼 보일 수 있다는 점이다.

현재 Codex의 잠정 권고는 **안 B 또는 안 C**다. 최소 조건은
`partial_assertion`과 `symbol_overlap`이 gate verdict를 완화하지 못하게 하는
것이다. 이 결론에 동의하도록 유도하지 말고 반례로 재판정해 달라.

## 7. LLM에 전달할 때 필요한 경계

LLM에 다음 문장을 전달하면 안 된다.

```text
BANK 기능이 DatabaseServicePureUtils.ts로 이동했습니다.
```

다음과 같이 미확인 상태와 근거를 구조화해야 한다.

```yaml
status: UNVERIFIED_CANDIDATE
old_path: DatabaseServiceUtils.tsx
candidate_path: DatabaseServicePureUtils.ts
evidence_strength: symbol_overlap
matched_assertion_count: 0
assertion_count: 4
matched_symbol_count: 3
automated_decision: none
required_next_actions:
  - 담당자 코드 확인
  - Candidate SHA에 결속된 BANK 전용 test
  - 새 assertion 검증
  - 사람 승인
prohibited_claims:
  - 기능 이동 확정
  - PASS 확정
  - 자동 정의 변경
```

LLM은 후보별 차이 요약과 확인할 test 제안만 할 수 있다. 후보 선택, 정의 변경,
승인, PASS 판정은 할 수 없어야 한다.

## 8. Claude가 답해야 할 적대적 질문

1. 현재 `eligible_for_migration`과 finding `APPROVAL`이 “진단 전용”이라는 rule과
   모순되는가?
2. `symbol_overlap` 오탐이 기능 test와 사람 승인 전에 어떤 잘못된 상태 전이를
   만들 수 있는가?
3. 기능 test가 후보 경로의 정의 자체와 충분히 결속되는가, 아니면 Candidate 전체
   test라는 이유만으로 무관한 후보도 승인 가능한가?
4. exact assertion 전체 일치는 APPROVAL로 올려도 안전한가? 미사용 코드, 주석,
   복제 코드, 호출되지 않는 코드 반례를 확인한다.
5. 안 B와 안 C 중 어느 쪽이 허위 승인과 불필요한 BLOCK을 더 잘 통제하는가?
6. 후보가 여러 개일 때 정렬 1위가 사람이나 LLM의 anchoring을 유발하는가? 순위를
   없애거나 동률 집합으로 보여야 하는가?
7. 후보 검색 기능을 완전히 제거해도 정의 이관·기능 검증·감사 추적이 가능한가?
   제거 시 사람이 제공한 새 경로를 어떤 독립 검사로 검증해야 하는가?
8. 후보가 없어 BLOCK일 때 사용자 출력이 “기능 손실 확정”으로 오해되지 않는가?
9. LLM 시스템 규칙만으로 오해를 막을 수 있는가, 아니면 JSON schema와 gate 코드가
   `automated_decision: none`을 기계적으로 강제해야 하는가?
10. 후보 검색의 실제 편익이 복잡성·오탐·검토 비용보다 큰지, 이번 OM 1.13.2
    사례와 synthetic 반례를 분리해 판정한다.

## 9. 반드시 확인할 반례 test

| 반례 | 기대 판정 |
|---|---|
| exact assertion이 새 source에서 모두 일치 | 설계안별 verdict를 명시하고 기능 확정은 금지 |
| symbol만 30% 이상 겹치고 BANK 값은 공식 값으로 바뀜 | PASS 금지, 최소 UNVERIFIED |
| assertion 일부만 일치 | PASS 금지, 새 assertion·기능 test·사람 승인 필요 |
| 같은 symbol의 후보가 여러 개 | 첫 후보 자동 선택 금지 |
| code가 주석에만 존재 | 후보 제외 |
| code가 test/generated 파일에만 존재 | 이관 가능 후보 제외 |
| source 파일에 복제됐지만 호출되지 않음 | 기능 test 전 기능 유지 주장 금지 |
| 후보가 전혀 없음 | 정의 미검증 BLOCK, 기능 손실 확정 문구 금지 |
| LLM이 후보를 moved/pass로 변환한 출력 | schema 또는 정책 검사에서 거부 |
| 사람이 제시한 새 경로가 후보 목록 밖 | 현재 차단의 필요성과 대체 독립 검증을 비교 |

기존 test 이름만 확인하지 말고 fixture의 코드가 실제 오탐을 만드는지 확인한다.
필요한 반례가 없으면 먼저 실패해야 할 test 코드와 예상 verdict를 제시한다.

## 10. 결과 형식

```text
1. 현재 동작 사실 정정
2. 후보 검색 기능의 실제 필요성: 필수 / 선택 / 제거 권고
3. 안 A·B·C 비교표
4. P0 — 허위 PASS·허위 승인 가능성
5. P1 — 구현 전 필수 변경
6. P2 — 출력·LLM·성능 보완
7. 반례 test 완전성 표
8. 최종 권고와 정확한 상태 전이
```

코드·문서를 수정하지 않는다. 근거 없는 동의나 “test가 있으니 안전하다”는 결론을
금지한다. 후보 검색을 유지하라고 권고할 경우, 후보가 실제 판정을 완화해야 하는
이유와 오탐을 막는 기계적 조건을 반드시 제시한다.

## 12. 이후 반복 논의할 변화

이번 문서는 유사도 후보 한 항목만 다룬다. 다음 항목도 같은 순서로 진행한다.

1. 개발 전·후 차이를 쉬운 말로 설명한다.
2. 자동 확인과 사람 판단의 경계를 확인한다.
3. 필요성, 중복, 오탐·누락 가능성을 논의한다.
4. 합의 내용을 별도 Claude 검토 요청에 누적한다.
5. 모든 항목을 논의한 뒤 최종 통합 검토 요청서를 만든다.

다음 논의 후보는 다음과 같다.

- merge-base와 upgrade base 분리
- 공식·BANK·Candidate 3집합 전체 구조 비교
- `CUSTOM_LOSS_SUSPECT`·`OFFICIAL_LOSS_SUSPECT`의 실제 의미
- rename·binary 진단과 판정 digest 분리
- 여러 merge-base와 unrelated history의 fail-closed 처리
- 버전별 shared-code 정의 이관·기능 test·사람 승인
- Phase 결과·Candidate SHA·harness digest 결속
- LLM이 할 수 있는 요약과 금지해야 할 승인 행동
