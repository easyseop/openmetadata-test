# Claude 검토 04 — 실제 1.13.2 적용과 최종 통합 판정

## 1. 실행 조건과 금지사항

1~3차 결과를 먼저 읽고 미해결 P0·P1을 최종 판정에 반영한다. 세 결과가 없거나
P0가 남았으면 통합 승인을 하지 않는다. 저장소·제품 WIP·예행연습 증거는 수정하지
않고 제품 build와 Docker도 재실행하지 않는다.
관련 harness pytest의 실제 재실행은 허용한다. 실행한 명령, exit code, 통과·skip 수를
기록하고 1~3차에서 제안한 회귀 test가 수정 commit에 실제 추가됐는지 확인한다.

검사기:

```text
repository: easyseop/openmetadata-test
branch: codex/structural-upgrade-safety-20260809
implementation: d5153f284d8808e7856896b106f0539e8fcf2c83
handoff: 00a0c581b97832b584abc5aac403c94e1bffa3c0
```

제품 입력:

```text
repository: easyseop/OpenMetadata
branch: codex/om-1.13.2-rehearsal-vendor-merge-20260809
upgrade base: afcb2d2cd7e7c28f1d0ce60538c60a96f4eb9dc9

```

```text

docs/04-진행/CODEX_CURRENT_HANDOFF.md
```

## 2. 사실로 가정하면 안 되는 결과 주장

```text
review surface: 1,786
loss suspects: 28
relocation findings: 2
relocation verdict: APPROVAL
BANK-OM-006/007 primary candidate: DatabaseServicePureUtils.ts
tests: 582 passed, 38 skipped, 0 failed, 620 collected
```

test 합계는 7개 묶음의 합산이다. test 파일 중복·누락과 skip 사유를 확인한다.

## 3. 통합 질문

1. 1~3차 P0·P1이 모두 해소됐는가?
2. 1,786개와 28개가 해당 SHA에서 재현되며 28개를 확정 손실로 과장하지 않는가?
3. BANK-OM-006·007 후보가 실제 코드와 일치하고 새 assertion·기능 test 전에는
   APPROVAL 이상으로 표현되지 않는가?
4. 이번 검사기가 48개 충돌을 자동 해결한다고 오해시키는가, 아니면 충돌 후 손실
   검토·증거 결속이라는 실제 역할이 분명한가?
5. `watch-suggest`, 구조 검토, shared definition, BANK Contract test 책임의 중복과
   공백은 무엇인가?
6. 불필요해진 양식·gate·수기 입력은 무엇이며 제거하면 어떤 신뢰를 잃는가?
7. Candidate activation branch와 구조 보완 branch의 안전한 통합 순서는 무엇인가?
8. 새 1.13.2 registration draft의 정식 승격 조건은 무엇인가?
9. 문서가 자동/사람, 전환용 첫 lock/이관 후 정식 lock, source-only/Runtime을
   구분하는가?
10. bundle·Docker·화면·조직 승인·운영 release 미완료를 과장하지 않는가?
11. 큰 버전 변경에서 이 검사기가 실질적인 위험 감소를 주는가?
12. merge 전 필수 수정과 merge 후 backlog를 명확히 분리할 수 있는가?

## 4. 최종 반례 완전성 감사

1~3차 표를 합쳐 다음을 확인한다.

- 모든 구현 주장에 정상·실패 반례가 하나 이상 있다.
- 모든 digest/SHA/승인 입력에 누락·위조·stale·불일치 반례가 있다.
- Git 경계, 파일 생성 동시성, schema 호환성, CLI/Phase 전파 반례가 있다.
- 발견된 모든 P0/P1에는 먼저 실패하는 회귀 test가 제안되어 있다.
- 해결됐다고 주장하는 P0/P1은 실제 추가 test와 수정 commit으로 확인된다.
- skip 38건이 이번 기능의 필수 반례를 건너뛰지 않는다.

확인하지 못한 범주는 “반례 없음”으로 쓰지 말고 검증 공백으로 기록한다.

## 5. 결과 형식

```text
1. 1~3차 결과 재판정
2. 사실 정정
3. 미해결 P0
4. 미해결 P1
5. P2·운영 backlog
6. 최종 반례 완전성 표
7. 실제 실행한 test 명령·exit code·통과·skip 수
8. 유지 / 단순화 / 폐기할 검사·양식 표
9. branch 통합 순서와 재실행 명령
10. 새 1.13.2 등록·postmerge 진입 조건
11. 최종 판정: merge 금지 / 조건부 merge / 구조 보완 branch 승인
```

P0/P1 또는 필수 반례 test 공백이 남으면 구조 보완 branch 승인을 선택하지 않는다.
수정은 하지 않는다.
