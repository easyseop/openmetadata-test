# OpenMetadata 공유문서 요구사항 정본

이 문서는 1차·2차·3차 공유문서와 최종 통합본을 만들 때 빠뜨리면 안 되는
사용자 요구사항을 모은 정본이다.

## 1. 대상 독자와 문장 원칙

- 대상은 처음 이 업무를 보는 경영진, 책임자, 비개발자와 개발자다.
- 비개발자용이라고 해서 실제 용어를 다른 비유로 바꾸지 않는다.
- 커스터마이징, repository, branch, commit, Manifest, API, test, Git commit
  SHA, digest처럼 업무에서 쓰는 용어는 유지하고 문장으로 뜻을 설명한다.
- 영수증, 요리, 레시피, 짐, 신호등처럼 코드와 무관한 비유를 사용하지 않는다.
- “제품”, “후보”, “현재”, “적용”처럼 대상이 여러 개일 수 있는 말은 정확한
  저장소나 코드 상태의 이름으로 바꾼다.
- BANK-OM ID, Git commit 메시지와 Git commit SHA를 명확히 구분한다.
- 구현 완료, 소스 테스트 완료, 행내 환경 대기, 실제 운영 실행 완료와 향후
  개발을 같은 상태로 보이게 만들지 않는다.

## 3. 1차 문서 필수 내용

### 목적과 저장소 역할

- `easyseop/OpenMetadata`는 행내 배포를 준비하는 OpenMetadata 제품 소스다.
- `easyseop/openmetadata-test`는 직원용 화면이 아니라 BANK-OM 변경관리표,
  검사기, 테스트 결과와 인수인계를 관리한다.
- 공식 저장소, 패치 브랜치, 커스터마이징 브랜치, 검사 후 배포 검토까지의 흐름을
  도식으로 보여준다.
- 공식 저장소의 화살표는 먼저 패치 브랜치로 이어져야 한다.
- 패치 브랜치와 커스터마이징 브랜치는 색으로 구분하되 글자가 도형 밖으로
  나가지 않게 한다.

### 사전 설정

- BANK-OM ID는 사용자가 정해진 양식으로 발급한다.
- ID의 종류(<code>kind</code>)에 넣을 수 있는 값을 설명한다.
- 커밋 명령 예시에는 `Customization-ID: BANK-OM-nnn` 항목을 보여준다.
- 변경관리표에서 `allowed_changed_paths`, `required_changed_paths`,
  `candidate_additional_paths`, `upgrade_watch`, 계약과 테스트의 역할을 설명한다.
- `allowed_changed_paths`, `required_changed_paths`, `upgrade_watch`는 변경관리표
  작성 단계 안에 속하도록 시각적으로 배치한다.
- 실제 BANK-OM-001 변경관리표와 실제 코드 파일을 연결해 보여준다.

### 실제 코드 관계

- `Entity.java`, `CollectionDAO.java`처럼 공식 원본에도 있는 공용 파일과
  `InstanceCodeResource.java`, `InstanceCodeMapper.java`처럼 커스터마이징으로
  추가하거나 변경한 구현 파일의 관계를 보여준다.
- 파일별 Git diff는 각 파일을 별도 펼치기로 나누고 왼쪽 공식 원본, 오른쪽 행내
  코드 형태로 보여준다.
- 추가된 줄은 초록색으로 표시한다.
- 파일 경로만 보여주지 말고 이 파일이 어떤 기능을 담당하며 다른 파일과 어떻게
  연결되는지 설명한다.
- 모든 BANK-OM ID를 한 화면에 나열할 필요는 없지만 BANK-OM-001이 전체
  커스터마이징 중 대표 사례라는 사실을 분명히 적는다.

### 현재 승인 상태

- 목적과 브랜치 전략은 사용자 검토를 통과했다.
- 1차 전체 HTML은 최종 통합 전 검토본이며 최종 승인본으로 표시하지 않는다.

## 4. 2차 문서 필수 내용

2차는 검사 결과표가 아니라 검사 방법 설명 문서다. 결과 라벨은 3차 실제 시연에서
보여준다.

각 검사기는 다음 네 항목을 설명한다.

1. 검사명
2. 무엇을 확인하는지
3. 실제로 어떤 파일·Git 기록·테스트 결과를 읽고 어떻게 판단하는지
4. 그 방법이 놓칠 수 있는 예외와 필요한 보완

검사기 설명 앞에서 다음 구분을 먼저 보여준다.

- Git 커밋·파일 경로·파일 상태를 검사하는 공통 계층은 프론트엔드와 백엔드,
  Java·TypeScript·Python·JSON·YAML·SQL 등 언어와 파일 형식에 상관없이 사용한다.
- 공통 계층은 각 커밋에서 바뀐 파일 경로와 공식 원본 대비 최종 파일 상태를
  확인한다. 파일 내부 코드의 의미와 실행 동작까지 언어에 관계없이 해석한다고
  설명하면 안 된다.
- 테스트 코드의 존재와 실행을 확인하는 계층은 언어·도구별 연결이 필요하다.
  현재 T60-I와 T61·T62는 Python pytest 연결을 사용하고 T63은 TypeScript
  전용이다.
- 공식 원본 이후의 커밋별 변경 파일과 공식 원본 대비 최종 파일 차이를 모두
  확인하지만, 저장소 경로 분류와 BANK-OM 변경관리표에 정확히 등록돼 있어야 한다.

반드시 답해야 하는 질문:

- T25-R에서 빈 줄 한 줄 차이는 어떻게 판단하는가?
- T25는 공식 원본 포함 여부를 Git에서 어떻게 증명하는가?
- T26은 특정 번호 범위를 쓰지 말고 “모든 활성 BANK-OM ID”라고 설명한다.
- T60-I가 확인하는 9개 업무 테스트의 대상, 현재 Python pytest만 확인하는
  이유와 Java JUnit·TypeScript Jest·`direct_tests`를 확인하지 못하는 한계를
  설명한다. 테스트 코드는 누가 언제 작성하고 등록하는지도 적는다.
- T30은 실제 Git 커밋 이력을 모두 읽는가?
- T40이 변경 범위 통제의 핵심인 이유와 파일 단위 검사의 한계는 무엇인가?
- T41은 AST 분석인지, 경로 분석인지, 무엇을 놓칠 수 있는가?
- T42가 `upgrade_watch`의 실제 검사 기능인지 설명한다.
- T43의 지표와 기준값, 충돌률 입력의 출처를 설명한다.
- T93은 실제 Git 이력과 변경관리표를 어떻게 비교하고 감시 규칙 노후화를 어떻게
  찾는가?
- T61·T62·T63·T90·T91도 같은 수준으로 실제 입력, 판단 방식과 예외를 설명한다.

## 5. 3차 실제 시연 필수 내용

3차는 다음 순서를 실제 화면으로 보여준다.

1. 커스터마이징이 포함된 현재 OpenMetadata 코드
2. 다음 공식 OpenMetadata 버전 지정
3. 공식 버전에 BANK-OM 커스터마이징 적용
4. BANK-OM 변경관리표와 Git 커밋 기록 확인
5. 검사기 실행
6. 검사 결과 생성
7. 책임자가 배포 가능, 담당자 검토 필요, 진행 중단을 판단

### 반드시 들어갈 실제 예시

- 공식 원본의 코드
- 커스터마이징으로 추가하거나 변경한 코드
- 새 공식 버전에 적용된 최종 코드
- 파일별 좌우 Git diff
- BANK-OM ID 발급 양식
- 실제 BANK-OM-001 변경관리표
- `git commit` 명령과 `Customization-ID:` 항목
- 실제 `git log`에서 BANK-OM ID가 보이는 화면
- 실제 검사기 실행 명령
- 실제 검사 결과 파일과 각 필드의 의미
- 각 검사 결과가 어떤 코드 버전과 연결됐는지 보여주는 commit SHA와 digest

### 검사 결과 표

최종 시연에서는 다음 형식을 사용한다.

| 검사명 | 검사 설명 | 실제 실행 내용 | 검사 결과 |
|---|---|---|---|
| T번호 | 무엇을 확인하는지 한 문장 | 어떤 명령과 입력을 사용했는지 | PASS·APPROVAL·PARTIAL·NOT RUN·ANALYSIS ERROR·BLOCK |

라벨은 색만으로 구분하지 않고 영어 라벨과 한국어 뜻을 함께 쓴다.

- PASS: 필요한 조건을 확인해 통과
- APPROVAL: 자동 통과할 수 없어 담당자 승인 필요
- PARTIAL: 전체 범위 중 일부만 완료
- NOT RUN: 필요한 버전이나 행내 환경이 없어 아직 실행하지 않음
- ANALYSIS ERROR: 검사할 근거가 부족하거나 입력을 신뢰할 수 없어 판단하지 않음
- BLOCK: 다음 단계로 진행하면 안 됨

### 현재 사실을 반영한 시연 결과

- 소스 검사는 통과한 항목을 실제 출력으로 보여준다.
- T42는 실제 다음 공식 버전으로 실행하지 않았으므로 통과로 표시하지 않는다.
- T43 충돌률은 실제 업그레이드 재적용 결과가 없으므로 승인 근거로 표시하지 않는다.
- T61은 2/5만 완료로 표시한다.
- T62는 실제 행내 실행 결과가 없으므로 NOT RUN으로 표시한다.
- T63은 기존 TypeScript 오류가 남아 있으므로 APPROVAL로 표시한다.
- T90·T91은 실제 실행 전이므로 NOT RUN으로 표시한다.
- 최종 운영 배포 판단은 BLOCK으로 표시한다.

### 화면 캡처 원칙

- 실제 코드, 실제 Git 기록과 실제 명령 결과를 캡처한다.
- 실제 실행하지 않은 화면을 실행 결과처럼 만들지 않는다.
- 설명을 위한 시뮬레이션 화면은 “설명용 시뮬레이션”이라고 명확히 표시한다.
- 책임자가 화면만 보고 검사 대상, 검사 방법, 결과, 남은 작업을 판단할 수 있어야
  한다.
- 캡처에는 비밀값, 행내 URL, 인증 토큰과 실제 고객·직원 데이터를 넣지 않는다.

현재 3차 초안은
`docs/00-사용가이드/공유문서/openmetadata-phase3-demo-preview.html`이다.
초안에는 실제 로컬 소스 검사 출력과 코드 예시를 화면 형태로 구성했으며, 실제
공식 업그레이드와 행내 실행 화면 캡처는 아직 포함하지 않았다.

## 6. 검사기 보완 사항을 3차와 향후 개발에 연결

- T41: 경로 검사에 정적 보안 분석과 보안 담당자 리뷰 추가
- T42·T93: 감시 파일 자동 제안과 민감 경로 규칙 노후화 검사 추가
- T43: 실제 재적용 결과에서 충돌률 자동 계산
- T60-I: Python 외 Java JUnit·TypeScript Jest 등록과 `direct_tests` 코드 존재 확인
- T61: 예상한 오류 종류와 메시지를 확인해 다른 원인의 실패를 제외
- T62·T63: 실행 환경 digest와 신뢰할 수 있는 실행 시스템 서명 추가
- T90·T91: 실제 로그, 결과 파일과 배포 digest의 서명·보관 추가

이 항목은 현재 완료된 기능처럼 쓰지 않는다. “추가 개발” 또는 “행내 운영
설정”으로 구분한다.
