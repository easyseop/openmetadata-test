# OpenMetadata 공유문서 요구사항 정본

이 문서는 1차·2차·3차·4차 공유문서와 최종 통합본을 만들 때 빠뜨리면 안 되는
사용자 요구사항을 모은 정본이다.

## 1. 대상 독자와 문장 원칙

- 대상은 처음 이 업무를 보는 경영진, 책임자, 비개발자와 개발자다.
- 비개발자용이라고 해서 실제 용어를 다른 비유로 바꾸지 않는다.
- 커스터마이징, repository, branch, commit, Manifest, API, test, Git commit
  SHA, digest처럼 업무에서 쓰는 용어는 유지하고 문장으로 뜻을 설명한다.
- 영수증, 요리, 레시피, 짐, 신호등처럼 코드와 무관한 비유를 사용하지 않는다.
- “제품”, “후보”, “현재”, “적용”처럼 대상이 여러 개일 수 있는 말은 정확한
  저장소나 코드 상태의 이름으로 바꾼다.
- BANK-OM ID, Git commit 메시지와 Git commit SHA를 명확히 구분한다.
- 구현 완료, 소스 테스트 완료, 행내 환경 대기, 실제 운영 실행 완료와 향후
  개발을 같은 상태로 보이게 만들지 않는다.

## 3. 1차 문서 필수 내용

### 목적과 저장소 역할

- `easyseop/OM_TEMP`는 현재 `1.13.0→1.13.1` 업그레이드와 검사를 재현하는
  OpenMetadata 제품 소스다.
- `easyseop/openmetadata-test`는 직원용 화면이 아니라 BANK-OM 변경관리표,
  검사기, 테스트 결과와 인수인계를 관리한다.
- 처음 분석할 때 사용한 `easyseop/OpenMetadata` 보관본은 현재 업그레이드
  흐름에 필요하지 않으므로 1차 공유문서의 저장소 역할 카드와 진행 절차에서
  제외한다. 기술 이력 보존이 필요하면 인수인계 문서에서만 확인한다.
- 공식 저장소, 패치 브랜치, 커스터마이징 브랜치, 검사 후 배포 검토까지의 흐름을
  도식으로 보여준다.
- 공식 저장소의 화살표는 먼저 패치 브랜치로 이어져야 한다.
- 패치 브랜치와 커스터마이징 브랜치는 색으로 구분하되 글자가 도형 밖으로
  나가지 않게 한다.

### 사전 설정

- BANK-OM ID는 사용자가 정해진 양식으로 발급한다.
- ID의 종류(<code>kind</code>)에 넣을 수 있는 값을 설명한다.
- 커밋 명령 예시에는 `Customization-ID: BANK-OM-nnn` 항목을 보여준다.
- 변경관리표에서 `allowed_changed_paths`, `required_changed_paths`,
  `candidate_additional_paths`, `upgrade_watch`, 계약과 테스트의 역할을 설명한다.
- `allowed_changed_paths`, `required_changed_paths`, `upgrade_watch`는 변경관리표
  작성 단계 안에 속하도록 시각적으로 배치한다.
- 실제 BANK-OM-001 변경관리표와 실제 코드 파일을 연결해 보여준다.

### 실제 코드 관계

- `Entity.java`, `CollectionDAO.java`처럼 공식 원본에도 있는 공용 파일과
  `InstanceCodeResource.java`, `InstanceCodeMapper.java`처럼 커스터마이징으로
  추가하거나 변경한 구현 파일의 관계를 보여준다.
- 파일별 Git diff는 각 파일을 별도 펼치기로 나누고 왼쪽 공식 원본, 오른쪽 행내
  코드 형태로 보여준다.
- 추가된 줄은 초록색으로 표시한다.
- 파일 경로만 보여주지 말고 이 파일이 어떤 기능을 담당하며 다른 파일과 어떻게
  연결되는지 설명한다.
- 모든 BANK-OM ID를 한 화면에 나열할 필요는 없지만 BANK-OM-001이 전체
  커스터마이징 중 대표 사례라는 사실을 분명히 적는다.

### 현재 승인 상태

- 목적과 브랜치 전략은 사용자 검토를 통과했다.
- 1차 전체 HTML은 최종 통합 전 검토본이며 최종 승인본으로 표시하지 않는다.

## 4. 2차 문서 필수 내용

2차는 검사 결과표가 아니라 검사 방법 설명 문서다. 현재 검사 결과 라벨은 3차에서
보여주고, 실제 Git 업그레이드 화면과 연결한 라벨은 4차에서 보여준다.

각 검사기는 다음 네 항목을 설명한다.

1. 검사명
2. 무엇을 확인하는지
3. 실제로 어떤 파일·Git 기록·테스트 결과를 읽고 어떻게 판단하는지
4. 그 방법이 놓칠 수 있는 예외와 필요한 보완

처음 보는 독자가 긴 표부터 읽지 않도록 다음 순서로 구성한다.

1. 검사기를 목적별 묶음으로 나눈 `검사기 지도`에서 ID·이름·한 줄 역할을 먼저
   보여준다.
2. 실제 검사 방법과 예외·보완은 검사기별 펼치기로 제공한다. 펼친 뒤에도
   `무엇을 확인하나 / 실제 검사 / 예외·보완`을 시각적으로 나눈다.
3. 입력·출력 전체 표는 별도 상세보기로 뒤에 둔다.
4. T번호는 이 문서의 목차 번호가 아니라 전체 개발 실행계획의 안정적인 태스크
   ID이므로 T01로 다시 매기지 않는다. 2차 문서는 전체 태스크 중 운영 판단에
   쓰는 검사기만 보여주기 때문에 T25-R·T25부터 보일 수 있음을 설명한다.

제목과 현재 상태는 다음 원칙을 따른다.

- 검사기 제목은 `공식 원본 포함`처럼 맥락 없는 명사형을 피하고, 독자가
  “무엇을 확인하는가”를 바로 알 수 있는 결과·질문형 이름으로 쓴다.
- 지도는 A 소스 기준, B 업그레이드 영향, C 테스트와 실행, D 승격과 배포로
  나누고 각 묶음에 `현재 사용 가능 / 제한적으로 사용 가능 / 부분 실행 /
  운영 미실행` 상태를 함께 표시한다.
- 초록 체크는 **구현됐고 현재 저장된 실제 결과까지 확인 가능한 검사기**에만
  붙인다. 초록 체크 자체가 PASS를 뜻하지 않으며 실제 결과는 PASS·APPROVAL·
  BLOCK일 수 있다.
- 구현 코드만 있고 실제 입력·실행 결과가 없는 검사기는 초록 체크를 붙이지
  않는다. `운영 적용 전에 우선 보완할 항목`에서 남은 입력·개발과 완료 기준을
  검사기별로 설명한다.
- 지도와 상세보기의 묶음은 같아야 한다. 특히 테스트 코드 존재를 확인하는
  T60-I는 C 묶음에 둔다.

검사기 설명 앞에서 다음 구분을 먼저 보여준다.

- Git 커밋·파일 경로·파일 상태를 검사하는 공통 계층은 프론트엔드와 백엔드,
  Java·TypeScript·Python·JSON·YAML·SQL 등 언어와 파일 형식에 상관없이 사용한다.
- 공통 계층은 각 커밋에서 바뀐 파일 경로와 공식 원본 대비 최종 파일 상태를
  확인한다. 파일 내부 코드의 의미와 실행 동작까지 언어에 관계없이 해석한다고
  설명하면 안 된다.
- 테스트 코드의 존재와 실행을 확인하는 계층은 언어·도구별 연결이 필요하다.
  현재 T60-I와 T61·T62는 Python pytest 연결을 사용하고 T63은 TypeScript
  전용이다.
- 공식 원본 이후의 커밋별 변경 파일과 공식 원본 대비 최종 파일 차이를 모두
  확인하지만, 저장소 경로 분류와 BANK-OM 변경관리표에 정확히 등록돼 있어야 한다.

반드시 답해야 하는 질문:

- T25-R에서 빈 줄 한 줄 차이는 어떻게 판단하는가?
- T25는 공식 원본 포함 여부를 Git에서 어떻게 증명하는가?
- T26은 특정 번호 범위를 쓰지 말고 “모든 활성 BANK-OM ID”라고 설명한다.
- T60-I가 확인하는 9개 업무 테스트의 대상, 현재 Python pytest만 확인하는
  이유와 Java JUnit·TypeScript Jest·`direct_tests`를 확인하지 못하는 한계를
  설명한다. 테스트 코드는 누가 언제 작성하고 등록하는지도 적는다.
- T30은 실제 Git 커밋 이력을 모두 읽는가?
- T40이 변경 범위 통제의 핵심인 이유와 파일 단위 검사의 한계는 무엇인가?
- T41은 AST 분석인지, 경로 분석인지, 무엇을 놓칠 수 있는가?
- T42가 `upgrade_watch`의 실제 검사 기능인지 설명한다.
- T43의 지표와 기준값, 충돌률 입력의 출처를 설명한다.
- T93은 실제 Git 이력과 변경관리표를 어떻게 비교하고 감시 규칙 노후화를 어떻게
  찾는가?
- T61·T62·T63·T90·T91도 같은 수준으로 실제 입력, 판단 방식과 예외를 설명한다.

## 5. 3차 검사 결과와 책임자 판정 필수 내용

3차는 현재 확보한 제품 소스·Manifest·Git 기록·로컬 검사 결과를 연결하고,
책임자가 각 라벨과 최종 배포 판단을 어떻게 읽는지 설명한다. 실제 Git 병합
화면 캡처는 4차에서 다룬다.

이 페이지는 이미 확보한 검사 증거를 읽고 `진행 가능 / 담당자 확인 /
중단`을 판단하는 **판정·보고 단계**다. 공식 버전을 올리거나 새 커스터마이징
후보를 만드는 실행 단계가 아니다.

1. 커스터마이징이 포함된 현재 OpenMetadata 코드 상태
2. BANK-OM-001 대표 코드 관계와 설명용 좌우 비교
3. BANK-OM 변경관리표와 Git 커밋 기록의 연결
4. 현재 실행 가능한 소스 검사 명령과 실제 결과
5. 미실행·부분 실행 검사를 포함한 전체 판정표
6. 책임자의 배포 가능, 담당자 확인 필요, 진행 중단 판단

### 반드시 들어갈 실제 예시

- 공식 원본의 코드
- 커스터마이징으로 추가하거나 변경한 코드
- 파일별 좌우 Git diff
- BANK-OM ID 발급 양식
- 실제 BANK-OM-001 변경관리표
- `git commit` 명령과 `Customization-ID:` 항목
- 실제 `git log`에서 BANK-OM ID가 확인되는 내용
- 실제 검사기 실행 명령
- 실제 검사 결과 파일과 각 필드의 의미
- 각 검사 결과가 어떤 코드 버전과 연결됐는지 보여주는 commit SHA와 digest

### 검사 결과 표

3차 판정표에서는 다음 형식을 사용한다.

| 검사명 | 검사 설명 | 실제 실행 내용 | 검사 결과 |
|---|---|---|---|
| T번호 | 무엇을 확인하는지 한 문장 | 어떤 명령과 입력을 사용했는지 | PASS·APPROVAL·PARTIAL·NOT RUN·ANALYSIS ERROR·BLOCK |

라벨은 색만으로 구분하지 않고 영어 라벨과 한국어 뜻을 함께 쓴다.

- PASS: 필요한 조건을 확인해 통과
- APPROVAL: 자동 통과할 수 없어 담당자 승인 필요
- PARTIAL: 전체 범위 중 일부만 완료
- NOT RUN: 필요한 버전이나 행내 환경이 없어 아직 실행하지 않음
- ANALYSIS ERROR: 검사할 근거가 부족하거나 입력을 신뢰할 수 없어 판단하지 않음
- BLOCK: 다음 단계로 진행하면 안 됨

### 현재 사실을 반영한 검사 결과

- 소스 검사는 통과한 항목을 실제 출력으로 보여준다.
- T42는 OM_TEMP 1.13.0→1.13.1 실제 영향 결과가 있으므로 결과를 보여주되,
  영향 경로가 발견된 `APPROVAL`로 표시한다. 자동 통과로 쓰지 않는다.
- T43 충돌률은 실제 업그레이드 재적용 결과가 없으므로 승인 근거로 표시하지 않는다.
- T61은 2/5만 완료로 표시한다.
- T62는 실제 행내 실행 결과가 없으므로 NOT RUN으로 표시한다.
- T63은 기존 TypeScript 오류가 남아 있으므로 APPROVAL로 표시한다.
- T90·T91은 실제 실행 전이므로 NOT RUN으로 표시한다.
- 최종 운영 배포 판단은 BLOCK으로 표시한다.

현재 3차 초안은
`docs/00-사용가이드/공유문서/openmetadata-phase3-demo-preview.html`이다.
초안에는 실제 로컬 소스 검사 출력과 코드 예시를 설명용 화면 형태로 구성했다.

## 6. 4차 실제 Git 업그레이드 시연 필수 내용

4차는 3차를 확정한 뒤 실제 Git 화면을 캡처해 다음 순서를 보여준다.

이 페이지는 새 공식 버전 위에 BANK-OM commit을 실제로 다시 적용하고 충돌을
해결해 새 `custom` commit과 검사 증거를 만드는 **실행·증거 생성 단계**다.
따라서 앞 페이지의 책임자 판정과 역할이 다르다.

1. 병합 전 기존 공식 버전, 업그레이드 대상 공식 버전과 커스터마이징 branch 확인
2. 공식 버전 간 Git diff와 기존 공식 원본 대비 커스터마이징 Git diff 확인
3. 시연이 끝나면 삭제할 임시 upgrade branch에서 실제 병합·재적용 실행
4. 충돌 파일, 충돌 해결 commit과 최종 Git graph 확인
5. 새 공식 버전 대비 최종 커스터마이징 Git diff 확인
6. 검사기 실행 명령과 실제 출력 확인
7. 병합 결과와 검사 결과를 한 표에서 라벨링

### 업그레이드 반복 테스트

- 장기 보관하는 `candidate/...` branch는 만들지 않는다. 검사기는
  `custom/...` branch의 정확한 Git commit SHA와 digest를 결과에 기록하고,
  통과한 상태는 `verified/...` tag로 보존한다.
- 임시 upgrade branch는 충돌 발생·해결 과정을 재현하기 위한 작업 공간이며,
  검사 결과와 `verified/...` tag를 보존한 뒤 삭제할 수 있다.
- 현재 시연 범위는 `1.13.0→1.13.1` 한 구간이다. 먼저 공식 1.13.0
  구조에 맞춰 BANK-OM-001~007을 재구현하고 검사한 뒤, 같은 BANK-OM commit을
  공식 1.13.1 기준에 재적용해 충돌·보완·재검사 과정을 확인한다.
- 1.12.x 구간은 이번 시연에서 제외한다. 1.13.1 기준 commit을 과거 구조에
  역방향 적용하면 실제 순방향 업그레이드보다 충돌이 과장되기 때문이다.
- 이 시연은 실제 과거 운영 이력이 아니라 검사기와 브랜치 전략의 반복
  검증이라고 표시한다.

### 화면 캡처 원칙

- 실제 코드, 실제 Git 기록, 실제 병합 명령과 실제 검사 결과를 캡처한다.
- 실제 실행하지 않은 화면을 실행 결과처럼 만들지 않는다.
- 병합 결과와 검사 결과를 분리하지 말고 같은 구간·같은 commit SHA로 연결한다.
- 각 구간에 PASS·APPROVAL·PARTIAL·NOT RUN·ANALYSIS ERROR·BLOCK 라벨을 붙인다.
- 책임자가 화면만 보고 병합 대상, 변경 파일, 병합 결과, 검사 결과와 남은 작업을
  판단할 수 있어야 한다.
- 캡처에는 비밀값, 행내 URL, 인증 토큰과 실제 고객·직원 데이터를 넣지 않는다.
