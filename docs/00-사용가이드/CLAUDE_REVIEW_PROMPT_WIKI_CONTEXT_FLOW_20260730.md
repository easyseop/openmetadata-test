# Claude 검토 요청 — 운영 위키의 이해 가능성·맥락·논리 흐름

## 검토 목적

첨부한 HTML은 OpenMetadata 커스터마이징 변경을 등록하고 검사하는 운영 위키와
그 근거가 된 보고용·실행용 가이드입니다.

이번 검토의 목적은 기술 구현을 칭찬하거나 문장을 단순 교정하는 것이 아닙니다.
처음 이 업무를 맡은 직원이 문서를 **목차 순서대로 그대로 읽을 때** 다음 문제가
있는지 찾는 것입니다.

- 앞에서 설명하지 않은 개념이 갑자기 나오는가?
- 독자가 “왜 이 단계가 필요한가?”, “누가 하는가?”, “무엇이 자동인가?”라고
  다시 물어야만 다음 단계로 갈 수 있는가?
- 설명 순서가 실제 업무 순서와 어긋나는가?
- 앞뒤 문장이 논리적으로 이어지지 않거나 중간 전제가 빠졌는가?
- 같은 개념을 여러 페이지에서 서로 다르게 설명하는가?
- 요약 페이지와 상세 페이지의 의미·범위·구현 상태가 다른가?
- 명령·예시·결과 예시가 설명한 동작을 실제로 보여 주지 못하는가?

대상 독자는 **컴퓨터공학과 1학년 수준의 기본 Git 지식만 있고 이 시스템은 처음
보는 신입 운영자**로 가정해 주세요. 쉬운 표현을 쓰되 요리·영수증 같은 뜬금없는
비유로 바꾸지 말고, Manifest·커스터마이징·브랜치처럼 현업에서 일반적으로 쓰는
용어는 유지해야 합니다.

## 읽는 순서

### 1. 주 검토 문서

먼저 아래 단독 HTML을 왼쪽 목차의 번호 순서대로 처음부터 끝까지 읽어 주세요.

- `00_WIKI_STANDALONE.html`

이 파일은 위키 데이터와 보고용 페이지를 포함한 단독 검토본입니다. 검토 결과의
주 위치는 이 파일의 목차 번호와 화면 제목으로 적어 주세요.

### 2. 교차 확인 문서

그다음 나머지 HTML을 읽어 같은 개념이 다르게 설명됐는지 확인해 주세요.

- `01_WIKI_SOURCE.html`: 위키 원본
- `02_PHASE1_BRANCH_STRATEGY_PREVIEW.html`: 목적·브랜치 전략 요약
- `03_PHASE2_VERIFIERS_PREVIEW.html`: 검사기 원리 요약
- `04_PHASE3_DEMO_PREVIEW.html`: 시연·결과 요약
- `05_MANIFEST_REGISTRATION_GUIDE.html`: Manifest 등록 가이드
- `06_UPGRADE_EXECUTION_GUIDE.html`: 업그레이드 실행 가이드
- `07_MANAGEMENT_FIELD_DICTIONARY_PREVIEW.html`: 관리 파일 필드 사전
- `08_LEGACY_DEMO_WALKTHROUGH.html`: 과거 통합 시연본
- 이름에 `FRAGMENT`가 붙은 파일: 위 보고용 페이지를 만든 구성 요소입니다.
  단독 문서처럼 평가하지 말고 preview·위키에 포함된 내용과 다른지만 확인해
  주세요.

## 반드시 검토할 관점

### A. 문장 단위 이해 가능성

각 설명 문장 또는 의미가 이어지는 두 문장을 읽고 아래를 확인해 주세요.

1. 주어와 행위자가 분명한가?
2. “이것”, “이 규칙”, “해당 값”, “기준”, “대상”이 무엇을 가리키는지
   하나로 확정되는가?
3. 한 문장이 자동 처리와 사람 판단을 섞어 쓰지 않았는가?
4. “갱신한다”, “생성한다”, “검사한다”가 어떤 파일·값·명령을 뜻하는가?
5. 생략한 전제 때문에 두 명의 독자가 서로 다르게 이해할 가능성이 있는가?
6. 첫 등장 용어가 그 문장 또는 바로 앞에서 설명됐는가?
7. 기술적으로 맞더라도 처음 읽는 직원이 다시 질문해야 이해할 문장인가?

문제가 없다는 총평만 하지 말고, 문제가 있는 **원문 일부와 정확한 위치**를
인용해 주세요.

### B. 맥락과 배치 순서

각 장을 읽은 뒤 다음 질문에 답해 주세요.

1. 이 장을 이해하기 전에 반드시 알아야 할 내용이 앞 장에 있는가?
2. 결과를 먼저 보여 주고 입력이나 목적을 뒤에서 설명하는 곳은 없는가?
3. 개념 설명 → 입력 → 자동 처리 → 사람 승인 → 출력 → 실패 대응 → 보관
   순서가 필요한 절차에서 중간 단계가 빠지지 않았는가?
4. 같은 설명을 합쳐야 더 명확한 곳은 어디인가?
5. 한 페이지가 너무 많은 목적을 다루므로 나눠야 하는 곳은 어디인가?
6. 다른 장으로 옮겨야 흐름이 자연스러운 단락은 어디인가?

순서 변경을 제안할 때는 반드시
`현재 위치 → 권장 위치 → 먼저 읽어야 할 이유` 형식으로 적어 주세요.

### C. 설명·예시 부족

독자가 아래 질문을 할 가능성이 있는 모든 지점을 찾으세요.

- 왜 필요한가?
- 언제 만들고 언제 그대로 두는가?
- 누가 입력하고 누가 승인하는가?
- 무엇이 자동이고 무엇이 수동인가?
- 어떤 입력 파일·명령이 필요한가?
- 실행하면 어떤 파일이나 결과가 생기는가?
- 결과가 PASS·BLOCK·APPROVAL이면 다음에 무엇을 하는가?
- 기존 BANK-OM ID의 후속 commit과 새 ID는 어떻게 구분하는가?
- 새 commit이 생기면 Manifest·Registry·Contract·Candidate lock 가운데
  무엇이 자동 갱신되고 무엇을 사람이 판단하는가?
- 동일한 파일 내용 수정과 새 파일 추가는 처리 방식이 어떻게 다른가?

설명이 부족하다고만 쓰지 말고, 필요한 보완 내용을 다음 중 하나로 제안해 주세요.

- 한 문장 정의
- 입력/자동 처리/사람 판단/출력 표
- 실제 명령 예시
- 변경 전·후 예시
- PASS·BLOCK·APPROVAL 결과와 다음 행동 예시
- 실패 후 복구 절차

### D. 용어의 첫 등장과 일관성

다음 용어는 특히 엄격하게 확인해 주세요.

- 제품 코드 저장소 / 검사기 저장소
- patch 브랜치 / custom 브랜치 / 검사기 저장소 작업 브랜치
- BANK-OM ID / Git commit SHA / 최종 검사 대상 commit
- Manifest / Registry / Contract
- `changed_paths` / `required_changed_paths` / `upgrade_watch.paths`
- `series.allowed`
- plan / 승인 / apply
- Candidate lock / Release lock
- 자동 생성 파일 / 사람이 결정하는 정책값
- 검사기 ID(T25, T30, T42 등)와 그 검사가 답하는 실제 질문

`저장소`처럼 둘 이상의 대상을 가리킬 수 있는 단어는 역할명이 붙었는지,
`브랜치`처럼 종류가 여러 개인 단어는 어느 브랜치인지 명시됐는지 확인하세요.
설명 문장에서는 `저장소`와 `레포지토리`를 섞어 쓰지 않아야 합니다. 단,
`repository-layout.yaml`, `source.repository` 같은 실제 파일명·필드명은
바꾸라는 지적을 하지 마세요.

### E. 자동화 범위와 구현 상태

문서가 아래 경계를 일관되게 설명하는지 확인해 주세요.

- 개발자가 commit 본문에 BANK-OM ID를 기록하고 plan을 실행한다.
- plan은 commit SHA와 실제 변경 경로를 찾아 변경안을 만든다.
- plan 단계에서는 실제 등록 파일을 바꾸지 않는다.
- `series.allowed`, 필수 파일, watch, Contract, 담당자 등 업무 판단은 사람이
  검토·승인한다.
- apply는 승인된 변경안만 관리 파일에 반영한다.
- 소스 검사를 실행하면 검사 대상 최종 commit과 파일 상태로 Candidate lock이
  계산되어 결과에 기록된다.
- 새 ID 발급 여부와 충돌 코드의 최종 선택은 자동으로 확정하지 않는다.
- 구현 완료, 추가 개발, 현재 환경에서 실행하지 못한 항목을 같은 상태처럼
  표현하지 않는다.

위 경계와 다른 문장을 발견하면
`문서의 주장 → 다른 문서 또는 같은 문서의 상충 문장 → 독자가 할 오해`를
나란히 적어 주세요.

### F. 요약과 상세의 대응

보고용 요약과 위키 상세가 서로 대응하는지 확인해 주세요.

- 1차 브랜치 도식의 각 단계가 상세 브랜치·업그레이드 설명에 있는가?
- 2차 검사기 목록의 각 검사가 상세 검사 페이지와 같은 입력·판정을 설명하는가?
- 3차 시연의 코드·Manifest·검사 결과가 상세 등록·증거 설명과 연결되는가?
- 사전환경 설정, 업그레이드, 충돌 해결, 배포 승인 흐름이 하나의 업무
  이야기로 이어지는가?

같은 개념인데 그림·표·본문이 다르게 말하면 어느 쪽을 기준으로 통일할지
이유와 함께 제안해 주세요.

### G. 중복·삭제·분리 판단

반복이 모두 나쁜 것은 아닙니다. 요약과 상세의 의도적인 반복은 유지할 수
있습니다. 다음 기준으로 분류해 주세요.

- `유지`: 요약과 상세의 역할이 분명한 반복
- `합치기`: 같은 수준에서 같은 설명을 반복
- `삭제`: 더 정확한 설명이 이미 있고 흐름만 끊는 문장
- `이동`: 필요한 내용이지만 현재 위치가 잘못됨
- `분리`: 한 단락에 서로 다른 목적이 섞임

## 하지 말아야 할 검토 방식

- “전반적으로 잘 작성됐다” 같은 총평으로 끝내지 마세요.
- 기술 용어가 있다는 이유만으로 무조건 쉬운 비유로 바꾸지 마세요.
- 문서에 없는 구현 상태·실행 결과·승인 완료를 추측하지 마세요.
- fragment의 레이아웃 차이를 별도 기능 차이로 오해하지 마세요.
- 모든 문장을 짧게 줄이는 것을 목표로 삼지 마세요. 이해에 필요한 설명과
  예시는 남겨야 합니다.
- 문법·맞춤법 문제는 의미나 흐름을 방해할 때만 우선 항목에 넣으세요.

## 답변 형식

### 1. 읽기 흐름 진단

| 현재 순서 | 이해가 끊기는 지점 | 독자가 먼저 알아야 할 내용 | 권장 위치·순서 |
|---|---|---|---|

### 2. 문장·설명 문제

| 우선순위 | HTML·목차 위치 | 원문 일부 | 독자가 할 질문·오해 | 부족한 설명 | 권장 수정 방향 |
|---|---|---|---|---|---|

우선순위는 다음 기준을 사용해 주세요.

- `치명적`: 절차를 잘못 실행하거나 자동/수동 범위를 반대로 이해할 수 있음
- `높음`: 다음 단계로 진행할 수 없거나 같은 개념을 다르게 이해함
- `보통`: 재질문이 필요하지만 앞뒤를 찾아보면 이해할 수 있음
- `낮음`: 가독성·표현 개선

### 3. 같은 개념의 불일치

| 개념 | 문서 A의 설명 | 문서 B의 설명 | 차이로 생기는 오해 | 통일 기준 |
|---|---|---|---|---|

### 4. 중복·구조 조정

| 위치 | 유지/합치기/삭제/이동/분리 | 이유 | 구체적인 조정안 |
|---|---|---|---|

### 5. 부족한 예시

| 위치·개념 | 현재 설명만으로 부족한 이유 | 추가할 예시 형식 | 예시에 반드시 들어갈 값 |
|---|---|---|---|

### 6. 장별 판정

0장부터 6장까지 각각 아래 형식으로 적어 주세요.

- 이 장이 답하는 질문
- 현재 답하지 못하는 질문
- 앞 장에서 알아야 할 내용
- 다음 장으로 자연스럽게 연결되는지
- 신입 운영자가 이 장만 보고 수행할 수 있는 범위

### 7. 최종 판정

다음 셋 중 하나를 선택하고 근거를 적어 주세요.

- `공유 가능`: 중대한 이해·순서 문제가 없음
- `수정 후 공유`: 명시한 치명적·높음 항목을 먼저 수정해야 함
- `구조 재검토`: 장 순서나 요약·상세 관계를 다시 설계해야 함

마지막에 **가장 먼저 고칠 10개 항목**을 실제 수정 순서대로 정리해 주세요.
