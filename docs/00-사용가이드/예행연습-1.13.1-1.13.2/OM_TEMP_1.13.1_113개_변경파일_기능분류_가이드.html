1. 분류 기준

비교 기준branchGit commit SHA
공식 기준 코드official/om-1.13.1e6199070…

Git은 변경 파일 113개를 자동으로 찾습니다. 그러나 각 변경 파일을 어떤 BANK-OM 커스터마이징 ID에 연결할지는 자동 결정하지 않으며 사용자가 승인합니다.

이 문서에서 구분하는 네 가지 대상

용어의미예시
BANK-OM 커스터마이징 ID하나의 커스터마이징 업무 단위를 계속 추적하는 관리번호BANK-OM-001
업무 기능명해당 BANK-OM 커스터마이징 ID가 제공하는 동작의 이름InstanceCode
Git commit SHA특정 시점의 코드 변경 묶음을 Git이 식별하는 값59dae915…
변경 파일official branch와 custom branch를 비교했을 때 내용이 다른 파일Entity.java
이 문서의 분류 대상은 Git commit SHA가 아니라 113개 변경 파일입니다. 각 변경 파일을 BANK-OM-001~007 중 어느 커스터마이징 ID에 연결할지 확인합니다.
현재 등록 범위 — 과거 재구성 과정에서 만든 BANK-OM-008~011은 이번 1.13.1 등록 대상에서 제외합니다. 이 문서의 분석·승인·완료 조건은 BANK-OM-001~007만 대상으로 합니다.

2. 자동 분석 결과

기존 kb-openmetadata 등록자료는 분류 참고자료로만 사용했습니다. 이번 1.13.1 등록자료는 아직 생성하지 않았습니다.
변경 파일 분류고유 파일 수의미
하나의 BANK-OM 커스터마이징 ID에만 연결747개 ID 중 하나에만 연결됩니다.
둘 이상의 BANK-OM 커스터마이징 ID에 연결된 공용 파일37한 파일에 여러 커스터마이징의 코드가 함께 있습니다.
BANK-OM-001~007 중 어느 ID에도 미연결2이번 등록에서 제외하기로 결정한 파일입니다.
전체 변경 파일11374 + 37 + 2

74개와 37개는 서로 겹치지 않는 고유 변경 파일 수입니다. 37개 공용 파일은 관련된 각 BANK-OM 커스터마이징 ID에서 다시 표시됩니다. 미등록 2개를 제외하면 BANK-OM 등록 대상은 111개입니다.

BANK-OM 커스터마이징 ID업무 기능명전체 연결 파일해당 ID 전용다른 ID와 공용대표 근거
BANK-OM-001InstanceCode481632schema·Resource·Repository·UI
BANK-OM-002QueryReport552332schema·Resource·Repository·UI
BANK-OM-003Data Assertions25421페이지·API·MyData UI
BANK-OM-004은행 컬럼 확장 표시331419SchemaTable·검색·Entity 유틸리티
BANK-OM-005한글 IME 보정110SchemaEditor 입력 처리
BANK-OM-006Sybase18135schema·아이콘·서비스 UI
BANK-OM-007Tibero835schema·아이콘·서비스 UI

공용 변경 파일은 관련된 각 BANK-OM 커스터마이징 ID에 반복 집계되므로 전체 연결 파일 열을 합산하지 않습니다.

Tibero 경로 권장안 — BANK-OM-007은 8개 경로 그대로 유지합니다. 추가 후보였던 serviceConnection.ts와 DatabaseServiceUtils.test.tsx의 실제 diff에는 Sybase 코드만 있고 Tibero 코드는 없으므로 Tibero에 연결하지 않습니다.

공용 변경 파일 예시

변경 파일 경로함께 연결되는 BANK-OM 커스터마이징 ID공용인 이유
.../mysql/schemaChanges.sql001·002두 entity의 DB 변경이 같은 migration에 기록됨
.../service/Entity.java001·002두 신규 entity를 공통 등록함
.../AuthenticatedAppRouter.tsx001·002·003세 업무 기능의 화면 경로를 같은 router에 등록함
.../locale/languages/ko-kr.json001·002·003·004네 업무 기능의 번역 항목이 같은 파일에 기록됨
.../databaseService.json006·007두 DB 서비스를 같은 목록에 등록함
공용 변경 파일 승인이 필요한 이유 — 공용 파일은 한 개의 물리적 파일 안에 둘 이상의 BANK-OM 커스터마이징 코드가 함께 있습니다. 파일을 여러 번 복사하는 것이 아니라, 공용 경로 관리자료에 실제 관련 ID를 모두 기록합니다. 이 연결이 빠지면 업그레이드 재구성 과정에서 다른 ID의 코드가 누락될 수 있습니다. 검사기는 공용 경로 관리자료가 실제 다중 연결 관계와 다르면 SHARED_OWNER_MAP_MISMATCH로 중단합니다.
권장안 — 37개 공용 변경 파일을 현재 분석표에 기록된 모든 관련 ID에 연결합니다. 하나의 대표 ID에만 임의 배정하지 않습니다.

공용 경로 연결만으로 부족한 부분과 보완 검사

shared-path-owners.yaml은 한 파일을 어떤 BANK-OM 커스터마이징 ID가 함께 사용하는지 확인합니다. 그러나 파일을 001과 002에 연결해도 최종 파일에 001 코드만 남을 수 있습니다.

새 관리파일 — shared-code-definitions.yaml의 정식 명칭은 공용 파일 ID별 코드 정의입니다. Java 변수명만 기록하지 않고 Java·TypeScript·TSX·SQL의 실제 코드 조각과 JSON·YAML의 실제 경로·값을 ID별로 기록합니다.
schema_version: 1
definitions:
  - path: openmetadata-service/src/main/java/org/openmetadata/service/Entity.java
    customization_id: BANK-OM-001
    assertions:
      - id: instance-code-constant
        matcher: code_fragment
        fragment: |
          public static final String INSTANCE_CODE = "instanceCode";
  - path: openmetadata-service/src/main/java/org/openmetadata/service/Entity.java
    customization_id: BANK-OM-002
    assertions:
      - id: query-report-constant
        matcher: code_fragment
        fragment: |
          public static final String QUERY_REPORT = "queryReport";
구분자동 처리사용자 확인
초안 생성공용 경로와 BANK-OM ID 조합을 모두 생성없음
실제 정의 작성자동 추측하지 않음실제 diff에서 전체 코드 조각 또는 JSON·YAML 경로와 값을 선택
검사주석·공백을 제외한 코드 토큰 또는 구조화 값을 최종 custom commit과 비교불일치가 의도된 변경인지 확인
결과형식·ID 연결 누락은 ANALYSIS_ERROR, 승인한 정의 누락·값 불일치는 BLOCK수정 후 같은 검사 재실행

주석에 QUERY_REPORT 이름만 적혀 있거나 실제 상수 값이 "wrong"이면 통과하지 않습니다. 실제 생성·검색 동작은 Contract test가 별도로 확인합니다.

현재 상태 — 검사 코드와 단위 테스트는 구현됐습니다. 실제 1.13.1 등록용 파일은 아직 만들지 않았으며, 다음 Manifest 정의 단계에서 실제 diff를 함께 확인한 뒤 작성·승인합니다.

3. 미등록 경로 처리 결정

결정 완료 — 아래 2개 경로는 어느 BANK-OM 커스터마이징 ID에도 연결하지 않고 이번 등록에서 제외합니다.
두 파일은 현재 source snapshot의 113개 변경 파일에는 포함되지만 BANK-OM 등록 대상에는 포함되지 않습니다. 따라서 등록 대상은 111개입니다. 이후 재구성할 custom candidate에서는 두 파일을 official branch와 같은 내용으로 유지해야 하며, 검사기는 제외 경로가 official branch와 다르면 중단합니다.

3-1. .claude/settings.json

변경 성격Claude Code 개발 도구 권한과 자동 승인 설정
결정BANK-OM 등록 대상에서 제외
이유OpenMetadata 제품 기능 코드가 아니며 제품 커스터마이징 운영에 필요하지 않음
다음 코드 처리최종 custom candidate에서는 official branch의 파일 내용으로 복원

3-2. docker/development/docker-compose.yml

변경 성격로컬 개발용 ingestion image를 openmetadata/ingestion:1.9.6으로 바꾸는 설정
결정BANK-OM 등록 예외 경로로 제외
이유BANK-OM-001~007의 업무 기능과 직접 연결되지 않고 OpenMetadata 1.13.1과 다른 ingestion 버전을 사용할 위험이 있음
다음 코드 처리최종 custom candidate에서는 official branch의 파일 내용으로 복원
예외 처리의 정확한 의미 — 파일을 현재 내용 그대로 두고 검사만 생략한다는 뜻이 아닙니다. Manifest에는 등록하지 않으며, 최종 custom candidate에서는 official branch와 같은 내용이어야 합니다. 과거 source snapshot에 해당 변경이 있었다는 사실은 source inventory와 Git 이력에 남습니다.

4. 변경 파일 목록 확인 명령

수행 내용 — official·custom 사이의 전체 변경 경로와 변경 유형을 출력합니다.

git -C ~/om-work/om-temp-real-1.13.1 diff --name-status official/om-1.13.1 custom/om-1.13.1

예상 결과 — 113개 경로가 표시됩니다. 현재 기준은 기존 파일 수정 M 70개와 새 파일 추가 A 43개입니다.

중단 조건 — 113개가 아니거나 D가 표시되면 변경 파일과 BANK-OM 커스터마이징 ID 연결 작업을 중단하고 branch 검증 단계로 돌아갑니다.

왜 남은 두 항목을 승인해야 하는가

항목승인이 필요한 이유잘못 결정했을 때의 우려
7개 ID 유지Git은 파일 차이를 찾을 수 있지만 어떤 변경들이 하나의 업무 기능인지 결정하지 못합니다.서로 다른 기능을 합치면 한 기능만 제거·업그레이드·검증하기 어려워지고 Contract 연결도 불명확해집니다.
37개 공용 경로의 다중 연결한 파일 안에 여러 ID의 symbol·JSON key·route·SQL block이 함께 있어 실제 관련 ID를 모두 확정해야 합니다.한 ID에만 독점 배정하면 다른 ID의 코드가 업그레이드 재구성에서 누락될 수 있습니다. 연결표가 실제 관계와 다르면 검사기가 중단합니다.
최종 권장안 — BANK-OM-001~007을 유지하고, 공용 변경 파일 37개는 현재 분석된 모든 실제 관련 ID에 연결합니다.

7. 다음 단계

  1. 남은 두 승인 항목을 확정합니다.
  2. .claude/settings.json과 docker/development/docker-compose.yml을 official branch 내용으로 복원하는 code commit을 준비합니다.
  3. 복원 후 official·custom 차이가 등록 대상 111개인지 다시 확인합니다.
  4. 승인된 7개 ID와 공용 경로 연결표를 입력으로 Manifest·Registry·Contract 초안을 생성합니다.
  5. 같은 단계에서 shared-code-definitions.yaml의 경로·ID 초안을 자동 생성하고 실제 diff를 보며 ID별 코드 정의를 함께 채웁니다.
  6. Registry가 코드 정의파일을 사용하도록 선언한 뒤 준비도구의 plan을 실행합니다. 이 파일도 승인 digest에 포함되므로 승인 후 바뀌면 apply가 중단됩니다.
이 문서에서는 아직 code commit이나 등록자료를 만들지 않습니다. 다음 단계에서 명령과 결과를 별도 가이드로 안내합니다.
