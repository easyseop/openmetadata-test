별도 branch에서 개발한 검사기로 반복 작업을 묶으면 7단계로 보인다는 비교 화면입니다. 구현 기준 commit은 6079aaff4d1b227df699d3f67262d60a96cd6b07입니다. 실제 OM_TEMP 예행연습에 적용하거나 승인한 상태가 아닙니다.

1. 원본 11단계를 통합한 7단계 초안

여러 페이지를 없앤다는 뜻이 아니라, 한 번의 업무 흐름에서 함께 준비·검사할 수 있는 항목을 하나의 실행 단계로 묶은 모습입니다. 각 카드에는 원본 몇 단계가 합쳐졌는지 표시했습니다.

원본 페이지 보존 통합 실행·자동 확인 사람이 판단·실행 실제 적용 안 함
1

작업환경과 1.13.1 기준 branch 확인

원본 1~2단계를 묶습니다. Git·접근 권한·작업 폴더를 준비하고 official/om-1.13.1과 custom/om-1.13.1을 확인합니다.

원본 1~2단계 통합환경과 branch는 사람이 준비합니다. 검사기가 저장소를 임의로 만들거나 수정하지 않습니다.
2

BANK-OM 코드와 등록자료 준비

원본 3~5단계를 묶습니다. 111개 등록 경로를 BANK-OM ID에 연결하고 ID별 commit과 Manifest·Registry·Contract 초안을 준비합니다.

원본 3~5단계 통합Git이 경로·commit 후보를 계산할 수 있지만, 업무 기능·필수 경로·담당자·Contract 기준은 사람이 결정합니다.
3

1.13.1 기준선 승인과 자동 검증

원본 6~7단계를 묶습니다. 판정 의미를 화면에서 바로 안내하고, 등록 승인·apply·기준 검사 뒤 활성 기준선을 선택합니다.

통합 실행: candidate-select승인된 1.13.1 Candidate lock이 활성 기준선과 정확히 같은지 확인합니다. 승인 판단은 자동화하지 않습니다.
4

공식 1.13.2 준비와 병합 전 검사

원본 8단계를 하나의 실행 묶음으로 만듭니다. 공식 tag·commit을 고정하고 BANK-OM 영향과 민감 경로를 검사합니다.

통합 실행: prep-official → phase-preflight → premerge-check누락 입력을 한 번에 보여주고, 공식 코드와 병합 전 검사 결과를 같은 SHA에 결속합니다.
5

vendor merge와 충돌 해결

원본 9단계입니다. 직전 custom 코드와 공식 1.13.2를 병합하고 충돌 코드를 검토·수정합니다.

독립 단계 유지검사기가 코드를 병합하거나 충돌 해결안을 승인하지 않습니다. 담당자는 병합 전 custom SHA, 충돌 경로와 해결 commit을 보관합니다.
6

1.13.2 종합 검사와 승인 판단

원본 10단계의 소스·공용 코드·build·Contract test·보고서 확인을 하나의 결과 흐름으로 묶습니다.

통합 실행: candidate-select → phase-preflight → postmerge-check → phase-status병합 입력과 충돌 재현, Candidate SHA, build artifact digest, Runtime 결과와 3단 보고서 무결성을 확인합니다.
7

검증 tag와 release branch 고정

원본 11단계입니다. 승인한 동일 commit을 tag·release branch·release lock으로 고정합니다.

독립 단계 유지phase-status가 통과해도 tag 생성이나 운영 배포를 자동 실행하지 않습니다. 조직 승인과 원본 완료 조건을 따릅니다.

가이드 5 · vendor merge와 충돌 해결

원본 9 유지코드 판단은 사람 작업

반드시 넣을 내용

  • 병합 방향: 직전 1.13.1 custom head와 공식 1.13.2 target
  • custom_head_sha는 승인된 1.13.1 기준선 Candidate commit과 정확히 같아야 합니다. fix commit이 있으면 먼저 새 기준선으로 등록·승인합니다.
  • 순서 1: vendor merge를 실행하고 충돌 코드를 해결·test한 뒤 해결 commit을 만듭니다.
  • 순서 2: 최종 1.13.2 Candidate SHA의 새 Candidate lock을 작성·승인·활성화하고 candidate-select를 실행합니다.
  • 순서 3: python harness/om_workflow.py collect-conflict-evidence --repo <제품저장소> --version 1.13.1 --baseline-lock-digest <digest> --custom-head <SHA> --output <증거.yaml>로 자동 수집합니다.
  • 순서 4: 생성된 증거를 phase-preflight와 postmerge-check에 전달합니다.
  • 수집기는 rename 탐지를 비활성화한 결정적 Git 설정으로 merge_changed_paths와 conflicted_paths를 생성합니다.
  • 충돌 파일·유형, 해결 전후 diff와 담당자 판단 근거는 별도로 보관합니다.

강조할 부분

  • 검사기는 vendor merge를 실행하거나 충돌 해결 내용을 승인하지 않습니다.
  • 새 1.13.2 Candidate lock이 활성화되지 않은 상태에서 수집하면 “활성 lock이 아직 병합 전 기준선”이라는 오류로 중단합니다.
  • 경로 목록을 손으로 수정하지 않습니다. 자동 수집기가 생성 즉시 postmerge와 같은 함수로 자기 검증하고 기존 파일·동시 실행을 차단합니다.
  • conflict-rate는 실제 대화형 merge 화면의 충돌 수가 아니라 rename 탐지를 끈 결정적 재현 정책에서 계산한 지표입니다.
  • 현재 CLI에는 custom merge driver 허용 override가 없으며, 설정이 있으면 ANALYSIS_ERROR로 중단합니다. commit에 결속된 .gitattributes의 내장 driver는 동일 코드로 재현합니다.
  • replay_config_digest는 감사용 정보 필드이며, 사용자의 무효화된 설정까지 기록해 머신별로 달라질 수 있습니다.
  • Git 충돌 해결 성공과 BANK-OM 기능 정상은 다른 판정입니다.

완료 결과와 중단 조건

  • 완료: 병합 부모와 해결 commit이 있는 하나의 1.13.2 Candidate SHA가 만들어집니다.
  • 중단: 해결 기준 불명확, 비JSON 충돌 미해결, test 실패 또는 승인되지 않은 코드 선택입니다.
  • 복구: fix commit 등으로 Candidate SHA가 바뀌면 기존 lock·결과·승인을 재사용하지 않고, 새 lock 승인 후 candidate-select부터 다시 실행합니다.

가이드 6 · 1.13.2 종합 검사와 승인 판단

원본 10 유지postmerge · phase-status

반드시 넣을 내용

  • postmerge Candidate 재선택과 필수 입력 preflight
  • 승인된 custom head·merge-base·Candidate ancestry의 3중 결속

  • 검사기는 승인 형식·digest 결속을 검사하지만 승인자의 조직 권한은 별도 정책에서 확인해야 합니다.

  • 중단: 충돌 증거 불일치, 필수 gate 미실행, build·Runtime 실패, 보고서 변조 또는 조직 승인 누락입니다.

3. 통합된 7단계 안에서 검사기 화면이 열리는 순서

여섯 검사 화면은 새 3·4·6단계 안에서 실행됩니다. vendor merge와 release는 검사기가 대신할 수 없어 새 5·7단계로 독립 유지합니다.

재실행 안내: Candidate 선택[1/6]과 실행 전 점검[3/6]은 병합 전(새 3·4단계)과 병합 후(새 6단계)의 입력이 다르므로 각 맥락에서 다시 실행합니다.

2/6공식 버전 준비tag·commit 고정
3/6실행 전 점검누락 입력 수집
4/6병합 전 검사영향·민감 경로
5/6병합 후 검사소스·산출물·Runtime
6/6결과 재검증3단 보고서 대조
검사기가 자동으로 확인사람이 계속 해야 함
Candidate·공식 commit·결과 digest가 같은 실행 대상을 가리키는지 확인어떤 공식 버전을 사용할지 결정하고 실제 담당자를 지정
병합 전 custom head, merge-base와 git merge-tree 충돌 목록 재현vendor merge 실행, 충돌 코드 선택·수정, 업무 의미 검토
build artifact digest와 승인된 Candidate lock의 일치 확인실제 이미지를 build하고 실행 환경·비밀값·fixture 준비
PASS·APPROVAL·BLOCK·ANALYSIS_ERROR 집계와 보고서 변조 확인APPROVAL 판단, release tag 생성, 운영 배포 승인과 실행

검사기 구현과 합성 Git 저장소 회귀는 완료했습니다. 실제 OM_TEMP 예행연습에 적용했다는 뜻은 아닙니다.

환경 의존 38건은 skip입니다. 실제 제품 ref, API, 브라우저 또는 실행 환경이 필요한 기존 항목이며 PASS로 계산하지 않았습니다.
고정한 주요 차단 반례와 동작 경계 보기
  • 가짜 custom_head_sha와 승인되지 않은 이전 기준선
  • target만 변경한 경로를 충돌 경로라고 기록한 허위 증거
  • base 내용으로 해결돼 최종 diff에서 사라진 실제 충돌
  • 차단 반례: rename/rename, add/add, 중복 경로, 조작한 conflict-rate, merge-tree 결과 누락·초과
  • 차단 반례: 허용되지 않은 custom merge-driver 설정
  • 동작 경계: commit에 결속된 .gitattributes는 동일 Git 정책으로 재현
  • 누락된 target, 변조된 관리자·실무자 결과, 잔존·손상 lock
  • 동작 경계: 이전 버전 증거는 범위 표시가 없으므로 최신 검사기로 해당 Phase를 재실행

6. 11단계와 7단계의 관계

원본은 상세 절차서로 보존하고, 7단계 화면은 통합 실행용 시작 페이지로 추가하는 방식입니다. 원본 내용을 삭제하거나 기존 예행연습 중간에 절차를 바꾸지 않습니다.

새 통합 단계묶이는 원본 단계통합 이유
1. 환경·branch 확인원본 1~2같은 시작 준비이며 결과가 하나의 1.13.1 기준 코드로 이어짐
2. BANK-OM 등록 준비원본 3~5파일–ID 관계, commit, 등록자료가 하나의 승인 입력을 구성함
3. 기준선 승인·검증원본 6~7판정 학습을 실행 화면에 포함하고 같은 기준선에서 즉시 검사함
4. 공식 버전·병합 전 검사원본 8공식 코드 고정과 사전 영향 검사가 같은 입력 SHA를 사용함
5. vendor merge·충돌 해결원본 9사람의 코드 판단이 필요하므로 독립 유지
6. 종합 검사·승인 판단원본 10소스·artifact·Runtime·보고서가 같은 Candidate 결과로 집계됨
7. tag·release 고정원본 11조직 승인 후 실행하는 변경 작업이므로 독립 유지

현재 권장: 이 7단계 초안은 비교용으로만 봅니다. 사용자가 도입을 결정하기 전까지 진행 중인 예행연습은 원본 11단계로 계속합니다.
