이 페이지의 명령을 실행할 터미널에서 검사기 저장소로 이동한 뒤 공통 경로를 불러옵니다. 다른 컴퓨터에서는 clone 위치만 바꾸면 됩니다.

OM_TEST_REPO는 검사기 저장소, OM_CODE_REPO는 OpenMetadata 코드 작업 폴더, KB_SOURCE_REPO는 실제 커스터마이징 원본 폴더를 가리킵니다. 새 터미널을 열면 다시 실행합니다.

1. 문서 범위

이 문서는 openmetadata-test 검사기 카탈로그 23종과, 이번 예행연습에서 추가한 공용 파일의 BANK-OM ID별 코드 정의 검사 1종을 설명합니다. 실행 명령을 따라 하는 문서가 아니라, 각 검사가 브랜치 전략의 어느 시점에서 무엇을 확인하는지 먼저 익히는 문서입니다.

T42와 같은 번호는 OpenMetadata 기본 기능이 아니라 openmetadata-test 검사기 저장소에서 관리하는 내부 검사 ID입니다.

2. 판정 결과

표시의미다음 조치
PASS (pass)자동 검사 조건을 모두 충족했습니다.다음 단계를 계속합니다.
APPROVAL (approval)자동으로 오류라고 확정할 수는 없지만 담당자 검토가 필요합니다.이유를 확인하고 승인 근거를 남긴 뒤 계속합니다.
BLOCK (block)위반 또는 기능 누락을 확인했습니다.코드나 등록자료를 고친 뒤 같은 검사를 다시 실행합니다.
ANALYSIS_ERROR (analysis_error)입력 누락이나 환경 오류로 검사기가 안전하게 판단하지 못했습니다.이유에 적힌 입력·환경 문제를 해결하고 다시 실행합니다.

3. 브랜치 전략에서의 사용 위치

[새 공식 OpenMetadata branch] -- A. 병합 전 영향 확인 --\
                                                        +--> B. 다음 커스텀 브랜치에서 vendor merge
[직전 커스텀 브랜치] -------------------------------/                  |
                                                           Git 충돌이면 사람이 해결
                                                                         |
                                                     C. 등록자료·소스 규칙 검사
                                                                         |
                                                     D. 소스·동작 test 검사
                                                                         |
                                                     E. 결과 집계·승인
                                                                         |
                                                     [검증 표시 tag → 릴리즈 브랜치]
Git 충돌은 검사기 판정이 아닙니다. vendor merge 중 Git이 같은 코드 구간의 두 변경을 자동으로 합치지 못하면 충돌로 중단합니다. 담당자가 코드를 선택·수정하고 merge를 완료한 뒤에 검사기를 실행합니다.

아래 표는 실제 상황 예시 → 검사기가 묻는 질문 → 결과를 받은 뒤의 조치 순서로 읽습니다.

4. 1.13.1 → 1.13.2 예행연습에서의 사용 순서

  1. 1.13.1 기준 Manifest·Registry·Contract와 공용 파일 ID별 코드 정의를 승인합니다.
  2. OpenMetadata 1.13.2 포크 브랜치를 준비한 뒤 A 검사로 병합 전 영향을 확인합니다.
  3. 직전 커스텀 브랜치와 1.13.2 포크 브랜치를 다음 커스텀 브랜치에서 vendor merge합니다.
  4. Git 충돌이 있으면 담당자가 충돌 코드를 해결합니다.
  5. merge가 완료된 다음 커스텀 브랜치에서 B·C 검사를 실행합니다.
  6. 필요한 실행 환경을 준비한 뒤 D 검사를 실행합니다.
  7. E 검사로 결과를 집계하고 필수 APPROVAL의 승인 근거를 확인합니다.
  8. 모든 BLOCK과 ANALYSIS_ERROR가 해결되고 필수 승인이 완료된 동일한 1.13.2 업그레이드 후보 commit에만 검증 표시 tag를 붙이고 릴리즈 브랜치로 승격합니다.

5. 현재 경계

  • 이 페이지는 검사기를 익히기 위한 개념 문서입니다. 실행 명령·입력 파일·예상 출력은 후속 예행연습 실행 페이지에서 단계별로 제공합니다.
  • T61·T90·T91은 실제 runtime·승격 환경의 운영 증거가 아직 필요합니다.
  • T62는 실행기가 구현됐지만 운영 run 증거가 아직 필요합니다.
  • T80은 보조 자료만 만들며 통과·차단을 판정하지 않습니다.
  • T20·T21·T22·patch-lock은 선택 patch-replay 방식용이며, 현재 기본 vendor merge 방식의 필수 절차로 표시하지 않습니다.

6. 다음 단계

앞 단계에서 준비한 ID별 commit 후보 branch, 공용 파일의 ID별 코드 정의와 Manifest·Registry·Contract를 plan → 사용자 승인 → apply 순서로 반영합니다. 다음 실행 가이드에서 등록·소스·공용 코드 검사의 입력과 결과를 직접 확인합니다.
