# OM 운영 위키 피드백 반영안 재검토 수정안

- 작성일: 2026-07-30
- 대상 문서: `OM_운영위키_피드백_반영안_가이드완성도_전략부록_20260730.md`
- 문서 목적: 첨부된 피드백 반영안을 실제 운영 위키와 검사기 코드에 적용하기 전에, 수용할 내용과 다시 고칠 내용을 확정한다.
- 현재 상태: **검토안 작성 완료 · 운영 위키와 검사기 코드는 아직 변경하지 않음**

## 1. 결론

첨부된 반영안은 기존 반영안보다 구조와 논리 흐름이 개선됐다.

특히 다음 변화는 그대로 수용한다.

1. 운영 가이드의 설명 보완과 검사기·운영전략 변경 제안을 본문과 부록으로 분리한다.
2. 기존 기능에 후속 commit을 추가하는 흐름과 공식 OpenMetadata 버전을 업그레이드하는 흐름을 분리한다.
3. T41과 T42의 역할을 구분한다.
4. T90을 업그레이드 실행 도구가 아니라 업그레이드 결과를 판정하는 검사로 설명한다.
5. 문서 수정, 검사기 코드 변경, 조직 정책 결정을 각각 다른 승인 대상으로 구분한다.
6. 문서에 현재 구현과 추가 개발 제안을 함께 적을 때 상태 라벨을 붙인다.

다만 Contract의 정의, T42 실행 시점, 승인 절차의 구현 상태, T90 단계명, digest와 apply 설명에는 사실관계 또는 표현 문제가 남아 있다.

따라서 첨부본을 그대로 정본으로 사용하지 않고, 이 문서의 수정안을 먼저 반영한 뒤 최종 승인을 받는다.

## 3. 수정해서 수용할 내용

### 3.1 Contract 정의

#### 현재 반영안의 문제

Contract를 “자동 등록 도구와 검사기가 따라야 할 입력·출력 조건”으로 설명하면 일반적인 프로그램 인터페이스 규격으로 오해할 수 있다.

이 프로젝트에서 Contract는 커스터마이징 기능이 정상인지 판단할 업무 동작과 필수 test를 기록한다.

#### 수정할 문장

> Contract는 커스터마이징 기능이 정상이라고 판단할 업무 동작과, 그 동작을 확인할 필수 test를 기록한 관리파일입니다.

#### 예시

```yaml
- id: CONTRACT-KOREAN-IME
  invariant: 한글 입력 중 자모가 중복·역전·소실되지 않는다.
  required_tests:
    - tests/bank/contracts/test_korean_ime.py::test_hangul_composition_roundtrip
  customization_ids:
    - BANK-OM-005
```

이 예시에서 `invariant`는 정상이어야 하는 업무 동작이고, `required_tests`는 그 동작을 확인할 test다.

### 3.2 일반 후속 변경 흐름

#### 현재 반영안의 문제

모든 후속 commit을 등록할 때마다 빌드, 실행, 배포 준비까지 진행하는 것처럼 읽힐 수 있다.

등록 변경과 실제 배포 후보 검증은 구분해야 한다.

#### 수정할 흐름

1. 코드 저장소에서 기존 BANK-OM ID로 후속 commit을 만든다.
2. 준비 도구가 해당 ID의 최신 commit과 변경 경로를 찾아 등록 변경안을 만든다.
3. 담당자가 변경안을 검토하고 승인한다.
4. 승인된 변경안을 변경 대상 Manifest와 관련 파생 등록자료에 반영한다. Registry 변경이 필요한 경우에는 proposal에 해당 변경을 함께 표시한다.
5. 등록 검사와 소스 검사를 실행한다.
6. 실제 release branch 후보로 정할 때 빌드·실행·배포 검사를 추가로 실행한다.

#### 문서에 넣을 핵심 문장

> 후속 commit 등록과 소스 검사를 먼저 완료합니다. 빌드·실행·배포 검사는 해당 변경이 실제 release branch 후보에 포함될 때 실행합니다.

---

### 3.3 공식 버전 업그레이드 흐름과 T42 실행 시점

#### 현재 반영안의 문제

T42가 vendor-merge 이후에 실행되는 것처럼 읽힌다.

T42는 기존 공식 버전과 새 공식 버전을 비교해 watch 경로에 공식 변경이 생겼는지 병합 전에 알려주는 검사다. 따라서 vendor-merge 전에 실행해야 한다.

#### 수정할 흐름

1. 현재 custom branch와 등록자료가 정상인지 확인한다.
2. 새 공식 OpenMetadata 버전을 official fork branch에 준비한다.
3. T42로 이전 공식 버전과 새 공식 버전의 watch 경로를 비교한다.
4. T42 결과를 보고 영향을 받을 BANK-OM ID와 확인할 파일을 파악한다.
5. 새 official fork branch의 코드를 custom branch에 vendor-merge한다.
6. Git 충돌이 발생하면 담당자가 해결하고 해결 commit을 남긴다.
7. 병합이 끝난 custom branch를 기준으로 등록 변경안을 생성한다.
8. 담당자가 변경안을 승인하고 등록자료에 반영한다.
9. 등록 검사와 소스 검사를 실행한다.
10. 빌드·실행·업그레이드 검사를 완료한다.
11. 승인된 commit을 release branch와 Release lock으로 확정한다.

#### T42 설명

> T42는 커스터마이징 코드를 포함한 custom branch와 새 공식 코드를 비교하는 검사가 아닙니다. 이전 공식 버전과 새 공식 버전을 비교해, Manifest의 watch 경로에 공식 변경이 생겼는지 확인합니다.

---

### 3.4 최종 승인 절차의 현재 상태

#### 현재 반영안의 문제

`승인 ID 발급 → RELEASE` 흐름이 이미 자동화된 기능처럼 읽힐 수 있다.

현재는 담당자가 검사 결과와 승인 근거를 확인하고 Release lock에 승인 정보를 기록한다. 승인 ID를 자동 발급하는 별도 서비스와 release branch 생성을 자동 차단하는 최종 승인 게이트는 완성되지 않았다.

#### 현재 기능 설명

> 담당자는 검사 결과와 승인 근거를 확인한 뒤 Release lock에 승인 정보를 기록합니다. T91은 Release lock에 기록한 commit과 실제 배포 대상 commit이 같은지 확인합니다.

#### 추가 개발 설명

> 승인 ID 자동 발급, 필수 승인 누락 차단, 승인 완료 전 release branch 생성 차단은 추가 개발 및 조직 정책 결정 대상입니다.

---

### 3.5 T90 단계명

#### 현재 반영안의 문제

한글 설명만 사용하면 실제 검사 결과의 단계 ID와 연결하기 어렵다.

#### 수정 방식

한글 설명 뒤에 실제 단계 ID를 함께 쓴다.

| 한글 설명 | 실제 단계 ID |
|---|---|
| 운영 데이터 복원 | `restore-production-snapshot` |
| DB 변경 적용 | `migration` |
| 데이터 건수 대조 | `row-reconciliation` |
| 검색 인덱스 재생성 | `reindex` |
| 메타데이터 수집 확인 | `ingestion` |
| 로그인 동작 비교 | `differential-authentication` |
| 권한 동작 비교 | `differential-authorization` |
| API 동작 비교 | `differential-api` |
| 관계 정보 비교 | `differential-relations` |
| 검색 결과 비교 | `differential-search` |
| 수집 결과 비교 | `differential-ingestion` |
| 되돌리기 연습 | `rollback-drill` |

#### T90 설명

> T90은 위 단계를 직접 실행하지 않습니다. 담당자나 CI가 실행한 각 단계의 결과 자료가 모두 있고 성공으로 기록됐는지 확인합니다.

---

### 3.6 등록 상태 digest

#### 현재 반영안의 문제

Contract만 digest에 포함되고 다른 등록자료는 포함되지 않는 것처럼 설명하면 실제 구현과 다르다.

현재 등록 상태 digest에는 다음 등록 입력이 포함된다.

- Registry
- Contract
- 저장소 구조 설정
- 공식 원본 기준 경로 분류 자료
- 여러 BANK-OM ID가 함께 사용하는 경로 자료
- 모든 Manifest

#### 수정할 문장

> 준비 도구는 주요 등록자료의 내용을 digest로 묶어, 담당자가 승인한 뒤 파일 내용이 달라졌는지 확인합니다. 다만 어떤 버전의 준비 도구로 변경안을 만들었는지까지 승인 정보에 고정할 필요가 있는지는 추가 설계가 필요합니다.

---

### 3.7 `plan → 승인 → apply`의 안전성

#### 현재 반영안의 문제

현재 apply가 파일을 아무 보호 없이 덮어쓰는 것처럼 설명하면 실제 구현과 다르다.

현재 apply는 다음 항목을 확인한다.

- 승인한 plan의 digest가 같은지
- 코드 기준 commit이 같은지
- 등록자료가 plan 생성 후 바뀌지 않았는지
- 작업 폴더에 승인되지 않은 변경이 있는지
- 반영 도중 실패하면 기존 파일로 되돌릴 수 있는지

#### 수정할 문장

> 현재 apply에는 승인 후 변경 여부 확인과 실패 시 원복 처리가 있습니다. 추가 검토 대상은 준비 도구 버전까지 승인 정보에 고정할지, 여러 파일의 반영 성공을 별도 결과 파일로 남길지입니다.

---

### 3.8 관리파일의 구분

#### 수정할 분류

| 구분 | 파일 예시 | 의미 |
|---|---|---|
| 담당자가 승인하는 기준 입력 | Manifest, Registry, Contract | 검사기가 어떤 기능과 경로, 정상 조건을 확인할지 정한다. |
| 준비 도구가 만드는 변경안 | proposal, approval template | 어떤 등록자료가 어떻게 바뀔지 승인 전에 보여준다. |
| 승인 후 반영되는 파생 등록자료 | `commit-inventory.yaml`, `current-diff-paths.txt` | 승인된 최신 commit과 현재 변경 경로를 검사기가 읽을 수 있게 정리한다. |
| 검사 실행 결과 | 검사별 JSON·로그·요약 | 검사 입력, 판정과 실패 이유를 기록한다. |
| 배포 후보 고정 자료 | Candidate lock, Release lock | 검사한 commit과 실제 배포할 commit을 고정한다. |

`current-diff-paths.txt`는 단순한 임시 로그가 아니다. 승인된 현재 변경 범위를 검사기가 읽도록 만든 파생 등록자료로 설명한다.

### 3.9 vendor-merge 조건

#### 현재 반영안의 문제

병합 commit의 첫 번째 parent와 두 번째 parent의 방향을 아직 검사기 설계가 확정된 것처럼 고정하면 안 된다.

#### 수정할 문장

> vendor-merge commit은 기존 custom branch와 새 official fork branch를 연결하는 병합 commit이어야 합니다. parent의 방향과 commit message 규칙은 실제 병합 명령으로 검증한 뒤 T30의 허용 조건으로 확정합니다.

---

### 3.10 Registry snapshot 설명

#### 현재 반영안의 문제

“최초 등록자료”라는 표현은 한 번 생성한 뒤 영원히 바뀌지 않는 자료로 오해할 수 있다.

#### 수정할 문장

> `source.snapshot_sha`는 해당 제품 버전의 등록 revision을 처음 만든 시점에 BANK-OM 변경이 적용돼 있던 코드 commit을 기록합니다. 같은 제품 버전의 등록 revision 정책을 변경할 경우 기존 값을 덮어쓸지 새 revision으로 보관할지는 별도 정책으로 결정합니다.

## 4. 문서 구조 수정안

### 4.1 문서 수정 승인안

파일명 예시:

- 어떤 설명을 삭제·변경·추가할지

- 현재 구현과 추가 개발 구분
- 운영 위키 수정 순서
- 문서 수정 완료 조건

### 4.2 검사기·운영전략 설계 제안

파일명 예시:

`OM_검사기_운영전략_설계제안_20260730.md`

포함할 내용:

- APPROVAL 최종 판정 방식

두 번째 문서의 내용은 문서 표현 수정 승인을 받았다는 이유만으로 검사기 코드에 적용하지 않는다. 각 항목의 설계와 테스트 방법을 별도로 승인받은 뒤 개발한다.

## 5. 실제 수정 순서

### 1단계 · 반영안 확정

- 이 재검토 수정안을 첨부본에 반영한다.
- 문서 변경 항목과 설계 제안을 분리한다.
- 사용자가 수정 범위를 확인한다.

### 2단계 · 위험한 기존 안내 수정

- 일반 후속 commit마다 `generate_registration_bundle.py`를 실행하라는 안내를 제거한다.
- 옛 Manifest 생성 명령을 현재 `plan → 승인 → apply` 명령으로 교체한다.
- watch 자동 포함 규칙을 실제 구현과 동일하게 수정한다.
- 자동화되지 않은 Contract와 담당자 판단 항목을 직접 확인 대상으로 표시한다.

### 3단계 · 운영 위키 흐름 수정

- 일반 후속 변경과 공식 업그레이드 흐름을 분리한다.
- 공식 업그레이드에서 T42를 vendor-merge 전에 배치한다.
- 각 단계에 담당자 작업, 자동화 작업, 입력, 출력과 다음 행동을 표시한다.
- 현재 구현과 추가 개발 제안을 분리한다.

### 4단계 · 문장 단위 검토

각 문장을 다음 기준으로 검토한다.

- 처음 등장한 용어가 바로 설명되는가
- “저장소”, “브랜치”, “승인”, “후보”가 어느 대상을 뜻하는지 명확한가
- 독자가 결과를 본 뒤 다음에 무엇을 해야 하는지 알 수 있는가
- 같은 내용을 다른 페이지에서 다르게 설명하지 않는가
- OpenMetadata와 BANK-OM 관리 체계를 처음 접하지만 Git 기본 사용 경험이 있는 신규 운영 담당자가 위키만 보고 따라 할 수 있는가

### 5단계 · 별도 승인 후 검사기 변경

- 부록의 설계 제안별로 구현 범위와 테스트를 작성한다.
- 사용자 승인을 받은 항목만 검사기 코드에 반영한다.
- 테스트 결과와 변경 전·후 동작을 문서에 추가한다.
