  1. 보고 있는 브랜치가 다를 수 있습니다. 현재 행내 코드는 기본 브랜치가 아니라 codex/bank-vendor-1.13.1-rebuild 브랜치에 있습니다.

따라서 제품 저장소에서 BANK-OM 문서를 찾는 것이 아니라, 해당 제품 브랜치의 실제 코드·커밋 이력과 검사 저장소의 변경관리표를 함께 확인해야 합니다.

“어느 파일이 빠지면 기능의 필수 부품이 사라진 것인가?”에 답합니다.

BANK-OM-001 실제 파일전체 명단즉시 실패 표시이렇게 정한 이유
InstanceCodeResource.java 예 예 InstanceCode API 전용 파일이라 없어지면 API 자체가 없어졌다고 바로 판단 가능
instanceCode.json 예 예 InstanceCode 데이터 구조 전용 파일이라 없어지면 엔터티 정의가 성립하지 않음
Entity.java 예 아니오 여러 기능이 함께 쓰는 파일이라 파일 전체가 달라 보이는 것만으로 INSTANCE_CODE 코드가 남았다고 증명할 수 없음. 업그레이드 전후 코드 비교와 실제 동작 검사로 확인
ko-kr.json 예 아니오 번역 누락은 결함이므로 검토 대상이지만, 그 파일 하나만으로 InstanceCode 전체가 사라졌다고 단정하지 않음
보통 어떤 파일을 “없으면 즉시 실패”로 정하나?
  1. 행내 기능을 위해 새로 만든 Resource·Mapper·스키마처럼 전용 역할이 명확한 파일
  2. 그 파일이 없거나 공식 원본 상태면 기능의 필수 구성요소가 실제로 빠졌다고 단정할 수 있어야 함
  3. 다른 BANK-OM 변경 때문에 파일 전체가 달라 보이는 공용 파일은 경로만으로 증명하지 않고 코드·계약 검사로 확인
  4. 왜 즉시 실패해야 하는지 변경관리표 검토 기록에 남기고 코드 책임자가 승인

추측으로 넣지 않습니다. Git이 보여주는 공식 원본과 행내본의 실제 파일 차이, 공용 파일 안에서 각 BANK-OM이 수정한 코드 구간, 코드 연결 관계, 동작·기술 테스트와 코드 책임자 승인으로 결정합니다.

이번 커밋이 실제로 수정한 공식 공용 코드 파일이므로 “실제 변경 파일 전체 명단”(allowed)에 들어갑니다. 1차 개선을 적용하면 검사기가 업그레이드 전후도 자동 비교하므로 사용자가 수동 감시 목록에 같은 경로를 또 적지 않습니다.

네 파일을 보고 만드는 사전 설정

Entity.java, CollectionDAO.java 수정과 신규 InstanceCode 파일들은 하나의 업무 기능이므로 BANK-OM-001로 묶습니다. 먼저 실제 변경 파일 48개를 전부 기록합니다. 그중 필수 부품이 사라졌다고 즉시 판단 가능한 2개에는 실패 표시를 붙입니다. 1차 개선을 적용하면 48개 중 공식 원본에도 있던 파일은 검사기가 업그레이드 전후를 자동 비교하고, 수동 감시는 48개 밖의 의존 파일에만 사용합니다.

Customization-ID: BANK-OM-001

마지막으로 같은 ID를 실제 커밋 메시지에 기록합니다. 저장 후 Git이 a2566fac…라는 SHA를 자동 생성합니다.

ID는 관리 담당자가 ID 대장에서 다음 미사용 번호를 발급합니다. LLM이나 Git이 만드는 값이 아닙니다. kind는 실제 검사기 스키마가 허용하는 core-patch·extension·governance 중 하나만 사용합니다. 변경관리표는 실제 코드 근거와 검토를 거쳐 작성하며, Git 커밋 식별값(SHA)만 Git이 저장할 때 자동 생성합니다.

제품 작업 브랜치 안의 공식 Core 파일 수정 같은 브랜치 안의 행내 전용 파일 추가
왜 이 구조가 필요한가?

색상은 별도 제품이나 반드시 유지해야 하는 장기 브랜치 두 개가 아니라, 하나의 제품 작업 브랜치 안에서 변경의 역할을 구분합니다. Core 패치는 공식 공용 파일을 수정하는 변경이고, 행내 전용 변경은 신규 Resource·Mapper·Repository 등을 추가합니다. BANK-OM-001처럼 한 업무 기능이 두 역할을 모두 사용하면 같은 BANK-OM ID로 연결해 추적합니다.

Q&A

가장 중요한 질문

파일이 사라진 경우와 파일 안의 행내 변경이 사라진 경우를 구분합니다.

Q1. “파일이 사라졌다”는 정확히 무슨 뜻인가?

업그레이드 결과물에 파일 자체가 없는 경우입니다. 예를 들어 새로 만든 InstanceCodeResource.java가 생성되지 않았다면 파일 소실입니다.

해당 파일의 등록검사 결과이유
실제 변경 파일(allowed)담당자 확인 알림변경이 빠졌을 가능성이 있어 자동 통과시키지 않음
즉시 실패 파일(required)즉시 실패필수 구현 파일 누락을 파일 상태만으로 확인할 수 있음
Q2. “변경이 사라졌다”는 정확히 무슨 뜻인가?

파일은 있지만 공식 새 버전의 파일과 완전히 같아서 행내 변경 흔적이 보이지 않는 경우입니다. 검사기는 업그레이드 결과물과 공식 새 버전을 비교해 이를 찾습니다.

Entity.java 파일은 존재
하지만 공식 새 버전의 Entity.java와 완전히 동일
→ BANK-OM 변경이 적용되지 않았을 가능성
→ allowed이면 담당자 확인, required이면 즉시 실패
Q3. 파일이 다르면 행내 코드가 전부 적용됐다는 뜻인가?

아닙니다. 현재 파일 단위 검사는 “공식 원본과 다른가?”까지 확인합니다. 공용 파일이 다른 BANK-OM 때문에 달라졌다면, 정작 BANK-OM-001의 INSTANCE_CODE가 빠져도 파일 전체는 다르게 보일 수 있습니다.

따라서 세 단계로 확인합니다
  1. 파일 검사: 필요한 파일이 있고 공식 원본 대비 변경이 보이는가?
  2. 코드 내용 검사: Entity.INSTANCE_CODE, instanceCodeDAO() 같은 필수 코드가 실제로 남아 있는가?
  3. 동작 검사: API 호출·저장·조회 등 InstanceCode 기능이 실제 환경에서 동작하는가?
Q4. allowed·required·watch를 한 문장씩만 설명하면?
항목한 문장 정의문제가 발견되면
allowed이 BANK-OM 기능이 실제로 변경한 파일 전체누락·변경 없음 → 담당자 확인
required보통 행내 전용 파일 중, 누락되면 필수 구현 누락을 확인할 수 있는 파일누락·변경 없음 → 즉시 실패
watch직접 수정하지 않았지만 행내 기능에 영향을 줄 수 있는 의존 파일공식 버전에서 변경 → 담당자 확인
Q5. 기존 BANK-OM에 나중에 새 파일을 추가하면?

최초 BANK-OM-001의 48개 파일 기록은 그대로 두고, 후속 커밋에서 새로 추가한 파일만 candidate_additional_paths에 기록합니다.

candidate_additional_paths:
  - .../InstanceCodeValidator.java
기록검사기에 알려주는 내용
새 Git 커밋 식별값(SHA)어떤 코드 변경을 어떤 순서로 추가했는가
candidate_additional_paths새 파일을 BANK-OM-001의 변경 범위로 승인했는가

Git 커밋 식별값(SHA)만 추가하면 새 파일은 등록 범위 밖 변경으로 판단됩니다. 반대로 최초 48개 명단을 49개로 고치면 과거 최초 커밋에도 새 파일이 있었던 것처럼 기록이 바뀝니다. 따라서 최초 기록은 보존하고 후속 파일만 별도로 추가합니다.

최초 설정에는 필요하지 않으며, 같은 BANK-OM ID로 후속 파일을 추가할 때만 사용합니다. 별도 기능이라면 새 BANK-OM ID를 발급합니다.
