01

우리의 목적

자체 제품을 새로 만드는 것이 아니라, 공식 OpenMetadata를 안전하게 계속 사용하는 것이 목적입니다.

유지할 것 공식 OpenMetadata

공식 기능과 보안 업데이트를 계속 반영합니다.

보호할 것 등록된 행내 기능

각 기능을 BANK-OM ID별 독립 변경 기록으로 관리합니다.

증명할 것 병합 후 생존과 실제 동작

공식 버전 병합 뒤 BANK-OM 코드가 남았는지와 행내 환경 동작을 서로 다른 검사로 확인합니다.

현재 업그레이드·검사를 진행하는 코드 저장소 easyseop/OM_TEMP

공식 1.13.0과 BANK-OM-001~007을 바탕으로 1.13.1 코드 후보를 만들고, 충돌·해결·검사를 연습합니다. 이 연습은 커밋별 재적용으로 충돌을 진단했으며, 아래 목표 운영 방식인 vendor-merge 전체를 완료한 것은 아닙니다.

검사 기준과 결과를 관리하는 저장소 easyseop/openmetadata-test

직원용 OpenMetadata 화면이 아니라, 각 BANK-OM의 변경 파일과 검사 기준을 기록한 Manifest, 검사기, 검사 결과, 가이드와 인수인계 문서를 관리합니다.

02

브랜치 전략

기본 운영 방식은 vendor-merge입니다. 직전 custom branch의 행내 변경 이력을 유지한 채, 새 공식 버전을 병합해 다음 검사 후보를 만듭니다.

이 페이지에서는 공식 코드와 BANK-OM 변경이 custom branch에서 합쳐지고, 충돌 해결·검사·배포 후보 고정을 거쳐 다음 공식 버전으로 이어지는 흐름만 설명합니다. BANK-OM ID 발급, 커밋 메시지와 Manifest 작성 방법은 3번 · 검사 전 사전환경 설정에서 단계별로 설명합니다.

공식 버전과 patch branch · 공식 코드만 유지 BANK-OM 변경과 custom branch · 행내 변경 적용

그림에서 무엇과 무엇이 합쳐지나? 새 공식 코드만 담은 patch branch를, 직전 공식 코드와 검증된 BANK-OM 변경을 함께 보유한 custom 이력에 병합합니다. 결과는 다음 버전의 custom candidate입니다.

Git 충돌은 어디서 발생하나? 직전 custom 코드와 새 공식 코드가 같은 구간을 다르게 바꿨을 때 ③ 병합 지점에서 발생합니다. 해결 코드는 다음 custom branch에 commit으로 남기고 병합을 완료합니다.

충돌 해결 때 새 BANK-OM을 만드는가? 기존 기능을 새 공식 버전에 맞춘 것이라면 같은 BANK-OM ID를 사용합니다. 기존 Manifest를 새 버전 등록 묶음으로 복사해 다시 검토하고, 해결 과정에서 변경 범위나 검증 기준이 달라진 항목만 갱신합니다. 별도 업무 기능이 생겼을 때만 새 ID와 Manifest를 만듭니다.

검사 BLOCK은 무엇이 다른가? Git 병합은 끝났지만 Manifest 범위, 필수 구현, 테스트 또는 승인 조건을 통과하지 못한 경우입니다. 이때도 다음 custom branch를 보완하지만 Git 병합 충돌과는 다른 문제입니다.

검사를 통과하면 바로 배포하는가? 소스 검사 통과 commit에 먼저 배포 후보 tag를 붙여 대상을 고정합니다. 전체 build, 행내 API·화면·DB 테스트, 담당자 승인과 배포 파일 일치까지 끝난 뒤에만 실제 배포할 수 있습니다.

4번의 커밋별 재적용 실습은 무엇인가? 현재 OM_TEMP 연습은 어느 BANK-OM에서 충돌하는지 분리해 보기 위해 commit을 하나씩 적용했습니다. 이는 진단 자료이며, 위 vendor-merge 운영 Cycle 전체가 검증됐다는 뜻은 아닙니다.
