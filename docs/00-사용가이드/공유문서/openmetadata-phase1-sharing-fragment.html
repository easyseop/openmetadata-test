instanceCode.json 예 예 InstanceCode 데이터 구조 전용 파일이라 없어지면 엔터티 정의가 성립하지 않음
Entity.java 예 아니오 여러 기능이 함께 쓰는 파일이라 파일 전체가 달라 보이는 것만으로 INSTANCE_CODE 코드가 남았다고 증명할 수 없음. 업그레이드 전후 코드 비교와 실제 동작 검사로 확인
ko-kr.json 예 아니오 번역 누락은 결함이므로 검토 대상이지만, 그 파일 하나만으로 InstanceCode 전체가 사라졌다고 단정하지 않음
보통 어떤 파일을 “없으면 즉시 실패”로 정하나?
  1. 행내 기능을 위해 새로 만든 Resource·Mapper·스키마처럼 전용 역할이 명확한 파일
  2. 그 파일이 없거나 공식 원본 상태면 기능의 필수 구성요소가 실제로 빠졌다고 단정할 수 있어야 함
  3. 다른 BANK-OM 변경 때문에 파일 전체가 달라 보이는 공용 파일은 경로만으로 증명하지 않고 코드·계약 검사로 확인
  4. 왜 즉시 실패해야 하는지 Manifest 검토 기록에 남기고 코드 책임자가 승인

추측으로 넣지 않습니다. Git이 보여주는 공식 원본과 행내본의 실제 파일 차이, 공용 파일 안에서 각 BANK-OM이 수정한 코드 구간, 코드 연결 관계, 동작·기술 테스트와 코드 책임자 승인으로 결정합니다.

Customization-ID: BANK-OM-001

마지막으로 같은 ID를 실제 커밋 메시지에 기록합니다. 저장 후 Git이 a2566fac…라는 SHA를 자동 생성합니다.

ID는 관리 담당자가 ID 대장에서 다음 미사용 번호를 발급합니다. LLM이나 Git이 만드는 값이 아닙니다. kind는 실제 검사기 스키마가 허용하는 core-patch·extension·governance 중 하나만 사용합니다. Manifest는 실제 코드 근거와 검토를 거쳐 작성하며, Git 커밋 식별값(SHA)만 Git이 저장할 때 자동 생성합니다.

공식 버전과 patch branch · 공식 코드만 유지 BANK-OM 변경과 custom branch · 행내 변경 적용

그림에서 무엇과 무엇이 합쳐지나? 왼쪽 patch branch의 공식 코드와 오른쪽 BANK-OM commit이 새 custom branch에서 합쳐집니다. 이미 존재하는 두 branch를 마지막에 통째로 merge하는 구조는 아닙니다.

Git 충돌은 어디서 발생하나? 새 custom branch에 BANK-OM commit을 다시 적용하는 ③ 합류 지점에서 발생합니다. 해결 코드는 custom branch에 commit으로 남기고 다음 BANK-OM 재적용을 계속합니다.

검사 BLOCK은 무엇이 다른가? 모든 BANK-OM commit 적용이 끝난 ④ 상태를 검사한 뒤 기준을 통과하지 못한 경우입니다. 이때도 custom branch를 보완하지만, Git이 코드를 합치지 못한 충돌과는 다른 문제입니다.

다음 버전은 어떻게 이어지나? 검사에 통과한 마지막 custom commit에 검증 tag를 붙여 배포 대상을 고정합니다. 다음 공식 버전에서는 새 patch와 새 custom branch를 만든 뒤 같은 Cycle을 반복합니다. 공식 코드만 담는 patch에는 충돌 해결이나 검사 보완 commit을 합치지 않습니다.

왜 이 구조가 필요한가?

Cycle의 파란색은 공식 버전과 patch branch, 주황색은 BANK-OM 변경 이력과 custom branch를 뜻합니다. BANK-OM 변경에는 공식 공용 Core 파일의 최소 수정과 신규 Resource·Mapper·Repository 같은 행내 전용 파일 추가가 함께 들어갈 수 있습니다. BANK-OM-001처럼 한 업무 기능이 두 역할을 모두 사용하면 같은 BANK-OM ID로 연결해 추적합니다.

파일이 사라진 경우와 파일 안의 행내 변경이 사라진 경우를 구분합니다.

Q1. “파일이 사라졌다”는 정확히 무슨 뜻인가?

업그레이드 결과물에 파일 자체가 없는 경우입니다. 예를 들어 새로 만든 InstanceCodeResource.java가 생성되지 않았다면 파일 소실입니다.

즉시 실패 파일(required)즉시 실패필수 구현 파일 누락을 파일 상태만으로 확인할 수 있음
Q2. “변경이 사라졌다”는 정확히 무슨 뜻인가?

파일은 있지만 공식 새 버전의 파일과 완전히 같아서 행내 변경 흔적이 보이지 않는 경우입니다. 검사기는 업그레이드 결과물과 공식 새 버전을 비교해 이를 찾습니다.

Entity.java 파일은 존재
하지만 공식 새 버전의 Entity.java와 완전히 동일
→ BANK-OM 변경이 적용되지 않았을 가능성
→ allowed이면 담당자 확인, required이면 즉시 실패
Q3. 파일이 다르면 행내 코드가 전부 적용됐다는 뜻인가?

아닙니다. 현재 파일 단위 검사는 “공식 원본과 다른가?”까지 확인합니다. 공용 파일이 다른 BANK-OM 때문에 달라졌다면, 정작 BANK-OM-001의 INSTANCE_CODE가 빠져도 파일 전체는 다르게 보일 수 있습니다.

따라서 세 단계로 확인합니다
  1. 파일 검사: 필요한 파일이 있고 공식 원본 대비 변경이 보이는가?
  2. 코드 내용 검사: Entity.INSTANCE_CODE, instanceCodeDAO() 같은 필수 코드가 실제로 남아 있는가?
  3. 동작 검사: API 호출·저장·조회 등 InstanceCode 기능이 실제 환경에서 동작하는가?
Q4. allowed·required·watch를 한 문장씩만 설명하면?
항목한 문장 정의문제가 발견되면
allowed이 BANK-OM 기능이 실제로 변경한 파일 전체누락·변경 없음 → 담당자 확인
required보통 행내 전용 파일 중, 누락되면 필수 구현 누락을 확인할 수 있는 파일누락·변경 없음 → 즉시 실패
watch업그레이드 때 공식 변경 여부를 비교할 파일. 실제 변경 파일은 자동 포함하고, 직접 수정하지 않은 의존 파일은 담당자가 추가공식 버전에서 변경 → 담당자 확인
Q5. 기존 BANK-OM에 나중에 새 파일을 추가하면?

candidate_additional_paths는 같은 BANK-OM ID의 후속 커밋에서 처음 생긴 파일만 적는 항목입니다. 실제 BANK-OM-007은 최초 커밋에서 8개 파일을 변경했고, 후속 커밋에서 아래 2개 파일을 새로 추가했습니다.

candidate_additional_paths:
  - .../connections/serviceConnection.ts
  - .../DatabaseServiceUtils.test.tsx
항목BANK-OM-007 실제 사용검사기에 알려주는 내용
allowed_changed_paths최초 커밋의 8개 파일최초 등록 시점의 실제 변경 범위
candidate_additional_paths후속 커밋의 새 파일 2개현재 검사 대상에 추가로 허용할 범위
series.allowed: true같은 ID의 후속 커밋 허용여러 커밋이 실수가 아니라 계획된 이력임을 확인

왜 기존 allowed_changed_paths에 바로 더하지 않나? 최초 8개 명단을 10개로 고치면 최초 커밋에도 나중 파일 2개가 있었던 것처럼 과거 기록이 바뀝니다. 그러면 T25-R이 “최초 커밋을 정확히 재구성했는가”를 검사할 수 없습니다. 최초 범위 8개는 보존하고, 현재 후보의 T26·T40·T93은 8개와 추가 2개를 합친 10개를 검사합니다.

새 파일이 기능 유지에 반드시 필요하다면 required_changed_paths에도 추가합니다. 최초 설정에는 이 항목이 필요 없고, 같은 BANK-OM ID의 목적을 이어가는 후속 커밋에만 사용합니다. 별도 기능이면 새 BANK-OM ID를 발급합니다.
