각 검사기는 무엇을 읽고, 어떻게 판단하는가

이 문서는 검사 결과가 아니라 검사 방법을 설명합니다. 3번에서 검사 기준자료를 준비하고, 4번에서 OM_TEMP 업그레이드 연습 결과를 확인합니다.

검토 결론 현재 검사기는 소스 변경을 관리하는 데는 유효하지만, 경로 기반 검사와 외부 입력에 의존하는 부분이 있어 행내 동작·보안·배포 검사를 함께 사용해야 합니다.

각 검사는 어떤 입력을 읽고, 어떤 방법으로 PASS·APPROVAL·BLOCK을 판단하는가?

특정 commit의 실제 결과와 배포 가능 여부는 4번과 부록에서 구분해 보여줍니다.

읽고 나면

3번에서 검사에 필요한 Manifest·Registry·Contract를 직접 준비합니다.

우리 내부에서 만든 검사 체계: T25·T42 같은 번호, PASS·APPROVAL·BLOCK 판정과 아래 검사기는 OpenMetadata 기본 기능이 아니라 easyseop/openmetadata-test에서 BANK-OM 변경을 관리하기 위해 만든 검사 체계입니다.

검사기가 사용하는 정보와 검사 순서

  1. 1 코드 버전 지정

    공식 원본과 검사할 custom branch의 Git commit SHA를 지정합니다.

  2. 2 Manifest 입력

    활성 BANK-OM ID별 파일 범위, 필수 파일, 감시 파일과 테스트를 읽습니다.

  3. 3 Git 기록 비교

    공식 원본 이후의 모든 커밋과 각 커밋이 변경한 파일을 확인합니다.

  4. 4 업그레이드·동작 검사

    다음 공식 버전의 변경과 행내 API·화면·DB 테스트 결과를 확인합니다.

  5. 5 배포 파일 일치 확인

    검사한 코드와 이미지·설정 파일이 실제 배포 대상과 같은지 확인합니다.

Git commit SHA는 저장된 코드 버전을 식별하는 값입니다. SHA-256 digest는 파일 내용이 같은지 비교하기 위해 계산한 값입니다.

프론트엔드와 백엔드에 같은 검사기를 쓸 수 있나?

Git 커밋과 파일 변경을 확인하는 검사는 언어에 상관없이 그대로 사용할 수 있습니다. T25-R·T25·T26·T30·T31·T40·T41·T42·T43·T93은 Java·TypeScript·Python·JSON·YAML·SQL 등 파일 종류와 관계없이 Git 이력, 각 커밋에서 바뀐 파일 경로와 공식 원본 대비 최종 파일 상태를 확인합니다. 따라서 프론트엔드와 백엔드 파일을 같은 방식으로 관리할 수 있습니다. 다만 이 공통 검사는 파일 내부 코드의 의미나 실행 동작까지 언어에 관계없이 이해하는 검사가 아닙니다.

테스트 코드 자체를 해석하거나 실행하는 검사는 언어·도구별 지원이 필요합니다. 현재 T60-I는 Python pytest 코드만 확인하고, T63은 TypeScript 오류만 비교합니다. T61·T62도 Python pytest를 실행 도구로 사용하지만 그 테스트가 Java 백엔드 API와 TypeScript 프론트 화면을 호출하는 것은 가능합니다. Java JUnit이나 TypeScript Jest를 직접 등록·실행하려면 해당 도구용 확인 방식과 실행 연결을 추가해야 합니다.

왜 T1이 아니라 T25부터 보이나?

T번호는 이 문서에서 새로 매긴 순번이 아니라 검사기 개발계획과 결과 파일에서 함께 사용하는 태스크 ID입니다. T01~T24에는 커스터마이징 조사, 경로 정책, Manifest 스키마, Git 공통 기능, 선택적 재적용 도구 같은 기반 작업이 있습니다. 이 페이지는 책임자가 직접 판정을 읽는 검사기만 추렸기 때문에 첫 항목이 T25-R·T25로 보입니다. 코드·결과 파일·증거가 같은 ID를 사용하므로 화면에서 T1부터 다시 번호를 붙이지 않습니다.

왜 T93이 두 번 나오나?

현재 구현에서 T93이라는 한 정책 점검 묶음이 두 질문을 처리하기 때문입니다. 이 문서에서는 혼동을 줄이려고 T93-범위(실제 변경 파일과 Manifest 일치)와 T93-정책(공식 파일 이동으로 경로 규칙이 낡았는지)으로 표시합니다. 결과 파일의 내부 ID는 아직 둘 다 T93 계열입니다.

검사기별 실제 검사 방법과 예외 가능성

각 항목은 닫힌 상태에서 한 줄 역할만 보여줍니다. 펼치면 검사 목적, 실제 판단 방법과 놓칠 수 있는 경우를 확인할 수 있습니다. 특정 commit의 실제 판정은 이 페이지에 섞지 않았습니다.

✓

실제 검사

공식 원본과 과거 행내 소스의 변경 파일 목록을 먼저 고정한 뒤, 재구성한 브랜치의 파일을 비교합니다. JSON은 공백과 키 순서를 제외한 실제 값을 비교하고, Java·TypeScript 등 나머지 파일은 Git에서 차이가 없어야 합니다.

예외·보완

Java 파일에 빈 줄 하나만 달라도 차이로 판단해 중단합니다. 의미는 같지만 서식만 다른 경우에도 중단될 수 있으므로, 자동 통과시키기보다 서식 차이를 따로 보여주고 담당자가 확인하도록 보완하는 편이 안전합니다. 공식 Git 이력을 계속 유지하는 vendor branch에는 이 검사가 아니라 T25를 사용합니다.

실제 검사

Git의 공통 조상과 포함 관계를 조회해 공식 버전의 commit SHA가 행내 코드의 조상인지 확인합니다. 동시에 검사 대상 commit SHA와 전체 파일 상태가 사전에 기록한 검사 대상과 같은지도 확인합니다.

예외·보완

공식 코드가 이력에 포함됐다는 사실만 증명하며, 충돌을 올바르게 해결했는지 또는 기능이 정상인지까지 증명하지는 않습니다. 그래서 T26·T40과 행내 동작 검사가 함께 필요합니다.

T26 · 등록 기능 생존 확인활성 BANK-OM의 필수 구현과 테스트 연결이 남아 있는가✓

실제 검사

각 활성 BANK-OM ID의 필수 파일이 존재하고 공식 원본과 실제로 다른지 확인합니다. 전체 등록 파일 중 필수가 아닌 파일이 없어졌거나 공식 원본과 같아지면 담당자 확인 대상으로 분류하며, 업무 계약과 연결된 테스트 목록도 함께 확인합니다.

예외·보완

파일이 존재하고 공식 원본과 다르더라도 기능이 올바르게 동작한다고 단정할 수는 없습니다. 실제 테스트 코드의 존재는 T60-I가, 실제 실행 결과는 T62가 따로 확인합니다.

T30 · 커밋별 BANK-OM 식별 확인공식 원본 이후의 각 행내 코드 커밋에 BANK-OM ID가 정확히 하나 있는가✓

실제 검사

검사기는 공식 원본부터 검사 대상 commit SHA까지의 모든 커밋을 Git에서 순서대로 가져옵니다. 각 커밋 메시지의 Customization-ID: 항목과 그 커밋이 변경한 파일을 읽어, 행내 소스를 바꾼 커밋에 BANK-OM ID가 정확히 하나 있는지 확인합니다.

하나의 BANK-OM ID 안에 서로 다른 목적의 변경을 섞어도 파일 범위가 같으면 이 검사만으로는 구분하기 어렵습니다. 커밋 목적을 작게 유지하고 T40·T93 변경범위 검사로 실제 변경 파일까지 함께 비교해야 합니다.

T31 · BANK-OM 적용 순서 확인후속 커밋과 ID 의존관계가 등록된 순서를 지키는가✓

예외·보완

선행 관계 자체를 빠뜨린 경우에는 검사기가 업무 관계를 새로 추론하지 못합니다. 커스터마이징 설계자가 선행 BANK-OM ID를 Manifest에 등록하고 리뷰하는 절차가 필요합니다.
