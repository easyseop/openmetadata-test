각 검사기는 무엇을 확인하고, 결과를 어떻게 읽어야 하는가

이 페이지는 각 검사가 어떤 문제를 찾는지 설명합니다. 실제 검사 자료를 만드는 방법은 다음 3번 가이드에서, OM_TEMP 1.13.1 진단 결과는 4번 업그레이드 연습에서 확인합니다.

이 페이지의 핵심 검사기는 커스터마이징 파일의 누락과 등록 오류를 자동으로 찾습니다. 그러나 기능이 실제로 정상인지, 충돌을 올바르게 해결했는지, 배포해도 되는지는 별도의 기능 테스트와 담당자 승인이 필요합니다.
이 페이지가 답하는 질문

각 검사는 무엇을 비교하며, 어떤 경우에 통과·담당자 확인·중단으로 판단하는가?

이 페이지의 범위

검사 원리만 설명합니다. 특정 코드의 실제 검사 결과와 아직 확인하지 못한 배포 범위는 4번 업그레이드 연습에서 구분해 보여줍니다.

다음 단계

검사 원리를 이해한 뒤 다음 가이드에서 변경 등록표(Manifest), ID 관리대장(Registry), 업무 테스트 기준(Contract)을 준비합니다.

우리 내부에서 만든 검사 체계: T25·T42 같은 번호, PASS·APPROVAL·BLOCK 판정과 아래 검사기는 OpenMetadata 기본 기능이 아니라 easyseop/openmetadata-test에서 BANK-OM 변경을 관리하기 위해 만든 검사 체계입니다.

검사기가 사용하는 정보와 검사 순서

  1. 1 비교할 코드 지정

    기준이 되는 공식 버전과 검사할 행내 커스터마이징 버전을 지정합니다.

  2. 2 변경 등록표 입력

    Manifest에 등록한 BANK-OM ID별 변경 파일, 필수 파일, 업그레이드 확인 대상과 테스트를 읽습니다.

  3. 3 변경 기록 비교

    공식 버전 이후에 추가된 행내 변경과 각 변경에서 수정한 파일을 확인합니다.

  4. 4 업그레이드·동작 검사

    다음 공식 버전의 변경과 행내 API·화면·DB 테스트 결과를 확인합니다.

  5. 5 배포 파일 일치 확인

    검사한 코드와 이미지·설정 파일이 실제 배포 대상과 같은지 확인합니다.

화면에서는 “코드 버전 번호”와 “파일 내용 식별값”으로 설명합니다. 결과 파일에서는 각각 Git commit SHA와 SHA-256 digest라는 기술 명칭으로 저장됩니다.

운영 원칙: Manifest·Registry·Contract는 Git에서 변경 이력을 관리하고 담당자 리뷰를 받아 갱신합니다. candidate-lock.yaml, test-run-set.yaml, 검사 결과는 실행 증거이므로 생성 후 수정하거나 덮어쓰지 않고, 검사 대상 Git 번호와 실행 번호별로 분리해 보관합니다.

현재 구현 범위: 실제 Runtime contracts 실행기는 candidate-lock.yaml, test-run-set.yaml, acgh-result.yaml을 한 번의 실행에서 함께 생성합니다. 현재 OM_TEMP 문서에 있는 source-gate-results.json은 소스 검사 연습 결과이며, 운영 환경의 실제 Runtime contracts 결과를 대신하지 않습니다.

프론트엔드와 백엔드에 같은 검사기를 쓸 수 있나?

변경된 파일을 찾는 검사는 프로그래밍 언어와 관계없이 사용할 수 있습니다. Java·TypeScript·Python·JSON 등 어떤 파일이든 “어느 변경에서 어떤 파일이 바뀌었는가”는 같은 방식으로 확인합니다. 다만 파일 안의 코드가 올바르게 동작하는지는 이 검사만으로 알 수 없습니다.

기능을 실제로 실행하는 검사는 언어와 테스트 도구별 지원이 필요합니다. 현재 테스트 코드 존재 확인은 Python 테스트만 지원하고, 화면 코드 오류 비교는 TypeScript만 지원합니다. Java JUnit이나 TypeScript Jest를 직접 등록하고 실행하는 기능은 추가 개발이 필요합니다.

검사 목적별로 먼저 보기

검사기를 네 가지 질문으로 나눴습니다. 오른쪽 상태는 “검사 프로그램이 존재하는가”가 아니라 “현재 OM_TEMP 자료로 실제 결과까지 확인했는가”를 표시합니다.

B · 공식 업그레이드 영향영향 경로 결과만 확인

관련 파일 변경 여부는 확인했습니다. 전체 커스터마이징 규모와 실제 충돌 비율을 자동 계산하는 연결은 아직 완료되지 않았습니다.
C · 기능 테스트테스트 파일만 확인
커스터마이징이 빠지거나 새로운 화면 오류가 생기면 테스트가 찾아내는가

T60-I 필수 테스트 파일 존재 · T61 기능 누락 시 테스트 실패 여부 · T62 테스트 결과가 나온 코드 확인 · T63 공식 원본 대비 새 TypeScript 오류

현재는 등록한 Python 테스트 파일이 존재하는지만 확인했습니다. 실제 기능 실행 결과는 행내 서버와 브라우저 환경이 필요합니다.
D · 배포 전 최종 확인행내 실행 결과 없음
검사한 코드와 실제로 배포할 파일이 같은가

T90 업그레이드 전 과정 결과 · T91 검사 산출물과 배포 산출물 일치

현재는 결과 문서 형식만 있습니다. 행내 실행 시스템이 만든 실제 로그와 배포 파일의 내용 식별값이 있어야 결과를 판단할 수 있습니다.
T25 같은 번호는 무엇인가?

검사기 코드와 결과 파일을 서로 연결하기 위한 내부 번호입니다. 화면의 읽는 순서를 뜻하지 않으며, 현업 사용자는 번호보다 각 검사 제목과 판정을 확인하면 됩니다.

T93이 두 번 나오는 이유

한 검사 프로그램이 두 가지 질문을 처리하기 때문입니다. 이 화면에서는 “실제 변경 파일이 등록 내용과 같은가”를 T93-범위, “공식 파일 이동으로 기존 검사 규칙이 낡았는가”를 T93-정책으로 나눠 표시합니다.

검사기별 판단 방법과 한계

각 항목을 펼치면 “검사가 답하는 질문 → 판단 방법 → 이 검사만으로 알 수 없는 것” 순서로 설명합니다. 실제 판정은 마지막 실행 결과 가이드에서 확인합니다.

✓

이 검사가 답하는 질문

과거에 파일 상태만 보관하고 변경 기록은 남기지 못한 행내 소스를, 공식 원본과 등록자료만으로 같은 상태까지 다시 만들 수 있는지 확인합니다.

어떻게 판단하나

다시 만든 코드와 과거 보관 소스의 파일 내용을 비교합니다. JSON은 공백과 항목 순서가 달라도 실제 값이 같으면 같은 것으로 판단합니다. Java·TypeScript 등 나머지 파일은 내용이 완전히 같아야 통과합니다.

이 검사만으로 알 수 없는 것

빈 줄처럼 기능에 영향이 없는 차이도 불일치로 판단할 수 있습니다. 현재 OM_TEMP처럼 공식 변경 기록을 유지하는 브랜치에는 이 검사를 사용하지 않고 T25를 사용합니다.

T25 · 공식 버전 출발점 확인검사할 코드가 지정한 공식 버전에서 출발했는가✓
이 검사가 답하는 질문

검사할 행내 커스터마이징 브랜치가 지정한 공식 버전에서 시작했는지 확인합니다.

어떻게 판단하나

검사할 행내 코드의 변경 기록을 거슬러 올라가 지정한 공식 버전이 실제 출발점으로 포함되어 있는지 확인합니다. 이어서 검사를 시작할 때 기록한 코드 버전과 현재 파일 상태가 그대로인지 확인합니다.

이 검사만으로 알 수 없는 것

T26 · 필수 커스터마이징 유지 확인업그레이드 후에도 필수 파일과 테스트 연결이 유지됐는가✓
이 검사가 답하는 질문

어떻게 판단하나

Manifest에서 “반드시 커스터마이징 상태로 남아야 한다”고 지정한 파일이 실제로 존재하며 공식 원본과 다른지 확인합니다. 또한 해당 기능을 확인할 테스트가 등록되어 있는지 확인합니다.

판정 기준

이 검사만으로 알 수 없는 것

파일이 존재하고 공식 원본과 다르더라도 기능이 올바르게 동작한다고 단정할 수는 없습니다. 실제 테스트 코드의 존재는 T60-I가, 실제 실행 결과는 T62가 따로 확인합니다.

T30 · 변경 기록별 BANK-OM 식별 확인공식 버전 이후의 각 행내 변경에 BANK-OM ID가 정확히 하나 있는가✓

판정 기준

이 검사만으로 알 수 없는 것

T31 · BANK-OM 적용 순서 확인후속 수정과 기능 간 선행 관계가 등록된 순서를 지키는가✓

이 검사만으로 알 수 없는 것

T40 · 등록한 변경 파일 범위 확인등록한 파일만 바뀌고 필수 변경은 최종 코드에 반영됐는가✓

판정 기준

등록하지 않은 파일을 수정했거나 필수 변경이 최종 코드에서 사라졌으면 BLOCK입니다.

이 검사만으로 알 수 없는 것

변경 범위를 통제하는 핵심 검사지만 파일 단위로만 판단합니다. 등록한 파일 안에서 잘못된 줄을 수정한 경우까지는 알 수 없습니다. 여러 BANK-OM ID가 같은 파일을 수정하면 공용 파일 소유정보는 공동 소유 ID까지만 알려주며, 실제 줄별 의도는 코드 리뷰가 확인해야 합니다.

T41 · 중요 시스템 파일 변경 확인보안·인증·설정·DB 관련 파일을 수정했는가현재 후보 재검증 필요

판정 기준

변경 금지 경로는 BLOCK, 보안·인증·설정처럼 담당자 검토가 필요한 경로는 APPROVAL입니다. DB 변경과 수집 경로는 위험 정보를 결과에 표시합니다.

현재 결과 상태

이 검사만으로 알 수 없는 것

새 보안 코드가 기존 경로 규칙 밖에 추가되면 놓칠 수 있습니다. 경로 규칙 점검 외에 정적 보안 분석, 보안 담당자 리뷰와 새 모듈 탐지를 함께 사용해야 합니다.

파일 목록이 같아도 파일 안의 어떤 줄을 누가 변경했는지는 알 수 없습니다. 공유 파일은 별도 소유 관계와 코드 리뷰가 필요하며, 폴더 전체 같은 넓은 패턴은 정확 비교가 불가능하므로 현재 검사는 개별 파일 경로만 허용합니다.

공식 공용 코드를 수정한 BANK-OM 기능 수, 공식 원본과 달라진 코드 줄 수, 한 파일을 함께 수정한 BANK-OM ID 수, 실제 업그레이드에서 충돌한 비율을 사전 기준과 비교합니다.

이 검사만으로 알 수 없는 것

판정 기준

파일이 없거나, Python 코드로 읽을 수 없거나, 등록한 테스트 항목을 찾을 수 없으면 BLOCK입니다.

T61 · 테스트의 누락 탐지 능력 확인커스터마이징을 제거하면 해당 테스트가 실제로 실패하는가과거 자료 일부만 확인

어떻게 판단하나

하나는 BANK-OM 기능이 포함된 코드, 다른 하나는 해당 기능만 제거한 코드로 준비합니다. 같은 테스트를 실행해 포함된 코드는 통과하고 제거한 코드만 예상한 이유로 실패하는지 확인합니다.

판정 기준

기능 포함본은 통과하고 제거본만 실패하면 PASS입니다. 기능을 제거했는데도 테스트가 통과하면 누락을 발견하지 못하는 테스트이므로 BLOCK입니다. 환경 문제로 실행하지 못했으면 판정을 보류합니다.

이 검사만으로 알 수 없는 것

제거본의 다른 장애를 커스터마이징 누락으로 오인할 수 있습니다. 따라서 커스터마이징 포함본은 통과하고 제거본만 미리 정한 오류 종류와 메시지로 실패하는지, 같은 환경에서 반복 확인해야 합니다.

판정 기준

필수 테스트가 빠지거나 실패했으면 BLOCK입니다. 결과가 다른 코드나 배포 파일에서 나온 것이면 결과를 신뢰할 수 없으므로 중단합니다. 중요한 테스트가 재실행 후에만 통과하면 APPROVAL입니다.

이 검사만으로 알 수 없는 것

현재 결과에는 DB·검색엔진·설정 버전처럼 실행 환경을 구분하는 값이 없습니다. 같은 코드라도 환경이 다르면 결과가 달라질 수 있으므로 운영 적용 전 환경 정보도 함께 고정해야 합니다.

어떻게 판단하나

판정 기준

행내 코드에만 생긴 오류는 BLOCK입니다. 공식 원본부터 있던 오류가 남아 있으면 자동 통과하지 않고 APPROVAL로 표시합니다.

이 검사만으로 알 수 없는 것

파일이 이동하면 같은 오류도 새로운 오류처럼 보일 수 있습니다. 또한 두 코드를 서로 다른 Node·Yarn 환경에서 검사하면 공정한 비교가 아니므로 동일 환경에서 실행해야 합니다.

판정 기준

판정 기준

이 검사만으로 알 수 없는 것

검사기별 입력과 출력 한눈에 보기
