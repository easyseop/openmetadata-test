각 검사기는 무엇을 읽고, 어떻게 판단하는가

이 문서는 검사 결과가 아니라 검사 방법을 설명합니다. 현재 검사 결과와 책임자 판정 라벨은 3차에서, 실제 Git 병합·검사 화면과 연결한 결과는 4차 시연에서 보여줍니다.

검토 결론 현재 검사기는 소스 변경을 관리하는 데는 유효하지만, 경로 기반 검사와 외부 입력에 의존하는 부분이 있어 행내 동작·보안·배포 검사를 함께 사용해야 합니다.

검사기가 사용하는 정보와 검사 순서

  1. 1 코드 버전 지정

    공식 원본과 행내 배포용 OpenMetadata의 Git commit SHA를 지정합니다.

  2. 2 변경관리표 입력

    활성 BANK-OM ID별 파일 범위, 필수 파일, 감시 파일과 테스트를 읽습니다.

  3. 3 Git 기록 비교

    공식 원본 이후의 모든 커밋과 각 커밋이 변경한 파일을 확인합니다.

  4. 4 업그레이드·동작 검사

    다음 공식 버전의 변경과 행내 API·화면·DB 테스트 결과를 확인합니다.

  5. 5 배포 파일 일치 확인

    검사한 코드와 이미지·설정 파일이 실제 배포 대상과 같은지 확인합니다.

Git commit SHA는 저장된 코드 버전을 식별하는 값입니다. SHA-256 digest는 파일 내용이 같은지 비교하기 위해 계산한 값입니다.

프론트엔드와 백엔드에 같은 검사기를 쓸 수 있나?

Git 커밋과 파일 변경을 확인하는 검사는 언어에 상관없이 그대로 사용할 수 있습니다. T25-R·T25·T26·T30·T31·T40·T41·T42·T43·T93은 Java·TypeScript·Python·JSON·YAML·SQL 등 파일 종류와 관계없이 Git 이력, 각 커밋에서 바뀐 파일 경로와 공식 원본 대비 최종 파일 상태를 확인합니다. 따라서 프론트엔드와 백엔드 파일을 같은 방식으로 관리할 수 있습니다. 다만 이 공통 검사는 파일 내부 코드의 의미나 실행 동작까지 언어에 관계없이 이해하는 검사가 아닙니다.

테스트 코드 자체를 해석하거나 실행하는 검사는 언어·도구별 지원이 필요합니다. 현재 T60-I는 Python pytest 코드만 확인하고, T63은 TypeScript 오류만 비교합니다. T61·T62도 Python pytest를 실행 도구로 사용하지만 그 테스트가 Java 백엔드 API와 TypeScript 프론트 화면을 호출하는 것은 가능합니다. Java JUnit이나 TypeScript Jest를 직접 등록·실행하려면 해당 도구용 확인 방식과 실행 연결을 추가해야 합니다.

검사기별 실제 검사 방법과 예외 가능성

검사명 무엇을 확인하나 실제로 어떻게 검사하나 예외 가능성과 보완 방법
A. 공식 원본과 행내 커스터마이징 소스 확인
T25-R
과거 행내 변경 재현		 과거 행내 소스에서 등록한 파일을 공식 원본 위에 다시 적용했을 때 같은 내용이 만들어지는지 확인합니다. 공식 원본과 과거 행내 소스의 변경 파일 목록을 먼저 고정한 뒤, 재구성한 브랜치의 파일을 비교합니다. JSON은 공백과 키 순서를 제외한 실제 값을 비교하고, Java·TypeScript 등 나머지 파일은 Git에서 차이가 없어야 합니다. Java 파일에 빈 줄 하나만 달라도 차이로 판단해 중단합니다. 의미는 같지만 서식만 다른 경우에도 중단될 수 있으므로, 자동 통과시키기보다 서식 차이만 따로 보여주고 담당자가 확인하도록 보완하는 편이 안전합니다.
T25
공식 원본 포함		 행내 배포용 OpenMetadata가 승인된 공식 버전의 코드를 실제 Git 이력에 포함하는지 확인합니다. Git의 공통 조상과 포함 관계를 조회해 공식 버전의 commit SHA가 행내 코드의 조상인지 확인합니다. 동시에 검사 대상 commit SHA와 전체 파일 상태가 사전에 기록한 검사 대상과 같은지도 확인합니다. 공식 코드가 이력에 포함됐다는 사실만 증명하며, 충돌을 올바르게 해결했는지 또는 기능이 정상인지까지 증명하지는 않습니다. 그래서 T26·T40과 행내 동작 검사가 함께 필요합니다.
T26
활성 커스터마이징 확인		 변경관리표에서 상태가 active인 모든 BANK-OM ID의 커스터마이징이 검사 대상 코드에 남아 있는지 확인합니다. 각 활성 BANK-OM ID의 필수 파일이 존재하고 공식 원본과 실제로 다른지 확인합니다. 전체 등록 파일 중 필수가 아닌 파일이 없어졌거나 공식 원본과 같아지면 담당자 확인 대상으로 분류하며, 업무 계약과 연결된 테스트 목록도 함께 확인합니다. 파일이 존재하고 공식 원본과 다르더라도 기능이 올바르게 동작한다고 단정할 수는 없습니다. 실제 테스트 코드의 존재는 T60-I가, 실제 실행 결과는 T62가 따로 확인합니다.
T60-I
필수 테스트 코드 확인		 각 커스터마이징의 핵심 업무 동작을 확인하기로 등록한 테스트가 이름만 있는 것이 아니라 실제 코드로 존재하는지 확인합니다. 현재 등록된 9개는 InstanceCode API·검색, QueryReport 연결, Data Assertions API·화면, 은행 컬럼 API·화면, 한글 입력 화면, Sybase·Tibero 연결 스키마를 확인합니다. contracts.yaml에 적은 Python pytest 파일 경로와 함수 이름을 읽고, Python 코드 구조 분석(AST)으로 파일을 정상적으로 해석할 수 있는지와 해당 테스트 함수가 실제로 존재하는지 확인합니다. 이 단계에서는 테스트를 실행하지 않습니다. 현재 T60-I는 .py 파일만 허용하므로 Java JUnit이나 TypeScript Jest 테스트의 존재는 확인하지 않습니다. Python 테스트가 Java API와 TypeScript 화면을 실제로 호출할 수는 있지만, 다른 테스트 언어를 직접 등록하려면 검사기에 언어·프레임워크별 확인 방식을 추가해야 합니다. 또한 현재는 계약에서 파생된 테스트만 확인하므로 Manifest의 direct_tests도 같은 방식으로 확인하도록 보완해야 합니다.
T30
커밋 메시지 형식		 공식 원본 이후의 각 커밋이 어떤 BANK-OM 변경인지 빠짐없이 구분되는지 확인합니다. 검사기는 공식 원본부터 검사 대상 commit SHA까지의 모든 커밋을 Git에서 순서대로 가져옵니다. 각 커밋 메시지의 Customization-ID: 항목과 그 커밋이 변경한 파일을 읽어, 행내 소스를 바꾼 커밋에 BANK-OM ID가 정확히 하나 있는지 확인합니다. 하나의 BANK-OM ID 안에 서로 다른 목적의 변경을 섞어도 파일 범위가 같으면 이 검사만으로는 구분하기 어렵습니다. 커밋 목적을 작게 유지하고 T40·T93 변경범위 검사로 실제 변경 파일까지 함께 비교해야 합니다.
T31
커밋 순서와 ID 사용		 같은 BANK-OM ID를 여러 커밋에 사용할 수 있는지, 커밋이 연속되어 있는지, ID 간 선행 관계가 순환하지 않는지 확인합니다. Git 커밋을 오래된 순서부터 나열한 뒤 같은 ID의 위치를 비교합니다. 여러 커밋 사용이 변경관리표에서 허용됐는지, 다른 ID가 중간에 끼지 않았는지, 폐기한 ID를 다시 쓰지 않았는지 확인합니다. 선행 관계 자체를 빠뜨린 경우에는 검사기가 업무 관계를 새로 추론하지 못합니다. 커스터마이징 설계자가 선행 BANK-OM ID를 변경관리표에 등록하고 리뷰하는 절차가 필요합니다.
T40
변경 파일 범위		 각 BANK-OM 커밋이 사전에 등록한 파일만 변경했고, 반드시 반영돼야 할 파일이 최종 코드에서 실제로 변경됐는지 확인합니다. 첫째, 각 커밋이 변경한 모든 파일을 allowed_changed_paths와 비교합니다. 둘째, 공식 원본과 최종 코드의 전체 차이를 구해 required_changed_paths가 실제 차이에 포함되는지 확인합니다. 잠깐 수정했다가 원상 복구한 필수 파일도 이 단계에서 잡힙니다. 변경 범위를 통제하는 핵심 검사지만 파일 단위로만 판단합니다. 허용된 파일 안에서 잘못된 줄을 수정한 경우까지는 알 수 없고, 여러 BANK-OM ID가 같은 파일을 수정할 때의 줄 단위 소유 관계는 T25-R의 공유 파일 설정과 코드 리뷰가 보완해야 합니다.
T41
민감 파일 확인		 보안·인증·설정·DB 경로를 위험도 단계로 나누고, 실제 변경 파일이 어느 단계에 해당하는지 확인합니다. AST로 코드 내용을 분석하는 검사가 아닙니다. sensitive-zones.yaml의 경로 규칙과 실제 변경 파일을 비교합니다. 현재 보안 서비스 경로는 변경 시 중단하고, 인증 스키마와 설정 경로는 담당자 승인을 요구하며, DB 변경과 수집 경로는 결과에 표시만 합니다. 새 보안 코드가 기존 경로 규칙 밖에 추가되면 놓칠 수 있습니다. 경로 규칙 점검 외에 정적 보안 분석, 보안 담당자 리뷰와 새 모듈 탐지를 함께 사용해야 합니다.
T93 · 변경범위
등록 파일과 실제 이력 일치		 각 BANK-OM ID가 실제로 변경한 파일 목록과 변경관리표에 등록한 정확한 파일 목록이 같은지 확인합니다. Git 커밋 이력을 BANK-OM ID별로 다시 모아 실제 변경 파일 목록을 만듭니다. 실제로 변경했지만 등록하지 않은 파일은 중단하고, 등록했지만 해당 ID가 변경하지 않은 파일은 담당자 확인 대상으로 분류합니다. 파일 목록이 같아도 파일 안의 어떤 줄을 누가 변경했는지는 알 수 없습니다. 공유 파일은 별도 소유 관계와 코드 리뷰가 필요하며, 폴더 전체 같은 넓은 패턴은 정확 비교가 불가능하므로 현재 검사는 개별 파일 경로만 허용합니다.
B. 다음 공식 OpenMetadata 버전의 영향 확인
T42
감시 파일 변경 확인		 행내에서 직접 수정하지 않았지만 커스터마이징이 의존하는 공식 파일·설정·라이브러리가 새 공식 버전에서 바뀌었는지 확인합니다. 기존 공식 버전과 새 공식 버전의 Git 차이를 구하고, 각 BANK-OM 변경관리표의 upgrade_watch에 등록한 경로·설정 키·라이브러리 이름과 비교합니다. 하나라도 일치하면 자동 통과하지 않고 담당자 확인을 요구합니다. 질문하신 감시 파일의 실제 검사 기능이 T42입니다. 다만 감시 대상을 누락하면 변경이 있어도 통과할 수 있으므로 자동 제안 기능과 담당자 검토가 필요합니다.
T43
관리 부담 증가		 공식 공용 코드의 커스터마이징 규모가 커져 다음 업그레이드를 감당하기 어려운 수준인지 확인합니다. 종류(kind)가 core-patch인 활성 BANK-OM ID 수, 공식 원본 대비 추가·삭제한 줄 수, 여러 BANK-OM ID가 함께 수정한 파일의 최대 ID 수와 재적용 충돌 비율을 정책 한도와 비교합니다. 현재 각 수치가 14/19개, 14,000/18,000줄, 4/8개, 충돌률 15%/35%를 초과하면 각각 담당자 승인 또는 중단이 필요합니다. 충돌률은 검사기가 직접 재현하지 않고 실행 명령의 입력값으로 받습니다. 실제 업그레이드 재적용 결과에서 자동 계산하고 근거 파일과 함께 저장하도록 보완하지 않으면 잘못된 숫자를 넣을 위험이 있습니다. 또한 수정량이 작아도 설계가 복잡할 수 있으므로 수치만으로 품질을 판단하면 안 됩니다.
T93 · 감시규칙
감시 규칙 유효성		 공식 버전의 파일 이동이나 모듈 추가 때문에 기존 감시 규칙이 더 이상 유효하지 않은지 확인합니다. 새 공식 버전의 전체 파일 목록에서 각 감시 경로가 최소 한 파일과 일치하는지 확인합니다. 이전에는 없던 최상위 폴더가 추가됐는데 소유 구분 규칙에 없으면 검사 불가로 처리합니다. 경로가 다른 파일과 우연히 일치하면 잘못 통과할 수 있습니다. 또한 현재 통합 실행기는 감시 파일 패턴만 넘기며 민감 경로 패턴의 노후화는 함께 검사하지 않으므로, T41의 민감 경로도 같은 방식으로 검사하도록 보완해야 합니다.
C. 행내 테스트·배포 환경에서 확인
T61
기능 누락 탐지 시험		 커스터마이징을 제거했는데도 테스트가 통과하는 형식적인 테스트인지 확인합니다. 해당 BANK-OM 변경이 없는 코드 버전을 별도로 만들고 같은 필수 테스트를 실행합니다. 이 버전에서 테스트가 명확한 실패로 끝나야 커스터마이징 누락을 잡는 테스트라고 판단합니다. 행내 환경에서는 API와 화면이 정상이라는 별도 확인을 전후에 실행하고 대상 테스트를 두 번 반복합니다. 테스트가 커스터마이징 누락이 아닌 다른 이유로 실패해도 현재 소스 검사는 성공으로 오인할 수 있습니다. 기대한 오류 종류와 핵심 메시지까지 확인하고, 커스터마이징이 있는 버전에서는 같은 테스트가 통과하는지 함께 비교해야 합니다.
T62
결과와 코드 연결		 테스트 결과가 정확히 어떤 소스 코드와 배포 파일, 어떤 검사기와 테스트 코드에서 나온 것인지 확인합니다. 테스트 결과에 행내 배포용 OpenMetadata commit SHA, 배포 파일의 SHA-256 digest, 검사기 버전, 테스트 묶음 버전을 함께 저장합니다. 필수 테스트가 빠졌거나 마지막 실행이 실패하면 중단하고, 중요 테스트가 재실행 후에만 통과하면 담당자 승인을 요구합니다. 현재 결과 형식에는 실행 환경의 설정과 버전을 식별하는 값이 없습니다. 같은 코드라도 DB·검색엔진·설정이 다르면 결과가 달라질 수 있으므로 환경 정보의 digest와 신뢰할 수 있는 실행 시스템의 서명을 추가해야 합니다.
T63
화면 코드 오류 비교		 행내 커스터마이징 때문에 공식 원본보다 새로운 TypeScript 오류가 생겼는지 확인합니다. 공식 원본과 행내 코드에서 같은 TypeScript 검사를 실행한 뒤, 파일 경로와 오류 코드별 발생 횟수를 비교합니다. 행내 코드에만 생긴 오류는 중단하며, 공식 원본부터 있던 오류가 남아 있으면 자동 통과하지 않습니다. 파일 이동은 같은 오류도 새 오류처럼 보이게 할 수 있고, 오류 메시지만 바뀐 경우에는 담당자 판단이 필요합니다. 현재 비교 함수는 Node·Yarn 버전이 같은지 직접 강제하지 않으므로 실행 환경과 전체 로그의 digest를 검사 입력에 연결해야 합니다.
T90
구·신 버전 동작 비교		 실제 데이터와 행내 환경에서 업그레이드, DB·검색·권한·API·수집·복구가 모두 정상인지 확인합니다. 운영 스냅샷 복원부터 롤백 연습까지 정해진 12단계의 결과가 모두 통과인지 확인하고, 결과 문서를 행내 배포용 OpenMetadata commit SHA·배포 파일 digest·T62 결과와 연결합니다. 현재 T90 코드는 12단계 결과 문서의 형식과 상태만 판단하며 각 단계를 직접 실행하거나 증거 파일의 내용을 검증하지 않습니다. 신뢰할 수 있는 실행 시스템이 각 단계의 실제 로그를 보관하고 서명하도록 보완해야 합니다.
T91
검사본과 배포본 일치		 검사를 마친 소스와 이미지·Helm 설정을 다시 만들지 않고 그대로 배포하는지 확인합니다. 승인 시점에 행내 배포용 OpenMetadata commit SHA, 컨테이너 이미지 digest, Helm 파일 digest, 검사 결과 digest를 고정합니다. 배포 시 관측한 값이 하나라도 다르거나 중간에 다시 빌드했으면 중단합니다. digest를 어디에서 읽었는지가 신뢰할 수 있어야 합니다. T91만으로는 외부망에서 내부망으로 옮기는 과정의 서명이나 내부망 재검증까지 보장하지 않으므로 별도의 반입 검증이 필요합니다.

운영 적용 전에 우선 보완할 항목

  1. T41경로 비교에 정적 보안 분석과 보안 담당자 리뷰를 추가합니다.
  2. T42·T93감시 파일 자동 제안과 민감 경로 규칙의 노후화 검사를 함께 실행합니다.
  3. T43충돌률을 사람이 입력하지 않고 실제 업그레이드 재적용 결과에서 자동 계산합니다.
  4. T60-IPython 외에 Java JUnit·TypeScript Jest를 등록할 수 있게 하고 direct_tests의 실제 코드 존재도 확인합니다.
  5. T61단순 실패가 아니라 커스터마이징 누락 때문에 발생한 실패인지 오류 종류와 메시지까지 확인합니다.
  6. T62·T63DB·검색엔진·Node·Yarn·설정 등 실행 환경을 하나의 digest로 기록하고 결과에 연결합니다.
  7. T90·T91각 단계의 실제 로그와 배포 digest를 신뢰할 수 있는 실행 시스템이 서명하고 보관하도록 합니다.
