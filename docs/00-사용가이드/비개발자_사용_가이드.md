# 비개발자용 OpenMetadata 업그레이드 안전 가이드

> 최종 갱신: 2026-07-31
>
> 대상: 업무 담당자, 데이터 오너, 승인자, 운영자, 감사 담당자
>
> 현재 결론: **코드를 읽어서 하는 검사는 통과했지만, 실제 서버에 올려서 하는
> 검증은 아직 하지 않았다. 그러므로 운영 배포는 아직 승인할 수 없다.**

> 이 문서는 “무엇을 어떻게 읽어야 하는가”를 설명한다. 화면을 보며 직접 따라
> 하고 싶으면
> [`비개발자용 OpenMetadata 시연·테스트 가이드`](비개발자_시연_가이드.md)를
> 먼저 연다. 그쪽에는 실제 GitHub 화면 캡처 10장과 함께, 명령어 없이 10분 안에
> 상태를 확인하는 방법이 있다.

## 1. 이 시스템은 무엇인가

공식 OpenMetadata가 새 버전으로 올라갈 때, 은행에서 추가한 기능이 빠지거나
잘못 바뀌지 않았는지 자동으로 확인하고 그 근거를 남기는 시스템이다.

쉽게 말하면 다음 세 가지 사고를 막는다.

1. 은행 기능을 새 버전에 옮기면서 일부를 빠뜨리는 사고
2. 테스트한 코드와 실제 배포한 파일이 달라지는 사고
3. 검사 오류나 LLM의 낙관적인 답을 정상 통과로 오해하는 사고

은행에서 추가한 기능에는 하나씩 `BANK-OM-001` 같은 번호를 붙여 관리한다.
현재 등록된 것은 11개이고, 성격이 두 가지로 나뉜다.

**업무 기능 7개** — 직원이 화면에서 직접 쓰는 기능이다.

| ID | 기능 | 무엇을 하는가 |
|---|---|---|
| `BANK-OM-001` | InstanceCode | 행내 기준코드를 등록·조회·검색한다 |
| `BANK-OM-002` | QueryReport | 쿼리 리포트와 사용된 쿼리 목록을 연결해 본다 |
| `BANK-OM-003` | Data Assertions | 실패한 데이터 점검 결과를 담당자·테이블과 함께 본다 |
| `BANK-OM-004` | 은행 컬럼 표시 | 컬럼 순번·키·제약조건 등 행내 확장 정보를 보여준다 |
| `BANK-OM-005` | 한글 입력 보정 | 한글 입력 중 글자가 끊기거나 중복되지 않게 한다 |
| `BANK-OM-006` | Sybase 연결 | Sybase 데이터베이스에 연결해 메타데이터를 수집한다 |
| `BANK-OM-007` | Tibero 연결 | Tibero 데이터베이스에 연결해 메타데이터를 수집한다 |

**안전 보강 4개** — 새 화면이 아니다. 위 기능들이 UI 타입 검사에서 깨지지
않도록 받쳐 주는 부품이며, 직원 눈에는 보이지 않는다.

| ID | 무엇을 막는가 |
|---|---|
| `BANK-OM-008` | InstanceCode·QueryReport 검색을 화면에 연결할 때 생기던 타입 오류 |
| `BANK-OM-009` | 공통 검색 결과 타입표에서 일부 항목이 빠져 있던 문제 |
| `BANK-OM-010` | 알림 검색 결과에 엔터티 ID가 없을 때 화면이 깨지던 문제 |
| `BANK-OM-011` | 공통 목록 검색이 결과 타입을 추측하던 문제(Domain·DataProduct가 각자 명시하게 바꿈) |

안전 보강 4개는 1.13.1 후보 쪽 등록(`kb-openmetadata`)에만 있다. 1.13.0
등록에는 업무 기능 7개만 들어 있다. 그래서 아래 글에서 “7개”와 “11개”가
번갈아 나오는데, 어느 버전을 말하는지에 따라 숫자가 달라지는 것이다.

## 2. 5분 안에 현재 상태 확인하기

비개발자는 코드를 읽을 필요가 없다. 아래 순서만 확인하면 된다.

1. 화면을 직접 보며 따라 하고 싶으면
   [`비개발자용 시연·테스트 가이드`](비개발자_시연_가이드.md)를 먼저 연다.
2. [`STATUS.md`](../../STATUS.md)를 연다. 현재 구현 상태를 한 장으로 적어 둔
   파일이다.
3. 그 파일 맨 위의 **현재 결론**과 `Important production blockers`(배포를
   막고 있는 항목 목록)를 읽는다.
4. GitHub Actions에서 `source-candidate` 검사의 가장 최근 실행이 성공했는지
   본다. 이것이 “코드를 읽어서 하는 검사”다.
5. `Runtime contracts` 검사의 실행 결과를 따로 본다. 이것이 “실제 서버에
   올려서 하는 검사”다. 4번이 성공해도 5번은 별개다.
6. `skip`, `UNASSIGNED`, `blocker`가 하나라도 남아 있으면 배포 완료로
   승인하지 않는다.
7. 실제 배포 판단은 아래 네 가지 증거가 모두 준비된 뒤에만 한다. T로 시작하는
   번호는 이 시스템의 검사 단계 번호이며, 뜻은 9절 용어표에 있다.
   - T62: 실제 서버에서 기능이 동작하는지 확인한 결과
   - T90: 구버전에서 신버전으로 실제로 올려 본 결과
   - T91: 검증한 그 산출물만 배포 단계로 올렸다는 기록
   - T94: 내부망에 들여올 때 서명과 해시를 다시 확인한 기록

현재 확인 가능한 링크:

- [검사 저장소와 문서](https://github.com/easyseop/openmetadata-test/tree/claude/markdown-file-feedback-26933w)
- [현재 제품 후보 브랜치](https://github.com/easyseop/OpenMetadata/tree/codex/bank-vendor-1.13.1-rebuild)
- [현재 `BANK-OM-011` 후보의 소스 검사 성공 기록](https://github.com/easyseop/openmetadata-test/actions/runs/30222439344)
- [실제 환경 계약 실행 화면](https://github.com/easyseop/openmetadata-test/actions/workflows/runtime-contracts.yml)

두 번째 링크의 후보 브랜치는 OpenMetadata 제품 저장소 쪽 후보다. 준비도구가
쓰는 `OM_TEMP`의 1.13.1 patch/custom 브랜치는 아직 원격에 올라와 있지 않아서
1.13.1 검사를 같은 후보로 다시 실행할 수 없다.

> 초록색 CI는 **소스 수준의 등록·누락·결속 검사가 통과했다**는 뜻이다.
> 실제 데이터와 운영 환경에서 배포해도 된다는 뜻은 아니다.

### 공유 HTML의 초록 체크를 읽는 방법

업그레이드 실행 가이드를 HTML로 공유한 화면에는 검사 항목마다 초록 체크가
붙어 있다. 이 체크는 GitHub CI의 “전체 성공” 표시와 뜻이 다르다. **화면 맨
위에 적힌 바로 그 OM_TEMP commit을 대상으로 실행한 결과 파일이 실제로 있을
때만** 붙는다.

현재 기준 commit은 `dee330ebd5abfe33e1ac61e1ca31879746a1b423`이고, 17개 상세
항목 중 8개에만 초록 체크가 있다. 나머지 9개에 체크가 없는 이유는 다음과 같다.

| 항목 | 체크가 없는 이유 |
|---|---|
| T25-R | 공식 이력이 끊긴 코드 뭉치를 기능별로 다시 쌓아 올려 검사 가능한 후보로 만드는 절차다. 지금 OM_TEMP 후보는 이미 공식 이력 위에 얹혀 있으므로 이 절차를 쓸 필요가 없다 |
| T61 소스 2건·T63 | 지금 화면의 OM_TEMP 후보가 아니라 다른 후보(`kb-openmetadata`)에서 나온 결과다 |
| T93 | 실제 정책 파일이 아니라 동작 확인용 임시 입력으로 돌린 결과다 |
| T41 | 검사 코드의 계산 오류를 고쳐 1.13.0에서는 다시 통과했다. 그러나 1.13.1 후보 브랜치가 원격에 없어 같은 후보로 재실행하지 못했으므로 `재검증 필요`로 둔다 |

정리하면, 다른 후보에서 나온 결과나 개발자용 단위 테스트 결과가 아무리 많아도
이 화면에서는 초록색으로 표시하지 않는다. 각 항목의 실제 판정값(`PASS`인지
`승인 필요`인지)은
`OM_TEMP_1.13.0_1.13.1_업그레이드_실행_가이드_미리보기.html`에서 확인한다.

### 검사 전 준비 자동화는 어디까지 됐나

예전에는 “어느 BANK-OM이 어느 파일을 바꿨는가”를 사람이 손으로 적어
등록자료(Manifest·Registry)에 넣었다. 손으로 적으면 빠뜨리거나 잘못 적어도
아무도 모른다. 2026-07-30에 이 부분을 자동화했다.

절차는 세 단계다.

```text
plan(도구가 Git에서 사실만 계산) → 사람이 업무 판단을 승인 → apply(승인분만 반영)
```

- `plan`은 읽기 전용이다. 등록자료를 건드리지 않고, patch/custom이 가리키는
  commit과 BANK-OM별 변경 파일을 계산해 제안서·질문 목록·변경 미리보기를 만든다.
- 도구는 담당자·중요도·필수 파일 같은 **업무 판단은 절대 추측하지 않는다.**
  대신 질문으로 만들어 사람에게 넘긴다.
- `apply`는 승인한 시점과 지금이 조금이라도 다르면(브랜치가 움직였거나
  등록자료가 바뀌었거나 제안서를 손으로 고쳤으면) 중단한다.
- ID가 없는 commit, 한 commit에 ID가 둘 이상인 경우, 이어지지 않는 두 브랜치,
  필수 파일 소실, symlink·submodule 같은 특수 파일은 자동으로 차단한다.

같은 시기에 검사 코드 쪽도 함께 고쳤다.

- Manifest의 전체 변경 파일을 T41이 빠짐없이 읽도록 수정
- Registry에 `provenance`(그 기능이 공식 snapshot 시점부터 있던 것인지,
  나중에 추가한 것인지)를 반드시 적도록 변경
- 등록자료 분석이 실패하면 개발자용 오류 덤프 대신 `analysis_error` 판정으로
  남도록 변경
- 검사 대상을 고정하는 Candidate lock에서 “소스 코드”와 “실제 빌드 산출물”을
  구분하도록 확장

**현재 1.13.0 실행 결과:** 도구가 자동으로 바꾼 등록자료 0건, 차단 0건, 분석
오류 0건이고, 기능별 사람 판단 5건이 남아 `REVIEW_REQUIRED` 상태다. 승인자를
추측하지 않았고 등록자료도 아직 반영하지 않았다. 1.13.0 후보는 공식 원본에서
그대로 다시 만들어 낼 수 있으며(`3a2811cf...`), 재현 방법은
`harness/registrations/om-temp-1.13.0/REPRODUCIBILITY.md`에 있다.

따라 하는 방법은
[`OM_TEMP 검사 전 준비도구 쉬운 사용법`](OM_TEMP_검사전_준비도구_쉬운사용법.md)에
있다. **이 자동화가 완성된 것을 실제 빌드·실서버 테스트·운영 승인이 끝난
것으로 읽으면 안 된다.** 자동화된 것은 “등록자료를 정확히 만드는 일”까지다.

## 3. 결과를 어떻게 읽는가

| 화면/결과 | 쉬운 뜻 | 해야 할 일 |
|---|---|---|
| `pass` | 이 검사가 요구한 근거는 충족됨 | 다음 단계로 진행 |
| `approval` | 자동 검사는 끝났지만 사람 판단이 필요함 | 지정 승인자가 근거 검토 |
| `block` | 필수 조건이 부족하거나 위험이 확인됨 | 원인 해소 전 배포 중지 |
| `analysis_error` | 검사가 답을 내지 못함. “문제 없음”이 아니라 “확인 자체를 못 했음” | 통과로 보지 말고 검사 입력부터 복구 |
| `skip` | 필요한 서버나 입력값이 없어 아예 실행하지 못함 | 실제 환경을 준비해 다시 실행 |
| `UNASSIGNED` | 책임자가 정해지지 않음 | 기능 오너와 승인자 지정 |

`block`과 `analysis_error`는 헷갈리기 쉽다. `block`은 검사가 정상으로 끝났고
그 결과가 “안 된다”인 상태이고, `analysis_error`는 검사가 끝까지 가지도
못한 상태다. 둘 다 통과가 아니지만 다음에 할 일이 다르다 — 앞은 원인을
고치는 일이고, 뒤는 검사를 다시 돌게 만드는 일이다.

여러 결과가 섞이면 그중 가장 위험한 것이 전체 결과가 된다. 예를 들어 9개가
`pass`이고 1개가 `block`이면 전체는 `block`이다. 그리고 `analysis_error`나
`block`은 사람이 승인해서 `pass`로 바꿀 수 없다.

## 4. 업무 담당자가 준비할 정보

변경이나 업그레이드를 요청할 때 아래 정보를 한 번에 전달한다.

| 필요한 정보 | 쉬운 설명 | 예시 |
|---|---|---|
| 변경 목적 | 무엇을 왜 바꾸는가 | “Tibero 연결 설정을 새 버전에서도 유지” |
| 영향 기능 | 1절 표의 11개 중 어느 것인가 | `BANK-OM-007` Tibero |
| 업무 오너 | 결과를 책임지는 사람/팀 | 데이터플랫폼팀 |
| 승인자 | 독립적으로 확인할 두 사람 | 개발 승인자, 운영 승인자 |
| 지켜야 할 업무 규칙 | 바뀌면 안 되는 동작 | “저장 후 다시 조회해도 연결 종류가 Tibero” |
| 테스트 준비값 | 실제 실행에 필요한 URL·대상 ID 등 | 테스트 환경 URL, 테스트 테이블 |
| 희망 일정 | 검증과 배포가 필요한 시점 | YYYY-MM-DD |

토큰, 비밀번호, 개인 키는 문서·티켓·인수인계서에 적지 않는다. 비밀값은 승인된
비밀 저장소나 CI secret으로만 전달한다.

## 5. 실제 사용 시나리오

### 시나리오 A — 공식 OpenMetadata 버전 업그레이드

1. 업무 오너가 새 공식 버전과 변경 목적을 제출한다.
2. 개발자가 승인된 공식 버전 위에 은행 기능을 다시 얹어 검사 후보를 만든다.
3. 소스 게이트가 11개 기능마다 “commit에 기능 ID가 제대로 붙었는가, 필수
   파일이 남아 있는가, 약속한 테스트 코드가 실제로 있는가”를 검사한다.
4. 실제 OpenMetadata 테스트 서버에 올려, 업무 규칙과 화면 동작을 확인한다.
5. 구버전 데이터를 복원한 뒤 DB 변경, 검색 재색인, ingestion, 권한과 API를
   포함한 업그레이드 시나리오를 실행한다.
6. 검증한 바로 그 이미지·패키지·Helm만 승격하고 내부망에서 서명과 해시를 다시
   확인한다.

어느 단계든 `block`, `analysis_error`, 필수 `skip`이 있으면 다음 배포 단계로
넘어가지 않는다.

### 시나리오 B — 은행 기능을 추가하거나 수정

1. 기존 `BANK-OM-nnn` 기능의 수정인지 새 기능인지 정한다.
2. 목적, 오너, 필수 파일, 업무 규칙과 테스트를 함께 등록한다.
3. 코드만 추가하고 테스트나 오너를 나중으로 미루지 않는다.
4. 검사 결과와 변경 근거가 해당 기능 ID에 묶였는지 확인한다.
5. 사용자에게 보이는 동작이 달라지면 이 가이드의 예시와 절차도 같은 개발 묶음에서
   갱신한다.

### 시나리오 C — CI는 초록색인데 배포 가능한지 묻는 경우

현재가 바로 이 경우다. 소스 후보 CI는 통과했지만 다음 항목이 남아 있으므로
답은 **아직 배포 불가**다.

현재 `BANK-OM-011` 후보는 원격 검사
[`30222439344`](https://github.com/easyseop/openmetadata-test/actions/runs/30222439344)에서
자동검사 316건을 통과했고, 실제 서버가 있어야만 돌릴 수 있는 7건은 건너뛰었다.
11개 등록 기능, 9개 필수 테스트 구현, 소스 게이트 5개, 그리고 시나리오 E에서
설명하는 “테스트가 진짜인지 확인하는 실험” 2건도 함께 통과했다. 이 결과는
제품 후보 `849ae756...` 하나에 묶여 있다.

여기서 통과한 것은 “코드와 등록자료를 대조해서 알 수 있는 것”뿐이다. 아래는
그 방법으로는 알 수 없어서 아직 남아 있는 항목이다.

| 남은 항목 | 왜 아직 확인 못 했는가 |
|---|---|
| 11개 기능 전부 오너가 `UNASSIGNED` | 누가 책임질지는 사람이 정해야 한다 |
| 두 사람 승인 경로 미지정 | 같은 이유 |
| API 검사 4건 미실행 | 실제 OpenMetadata 서버가 떠 있어야 한다 |
| 브라우저 검사 3건 미실행 | Data Assertions·은행 컬럼·한글 입력은 화면을 직접 띄워야 확인된다 |
| 전체 Java/UI 빌드와 타입 기준선 미완료 | 시나리오 G 참고 |
| 실제 업그레이드·승격·서명·내부망 반입 증거 없음 | 아직 실행하지 않았다 |
| GitHub 보호 브랜치와 2인 승인 규칙 미설정 | 저장소 설정을 사람이 켜야 한다 |

### 시나리오 D — 실제 환경 계약 검사를 요청

이 검사는 실제로 떠 있는 OpenMetadata 서버를 대상으로 한다. 그래서 시작 전에
준비할 값이 다섯 개 있다.

| 준비할 값 | 무엇인가 |
|---|---|
| 산출물 digest | 그 서버에 올라가 있는 이미지·패키지의 `sha256` 지문. “검사한 것과 배포한 것이 같은가”를 맞추는 기준이다 |
| API 주소 | OpenMetadata 서버의 API 주소 |
| Data Assertions 화면 주소 | 실패한 데이터 점검 결과가 보이는 화면 |
| 테이블 화면 주소 | 은행 컬럼 확장 정보가 보이는 테이블 화면 |
| SchemaEditor 화면 주소 | 한글 입력을 실제로 쳐 볼 수 있는, 수정 가능한 편집 화면 |

1. GitHub Actions에서 `Runtime contracts`를 선택한다.
2. `Run workflow`에 위 다섯 값을 입력한다.
3. `openmetadata-runtime` 환경 승인자가 “이 서버와 이 후보가 맞다”고 확인한다.
   승인 전에는 실행되지 않는다.
4. 시스템이 아홉 가지를 실행한다 — API 검사 4건, Sybase·Tibero 연결 2건,
   Data Assertions·은행 컬럼·한글 입력 브라우저 검사 3건. 결과는 T62로 남는다.
5. 아홉 개가 **모두 실행돼야** 통과 여부를 따질 수 있다. 하나라도 건너뛰거나
   실패하거나 도중에 오류가 나면 전체 결과는 `block` 또는 `analysis_error`다.
6. 실행이 끝나면 `runtime-contract-evidence-실행번호-재시도번호`라는 파일을
   내려받는다. 안에 후보 잠금, 테스트 결과, 최종 판정 YAML 세 개가 들어 있다.
7. **이 파일은 GitHub에 90일만 보관된다.** 감사나 규정상 더 오래 남겨야 하면
   90일이 지나기 전에 조직의 증거 저장소로 옮기고, artifact ID와 digest를 함께
   적어 둔다. 현재 조직 소유의 장기 보관 위치는 아직 정해지지 않았다.

API 토큰과 브라우저 로그인 상태는 GitHub environment secret에만 저장한다.
Query ID, 실패 assertion FQN, 테이블·컬럼 같은 테스트 대상값은 environment
variable로 관리한다. 업무 담당자가 채팅이나 문서에 비밀값을 복사하지 않는다.
증거 artifact는 같은 실행 안에서 덮어쓰지 못하며, 업로드 파일이 없으면 workflow
자체가 실패한다.

### 시나리오 E — 테스트가 정말 기능을 지키는지 확인

테스트가 통과했다는 말은 “기능이 살아 있다”는 뜻이어야 한다. 그런데 테스트가
사실상 아무것도 확인하지 않으면, 기능이 통째로 사라져도 그대로 통과한다. 이런
테스트를 두면 검사 전체가 무의미해진다.

그래서 시스템은 반대로 확인한다. **기능을 일부러 뺀 코드를 만들어 같은
테스트를 돌린다.** 여기서 테스트가 실패해야 정상이다. 기능이 없는데도 통과하면
그 테스트는 “껍데기 테스트”이므로 차단한다.

현재 Sybase와 Tibero는 각 기능을 넣기 직전의 코드에서 테스트가 실제로
실패하는 것을 확인했다. 두 테스트는 진짜다. 반면 InstanceCode, QueryReport,
Data Assertions는 API·DB·검색까지 얽혀 있어, 기능을 뺀 서버를 따로 띄워야만
같은 확인이 가능하다. 아직 하지 못했다. 따라서 현재는
**중요 기능 5개 중 2개만 확인 완료**다.

나머지 세 기능을 검사하는 `Runtime patch-kill` 전용 검사기는 구현됐다. 운영자는
일반 기능 검사용 `Runtime contracts`와 섞지 않고, 별도 승인 환경에서 한 기능씩
실행한다.

1. 선택한 기능을 넣기 직전의 코드로 별도 이미지·패키지를 빌드한다(이것을
   아래에서 “제거본”이라고 부른다).
2. 운영 후보와 완전히 분리된 테스트 환경에 제거본을 배포하고 기준 데이터를
   넣는다.
3. 제거본의 산출물 digest와, “어떤 소스·환경·기준 데이터로 배포했는지” 적은
   기록의 digest를 준비한다. 나중에 “그때 무엇을 대상으로 했는가”를 되짚기
   위한 값이다.
4. GitHub Actions의 `Runtime patch-kill`에서 기능 ID, 두 digest, 환경 이름,
   API 주소를 입력한다. Data Assertions를 검사할 때는 대상 화면 주소에 더해,
   “로그인은 정상이다”를 확인할 별도 화면 주소와 그 화면에서 찾을 표식도
   입력한다.
5. 시스템은 먼저 서버가 정상인지 확인한다(API 응답, 기준 데이터, 로그인 화면).
   그다음 대상 테스트가 **연속 두 번 실패**하는지 본다. 마지막으로 정상 확인을
   한 번 더 반복한다. 검사 도중에 서버가 죽어서 실패한 것이 아님을 확인하기
   위해서다.
6. 결과 읽는 법:
   - 정상 확인이 하나라도 실패하거나 대상 검사가 건너뛰어지거나 오류가 나면
     → `analysis_error` (실험 자체가 성립하지 않았다)
   - 기능이 없는데 대상 검사가 통과하면 → `block` (껍데기 테스트다)
   - 대상 검사가 두 번 다 실패하면 → 그 테스트는 진짜다
7. 실행 증거는 덮어쓸 수 없는 파일로 90일 보존한다.

검사기만 준비됐을 뿐 세 제거본은 아직 실제로 빌드·배포하지 않았다. 따라서
이 절차가 있다는 사실을 세 기능의 확인 완료로 읽으면 안 된다.

### 시나리오 F — 긴급 변경

긴급 절차는 검사를 없애는 기능이 아니다. 긴급 사유, 만료 시간, 영향 범위와
승인을 별도 기록하더라도 machine `block`과 무결성 검사는 그대로 남는다.
사후 검토와 정상 절차 복귀 시점도 반드시 정한다.

### 시나리오 G — “타입 오류가 남았는데 이번 개발은 끝났나?”라고 묻는 경우

UI 코드에는 “타입 검사”라는 자동 점검이 있다. 여기서 나오는 오류 건수가 0이
아니면 불안해 보이지만, **공식 OpenMetadata 원본에서도 원래 오류가 많이 난다.**
그래서 봐야 할 것은 “0인가”가 아니라 **“이번 작업이 오류를 늘렸는가”**다.

먼저 이번 작업이 만든 오류부터 정리했다.

| 시점 | 건수 | 무엇을 했나 |
|---|---|---|
| 처음 측정 | 399 | 은행 기능을 연결한 직후 |
| 3건 수정 | 396 | 이번 연결 때문에 새로 생긴 3건을 고침 |
| `BANK-OM-009` | 357 | 공통 검색 타입표에 빠져 있던 항목을 채우고 지나치게 넓던 타입을 좁힘 |
| `BANK-OM-010` | 356 | 알림 검색에서 엔터티 ID가 없을 때의 처리를 안전하게 바꿈 |
| `BANK-OM-011` | 355 | 공통 목록 검색이 타입을 추측하지 않고 Domain·DataProduct가 각자 명시하게 바꿈 |

그다음 공식 원본과 나란히 비교했다. 같은 Node 22, 같은 준비 절차로 공식
OpenMetadata 1.13.1 원본을 검사하니 **141개 파일에서 396건**이 나왔다. 현재
후보는 **133개 파일에서 355건**이다.

파일 경로와 오류 종류를 중복 횟수까지 하나씩 맞춰 본 결과는 이렇다.

- 원본에 없던 **새 오류: 0건**
- 원본에 있었는데 없어진 오류: **41건**
- 같은 파일·같은 오류인데 설명 문구만 달라진 것: **10건**

이 10건은 깨끗한 캐시에서 원문을 다시 뽑아 하나씩 대조했다. 새 결함은 없었고
모두 TypeScript가 같은 타입을 다르게 줄여 쓴 차이였다. 다만 이 대조는
개발자가 한 기술 검토이지 조직 책임자의 승인이 아니다.

**결론:** “이번 기능이 새 타입 오류를 만들지 않았다”는 근거는 확보했다.
그러나 “UI 전체가 깨끗하다”는 뜻은 아니다. 그래서 판정은 `통과`가 아니라
`승인 필요`다. 남은 355건을 조직이 “여기까지는 원래 있던 것으로 인정한다”고
기준선 승인하거나 실제로 고치기 전까지, UI 품질 항목은 계속 차단으로 읽는다.

## 6. LLM 위키와 Claude는 어디에 사용하는가

LLM은 다음 용도로 사용한다.

- 어려운 변경 내용을 쉬운 말로 설명
- 관련 파일과 위험 후보를 좁혀 리뷰 순서 제안
- 빠진 테스트 후보나 확인 질문 제안
- 인수인계서와 사용자 가이드 초안 정리

LLM은 다음 권한이 없다.

- `pass` 판정 부여
- 배포 승인
- 테스트 `skip`을 성공으로 변경
- 사람 승인 또는 서명 대체
- 근거 없이 “영향 없음”이라고 단정

따라서 LLM 위키의 답은 **탐색과 설명을 돕는 메모**다. 최종 판단은 고정된
소스·테스트·산출물 증거와 지정된 사람의 승인으로 한다.

사용자용 LLM 위키 화면은 아직 운영에 연결하지 않았다. 지금 만들어져 있는 것은
“Impact Memo”라는 형식 약속뿐이다. LLM이 영향 범위를 설명할 때 어떤 항목을
반드시 채워야 하는지를 정해 둔 것이며, 이 메모는 어떤 검사 결과도 바꾸지
못한다.

## 7. 검사기는 왜 나뉘어 있는가

검사를 하나로 뭉쳐 두면 “어딘가 실패했다”만 알 수 있다. 단계를 나눠 두면
“어느 지점에서 무엇이 부족한가”를 바로 알 수 있다. 뒤로 갈수록 더 실제에
가까운 것을 확인한다.

| 검사 단계 | 무엇을 확인하는가 | 현재 상태 |
|---|---|---|
| 1. 등록·소스 게이트 | 11개 기능과 공식 버전이 후보 코드에 그대로 남아 있는가 | 통과 |
| 2. 계약 구현 게이트 | 지키기로 약속한 업무 규칙마다 테스트 코드가 실제로 존재하는가 | 9개 필수 테스트 모두 존재·통과 |
| 3. 테스트 생존 게이트 | 그 테스트가 껍데기가 아닌가(기능을 빼면 실패하는가) | 중요 기능 5개 중 2개 확인, 3개 대기 |
| 4. 실제 기능 게이트 | 실제 서버에서 API·검색·데이터·화면이 제대로 동작하는가 | Sybase·Tibero 2건 통과, API 4건·브라우저 3건 대기 |
| 5. 릴리스 게이트 | 검증한 바로 그 산출물만 배포·서명·반입했는가 | 절차만 준비, 실행 대기 |

1단계가 통과했다고 3~5단계를 건너뛸 수 없다. 각 단계는 별도 검사기와 별도
증거를 쓴다. 예를 들어 한글 입력 보정은 “코드가 제대로 연결돼 있는가”(1단계)는
통과했지만, 실제 브라우저에서 한글을 쳐 보는 검사(4단계)는 아직 하지 않았다.
앞 단계 통과는 뒤 단계를 대신하지 못한다.

## 8. 전체 완성 후 보이는 모습

완성된 운영 흐름에서는 업무 담당자가 기능 ID와 목적을 선택하고, 시스템은
공식 버전 통합부터 실제 기능 테스트, 업그레이드, 산출물 승격과 내부망 검증까지
한 후보에 묶어 보여준다. 담당자는 각 단계의 초록/승인 필요/차단 상태와 근거를
보고 승인한다. 감사 담당자는 누가 무엇을 승인했고 어떤 코드와 이미지가 실제로
배포됐는지를 같은 기록에서 추적한다.

최종 배포 가능 표시는 아래가 **모두** 충족될 때만 나온다. 하나라도 빠지면
표시되지 않는다.

- 모든 필수 검사가 `pass`
- 필요한 사람 승인이 모두 유효
- 필수 테스트 중 건너뛴(`skip`) 것이 없음
- 후보 코드, 테스트 결과, 이미지·패키지 digest가 모두 같은 대상을 가리킴
- 실제 업그레이드를 해 본 증거와 내부망 서명 확인 증거가 있음

## 9. 자주 쓰는 말

| 용어 | 쉬운 뜻 |
|---|---|
| `BANK-OM-nnn` | 은행에서 추가한 기능마다 붙인 번호. 1절 표 참고 |
| candidate(후보) | 이번에 검사하고 배포하려는 정확한 코드 한 벌 |
| commit / SHA | 특정 시점의 코드를 딱 하나로 가리키는 고유 번호. 나중에 바뀌지 않는다 |
| Manifest | 기능 하나가 어느 파일을 바꾸는지 적어 둔 등록자료 |
| Registry | 기능 목록과 담당자를 적어 둔 등록자료 |
| Contract(계약) | 반드시 지켜야 하는 업무 동작 규칙과, 그것을 확인하는 테스트 |
| gate(게이트) | 조건을 확인해 진행·승인 필요·차단을 결정하는 자동 검사 |
| owner | 해당 기능과 결과를 책임지는 사람 또는 팀 |
| digest | 파일이나 이미지가 한 글자도 다르지 않은지 확인하는 지문값 |
| artifact(산출물) | 실제 배포할 이미지, 패키지, Helm 같은 결과물 |
| patch / custom 브랜치 | 공식 코드만 있는 쪽(patch)과 은행 변경까지 얹은 쪽(custom) |
| T62 | 테스트 결과를 정확한 후보 코드에 묶어 두는 단계 |
| T90 | 실제 구버전에서 신버전으로 올려 보는 전체 시나리오 |
| T91 | 검증한 그 산출물만 배포 단계로 올리는 절차 |
| T94 | 내부망에 들여올 때 해시와 서명을 다시 확인하는 절차 |

## 10. 이 가이드의 갱신 규칙

다음 중 하나가 바뀔 때마다 개발 작업과 같은 묶음에서 이 문서를 갱신한다.

1. 사용자가 보는 상태나 결과 문구
2. 업무 담당자가 준비할 정보
3. 승인·긴급·배포 절차
4. `pass`, `skip`, `block` 등의 해석
5. 새 기능, 새 게이트, 새 운영 화면
6. 현재 blocker 또는 실제 배포 가능 여부

각 개발 묶음이 끝날 때 이 가이드와
[`Claude 인수인계서`](../04-진행/CLAUDE_REVIEW_HANDOFF.md)를 함께 확인한다.
작업 주체가 바뀌거나 컨텍스트가 소진되기 전에는 인수인계서에 완료 내용,
구현 방법, 검증 결과, 남은 작업과 다음 실행 명령을 반드시 남긴다.
