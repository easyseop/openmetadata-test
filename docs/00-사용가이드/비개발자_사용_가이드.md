# 비개발자용 OpenMetadata 업그레이드 안전 가이드

> 최종 갱신: 2026-07-27
>
> 대상: 업무 담당자, 데이터 오너, 승인자, 운영자, 감사 담당자
>
> 현재 결론: **소스 후보 검사는 통과했지만 실제 운영 배포는 아직 차단 상태다.**

## 1. 이 시스템은 무엇인가

공식 OpenMetadata가 새 버전으로 올라갈 때, 은행에서 추가한 기능이 빠지거나
잘못 바뀌지 않았는지 자동으로 확인하고 그 근거를 남기는 시스템이다.

쉽게 말하면 다음 세 가지 사고를 막는다.

1. 은행 기능을 새 버전에 옮기면서 일부를 빠뜨리는 사고
2. 테스트한 코드와 실제 배포한 파일이 달라지는 사고
3. 검사 오류나 LLM의 낙관적인 답을 정상 통과로 오해하는 사고

현재 등록된 은행 기능은 InstanceCode, QueryReport, Data Assertions, 은행 컬럼
표시, 한글 입력 보정, Sybase, Tibero의 일곱 가지다.

## 2. 5분 안에 현재 상태 확인하기

비개발자는 코드를 읽을 필요가 없다. 아래 순서만 확인하면 된다.

1. [`STATUS.md`](../../STATUS.md)를 연다.
2. 맨 위의 **현재 결론**과 `Important production blockers`를 확인한다.
3. GitHub Actions의 최신 `source-candidate` 실행이 성공했는지 확인한다.
4. 실제 환경 검증은 별도 `Runtime contracts` 실행 결과를 확인한다.
5. `skip`, `UNASSIGNED`, `blocker`가 하나라도 남아 있으면 배포 완료로 승인하지 않는다.
6. 실제 배포 판단은 T62 운영 테스트, T90 업그레이드 실행, T91 승격,
   T94 내부망 반입 증거까지 모두 준비된 뒤에만 한다.

현재 확인 가능한 링크:

- [거버넌스 저장소와 문서](https://github.com/easyseop/openmetadata-test/tree/claude/markdown-file-feedback-26933w)
- [현재 제품 후보 브랜치](https://github.com/easyseop/OpenMetadata/tree/codex/bank-vendor-1.13.1-rebuild)
- [최근 확인된 source-candidate·patch-kill 성공 실행](https://github.com/easyseop/openmetadata-test/actions/runs/30212561441)
- [실제 환경 계약 실행 화면](https://github.com/easyseop/openmetadata-test/actions/workflows/runtime-contracts.yml)

> 초록색 CI는 **소스 수준의 등록·누락·결속 검사가 통과했다**는 뜻이다.
> 실제 데이터와 운영 환경에서 배포해도 된다는 뜻은 아니다.

## 3. 결과를 어떻게 읽는가

| 화면/결과 | 쉬운 뜻 | 해야 할 일 |
|---|---|---|
| `pass` | 이 검사가 요구한 근거는 충족됨 | 다음 단계로 진행 |
| `approval` | 자동 검사는 끝났지만 사람 판단이 필요함 | 지정 승인자가 근거 검토 |
| `block` | 필수 조건이 부족하거나 위험이 확인됨 | 원인 해소 전 배포 중지 |
| `analysis_error` | 검사 자체를 신뢰할 수 없음 | 통과로 보지 말고 검사 복구 |
| `skip` | 필요한 운영 환경이나 입력이 없어 실행하지 못함 | 실제 환경에서 다시 실행 |
| `UNASSIGNED` | 책임자가 정해지지 않음 | 기능 오너와 승인자 지정 |

여러 결과가 섞이면 가장 위험한 상태가 최종 상태가 된다.
`analysis_error`나 `block`을 사람 승인으로 `pass`로 바꿀 수 없다.

## 4. 업무 담당자가 준비할 정보

변경이나 업그레이드를 요청할 때 아래 정보를 한 번에 전달한다.

| 필요한 정보 | 쉬운 설명 | 예시 |
|---|---|---|
| 변경 목적 | 무엇을 왜 바꾸는가 | “Tibero 연결 설정을 새 버전에서도 유지” |
| 영향 기능 | 일곱 기능 중 어디인가 | `BANK-OM-007` Tibero |
| 업무 오너 | 결과를 책임지는 사람/팀 | 데이터플랫폼팀 |
| 승인자 | 독립적으로 확인할 두 사람 | 개발 승인자, 운영 승인자 |
| 지켜야 할 업무 규칙 | 바뀌면 안 되는 동작 | “저장 후 다시 조회해도 연결 종류가 Tibero” |
| 테스트 준비값 | 실제 실행에 필요한 URL·대상 ID 등 | 테스트 환경 URL, 테스트 테이블 |
| 희망 일정 | 검증과 배포가 필요한 시점 | YYYY-MM-DD |

토큰, 비밀번호, 개인 키는 문서·티켓·인수인계서에 적지 않는다. 비밀값은 승인된
비밀 저장소나 CI secret으로만 전달한다.

## 5. 실제 사용 시나리오

### 시나리오 A — 공식 OpenMetadata 버전 업그레이드

1. 업무 오너가 새 공식 버전과 변경 목적을 제출한다.
2. 개발자가 승인된 공식 버전을 은행 제품 후보에 합친다.
3. 소스 게이트가 일곱 기능의 이름표, 필수 파일, 테스트 구현 존재 여부를 검사한다.
4. 실제 OpenMetadata 테스트 환경에서 기능 계약과 브라우저 동작을 실행한다.
5. 구버전 데이터를 복원한 뒤 DB 변경, 검색 재색인, ingestion, 권한과 API를
   포함한 업그레이드 시나리오를 실행한다.
6. 검증한 바로 그 이미지·패키지·Helm만 승격하고 내부망에서 서명과 해시를 다시
   확인한다.

어느 단계든 `block`, `analysis_error`, 필수 `skip`이 있으면 다음 배포 단계로
넘어가지 않는다.

### 시나리오 B — 은행 기능을 추가하거나 수정

1. 기존 `BANK-OM-nnn` 기능의 수정인지 새 기능인지 정한다.
2. 목적, 오너, 필수 파일, 업무 규칙과 테스트를 함께 등록한다.
3. 코드만 추가하고 테스트나 오너를 나중으로 미루지 않는다.
4. 검사 결과와 변경 근거가 해당 기능 ID에 묶였는지 확인한다.
5. 사용자에게 보이는 동작이 달라지면 이 가이드의 예시와 절차도 같은 개발 묶음에서
   갱신한다.

### 시나리오 C — CI는 초록색인데 배포 가능한지 묻는 경우

현재가 바로 이 경우다. 소스 후보 CI는 통과했지만 다음 항목이 남아 있으므로
답은 **아직 배포 불가**다.

- 일곱 기능의 조직 오너와 두 사람 승인 경로 미지정
- 실제 OpenMetadata가 필요한 계약 테스트 네 건 미실행
- 실제 브라우저 한글 입력 테스트 한 건 미실행
- 전체 Java/UI 빌드와 UI 진단 기준선 미완료
- 실제 업그레이드, 산출물 승격, 서명, 내부망 반입 증거 없음

### 시나리오 D — 실제 환경 계약 검사를 요청

1. GitHub Actions에서 `Runtime contracts`를 선택한다.
2. 배포된 후보의 정확한 `sha256` 산출물 digest, OpenMetadata API 주소,
   수정 가능한 SchemaEditor 화면 주소를 준비한다.
3. `Run workflow`에 세 값을 입력한다.
4. `openmetadata-runtime` 환경 승인자가 대상 환경과 후보가 맞는지 확인한다.
5. 시스템이 API 계약 네 건, Sybase/Tibero 두 건, 브라우저 한글 입력 한 건을
   각각 실행하고 T62 결과를 만든다.
6. 하나라도 `skip`, 실패, 실행 오류이면 결과는 `block` 또는
   `analysis_error`다. 일곱 건이 모두 실행돼야 정상 통과를 검토할 수 있다.
7. 실행 결과의 `runtime-contract-evidence-실행번호-재시도번호` 파일을
   다운로드한다. 후보 잠금, 테스트 결과, 최종 판정 YAML 세 파일이 들어 있고
   GitHub에는 90일 동안 보존된다.
8. 감사·규정상 더 오래 보관해야 하면 90일 만료 전에 조직의 증거 저장소로
   이관하고 artifact ID와 digest를 함께 기록한다.

API 토큰과 브라우저 로그인 상태는 GitHub environment secret에만 저장한다.
Query ID, 실패 assertion FQN, 테이블·컬럼 같은 테스트 대상값은 environment
variable로 관리한다. 업무 담당자가 채팅이나 문서에 비밀값을 복사하지 않는다.
증거 artifact는 같은 실행 안에서 덮어쓰지 못하며, 업로드 파일이 없으면 workflow
자체가 실패한다.

### 시나리오 E — 테스트가 정말 기능을 지키는지 확인

시스템은 일부 기능을 일부러 뺀 검사본에서도 같은 테스트를 실행한다. 기능이
없어졌는데 테스트가 계속 통과하면, 그 테스트는 기능 소실을 잡지 못하는
“껍데기 테스트”이므로 차단한다.

현재 Sybase와 Tibero는 각 기능을 넣기 직전의 고정 소스에서 계약 테스트가 실제
실패하는 것을 확인했다. 두 테스트는 해당 기능 소실을 잡는다. InstanceCode,
QueryReport, Data Assertions는 API·DB·검색까지 포함한 제거본 서비스를 따로
배포해야 같은 검사를 할 수 있어 아직 대기 중이다. 따라서 현재 결과는
**중요 기능 5개 중 2개 확인 완료**이며 전체 완료가 아니다.

### 시나리오 F — 긴급 변경

긴급 절차는 검사를 없애는 기능이 아니다. 긴급 사유, 만료 시간, 영향 범위와
승인을 별도 기록하더라도 machine `block`과 무결성 검사는 그대로 남는다.
사후 검토와 정상 절차 복귀 시점도 반드시 정한다.

## 6. LLM 위키와 Claude는 어디에 사용하는가

LLM은 다음 용도로 사용한다.

- 어려운 변경 내용을 쉬운 말로 설명
- 관련 파일과 위험 후보를 좁혀 리뷰 순서 제안
- 빠진 테스트 후보나 확인 질문 제안
- 인수인계서와 사용자 가이드 초안 정리

LLM은 다음 권한이 없다.

- `pass` 판정 부여
- 배포 승인
- 테스트 `skip`을 성공으로 변경
- 사람 승인 또는 서명 대체
- 근거 없이 “영향 없음”이라고 단정

따라서 LLM 위키의 답은 **탐색과 설명을 돕는 메모**다. 최종 판단은 고정된
소스·테스트·산출물 증거와 지정된 사람의 승인으로 한다. 사용자용 LLM 위키 화면은
아직 운영 연결 전이며, 현재 구현된 것은 판정권이 없는 Impact Memo 계약이다.

## 7. 검사기는 왜 나뉘어 있는가

검사는 한 번에 뭉쳐 있지 않고 실패 지점을 알 수 있도록 역할별로 분리한다.

| 검사 단계 | 확인하는 것 | 현재 상태 |
|---|---|---|
| 1. 등록·소스 게이트 | 일곱 기능과 공식 버전이 후보에 남았는가 | 구현·현재 후보 통과 |
| 2. 계약 구현 게이트 | 필수 테스트 파일과 함수가 실제로 있는가 | 7/7 구현·통과 |
| 3. 테스트 생존 게이트 | 기능을 빼면 테스트가 실제로 실패하는가 | 중요 기능 5개 중 Sybase/Tibero 2개 확인, API 기반 3개 대기 |
| 4. 실제 기능 게이트 | API, 검색, 데이터, 브라우저 동작이 맞는가 | Sybase/Tibero 2건 통과, API 4건·브라우저 1건 실제 환경 대기 |
| 5. 릴리스 게이트 | 검증한 동일 산출물을 승격·서명·반입했는가 | 계약 구현, 실제 실행 대기 |

3~5단계는 각각 별도 검사기와 별도 증거를 사용한다. 소스 게이트가
통과했다고 이 단계를 건너뛰지 않는다.
한글 IME의 소스 배선 검사는 별도로 통과했지만 실제 브라우저 계약을 대신하지 않는다.

## 8. 전체 완성 후 보이는 모습

완성된 운영 흐름에서는 업무 담당자가 기능 ID와 목적을 선택하고, 시스템은
공식 버전 통합부터 실제 기능 테스트, 업그레이드, 산출물 승격과 내부망 검증까지
한 후보에 묶어 보여준다. 담당자는 각 단계의 초록/승인 필요/차단 상태와 근거를
보고 승인한다. 감사 담당자는 누가 무엇을 승인했고 어떤 코드와 이미지가 실제로
배포됐는지를 같은 기록에서 추적한다.

최종 배포 가능 표시는 다음이 모두 충족될 때만 나온다.

- 모든 필수 검사가 `pass`
- 필요한 사람 승인이 유효
- 필수 테스트에 `skip`이 없음
- 후보 코드, 테스트 결과, 이미지·패키지 digest가 서로 일치
- 업그레이드와 내부망 서명 검증 증거가 있음

## 9. 자주 쓰는 말

| 용어 | 쉬운 뜻 |
|---|---|
| candidate | 이번에 검사하고 배포하려는 정확한 코드 후보 |
| commit/SHA | 코드를 바꿀 수 없게 가리키는 고유 번호 |
| contract | 반드시 지켜야 하는 업무 동작 규칙 |
| gate | 조건을 확인해 진행·승인 필요·차단을 결정하는 자동 검사 |
| owner | 해당 기능과 결과를 책임지는 사람 또는 팀 |
| digest | 파일이나 이미지가 같은 바이트인지 확인하는 지문 |
| artifact | 실제 배포할 이미지, 패키지, Helm 같은 산출물 |
| T62 | 테스트 결과를 정확한 후보 코드에 묶는 단계 |
| T90 | 실제 구버전에서 신버전으로 올리는 전체 시나리오 |
| T91 | 검증한 동일 산출물만 배포 단계로 올리는 절차 |
| T94 | 내부망에서 해시와 서명을 다시 확인하는 절차 |

## 10. 이 가이드의 갱신 규칙

다음 중 하나가 바뀔 때마다 개발 작업과 같은 묶음에서 이 문서를 갱신한다.

1. 사용자가 보는 상태나 결과 문구
2. 업무 담당자가 준비할 정보
3. 승인·긴급·배포 절차
4. `pass`, `skip`, `block` 등의 해석
5. 새 기능, 새 게이트, 새 운영 화면
6. 현재 blocker 또는 실제 배포 가능 여부
