전체 검사 흐름

검사 번호를 나열하기 전에 각 단계가 왜 필요한지와 앞 단계의 출력이 다음 단계에서 어떻게 쓰이는지를 먼저 설명합니다.

Git commit·diff→Manifest·Registry·Contract→소스 검사→Candidate lock→환경 테스트→배포 대상 일치 검사
단계주요 입력주요 출력다음 단계 사용

소스 검사공식 OpenMetadata commit, 검사 대상 custom branch commit, 등록자료PASS·APPROVAL·BLOCK과 이유검사 대상 custom branch commit을 다음 검사로 넘길 수 있는지 판단

Candidate lock의 두 형태
소스 검사에서는 별도 YAML을 미리 만들지 않습니다. 검사기가 source-gate-results.json 안에 candidate_lock을 자동 기록합니다. 실제 이미지까지 검사하는 배포 단계에서는 별도 evidence/candidate-lock.yaml을 사용할 수 있습니다.

2-0 · 검사기 원리

검사가 읽는 핵심 관리자료

검사 번호보다 먼저 세 파일의 역할을 구분합니다. 세 파일은 같은 내용을 반복하지 않고 서로 다른 질문에 답합니다.

Manifest

이 기능이 어느 파일을 바꾸는가

BANK-OM 하나의 전체 변경 파일, 필수 파일, 공식 업그레이드 때 다시 볼 경로와 test 연결을 기록합니다.

Registry

어떤 BANK-OM을 관리하는가

활성 ID, 담당자, 중요도와 각 Manifest·Contract 위치를 한 목록으로 연결합니다.

Contract

어떤 동작이 정상이어야 하는가

파일 존재만으로 알 수 없는 업무 정상 조건과 그 조건을 확인할 필수 test를 기록합니다.

읽는 순서
Registry에서 검사할 BANK-OM을 찾고 → Manifest에서 변경 범위를 읽고 → Contract에서 실제 정상 동작 기준을 확인합니다. 자세한 변수와 갱신 방법은 3-4~3-6에서 확인합니다.
