# OM 운영 위키 전수 검토 피드백 반영안

> 작성 목적: `OM_Wiki_Full_Review_20260730`의 피드백을 실제 코드와 현재 위키에
> 대조한 뒤, 무엇을 어떤 방식으로 수정할지 본문 변경 전에 승인받기 위한 문서입니다.
>
> 현재 상태: **수정 전 검토안**입니다. 이 문서에 적힌 변경은 아직 운영 위키,
> 검사기 코드, 관리 파일에 적용하지 않았습니다.

## 1. 결론

전수 검토서의 `구조 재검토` 판정은 타당합니다. 특히 자동 등록 준비 절차,
운영용 vendor-merge와 진단용 commit replay의 구분, 관리 파일의 의미,
승인과 배포 증거의 연결을 현재보다 명확하게 설명해야 합니다.

다만 검토서의 제안을 전부 그대로 반영하지는 않습니다. 일부 제안은 현재 구현에
이미 반영돼 있거나, 현재 스키마를 불필요하게 나누거나, 조직이 결정해야 할 정책을
문서 작성자가 임의로 정하게 만들 수 있습니다.

이번 수정은 다음 원칙을 따릅니다.

1. 실제 오류와 문서 간 모순은 수정합니다.
2. 기술 용어는 없애지 않고 처음 사용할 때 쉬운 문장으로 설명합니다.
3. 현재 구현된 기능과 앞으로 개발할 기능을 구분합니다.
4. 요약에서는 업무 흐름만 보여주고, 실행 명령과 필드 설명은 상세 페이지에 둡니다.
5. 코드 변경이나 조직 정책 결정이 필요한 항목은 문서 수정으로 해결된 것처럼
   표현하지 않습니다.

| 문장 검토표가 운영자용 목차에 포함됨 | 수용 | 운영 목차에서 빼고 문서 작성·검토 기록으로 분리합니다. |

## 3. 피드백의 방향을 수정해서 수용할 항목

### 3.1 3장 제목

검토서의 제안은 `검사 입력 등록 및 승인`입니다. 이 제목은 Manifest·Registry·
Contract의 등록과 승인에는 맞지만, 3장에 포함된 저장소 상태, branch, Git 작업
상태, 경로 정책 확인까지 포함하지 못합니다.

따라서 다음 제목으로 변경할 예정입니다.

> **3. 검사 전 준비 및 등록자료 관리**

이 제목의 범위는 다음과 같습니다.

- 제품 코드 저장소와 검사기 저장소 확인
- OpenMetadata 포크 브랜치와 커스텀 브랜치 확인
- commit하지 않은 로컬 변경 여부 확인
- Manifest·Registry·Contract 준비
- `plan`을 이용한 읽기 전용 변경안 생성
- 담당자의 검토·승인
- `apply`를 이용한 등록자료 반영
- 등록자료 검사와 오류 대응

### 3.2 전체 흐름

검토서의 문제 제기는 수용하지만, 요약 화면에 10개 이상의 세부 단계를 모두
나열하면 핵심 흐름이 보이지 않습니다. 요약에는 다음 7단계를 표시하고 각 단계의
세부 작업은 상세 페이지에서 설명합니다.

```text
1. 커스터마이징 코드 commit
2. 등록 변경안 생성(plan)
3. 담당자 검토·승인
4. 승인안 반영(apply)과 등록자료 검사
5. 새 공식 버전 병합과 충돌 해결
6. 소스·실행 환경·업그레이드 검사
7. 검증 완료 태그·Release lock·릴리즈 브랜치 승격
```

이 흐름에서 `plan`은 실제 등록 폴더를 수정하지 않습니다. 담당자가 같은 변경안을
승인한 뒤 `apply`가 성공해야 Manifest와 관련 관리 파일이 변경됩니다.

### 3.3 3장 순서

검토서는 Manifest·Registry·Contract 상세를 등록 절차보다 모두 앞으로 옮길 것을
권고했습니다. 그러나 처음부터 전체 필드 사전을 읽게 하면 신입 운영자가 실제
작업을 시작하기 전에 긴 내부 구조를 먼저 학습해야 합니다.

따라서 앞부분에는 파일별 한 줄 역할만 제시하고, 전체 필드 설명은 실행 절차 뒤에
유지합니다.

```text
3-1 검사 전에 준비할 것
3-2 관리 파일 관계와 한 줄 역할
3-3 새 ID와 기존 ID 후속 변경 판단
3-4 plan → 검토·승인 → apply
3-5 등록자료 검사와 오류 대응
3-6 Manifest 상세
3-7 Registry 상세
3-8 Contract 상세
3-9 과거 기준 자료와 경로 정책
```

### 3.4 검사 실행 명령의 중복

모든 검사 페이지에서 통합 명령 전체를 반복하면 해당 명령이 그 검사 하나만
실행한다고 오해할 수 있습니다. 반대로 명령을 한 페이지에만 두면 특정 검사
페이지부터 읽은 운영자가 실행 위치를 찾기 어렵습니다.

따라서 다음 방식으로 수정합니다.

- 검사기 개요 페이지에 통합 명령 전체를 한 번 제공합니다.
- 각 검사 상세에는 `공통 소스 검사 명령이 만든 Txx 결과`라고 표시합니다.
- 각 상세에서 공통 명령 위치로 바로 이동할 수 있게 연결합니다.
- 해당 검사에만 필요한 별도 입력이나 명령이 있을 때만 전체 명령을 추가합니다.

### 3.5 자동화 상세 페이지 구성

자동화 페이지를 여러 메뉴로 완전히 분리하면 목차가 과도하게 길어집니다. 한
페이지 안에서 다음 하위 목차와 접기 영역으로 구분합니다.

1. 자동으로 만드는 것과 사람이 판단하는 것
2. 실행 전 확인 항목
3. `plan` 실행
4. 제안 검토와 승인서 작성
5. `apply` 실행
6. 상태별 복구와 보관할 증거

## 4. 새 구조를 만들지 않고 설명만 바로잡을 항목

### 4.1 Candidate lock

검토서는 소스용 Candidate lock과 배포용 Candidate lock을 새 파일로 분리할 것을
제안했습니다. 현재 Candidate lock 스키마에는 이미 다음 구분이 있습니다.

```yaml
candidate:
  artifact_kind: source-tree   # 소스 검사 단계
```

또는:

```yaml
candidate:
  artifact_kind: build-artifact  # 실제 빌드 산출물 검사 단계
```

따라서 새 파일 형식을 추가하지 않습니다. 대신 각 값이 언제 만들어지고 누가 읽는지
명확하게 설명합니다.

- `source-tree`: 소스 검사기가 현재 Git tree를 읽어 자동 계산
- `build-artifact`: 승인된 소스로 이미지·패키지를 빌드한 뒤 생성
- 두 값은 같은 이름의 digest라도 서로 다른 대상을 가리키므로 섞어 사용하지 않음

### 4.2 Registry의 `source.snapshot_sha`

새 필드를 만들지 않습니다. 다음 기준으로 문서를 통일합니다.

- `source.snapshot_sha`: 해당 버전의 최초 등록자료가 설명하는 과거 행내 코드 상태
- 현재 검사 대상 commit: Candidate lock의 `candidate.commit_sha`
- 같은 버전의 일반 후속 commit 때문에 `source.snapshot_sha`를 최신 commit으로
  계속 덮어쓰지 않음
- 새 공식 버전의 새 등록 폴더를 만들 때는 그 버전에 맞는 별도 Registry를 작성

### 4.3 과거 코드 경로 연결 파일

새 파일을 추가하지 않고 현재 두 파일의 관계를 통일합니다.

| 파일 | 의미 | 갱신 시점 |
| --- | --- | --- |
| `source-snapshot-path-owners.yaml` | 과거 행내 코드의 각 변경 파일을 어떤 BANK-OM ID가 복원하는지 기록한 전체표 | 최초 과거 기준 구축 또는 과거 기준 교체 |
| `shared-path-owners.yaml` | 위 전체표 중 둘 이상의 BANK-OM ID가 연결된 공용 경로만 모은 부분집합 | 전체표와 같은 시점 |

일반 후속 commit의 현재 범위는 Manifest `changed_paths`,
`commit-inventory.yaml`, `current-diff-paths.txt`로 관리합니다.

### 4.4 T41 중요 경로 정책

새 `enforcement` 필드를 추가하지 않습니다. 현재 구현은 경로 종류가 판정을
결정합니다.

| 경로 종류 | 자동 판정 | 의미 |
| --- | --- | --- |
| `frozen` | BLOCK | 변경을 허용하지 않는 경로 |
| `protected` | APPROVAL | 지정 승인 없이 진행할 수 없는 경로 |
| `watched` | PASS와 결과 표시 | 변경 사실을 결과에 표시하지만 자동 차단하지 않는 경로 |

정책을 설정으로 바꿀 필요가 생기면 별도 설계 변경으로 다룹니다.

### 4.5 APPROVAL 수용

새 `APPROVAL_ACCEPTED` 판정값을 추가하지 않습니다.

```text
검사 결과: APPROVAL
→ 담당자가 이유와 증거 확인
→ 승인 ID 발급
→ Release lock의 approval_ids에 기록
→ T91이 승인 ID와 동일 배포 대상을 확인
```

APPROVAL을 PASS로 바꾸기 위해 watch 경로나 검사 입력을 삭제하면 안 됩니다.

### 4.6 Contract와 proposal digest

현재 준비도구는 `contracts.yaml`을 등록 입력 내용 확인값에 포함합니다. 따라서
`plan` 이후 Contract가 변경되면 기존 승인서로 `apply`할 수 없습니다.

```text
plan 실행
→ Contract 변경
→ 기존 proposal로 apply
→ STALE_PROPOSAL로 중단
→ 새 plan과 새 승인 필요
```

코드에 Contract digest를 새로 추가하지 않고 이 동작을 위키에 설명합니다.

## 5. 현재 구현 상태를 정확하게 표시할 항목

### 5.1 Release lock

현재 구현 상태는 다음과 같습니다.

| 항목 | 상태 |
| --- | --- |
| Release lock 스키마 | 구현됨 |
| Release lock 생성·검사 라이브러리 | 구현됨 |
| 단위 테스트 | 구현됨 |
| 운영자가 실행할 전용 CLI | 아직 없음 |
| 실제 OM_TEMP 이미지·Helm digest | 아직 없음 |
| 실제 운영 승인 자료 | 아직 없음 |
| 실제 OM_TEMP Release lock | 아직 생성하지 않음 |

위키에서는 `Release lock 미구현`이라고 쓰지 않고, 구현된 부분과 운영 연결이 남은
부분을 나눠 표시합니다.

### 5.2 T90 업그레이드 전 과정 검사

T90 코드에는 다음 12개 단계가 구현돼 있습니다.

1. 운영 데이터 복원
2. DB migration
3. 데이터 건수·내용 대조
4. 검색 색인 재생성
5. 메타데이터 수집
6. 인증 변경 전후 비교
7. 권한 변경 전후 비교
8. API 변경 전후 비교
9. 관계 정보 변경 전후 비교
10. 검색 결과 변경 전후 비교
11. 수집 결과 변경 전후 비교
12. 이전 버전 복귀 연습

현재 상태는 `검사 규칙·스키마·단위 테스트 구현 완료, OM_TEMP 실제 업그레이드
환경 실행 미완료`로 표시합니다.

### 5.3 T91 배포 대상 일치 검사

T91의 Release lock 검사 로직은 구현돼 있지만 운영자가 사용할 CLI와 실제 배포
관측값 연결은 없습니다.

따라서 다음과 같이 표시합니다.

> **검사 로직 구현 완료 · 운영 실행 경로 추가 개발 필요**

형식 예시를 실제 배포 결과로 표시하지 않습니다.

## 6. 문서 수정 전에 별도 설계 승인이 필요한 코드 문제

### 6.1 vendor-merge와 T30 병합 커밋 규칙

현재 기본 전략은 vendor-merge이지만 T30은 검사 범위 안의 병합 커밋을
차단합니다. 문장 수정만으로 해결할 수 없습니다.

제안하는 코드 규칙은 다음과 같습니다.

1. vendor-merge 모드에서 새 공식 버전을 합친 지정 병합 커밋 1개는 허용합니다.
2. 지정되지 않은 임의 병합 커밋은 계속 BLOCK합니다.
3. 허용된 병합 커밋 뒤의 BANK-OM 변경 commit은 기존 ID 규칙으로 검사합니다.
4. 검사 결과에 허용한 병합 커밋 SHA와 두 부모 SHA를 기록합니다.

### 6.2 기존 ID의 비연속 후속 commit

현재 다음 이력은 같은 기능의 정상적인 보완일 수 있지만 T31은 BLOCK합니다.

```text
BANK-OM-001 최초 구현
BANK-OM-002 구현
BANK-OM-001 오류 보완
```

제안하는 코드 규칙은 다음과 같습니다.

- vendor-merge에서는 같은 ID의 비연속 후속 commit을 허용합니다.
- Manifest의 `series.allowed`와 commit inventory에는 전체 순서를 기록합니다.
- patch-replay 전략에서 연속성이 필요하면 해당 전략에서만 검사합니다.
- 새 기능인지 기존 기능의 보완인지는 현재 업무 기준과 사람 승인으로 결정합니다.

### 6.3 소스 Candidate에서 배포 Candidate로 넘어가는 단계

현재 소스 검사기는 `source-tree` Candidate lock을 만들 수 있지만, 실제 이미지와
패키지를 고정하는 운영 명령은 없습니다. 다음 단계의 설계와 구현이 필요합니다.

```text
소스 Candidate lock
→ 승인된 commit 빌드
→ 이미지·패키지 digest 생성
→ build-artifact Candidate lock
→ 실행 환경 검사
→ Release lock
```

이 단계가 구현되기 전에는 소스 검사 결과만으로 운영 배포가 가능하다고 설명하지
않습니다.

## 7. 조직 결정 없이는 확정하지 않을 항목

다음 값은 문서 작성자가 임의로 정하지 않습니다.

- 등록 변경안 승인자
- 충돌 해결 승인자
- 배포 승인자
- 승인 파일을 강제할 Git·CI·전자결재 방식
- 검사 증거의 공식 보관 저장소
- 증거 접근 권한과 보존 기간

조직 정책이 확정되기 전에는 다음 경고를 표시합니다.

> **운영 전 조직 결정 필요:** 승인 권한과 증거 보존 정책이 확정되지 않았으므로
> 현재 검사 통과만으로 운영 배포를 승인할 수 없습니다.

## 8. 실제 수정 순서

### 1단계 · 위험한 기존 안내 제거

1. 위키 3-9의 일반 후속 commit용 부트스트랩 명령 제거
2. 과거 watch 규칙 제거
3. Markdown·HTML·위키의 자동화 설명 통일
4. 실제·진단·예시·미실행 라벨 적용

### 2단계 · 읽기 흐름 정리

1. 0장 전체 흐름에 `plan → 승인 → apply` 추가
2. 3장 제목을 `검사 전 준비 및 등록자료 관리`로 변경
3. 3장 메뉴를 준비→파일 관계→등록 절차→오류 대응→상세 사전 순으로 재배치
4. 중요 용어를 처음 사용하는 위치에서 한 문장으로 설명

### 3단계 · 검사·승인·증거 설명 보강

1. 공통 명령→실행 검사→입력→결과 파일 표 추가
2. T90 12단계 공개
3. T91·Release lock의 구현 범위와 미완료 범위 분리
4. APPROVAL 수용과 승인 ID 기록 예시 추가
5. vendor-merge 운영 결과와 replay 진단 결과 분리

### 4단계 · 별도 승인 후 코드 변경

1. vendor-merge 병합 커밋 허용 규칙
2. 기존 ID의 비연속 후속 commit 허용 규칙
3. build-artifact Candidate lock 생성 경로
4. Release lock 생성·T91 실행 CLI

## 9. 수정 완료 조건

다음 조건을 모두 만족해야 위키 수정이 완료된 것으로 판단합니다.

- 전체 흐름에서 commit, plan, 승인, apply, 검사, 병합, 배포 준비 순서를
  설명할 수 있습니다.
- 어떤 항목이 자동이고 어떤 항목이 사람 판단인지 모든 관리 파일에서 구분됩니다.
- 같은 파일과 필드가 모든 페이지에서 같은 의미로 설명됩니다.
- 실제 실행 결과와 형식 예시가 시각적으로 구분됩니다.
- vendor-merge 운영 후보와 replay 진단 후보를 혼동할 수 없습니다.
- 각 명령에는 실행 위치, 입력값의 출처, 예상 결과, 실패 시 조치가 있습니다.
- BLOCK, APPROVAL, ANALYSIS ERROR 각각의 다음 행동이 다르게 설명됩니다.
- 구현됨, 단위 테스트됨, 실제 환경 실행됨, 운영 승인됨을 서로 구분합니다.
- 신입 운영자가 위키만 보고 검사 전 준비의 dry-run을 수행할 수 있습니다.
- 아직 정하지 않은 조직 정책을 구현 완료로 표현하지 않습니다.

## 10. 승인 요청 범위

본문을 수정하기 전에 다음 두 범위를 나누어 승인받습니다.

1. **문서 수정 승인**
   - 1~3단계의 문서 구조·문장·예시 수정
   - 기존 코드 동작과 스키마는 변경하지 않음

2. **검사기 설계 변경 승인**
   - T30 vendor-merge 병합 커밋 규칙
   - T31 비연속 후속 commit 규칙
   - build-artifact Candidate lock과 Release lock CLI

문서 수정 승인만 받은 경우에는 코드 변경이 필요한 항목을 `설계 결정 필요`로
표시하고 현재 동작을 사실대로 설명합니다.
