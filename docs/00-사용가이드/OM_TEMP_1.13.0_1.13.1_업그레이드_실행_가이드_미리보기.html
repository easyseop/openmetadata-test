검사기가 고정한 대상

검사기는 이 Git 번호를 입력으로 받아 “그 시점의 전체 코드와 변경 이력”을 검사합니다. 이후 변경이 하나라도 추가되면 코드 상태가 달라지므로 다시 검사해야 합니다.

운영 전략과 이번 후보 생성 방식은 다릅니다. 저장된 검사 결과에는 integration_strategy: vendor-merge가 기록됐지만, 실제 후보는 아래의 커밋별 재적용으로 만들었습니다. 따라서 공식 1.13.1 포함 관계는 확인했어도 실제 vendor branch 병합 기록과 충돌 해결 증거까지 검증한 것은 아닙니다. 이 후보를 vendor-merge 운영경로 통과로 해석하면 안 됩니다.

두 branch는 현재 로컬에만 있고 GitHub에는 아직 push하지 않았습니다.

cherry-pick은 무엇이고 왜 사용했나? 다른 branch에 저장된 특정 변경 기록 하나를 현재 branch에 복사해 적용하는 Git 명령입니다. 커밋 순서를 바꾸기 위해 사용한 것이 아닙니다. 이번에는 BANK-OM 변경을 한 건씩 적용해 어느 ID에서 충돌했는지 바로 기록하려고 사용했습니다. branch 전체를 병합해도 같은 코드 구간이 겹치면 충돌할 수 있으므로, 아래 결과는 변경 기록별 진단 결과이지 정식 병합 절차 전체의 결과가 아닙니다.

1. 실제로 충돌이 발생한 순간

BANK-OM-001의 1.13.0 변경 4df83b311f를 공식 1.13.1에 하나의 기능 단위로 적용했습니다. 실제 명령은 git cherry-pick 4df83b311f였고, Git이 아래 지점에서 자동 적용을 중단했습니다.

Auto-merging .../Entity.java
Auto-merging .../CollectionDAO.java
Auto-merging .../languages/ko-kr.json
CONFLICT (content): Merge conflict in .../languages/ko-kr.json
error: could not apply 4df83b311f... add InstanceCode customization

$ git diff --name-only --diff-filter=U | wc -l
18

Entity.java와 CollectionDAO.java는 자동 병합됐지만, 번역 JSON 18개는 Git이 자동으로 결정하지 못해 적용이 중단됐습니다.

왜 서로 다른 번역 항목인데 충돌했나? 두 변경 모두 공식 1.13.0에서 출발했습니다. 공식 1.13.1은 JSON 파일의 형식과 항목 배치를 크게 바꾸고 공식 번역 항목도 변경했습니다. BANK-OM-001은 1.13.0의 기존 형식을 유지한 채 같은 JSON 객체에 행내 번역 항목 9개를 추가했습니다. Git은 JSON의 의미가 아니라 줄 단위 차이를 계산하므로 충돌 구간의 두 결과를 자동으로 조립하지 못했습니다.

항목 이름별로 다시 비교한 결과 공식 1.13.1과 BANK-OM-001이 동시에 바꾼 동일 항목은 0개였습니다. 즉, 같은 번역 값을 서로 다르게 고친 충돌이 아닙니다. 파일 형식과 항목 배치가 크게 달라져 Git의 줄 단위 자동 병합이 실패한 충돌입니다.

3. 실제로 사용한 제한적 JSON 충돌 보조 도구

harness/tools/resolve_nonoverlapping_json_conflicts.py라는 실제 Python 도구가 있습니다. 검사기 전체의 필수 단계가 아니라, Git이 JSON 충돌로 멈췄을 때만 실행하는 제한된 보조 도구입니다.

stage 1·2·3은 실행 순서가 아니라 Git이 충돌 파일 하나에 보관한 세 버전의 번호입니다.

Git 표기Git에서 고정된 의미이번 연습의 실제 내용직접 확인 명령보조 도구에서 하는 일
stage 1 · BASE두 변경의 공통 기준공식 1.13.0과 BANK-OM이 갈라지기 전 JSONgit show :1:<파일경로>stage 1→2와 stage 1→3 변경 계산
stage 2 · OURS현재 checkout한 branch의 내용이번 연습에서는 HEAD인 공식 1.13.1 JSONgit show :2:<파일경로>해결 파일의 바탕으로 유지
stage 3 · THEIRS지금 적용 중인 반대편 변경이번 cherry-pick에서는 BANK-OM-001 commit의 JSONgit show :3:<파일경로>BANK-OM 변경 계산

이번 연습에서만: 공식 1.13.1 branch에서 BANK-OM commit을 cherry-pick했기 때문에 stage 2=공식, stage 3=BANK-OM입니다. 일반 merge에서도 stage 2는 현재 checkout한 쪽(OURS), stage 3은 들어오는 쪽(THEIRS)이므로 branch 방향을 바꾸면 공식/BANK-OM 대응도 바뀔 수 있습니다.

도구는 stage 1→stage 2에서 바뀐 최종 JSON 항목 목록과 stage 1→stage 3에서 바뀐 최종 JSON 항목 목록을 각각 만듭니다. 예를 들어 label 안의 instance-code는 label.instance-code라는 한 항목입니다. 줄 번호와 들여쓰기는 비교하지 않습니다.

판단도구가 비교하는 값계속 진행중단
충돌 파일 종류git diff --name-only --diff-filter=U 결과모두 JSONJSON 이외 파일이 하나라도 있으면 파일을 쓰기 전에 중단
OURS 변경 계산BASE와 OURS의 최종 JSON 항목별 값변경 항목 목록 생성JSON을 읽을 수 없으면 파일을 쓰기 전에 중단
THEIRS 변경 계산BASE와 THEIRS의 최종 JSON 항목별 값변경 항목 목록 생성JSON을 읽을 수 없으면 파일을 쓰기 전에 중단
두 목록 겹침OURS 변경 항목 경로 ∩ THEIRS 변경 항목 경로0개면 OURS에 THEIRS 변경 반영1개라도 겹치면 최종 값이 같아도 파일을 쓰기 전에 중단
자동 처리OURS와 THEIRS의 변경 항목 교집합이 0개인 경우
즉시 중단같은 항목을 둘 다 변경했거나 JSON 이외 파일이 충돌한 경우
사람이 할 일수정된 JSON 확인 후 git add와 git cherry-pick --continue
./.venv/bin/python harness/tools/resolve_nonoverlapping_json_conflicts.py   --repo ../om-temp-1.13.1-upgrade

resolved .../languages/ko-kr.json: BANK-OM leaf changes=9

도구가 실제로 남기는 것: 작업 폴더의 충돌 JSON을 깨끗한 JSON으로 다시 쓰고 터미널에 파일별 적용 건수를 출력합니다. leaf changes=9는 BANK-OM 쪽의 최종 JSON 항목 9개를 공식 파일에 반영했다는 뜻이며, 검사 PASS나 Git 충돌 해결 완료라는 뜻은 아닙니다.

작업 폴더JSON 내용은 공식 1.13.1 + BANK-OM 항목으로 바뀜
Git indexgit add 전이므로 아직 UU(충돌 미해결)
별도 산출물없음. 수정된 JSON과 터미널 출력만 남음
# 도구 실행 직후
git status --short
UU openmetadata-ui/.../languages/ko-kr.json

git add openmetadata-ui/.../languages/ko-kr.json
git cherry-pick --continue

자동 실행하지 않는 것: git add, commit, test, cherry-pick --continue, 별도 결과 보고서·승인 파일·plan.json 생성.

현재 운영 상태: 이 도구와 “같은 JSON 항목이 겹치지 않을 때만 합친다”는 기준은 이번 업그레이드 연습을 위해 구현했습니다. OpenMetadata의 기존 기능도, 확정된 행내 승인 정책도 아닙니다.

충돌 재현 증거 자료 보기도구의 자동 보고서가 아니라 이번 재현을 위해 별도 보관한 자료

아래 파일은 보조 도구의 자동 산출물이 아닙니다. 이번 충돌이 실제로 어떻게 발생했고 어떻게 해결됐는지 검토할 수 있도록 별도로 저장했습니다.

현재 Git 로그에서 BANK-OM ID는 어떻게 찾나?

현재 Git 원문은 error: could not apply 4df83b311f...처럼 source commit SHA만 보여주고 BANK-OM-001은 바로 표시하지 않습니다. commit 본문의 Customization-ID: BANK-OM-001을 한 번 더 조회해야 하므로 운영 로그로는 불친절합니다.

현재 로그

commit SHA를 다시 조회해야 ID를 알 수 있습니다.

개선할 로그

[BANK-OM-001] APPLY source=4df83b311f

적용 명령이 commit trailer를 읽어 ID를 모든 로그와 결과 JSON에 붙입니다.

현재 상태: commit과 ID의 연결은 결과 파일에 기록했지만, 실제 적용 명령의 모든 로그에 ID를 자동 표시하는 wrapper는 아직 추가 개발 대상입니다.

4. 정식 운영 전에 추가할 승인 기록

현재 미구현: 보조 도구는 충돌 파일을 수정하지만, 누가 비교 결과를 확인하고 해결을 승인했는지 별도 파일에 기록하지 않습니다. 아래 절차와 파일은 추가 개발 항목입니다.

1비교만 수행: 공식 변경, BANK-OM 변경, 동일 항목을 plan.json으로 출력하고 아직 코드는 수정하지 않습니다.
2담당자 선택: 기능 담당자가 자동 병합 승인, 수동 해결, 적용 중단 중 하나를 선택합니다.
3승인 기록: 승인자, BANK-OM ID, 공식 target SHA, source commit SHA, 선택 방법과 시각을 approval.yaml에 남깁니다.
4승인 후 적용: 승인 파일과 비교 계획의 digest가 일치할 때만 해결 도구가 코드를 수정합니다.
5자동 차단: 동일 JSON 항목이 겹치거나 JSON 외 코드가 충돌하면 BLOCK하고 코드 담당자가 수동 해결합니다. BLOCK은 자동 진행을 멈추고 사람이 원인을 확인해야 한다는 판정입니다.
6적용 후 재검사: Manifest 범위, build, Contract test를 실행하고 결과에 승인 기록을 연결합니다.
customization_id: BANK-OM-001
target_sha: afcb2d2...
source_commit: 4df83b311f...
decision: approve_non_overlapping_json
approved_by: 담당자 사번 또는 계정
approved_at: 승인 시각
plan_digest: sha256:...

정식 운영 전 추가 개발: ① dry-run plan 생성 ② 세 가지 선택 입력 ③ 승인 파일 검증 ④ ID 포함 로그 ⑤ BLOCK 결과와 재검사 연결
