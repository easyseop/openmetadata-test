# OpenMetadata 커스터마이징 검사 운영 위키 검토 요청

첨부한 `OM_TEMP_operations_wiki_Claude_review_20260729.html`을 브라우저에서 직접 열어 전체 페이지를 검토해 주세요. 이 파일은 보고용 요약과 운영 상세 문서를 한 위키 안에 합친 독립 실행형 HTML입니다.

## 검토 목표

이 문서는 처음 배치된 신입사원이 작성자에게 추가 질문하지 않고 다음 업무를 수행할 수 있는 수준이어야 합니다.

1. patch branch와 custom branch를 이용한 업그레이드 흐름을 이해한다.
2. BANK-OM ID와 Manifest를 등록·갱신한다.
3. Registry, Contracts, lock, test run set 등 관리 파일의 역할과 갱신 시점을 판단한다.
4. 검사기를 실행하고 PASS, APPROVAL, BLOCK, ANALYSIS ERROR 결과에 맞게 행동한다.
5. Git 충돌과 JSON 충돌 보조 도구의 결과를 해석하고, 사람이 해결해야 할 범위를 구분한다.
6. 검증이 끝난 변경을 tag·배포하고 다음 공식 버전에서 같은 과정을 반복한다.

문장을 매끄럽게 다듬는 수준이 아니라, 설명이 실제 코드·검사기·Git 동작과 일치하는지 비판적으로 검토해 주세요. 확인할 근거가 HTML 안에 없으면 사실로 단정하지 말고 `근거 부족`으로 표시해 주세요.

## 최근 사용자가 반복해서 강조한 검토 요구

아래 항목은 모두 빠짐없이 확인해 주세요.

### 1. 보고용 요약과 상세 문서의 관계

- 보고용 요약은 기존 보고서 HTML을 큰 상자 안에 그대로 끼워 넣은 모습이 아니라, 현재 위키 레이아웃에 맞게 재구성되어야 합니다.
- 보고용 요약의 각 내용은 상세 목차의 대응 페이지에서 더 구체적으로 설명되어야 합니다.
- 요약과 상세가 같은 개념을 서로 다른 용어·그림·절차로 설명하면 안 됩니다.
- 특히 `목적과 브랜치 전략`의 그림, patch branch와 custom branch의 관계, 병합 지점, 충돌 지점, 검사·배포·다음 버전 반복 흐름이 요약과 상세에서 동일해야 합니다.
- 보고용 `목적과 브랜치 전략` 요약에는 실제 브랜치 전략 그림이 보여야 합니다.
- 같은 설명이 반복되면 더 정확하고 흐름에 맞는 한 곳만 남기고, 나머지는 링크나 짧은 안내로 바꾸는 편이 나은지 판단해 주세요.

### 2. 기승전결과 정보 배치

페이지 전체가 다음 순서로 이해되어야 합니다.

1. 왜 이 체계가 필요한가
2. 어떤 repository·branch·공식 버전·커스터마이징을 다루는가
3. 일을 시작하기 전에 무엇을 준비하는가
4. 사람이 실제로 어떤 순서로 실행하는가
5. 각 검사가 무엇을 판단하는가
6. 어떤 결과에서 계속하고, 멈추고, 수정하고, 승인하는가
7. 현재 구현된 것과 아직 사람이 해야 하는 것, 다음 개발 대상은 무엇인가

정의나 예시가 절차와 같은 단계처럼 보이거나, 아직 소개되지 않은 용어가 갑자기 나오거나, 앞 문장이 삭제됐는데 `이 규칙`, `여기서`, `왜 임시 기준인가` 같은 표현만 남아 있지 않은지 확인해 주세요.

### 3. 문장 단위의 명확성

모든 문장을 한 문장씩 읽고 다음을 확인해 주세요.

- 누가, 무엇을, 언제, 어떤 입력으로, 왜 수행하는지 명확한가
- `현재`, `후보`, `제품`, `적용`, `이것`, `그 결과`가 무엇을 가리키는지 한 가지로만 해석되는가
- 두 명의 독자가 서로 다른 branch, commit, 버전, 비교 대상을 떠올릴 여지가 없는가
- 전문용어는 처음 등장하는 위치에서 평범한 완전한 문장으로 설명되는가
- `영수증`, `요리`, `레시피`, `짐`, `신호등`처럼 실제 개발·운영 용어가 아닌 비유를 쓰지 않았는가
- 커스터마이징, repository, branch, commit, Manifest, API, test, Git commit SHA, digest처럼 현업에서 쓰는 정확한 용어는 유지했는가
- BANK-OM ID, Git commit message, Git commit SHA가 서로 다른 개념임을 예시로 구분했는가

문제 문장을 발견하면 단순히 “어렵다”고 쓰지 말고, 독자가 실제로 할 수 있는 오해와 대체 문장을 함께 제시해 주세요.

### 4. 개념마다 필요한 다섯 가지 설명

Manifest, Registry, Contracts, candidate-lock, test-run-set, shared path owner, 검사기, branch, tag, 충돌 보조 도구 등 운영 요소마다 아래 다섯 항목이 있어야 합니다.

1. **의미**: 이 체계에서 무엇을 나타내는가
2. **시점**: 최초 생성, 갱신, 유지, 폐기 시점은 언제인가
3. **실제 사용**: 어떤 사람·명령·검사기가 읽고 어떤 판단에 사용하는가
4. **실제 예시**: 현재 repository의 필드, 경로, 명령, diff, 입력과 출력 예시가 있는가
5. **검사와 결과**: 무엇과 무엇을 비교하며 PASS, APPROVAL, BLOCK, ANALYSIS ERROR 중 어떤 결과가 나오는가

운영 시에는 “문서를 갱신한다”로 끝내지 말고, 다음 세 경우를 구분해야 합니다.

- 기존 값을 그대로 두는 경우
- 자동 생성 또는 자동 갱신되는 경우
- 담당자가 근거를 확인하고 직접 수정·승인해야 하는 경우

### 5. Manifest 필드와 커스터마이징 이력

- `allowed`, `required`, `watch`의 차이가 실제 검사 동작과 맞게 설명되어 있는지 확인해 주세요.
- 새 경로가 생겼을 때 해당 경로를 allowed, required, watch 중 어디에 넣는지 판단 기준과 예시가 있어야 합니다.
- 폐기하기로 한 `candidate_additional_paths` 개념이 남아 있거나, 같은 역할을 하는 낡은 설명이 다른 이름으로 남아 있지 않은지 검색해 주세요.
- Manifest를 버전별로 관리한다는 현재 방향과 과거 설명이 충돌하지 않는지 확인해 주세요.
- 같은 BANK-OM ID에 후속 commit이 생겼을 때 새 ID를 만드는지, 기존 Manifest를 어떻게 갱신하는지, commit message는 어떻게 쓰는지 예시가 있어야 합니다.
- Git commit SHA가 여러 개인 이유와 “가장 최근 SHA 하나만 쓰면 안 되는 이유”를 실제 commit 흐름 예시로 설명해야 합니다.

### 6. 사람과 자동화의 경계

전체 절차마다 다음 중 무엇인지 명확히 표시되어야 합니다.

- Git 또는 생성기가 자동으로 만드는 값
- 검사기가 자동으로 비교하고 결과만 내는 단계
- 사람이 업무 의미를 판단해 입력해야 하는 값
- 사람이 충돌 코드를 직접 선택·수정해야 하는 단계
- 승인권자가 확인해야 다음 단계로 갈 수 있는 단계

“자동화된다”는 표현만 쓰지 말고, 어떤 스크립트나 검사기가 어떤 입력을 읽어 어떤 파일 또는 결과를 만드는지 보여 주세요. 반대로 아직 자동화되지 않은 기능을 구현 완료처럼 표현하면 안 됩니다.

### 7. 검사기 설명

각 검사기마다 다음 정보가 있어야 합니다.

- 비개발자도 이해할 수 있는 한 문장 목적
- 입력 파일·branch·commit·버전
- 실제 비교 대상과 비교 방법
- PASS, APPROVAL, BLOCK, ANALYSIS ERROR 조건
- 출력 파일이나 화면 예시
- 실패했을 때 수정할 대상과 다시 실행할 검사
- 언어 독립적으로 동작하는 범위와 Java·TypeScript·Python 등 언어별 분석이 필요한 범위
- 현재 환경에서 바로 실행 가능한지, 구현은 됐지만 입력 자료가 부족한지, 추가 개발 예정인지

`commit SHA`, `공통 조상`, `leaf key`, `AST` 같은 용어를 원론적으로 나열하지 말고, 그 검사에서 왜 필요한지 바로 옆에서 실제 값과 함께 풀어 써야 합니다.

### 8. Git 병합과 충돌 설명

- patch branch의 공식 새 버전과 사전에 관리한 BANK-OM commit이 custom branch에서 합쳐지는 지점이 그림에 명확히 보여야 합니다.
- Git 충돌이 “같은 줄” 때문인지, 같은 JSON 파일의 넓은 변경 구간(hunk)이 겹쳤기 때문인지 실제 근거에 맞게 설명해야 합니다.
- 충돌 표시는 `<<<<<<< HEAD`, `=======`, `>>>>>>> commit`이 한 파일 안에 남은 전체 구조로 보여야 하며, 서로 무관한 두 코드 조각을 같은 줄의 양자택일처럼 배치하면 안 됩니다.
- 충돌 전 공식 코드, 적용하려는 BANK-OM 변경, Git이 만든 충돌 표시, 사람이 선택·수정한 해결 결과를 순서대로 보여 주세요.
- `cherry-pick`은 commit 순서를 바꾸는 명령이라고 단순화하지 말고, 다른 branch의 특정 commit 하나를 현재 branch에 적용하는 명령이라는 본래 의미를 설명해야 합니다.
- 이번 예시에서 cherry-pick을 사용한 이유가 BANK-OM ID별 commit을 하나씩 적용해 어느 ID에서 충돌했는지 분리해서 기록하기 위한 것인지, 정식 운영의 유일한 병합 방식인지 명확히 구분해야 합니다.
- branch merge나 rebase를 사용해도 같은 코드 구간이 겹치면 충돌할 수 있음을 필요 위치에서만 설명해야 합니다.

### 9. JSON 충돌 보조 도구

`충돌 해결 도구`라고 부르면서 자동으로 정답 코드를 만드는 것처럼 오해하게 하면 안 됩니다. 다음이 구체적으로 보여야 합니다.

- 도구의 정확한 목적
- 입력으로 읽는 세 코드: 공식 이전 버전, 공식 새 버전, 기존 커스터마이징 버전
- stage 1, 2, 3이 각각 어느 파일 또는 Git 상태를 뜻하는지
- 비교 조건과 중단 조건을 일반 문장으로 설명
- 실제 실행 명령
- 실제 출력 예시
- 출력에서 담당자가 읽어야 하는 항목
- 겹침이 없을 때 도구가 제안하는 결과
- 같은 key 또는 의미가 겹칠 때 자동 수정하지 않고 중단하는 결과
- 도구 결과를 받은 뒤 사람이 어떤 파일을 수정하고 어떤 검사를 다시 실행하는지

출력 예시는 “이렇게 나옵니다”로 끝내지 말고, 각 줄의 뜻과 다음 행동까지 연결해 주세요.

### 10. 운영·배포·반복 주기

- 검사 통과 후 custom branch가 어떻게 갱신되고 검증 tag와 배포로 이어지는지 보여야 합니다.
- 다음 공식 버전이 나오면 patch branch를 갱신하고 같은 과정을 반복한다는 cycle이 그림과 본문에서 일치해야 합니다.
- Manifest, Registry, Contracts, lock, test-run-set 등 각 파일이 “검사할 때마다” 갱신되는지, “버전이 바뀔 때” 갱신되는지, “업무 기준이 바뀔 때만” 갱신되는지 구분해야 합니다.
- 자동 생성 파일과 사람이 승인해야 하는 파일을 구분해야 합니다.
- 완료 조건, 보관할 증적, 보관 위치, 실패 복구, 중단·상신 조건이 있어야 합니다.

### 11. 예시 완전성

가능하면 모든 실행 기능과 관리 파일 필드에 실제 예시가 있어야 합니다. 특히 다음 항목을 확인해 주세요.

- 정상 예시 하나
- 실패 또는 충돌 예시 하나
- 실행 명령
- 예상 출력
- 출력 해석
- 다음 행동

예시가 가상의 값이면 가상 예시라고 표시하고, 실제 repository 근거가 있는 값처럼 보이게 하면 안 됩니다.

### 12. 화면과 사용성

- 보고용 요약과 상세 페이지가 같은 위키 디자인 체계로 보여야 합니다.
- 글자와 화살표, 표와 코드 블록, 펼치기 내용이 겹치거나 잘리지 않아야 합니다.
- 흰 배경의 지나치게 연한 회색 글씨처럼 대비가 낮은 텍스트가 없어야 합니다.
- 도식의 색은 patch/core와 custom/BANK-OM을 일관되게 구분해야 합니다.
- 목차 클릭 시 해당 상세 페이지로 이동하고, 현재 위치가 명확해야 합니다.
- 긴 설명은 접을 수 있어도, 결정을 내리는 데 필요한 핵심 문장은 펼치지 않아도 보여야 합니다.

## 이 문서가 적용해야 하는 가독성 사전검토 스킬

아래 기준을 “권고”가 아니라 공유 전 통과해야 하는 차단 조건으로 적용해 주세요.

1. 문서 전체를 읽고, 수정된 부분만 보지 않는다.
2. 설명을 실제 코드·schema·Git 상태·test 결과와 대조한다.
3. 목적 → 대상 → 준비 → 실행 순서 → 검사 → 결과 → 다음 단계의 흐름을 확인한다.
4. 한 개념에는 한 용어만 사용하고, 처음 등장할 때 설명한다.
5. 문장마다 행위자·대상·조건·결과가 하나로 해석되는지 확인한다.
6. 문단마다 신입사원이 바로 물을 질문을 예상하고 그 자리에서 답한다.
7. 구현 완료, test 완료, 계획, 현재 환경 미검증을 분리한다.
8. 중복 정의를 제거하고 한 곳을 기준 설명으로 삼는다.
9. 실행 절차에는 작업 위치, 권한, 입력, 명령, 예상 출력, 모든 결과별 다음 행동, 실패 복구, 증적 보관, 완료 조건을 넣는다.
10. 렌더링된 화면에서 표·코드·다이어그램·접힌 영역을 직접 확인한다.

## 원하는 검토 결과 형식

첫 답변에서는 HTML을 직접 수정하지 말고 발견 사항만 아래 표로 정리해 주세요.

| 우선순위 | 페이지/목차/정확한 문구 | 발견한 문제 | 독자가 할 수 있는 오해 | 근거 또는 확인 방법 | 권장 수정안 |
|---|---|---|---|---|---|

우선순위는 다음처럼 사용해 주세요.

- **치명적**: 사실과 다르거나, 잘못된 Git·검사·운영 행동을 유발함
- **높음**: 두 가지 이상으로 해석되거나 신입사원이 다음 행동을 결정할 수 없음
- **중간**: 필요한 예시·결과·복구 설명이 빠짐
- **낮음**: 중복, 배치, 시각적 가독성 문제

표 뒤에는 다음 네 항목을 별도로 작성해 주세요.

1. **요약과 상세의 불일치 목록**
2. **현재 구현 상태와 설명의 불일치 목록**
3. **신입사원이 추가로 물을 가능성이 높은 질문 목록**
4. **수정 순서 제안** — 치명적 사실 오류부터, 용어·흐름, 예시, 레이아웃 순서

문제가 없는 항목은 억지로 만들지 말고 `확인 결과 문제 없음`이라고 명시해 주세요. 반대로 HTML만으로 확인할 수 없는 실제 코드 동작은 추측하지 말고 `repository 코드 추가 확인 필요`라고 표시해 주세요.
