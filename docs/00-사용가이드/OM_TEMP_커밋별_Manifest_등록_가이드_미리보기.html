왜 먼저 설정해야 하나

검사기는 코드만 보고 업무 기능의 정상 조건을 추측하지 않습니다. 어떤 BANK-OM을 검사하고, 어떤 파일과 동작을 정상으로 볼지 정한 자료를 먼저 등록해야 합니다.

Manifest는 BANK-OM ID마다 한 파일을 만듭니다. 같은 기능의 후속 보완은 Git commit SHA가 여러 개여도 Manifest 하나에 연결합니다.

required_changed_paths그 파일이 없거나 공식 원본과 같아지면 기능 미적용으로 바로 차단할 핵심 파일입니다.

candidate_additional_paths같은 BANK-OM의 후속 commit에서 처음 추가된 파일입니다.

upgrade_watch.paths공식 버전 변경 시 T42가 다시 비교할 해당 기능의 경로입니다.

2 검사 기준자료 등록Registry·Contracts·공용 파일·전체 변경 목록

Git이 자동으로 만들 수 있는 값과 담당자가 결정해야 하는 기준을 나눠 등록합니다. 아래 코드는 작성 형태를 보여주는 예시이며, OM_TEMP 1.13.0의 실제 기준자료 파일 생성은 다음 작업입니다. 각 제목을 펼치면 의미·시점·실제 사용·예시·검사 결과를 확인할 수 있습니다.

2-1Registry검사할 BANK-OM과 연결정보

의미활성 BANK-OM이 어느 Manifest와 Contract를 사용할지 알려주는 목록입니다.

만드는 시점첫 기능 등록 때 만들고, ID·상태·중요도·대상 SHA가 바뀔 때 갱신합니다.

실제 사용검사기가 BANK-OM-005의 Manifest와 Contract 연결을 찾아 읽습니다.

검사 결과연결 파일이 없거나 ID가 서로 다르면 입력 묶음을 읽을 수 없어 검사를 시작하지 않습니다.

entries:
  - customization_id: BANK-OM-005
    title: 한글 입력 조합 보정
    status: active
    criticality: medium
    manifest: manifests/BANK-OM-005.yaml
    contracts: [CONTRACT-KOREAN-IME]
2-2Contracts기능이 정상이라는 동작 기준

의미파일 존재만으로 알 수 없는 실제 업무 동작의 정상 조건입니다.

만드는 시점최초 기능 등록 때 담당자가 정하고, 정상 조건이나 test가 바뀔 때 갱신합니다.

실제 사용T60-I가 연결된 test 코드의 파일과 test 이름이 실제로 있는지 확인합니다.

검사 결과필수 test 연결이 사라지면 BLOCK입니다. 현재는 Python pytest만 확인하며 Java·TypeScript test 확인은 추가 개발 대상입니다.

- id: CONTRACT-KOREAN-IME
  invariant: 한글 입력 중 자모가 중복·역전·소실되지 않는다.
  required_tests:
    - tests/bank/contracts/test_korean_ime.py::test_hangul_composition_roundtrip
  customization_ids: [BANK-OM-005]
2-3공용 파일 소유정보같은 파일을 변경한 BANK-OM 목록

의미여러 기능이 같은 공식 파일을 정상적으로 함께 변경했음을 기록합니다.

만드는 시점Manifest 경로의 중복을 자동 추출한 뒤 사람이 실제 diff를 확인하고, 버전마다 다시 계산합니다.

실제 사용Entity.java를 BANK-OM-001만의 파일로 잘못 판단하지 않고 001·002 공동 변경으로 검사합니다.

검사 결과중복 경로의 담당 ID를 결정할 수 없으면 재구성 검사가 ANALYSIS ERROR로 중단됩니다.

Entity.java:
  - BANK-OM-001  # INSTANCE_CODE
  - BANK-OM-002  # QUERY_REPORT

databaseService.json:
  - BANK-OM-006  # Sybase
  - BANK-OM-007  # Tibero
2-4전체 변경 목록patch와 custom 사이의 111개 경로

의미두 branch 사이에서 최종적으로 달라진 모든 파일 경로입니다.

만드는 시점검사 대상 commit이 확정된 뒤 Git으로 만들며, 업그레이드 버전마다 다시 생성합니다.

실제 사용실제 111개 경로와 7개 Manifest가 설명하는 경로를 양방향으로 비교합니다.

검사 결과Manifest에 없는 실제 변경은 BLOCK, 실제 변경이 없는 Manifest 경로는 APPROVAL 대상입니다.

git diff --name-only \
  origin/patch/om-1.13.0..origin/custom/om-1.13.0 \
  > source-diff-paths.txt

111개 경로는 사람이 입력하지 않습니다. Git이 만든 목록을 검사 기준자료로 보관합니다.

2-5Patch-lock커밋 재적용 방식을 쓸 때만 필요

의미patch-replay로 커스터마이징을 다시 적용할 때 사용할 SHA와 순서입니다.

만드는 시점vendor-merge 소스 검사의 필수자료가 아닙니다. 재적용·복구·재현을 선택할 때만 만듭니다.

실제 사용BANK-OM-007의 최초 commit 다음에 후속 보완 commit을 적용하도록 고정합니다.

검사 결과patch-replay에서는 잠금에 없는 SHA나 순서 변경을 동일한 재현으로 인정하지 않습니다. 설계상 첫 vendor-merge 소스 검사는 파일이 없어도 차단하지 않습니다.

patch_series:
  - id: BANK-OM-007
    revision: 1
    source_commits:
      - 62e39da...
      - 7d19c89...
3 로컬 검사 대상 연결OM_TEMP branch와 기준 commit 확인

검사기는 로컬 Git repository를 읽습니다. 현재는 독립 snapshot의 commit 연결 방식을 보완한 뒤 전체 검사를 실행해야 합니다.

3-1OM_TEMP 로컬 repository 준비검사할 branch와 commit을 가져오기

의미검사기는 GitHub 화면이 아니라 로컬 repository의 commit·diff·파일을 읽습니다.

만드는 시점새 노트북에서는 한 번 clone하고, 이후에는 검사 전에 fetch합니다.

실제 사용실행 명령의 --repo에 로컬 OM_TEMP 경로를 전달합니다.

확인 결과patch와 custom branch의 SHA가 예상값인지 확인한 뒤에만 검사를 시작합니다.

git clone https://github.com/easyseop/OM_TEMP.git
cd OM_TEMP
git fetch origin patch/om-1.13.0 custom/om-1.13.0
git rev-parse origin/patch/om-1.13.0
git rev-parse origin/custom/om-1.13.0
3-2독립 snapshot 연결 보완검사 실행 전 해결할 항목

OM_TEMP의 patch branch는 공식 OpenMetadata commit 이력을 그대로 포함하지 않고, 공식 1.13.0 파일 상태를 새 commit으로 가져왔습니다. 파일은 같아도 commit 계보는 다릅니다.

공식 OpenMetadata 1.13.0 commit  f329dd4a...
OM_TEMP patch/om-1.13.0 commit   2f4f3560...
두 commit의 동일한 Git tree    da56c24d...

왜 확인하나현재 실행기는 공식 commit이 OM_TEMP 이력의 조상이라고 가정해 T25가 잘못 실패할 수 있습니다.

필요한 보완공식 source SHA와 로컬 baseline SHA를 나누거나, 동일한 tree이면 같은 기준 코드로 인정해야 합니다.

현재 상태보완 전에는 전체 검사 연결 완료나 배포 승인으로 표시하지 않습니다.

다음 작업연결 방식을 확정한 뒤 실제 Registry·Contract·공용 파일·111개 목록을 생성합니다.

현재 상태: 실제 Git commit 기준 Manifest 초안 7개와 구조 검사는 완료했습니다. Registry·Contract·공용 파일·111개 목록의 실제 파일 생성, 독립 snapshot 연결 보완, 전체 코드 build, 업무 동작 test, 1.13.1 업그레이드 비교와 배포 승인은 아직 완료하지 않았습니다.
