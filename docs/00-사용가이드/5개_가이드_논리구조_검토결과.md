# 5개 가이드 논리구조 검토 결과

## 검토 기준

각 페이지를 처음 보는 부서 직원의 입장에서 다음 질문으로 검토했다.

1. 이 페이지는 한 문장으로 어떤 질문에 답하는가?
2. 이 설명은 우리가 만든 관리 개념인가, Git·OpenMetadata의 일반 개념인가?
3. 특정 저장소·버전·실습에만 해당하는데 일반 운영 규칙처럼 보이지 않는가?
4. 이 페이지를 읽고도 “그래서 누가, 언제, 무엇을 해야 하나?”라는 질문이 남는가?
5. 앞뒤 페이지와 같은 설명을 반복하거나 서로 다른 결과를 섞지 않는가?
6. 다음 페이지를 읽어야 하는 이유가 자연스럽게 이어지는가?

## 페이지별 질문과 조치

| 페이지 | 이 페이지가 답해야 하는 질문 | 독자가 가질 수 있었던 의문 | 검토 결과와 조치 |
|---|---|---|---|
| 1. 목적과 브랜치 전략 | 공식 업데이트와 행내 커스터마이징을 어떤 Git 흐름으로 함께 유지하는가? | 커밋을 하나씩 다시 적용하는 것이 운영 방식인가? patch와 custom 중 무엇을 무엇에 병합하는가? 소스 검사 PASS면 바로 배포하는가? | 승인된 설계인 `vendor-merge`를 기본 운영 방식으로 고정했다. 직전 custom 이력에 새 공식 patch를 병합하는 그림으로 바꾸고, 충돌·검사 BLOCK·배포 후보 tag를 서로 다른 단계로 분리했다. |
| 2. 검사기 원리 | 각 검사는 어떤 입력을 읽고 어떤 방법으로 판정하는가? | 원리 문서인데 특정 후보의 PASS와 미실행 결과가 왜 섞여 있는가? T93은 왜 두 번 나오는가? 입력과 출력은 어디서 확인하는가? | 특정 후보 결과와 보완 목록을 제거하고 원리만 남겼다. T93은 화면에서 `T93-범위`와 `T93-정책`으로 구분했다. 입력·출력 표는 실행 참고표로 유지했다. |
| 3. 검사 전 설정 | Manifest와 관련 기준자료를 언제 만들고 실제 diff를 어떻게 등록하는가? | 업그레이드 때 Manifest를 새로 만드는가? 같은 기능에 새 ID를 발급하는가? 긴 7개 Manifest 중 무엇부터 봐야 하는가? | 최초 기능 등록 때 Manifest를 만들고, 업그레이드 때 새 버전 폴더로 복사해 달라진 항목만 갱신한다고 명시했다. 같은 기능은 같은 ID를 유지한다. 전체 Manifest는 근거 보존을 위해 접힌 상세 자료로 유지했다. |
| 3번 보조. 관리파일 필드 사전 | Manifest·Registry·Contract의 각 필드는 누가 언제 작성하고 어느 검사에 사용되는가? | `assurance`, `series`, Candidate lock은 OpenMetadata 공식 설정인가? 자동 생성값과 담당자 판단값은 무엇이 다른가? | 실제 스키마 기준으로 의미·작성 시점·사용·문제 시 결과를 분리했다. 모두 `openmetadata-test`의 내부 관리 파일이며 OpenMetadata 실행 설정이나 직원용 화면을 바꾸지 않는다고 첫 화면에 명시했다. |
| 4. OM_TEMP 코드 업그레이드 연습 | 커밋별 재적용 진단에서 어떤 충돌이 발생했고 현재 검사기로 어디까지 확인했는가? | 왜 cherry-pick을 사용했는가? 이 결과가 실제 vendor-merge 결과인가? 소스 검사 8종 PASS면 배포 가능한가? | cherry-pick은 BANK-OM별 충돌을 분리하기 위한 진단 방법이라고 한정했다. 실제 후보 생성 방식과 결과의 `vendor-merge` 표시가 맞지 않는다는 제한을 공개하고, 운영 통합 방식은 `NOT VERIFIED`로 분리했다. |
| 부록. 과거 참고 코드 검사 | 과거 11개 변경 코드에서는 검사 결과가 어떤 형태로 나왔고 왜 배포가 BLOCK됐는가? | 현재 OM_TEMP와 같은 저장소인가? 왜 001~011인데 본문은 001~007인가? 현재 업그레이드 결과인가? | 본문 흐름에서 분리해 마지막 부록으로 이동했다. 008~011은 과거 참고 코드의 기술 보완이며 OM_TEMP 초기 업무 기능 범위에서는 제외했다고 명시했다. |

## 전체 순서

```text
1. 왜 이 체계가 필요한가
   └─ 목표 운영 방식: vendor-merge
        ↓
2. 검사기는 어떤 위험을 어떻게 판단하는가
        ↓
3. 검사가 읽을 Manifest·Registry·Contract를 어떻게 준비하는가
        ↓
4. OM_TEMP 1.13.0 → 1.13.1 연습에서 실제로 무엇이 확인됐는가
   └─ 소스 범위 확인 / vendor-merge·build·행내 동작·배포는 미완료
        ↓
부록. 과거 11개 변경 코드의 별도 검사 사례
```

## 합치지 않고 분리한 이유

- 1번과 2번을 합치면 운영 전략과 세부 검사 16종이 한 화면에 섞여 핵심 결론이 흐려진다.
- 2번과 3번을 합치면 “검사기가 판단하는 원리”와 “담당자가 입력자료를 작성하는 절차”가 섞인다.
- 3번의 7개 Manifest 전체는 길지만 실제 등록 근거이므로 삭제하지 않고 접힌 참고 자료로 유지한다.
- 3번의 필드별 정의는 본문에 모두 합치지 않고 별도 사전으로 분리해, 실행 흐름은 짧게 유지하면서 필요한 용어만 찾아볼 수 있게 한다.
- 과거 `easyseop/OpenMetadata` 결과는 현재 `OM_TEMP`와 저장소·ID 범위·목적이 다르므로 본문 중간에 두지 않고 부록으로 분리한다.
- 4번의 충돌 진단은 실제 증거이므로 유지하되, 목표 운영 방식인 vendor-merge 결과로 확대 해석하지 않도록 범위를 표시한다.

## 이번 검토에서 발견한 중요 사실

저장된 OM_TEMP 1.13.1 소스 결과에는 `integration_strategy: vendor-merge`가
기록돼 있지만, 후보는 실제로 BANK-OM commit을 하나씩 재적용해 만들었다.
따라서 현재 PASS는 공식 1.13.1 포함 관계와 커스터마이징 소스 생존을 확인한
결과이며, 실제 vendor branch 병합 기록과 충돌 해결 증거까지 검증한 결과가 아니다.

다음 운영 검증에서는 직전 custom branch에 공식 1.13.1을 실제로 merge하고,
merge 기록·충돌 증거·candidate lock의 전략값이 모두 일치하는지 확인해야 한다.
