# OM 검사기·운영전략 추가 개발 제안

> 상태: 제안
>
> 작성일: 2026-07-30
>
> 주의: 이 문서의 항목은 현재 구현 설명이 아니다. 별도 승인·개발·시험 전에는
> 운영 가이드에서 사용 가능한 기능으로 표시하지 않는다.

## 1. 이 문서를 따로 둔 이유

운영 위키는 지금 실행 가능한 절차와 확인된 제한만 설명한다. 아래 항목은 필요성이
있지만 구현 또는 조직 정책이 확정되지 않았으므로 운영 절차와 분리한다.

## 2. 추가 개발·정책 결정 후보

| 제안 | 현재 상태 | 필요한 검증 |
|---|---|---|
| 승인 ID 자동 발급 | 미구현 | 승인자 인증, 중복 방지, 감사 이력 |
| 승인 완료 전 릴리즈 브랜치 이동 차단 | 미구현 | Release lock·CI·브랜치 보호 연동 |
| 준비도구 버전 또는 commit을 승인 정보에 포함 | 미구현 | 서로 다른 도구 버전에서 proposal 재현 시험 |
| 여러 파일 apply 완료를 별도 결과 파일로 증명 | 일부 구현 | 기존 `registration-apply-result.json`으로 충분한지 결정 |
| vendor-merge parent 순서 고정 | 미확정 | 실제 운영 merge 명령으로 parent 1·2 방향과 T30 조건 시험 |
| 같은 제품 버전의 Registry revision 보관 정책 | 미확정 | `source.snapshot_sha` 덮어쓰기 또는 revision 추가 방식 결정 |
| 충돌 해결 승인 파일과 결과 JSON | 미구현 | JSON 보조 도구의 dry-run·승인·적용 분리 시험 |

## 3. 현재 구현과 혼동하면 안 되는 항목

- 준비도구의 `plan → 승인서 작성 → apply`는 현재 구현돼 있다.
- `apply`는 proposal digest, 제품 코드 commit, 등록 상태 digest, 작업 폴더
  변경, 적용 잠금을 확인하고 실패 시 파일을 복구한다.
- 현재 자동 승인 서비스는 없다. 담당자가 proposal과 질문을 읽고 승인서에
  근거를 작성한다.
- 현재 T91은 Release lock의 대상과 실제 배포 대상이 같은지 검사한다. 승인 ID를
  발급하거나 릴리즈 브랜치 이동을 직접 막지는 않는다.
- 현재 JSON 충돌 보조 도구는 해결 파일 초안을 만들지만 승인 파일이나 결과
  보고서를 만들지 않는다.

## 4. 구현 전 승인 기준

각 제안은 다음 네 가지가 정해진 뒤 별도 작업으로 개발한다.

1. 누가 정책을 결정하고 승인하는가
2. 기존 파일 형식과 검사 결과에 어떤 필드가 추가되는가
3. 실패하거나 중단될 때 어떤 상태와 복구 절차를 제공하는가
4. 현재 검사와 문서 중 무엇을 함께 갱신해야 하는가
